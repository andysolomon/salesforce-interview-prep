Page 3 · Learning Objectives

After studying this topic, you should be able to:

  • Explain the difference between the types of custom settings, and between custom settings vs. custom metadata.
  • Identify the benefits, considerations, and limitations of using custom settings and custom metadata.
  • Demonstrate how to set up and access custom metadata and custom settings in Apex and declarative solutions.
Page 4 · Introduction

Introduction

Custom settings and custom metadata types are used to store values which do not change frequently but need to be frequently referenced. The data is pulled into the application cache for efficient access and, in most cases, does not count toward the SOQL limit.

Both approaches support many data types. Referencing them in business logic makes customizations easier to maintain and read, and reduces the number of places where changes need to be made.

Custom metadata types are a newer concept and are preferred over custom settings in many cases. However, there are scenarios in which custom settings are still the preferred approach.

Page 5 · At-a-glance overview

Custom Settings vs Custom Metadata Types — at a glance

Custom Settings

List and Hierarchy Custom Settings can be used to create custom sets of data and associate them for an org, profile, or specific user.

Use Cases of Custom Settings

Use when data is referenced frequently but does not change frequently, or changes based on the logged-in user or their profile.

Using Custom Settings

Created in Setup → Custom Settings. API name ends with __c, similar to a custom object.

Custom Metadata Types

Define the structure of application metadata; records can be created and relationships can be defined.

Use Cases of CMT

Store mappings between configuration data, business rules, and configuration data linked by relationships.

Using CMT

Created in Setup → Custom Metadata Types. API name ends with __mdt.

Custom Settings

Page 7 · Custom Settings — data / usage / packages

Data / usage / packages

Custom settings are similar to custom objects in which data can be referenced in declarative and programmatic customizations.

Data

Custom settings allow creation of custom sets of data which can be exposed in application cache.

Usage

Used by formula fields, validation rules, flows, Apex, and the SOAP API.

Packages

Can be included in packages, but the data will not be included. To include data, Apex code must be used.

Page 8 · Custom Settings — visibility & cached data

Visibility & cached data

Visibility

To protect the value in managed packages, set Visibility to Protected. Changing the Visibility field is only allowed in Developer or Scratch orgs. This prevents the target org from editing the values or accessing them via Apex or API.

Cached Data

Custom settings can be used for quick and efficient access to cached custom data without using SOQL queries that count against the governor limits.

Page 9 · List vs Hierarchy

Two types of custom settings

List Custom Settings

Provides reusable static data that is the same for all users across the org.

Hierarchy Custom Settings

Uses built-in hierarchical logic to personalize settings based on specific Profiles or Users.

Page 10 · CMT-preferred note

Modern preference

For situations where List custom setting has been used in the past, Custom metadata types are now the preferred approach. Hierarchy custom settings, however, still have no CMT equivalent — keep using them for per-profile/per-user overrides.

API name format

Name Format

Same naming format as custom objects. The API name ends in __c.

Example Name

Page 14 · Formula & Apex access

Formula & Apex access

Formula Reference

Prefix the API name with $Setup in validations or formulas (e.g. $Setup.Run_Validation_Rules__c).

Apex Reference

Accessed the same way as a normal Salesforce object. Then methods specific to the type (list or hierarchy) can be used.

Interview angle

Hierarchy custom settings have a built-in getInstance() that automatically resolves the org → profile → user hierarchy and returns the most-specific match for the running user. That's the magic that makes them irreplaceable.

Page 21 · Postal code validation rule

Postal code validation rule

The custom setting is referenced to conditionally bypass a validation rule for postal codes.

// Rule Name: Valid_Canadian_Postal_Code
AND(
  $Setup.Run_Validation_Rules__c.Run_Validation__c,
  OR(BillingCountry = "CA", BillingCountry = "CAN", BillingCountry = "Canada"),
  NOT(REGEX(
      BillingPostalCode, "((?i)[ABCEGHJKLMNPRSTVXY]\\d[A-Z]?\\s?\\d[A-Z]\\d)?"
  ))
)
The validation only fires when the custom setting's Run_Validation__c field is true for the running user, giving admins a runtime kill-switch.
Page 22 · Close date validation rule

Close date validation rule

A custom setting allows administrators to create or save Opportunity records with close dates that are already in the past.

// Rule Name: Close_Date_Not_in_the_Past
AND(
  $Setup.Admin_Overrides__c.Run_Validation_Rule__c,
  CloseDate < TODAY()
)
Page 23 · Apex trigger validation

Trigger control via Hierarchy Custom Setting

trigger AccountTrigger on Account (before insert) {

  // retrieve the user-specific information of this hierarchy custom setting
  Run_Validation_Rules__c runVal = Run_Validation_Rules__c.getInstance();

  if (runVal.Run_Validation__c) {
      // perform validation steps only if the Run Validation checkbox is set
  }
}

Interview angle

This is the canonical "kill switch" pattern for Apex triggers: a Hierarchy Custom Setting that defaults to ON at the org level, but can be flipped OFF for specific users/profiles when you need to load data or troubleshoot.

Page 25 · Packages / fields / relationships

CMT — packages, fields, relationships

CMT can be used to easily customize, deploy, or update application metadata.

Packages

CMT allows the structure and actual record data to be included in a package.

Custom Fields

Like custom settings, a CMT consists of custom fields for storing attributes of metadata.

Relationships

Unlike custom settings, CMT allows creating relationships between related types.

Page 26 · Formula / migration / visibility

Formula / migration / visibility

Formula Fields

Records of a CMT can be referenced in an advanced formula field.

Migration

CMT can be migrated by using change sets.

Visibility

Visibility settings can only be set in Developer or Scratch orgs.

Page 27 · Public / Protected types & records

Protection levels in managed packages

Public Type

Can be accessed by all Apex code in an org.

Protected Type

Can only be accessed by the package.

Protected Record

Can only be accessed by code in the same namespace as the record or its type.

Add Values

A combination of Public type + Protected record allows package subscribers to add their own values, but not modify the type structure.

Page 28 · Field editing privileges

Field editing privileges (3 levels)

Package Developer

Only the package developer can edit the field via package upgrade.

Customize Application

Any user with the "Customize Application" permission can edit. Package upgrades will not override the value in this case.

None

No one can edit — not even the package developer.

Field types supported (CMT)

Metadata Relationship Checkbox Date Date/Time Email Number Percent Phone Picklist Text Text Area Text Area (Long) URL

Page 31 · Name format & data access

Name format & data access

Name Format

CMT append "__mdt" to the API name instead of "__c".

Example Name

A metadata type named "Country Codes" would be Country_Codes__mdt by default.

Data Access

CMT records can be accessed through Apex, formulas, or flows. To access records in Setup, additional permissions are required.

Page 32 · getAll / getInstance(recordId)

getAll & getInstance(recordId)

CMT provides static methods that retrieve records. These are faster than SOQL — they don't count against SOQL limits and return data directly.

Static methodUseExample
getAll()Retrieve a Map of all records of a specific CMT.MyCoolAppSettings__mdt.getAll();
getInstance(recordId)Retrieve a single record by its record ID.MyCoolAppSettings__mdt.getInstance('m00000000000123');
Page 33 · getInstance(developerName / qualifiedApiName)

getInstance(developerName) & getInstance(qualifiedApiName)

Static methodUseExample
getInstance(developerName)Retrieve by the record's DeveloperName.MyCoolAppSettings__mdt.getInstance('Enable_Advanced_Search');
getInstance(qualifiedApiName)Retrieve by qualified API name — namespace prefix + DeveloperName.MyCoolAppSettings__mdt.getInstance('FocusOnForce__Enable_Advanced_Search');

Interview angle

For configuration lookups in production code, prefer getInstance(developerName) — the developer name is stable, the recordId isn't (it differs between orgs).

Page 41 · Visibility options

Visibility options when configuring a CMT

  • All Apex code and APIs can use the type, and it's visible in Setup.
  • Only Apex code in the same namespace can see the type. The name of the type and the record are visible if they're referenced in a formula.
  • Only Apex code in the same managed package can see the type. The name of the type and the record are visible if they're referenced in a formula.
Visibility for custom metadata types can only be set in a developer, Sandbox, or scratch org. Protected custom metadata types aren't accessible by a subscriber's org; public custom metadata types are.

Page 44 · Retrieve via SOQL

Retrieve CMT records using SOQL

// retrieve a subset of metadata records
List<Area_Code_to_State_Mapping__mdt> vaCodes = [
  SELECT Label, State_Code__c
  FROM Area_Code_to_State_Mapping__mdt
  WHERE State_Code__c = 'VA'
];

// iterate through returned records
for (Area_Code_to_State_Mapping__mdt vaCode : vaCodes){
  // perform processing
}
Note: CMT SOQL queries are exempt from the SOQL row governor limit — but they still count toward the 100-statement limit. Use static methods to avoid both.
Page 45 · Retrieve via static methods

Retrieve CMT records using static methods

List<Area_Code_to_State_Mapping__mdt> codes = Area_Code_to_State_Mapping__mdt.getAll().values();
List<Area_Code_to_State_Mapping__mdt> vaCodes = new List<Area_Code_to_State_Mapping__mdt>();

for (Area_Code_to_State_Mapping__mdt code : codes) {
  if (code.State_Code__c == 'VA') { vaCodes.add(code); }
}

// iterate through list collection
for (Area_Code_to_State_Mapping__mdt vaCode : vaCodes){
  // perform processing
}

Page 53 · Protecting via Schema Settings

Protecting Custom Settings & CMT

To protect the data, Schema Settings should be configured so that Custom Settings & CMT can be accessed only in Apex, flows, and formulas.

  • Restrict access to custom metadata types — Allow access only through granted permissions and when accessing in system mode, e.g. from Apex.
  • Restrict access to custom settings — Allow access only through granted permissions and when accessing in system mode, e.g. from Apex.
When the settings are activated, users will be required to have the Customize Application permission in order to access the data. Also, SOAP API will be prevented access.

Bonus · Quick-Reference Cheatsheet

Quick-Reference Cheatsheet

API name suffix

  • Custom Settings → Name__c (just like a custom object).
  • Custom Metadata Types → Name__mdt.

Where they live

  • Custom Settings → Setup → Custom Code → Custom Settings. Edit data via Manage button.
  • CMT → Setup → Custom Code → Custom Metadata Types. Edit data via Manage button on each type.

Formula access

  • Hierarchy Custom Setting: $Setup.MySetting__c.MyField__c
  • CMT: $CustomMetadata.MyType__mdt.RecordName.MyField__c (type into Formula Editor manually for default-value fields)

Apex access

  • Hierarchy CS: MySetting__c.getInstance() resolves org → profile → user automatically.
  • List CS: MySetting__c.getValues('MyKey') for a single set; getAll() for everything.
  • CMT:
    • MyType__mdt.getAll() → Map<String, MyType__mdt> keyed by DeveloperName.
    • MyType__mdt.getInstance('DeveloperName') → single record.
    • MyType__mdt.getInstance(recordId) — works, but recordIds aren't stable across orgs.
    • MyType__mdt.getInstance('ns__DeveloperName') — qualified API name from a packaged namespace.

Decision flow

  1. Need per-user / per-profile overrides? → Hierarchy Custom Setting. (The only thing that does this natively.)
  2. Need configuration data to deploy/package? → Custom Metadata Type.
  3. Need relationships between config rows, picklists, or long text area? → CMT.
  4. Need currency type fields? → Custom Setting (CMT doesn't support Currency).
  5. Otherwise → default to CMT. It's the modern preferred option.

Common patterns

  • Trigger kill-switch: Hierarchy CS with a Run_Validation__c / Disable_Trigger__c checkbox + getInstance() early return.
  • Configurable validation rule: reference Hierarchy CS field in the rule's AND(...) so admins can override per-profile.
  • Lookup tables (country codes, area codes, ISO codes): CMT — survives sandbox refresh, ships in packages.
  • Default field values from config: $CustomMetadata.X__mdt.Y.Z__c in field default — must be typed manually, won't show up in the picker.

Schema Settings (governance)

  • Restrict access to custom metadata types + Restrict access to custom settings → require Customize Application permission, block SOAP API. Turn these on as a hardening step in regulated orgs.

Gotchas

  • Custom Settings data doesn't ship in packages — only the structure. CMT data does.
  • Visibility for both CS and CMT can only be changed in Developer/Scratch orgs.
  • CMT does NOT support Currency — surprise constraint.
  • Custom Settings cannot use Picklist, Long Text Area, or Metadata Relationships.
  • Use getInstance(developerName) in code shipped to multiple orgs — not getInstance(recordId).
