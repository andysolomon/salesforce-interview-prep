The Five Integration Patterns

Patterns · Selection matrix

Pick the pattern by timing & direction

Salesforce's "Integration Patterns and Practices" defines five canonical patterns. The exam is essentially: given a scenario, pick the right one.

PatternTimingDirectionOne-liner
Request & ReplySynchronousSF → externalSF calls out and waits for the answer now
Fire & ForgetAsynchronousSF → externalSF notifies; doesn't wait for a response
Batch Data SyncAsync / scheduledBothBulk move large data sets on a schedule
Remote Call-InSync or asyncExternal → SFExternal system creates/reads/updates SF data
UI Update on Data ChangeAsync (push)SF → SF UIPush data changes to the UI without refresh

Interview reflex

Decision order: Who initiates? → Do we need the answer synchronously? → What's the data volume? → What's the reliability requirement? Those four questions land you on the right pattern every time.

Pattern 1 · Request & Reply

Request & Reply (synchronous)

Salesforce calls an external system and blocks for the response — the user or process needs the answer immediately.

When

Real-time validation, a credit/KYC check, fetching a live quote, address verification.

Mechanism

Apex synchronous callout (REST/SOAP) via a Named Credential; External Services / Flow HTTP callout; Lightning component invoking Apex.

Watch out

Callout timeout (max 120s, default 10s); counts against per-transaction callout limits; user waits — keep it fast.

Fed angle

A loan/underwriting check that must return before the user proceeds is Request & Reply. If the external system is slow or unreliable, argue for moving it to Fire & Forget + status callback instead — that judgment is what they're testing.

Pattern 2 · Fire & Forget

Fire & Forget (asynchronous)

Salesforce notifies an external system and moves on — it doesn't wait for or need an immediate response.

When

Notify a downstream system of a new record; trigger a workflow elsewhere; decouple from a slow/unreliable endpoint.

Mechanism

Platform Events (preferred, modern), Outbound Messages (declarative, guaranteed retry), or async Apex callout (@future/Queueable).

Watch out

You don't get the result synchronously — design a callback or event for the response if you need confirmation.

Platform Events vs Outbound Messages: Outbound Messages are declarative and retry for 24h but only send a fixed SOAP message to one endpoint. Platform Events are the flexible, modern, pub/sub choice.
Pattern 3 · Batch Data Sync

Batch Data Synchronization

Move large data sets between Salesforce and external systems, usually on a schedule, often via middleware/ETL.

When

Nightly replication, data warehouse loads, master-data sync, seeding analytics.

Mechanism

Bulk API 2.0 (inbound), scheduled Apex + callouts (outbound), or middleware (MuleSoft/ETL). Use delta sync on a modified-date watermark.

Watch out

Use Bulk API (not REST row-by-row) for volume; PK chunking for large extracts; idempotent upserts on an External ID.

Fed angle

This is your pattern — the Bulk API 2.0 → S3 pipeline. Mention upsert on External ID and PK chunking to show you handle scale and idempotency, not just the happy path.

Pattern 4 · Remote Call-In

Remote Call-In (inbound to Salesforce)

An external system initiates — creating, retrieving, updating, or deleting Salesforce data.

When

A partner portal pushes records in; an external app reads/writes SF data; a webhook lands in SF.

Mechanism

Standard REST/SOAP API, Apex REST/Apex SOAP web services for custom endpoints, Composite API to batch related calls, all behind a Connected App + OAuth.

Watch out

Authentication & authorization, API limits, idempotency (upsert on External ID to avoid duplicates on retry).

Fed angle

Your Java connected apps for external clients are Remote Call-In. Pair with JWT bearer auth (server-to-server, no interactive login) — a common, secure choice for system integrations.

Pattern 5 · UI Update on Data Change

UI Update Based on Data Changes

When data changes (often from an external system), push the update to the Salesforce UI without a manual refresh.

When

A back-office update should appear live on an agent's screen; collaborative real-time dashboards.

Mechanism

Streaming API / Platform Events / Change Data Capture, consumed in an LWC via the empApi module / lightning/empApi.

Watch out

Event delivery limits; replay/durability; this pushes to the UI, it's not a data-integration channel by itself.

Mechanisms · Event-driven

Platform Events · CDC · Pub/Sub API

Platform Events

Custom, schema-defined events you publish/subscribe. Best when you define the message contract. Publish from Apex, Flow, or API.

Change Data Capture

Salesforce auto-publishes create/update/delete/undelete on selected objects. Best for replicating record changes downstream without custom code.

Pub/Sub API

Single gRPC interface to publish & subscribe to both, with efficient binary payloads and flow-controlled streaming.

Replay ID is the gotcha: subscribers track a Replay ID to resume after disconnect. Events are retained ~72 hours — a subscriber down longer than that loses the missed events. Design for it.

Interview angle

"Platform Events vs CDC?" — If you control the contract and want a purpose-built message → Platform Events. If you just want "tell me when these records change" → CDC. Both ride the same event bus and Pub/Sub API.

Mechanisms · Outbound

Outbound: callouts & messaging

Apex Callouts

REST/SOAP from Apex. Synchronous (Request & Reply) or async via @future(callout=true) / Queueable. Always through a Named Credential.

Outbound Messages

Declarative, fires a SOAP message on record change with guaranteed retry up to 24h. Limited & legacy but reliable.

External Services / Flow

Register an OpenAPI schema → invoke as an action in Flow. Low-code Request & Reply.

Mechanisms · Salesforce Connect

Salesforce Connect (external objects / OData)

Access external data in real time without copying it into Salesforce, via OData (or a custom Apex adapter).

When

Data must stay in the system of record (compliance, volume), but users need to see/relate it live in Salesforce.

How

External Objects (__x) map to remote tables; queried on demand, no storage consumed.

Watch out

Performance depends on the remote system; limited write support; not for high-frequency transactional writes.

Fed angle

For a central bank that must keep sensitive data in a system of record, Salesforce Connect is a strong "don't replicate the data" answer — minimize where regulated data lives.

Auth & Security

Authentication & Authorization

Auth · Named Credentials

Named & External Credentials

The modern, secure way to do callouts: never hardcode endpoints or secrets in Apex.

Named Credential

Defines the callout endpoint + which External Credential authenticates it. Reference as callout:My_Named_Cred.

External Credential

The newer split: holds the authentication protocol (OAuth, JWT, Basic, API key) and principals; secrets live in protected named principals.

Why

Secrets are encrypted & managed by the platform; per-user or per-org named principals; auth handled automatically on each callout.

HttpRequest req = new HttpRequest();
req.setEndpoint('callout:Underwriting_API/v1/score'); // no URL or secret in code
req.setMethod('POST');
HttpResponse res = new Http().send(req);

Fed angle

"Partner with Information Security to develop security configurations" → Named/External Credentials are the platform-native control: no secrets in source, encrypted at rest, auditable. Exactly what InfoSec wants to hear.

Auth · OAuth flows

OAuth 2.0 flows — pick by scenario

FlowUse when
JWT BearerServer-to-server, no interactive login; pre-authorized cert-based trust. Ideal for system integrations.
Web Server (auth code)A server-side app acting on behalf of a user who logs in.
Client CredentialsPure machine-to-machine where one integration user owns the access.
Refresh TokenLong-lived access by exchanging a refresh token for new access tokens.
User-AgentBrowser/mobile public clients (legacy; prefer PKCE/auth-code now).
A Connected App defines OAuth scopes, IP/refresh policies, and which flows are allowed — it's the authorization boundary for any external system calling in.

Interview angle

For a backend integration with no human in the loop, lead with JWT Bearer: a certificate establishes trust, no password is stored or sent, and access is scoped & revocable via the Connected App. You've set this up — it's an ARC skill in your toolkit.

Design & Build

Design, Build & Maintain

Design · Middleware

When to introduce middleware (MuleSoft / ESB)

Point-to-point integrations multiply into spaghetti. Middleware decouples systems behind a managed integration layer.

Use middleware when

Many systems, protocol/format translation, orchestration across systems, centralized monitoring & throttling, reuse via APIs.

MuleSoft API-led

System APIs → Process APIs → Experience APIs. Reusable building blocks instead of one-off connections.

Direct (no middleware)

Simple, low-volume, one-to-one integration where a managed layer is overkill.

Fed angle

"Heterogeneous datacenter, cloud, and SaaS environments" (JD) is the classic case for middleware. Be ready to argue both sides — when an ESB earns its keep vs. when it's unnecessary overhead.

Build · Reliability

Idempotency & error handling

  • Idempotency — design so a retry can't create duplicates. Use upsert on an External ID; have the caller pass a unique request key.
  • Delivery semantics — most async integrations are at-least-once, so consumers must dedupe. True exactly-once is rare and expensive.
  • Retry & back-off — exponential back-off; a dead-letter queue / error table for messages that exhaust retries.
  • Error visibility — log failures (Platform Event → log object) and alert; never swallow integration exceptions silently.

Fed angle

This connects to the "paved road" platform idea: a reusable callout framework with built-in retry, logging, and idempotency means every app team's integration is reliable by default.

Build · Limits

Limits & performance to respect

LimitValue (know the shape)
Callouts per transaction100 max
Callout timeout10s default, 120s max total per transaction
Daily API request limitOrg-wide, edition + license based — monitor it
Concurrent long-running requestsSynchronous calls > 5s are capped (e.g. 25 concurrent)
Bulk vs RESTUse Bulk API for volume — don't loop REST row-by-row
You can't make callouts after DML in the same transaction (uncommitted work) — restructure with async (Queueable) or commit first. Classic exam & real-world trap.
Maintain · Operations

Maintaining integrations over time

  • Versioning — pin API versions; plan for Salesforce retiring old API versions; version your own Apex REST endpoints.
  • Monitoring — Event Monitoring, integration logs, dashboards on error rate & latency; alert on failures.
  • Backward compatibility — additive changes to contracts; contract tests so a downstream change doesn't break consumers.
  • Deprecation — communicate, dual-run, then sunset old endpoints.
Bonus · Quick-Reference Cheatsheet

Quick-Reference Cheatsheet

The 5 patterns (one line each)

  • Request & Reply — SF calls out, waits (sync). Real-time validation.
  • Fire & Forget — SF notifies, moves on (async). Platform Events / Outbound Messages.
  • Batch Data Sync — bulk, scheduled, both directions. Bulk API 2.0 / ETL.
  • Remote Call-In — external system writes/reads SF. REST/SOAP + Connected App.
  • UI Update on Data Change — push to UI. Streaming / PE / CDC via empApi.

Event mechanisms

  • Platform Events — you define the contract.
  • CDC — auto record-change events, no code.
  • Pub/Sub API — one gRPC interface for both. Watch the Replay ID + ~72h retention.

Auth

  • Named + External Credentials — no secrets in code; callout:Name.
  • JWT Bearer — server-to-server, no interactive login (default for backend integrations).
  • Connected App — defines OAuth scopes & policies for inbound.

Reliability

  • Idempotency via upsert on External ID.
  • Assume at-least-once delivery → consumers dedupe.
  • Retry with back-off + dead-letter/error log.

Traps to memorize

  • No callout after DML in the same transaction (uncommitted work error).
  • Max 100 callouts/transaction; 120s total timeout.
  • Use Bulk API for volume, not row-by-row REST.
  • Outbound Messages retry 24h but only send a fixed SOAP payload to one endpoint.
  • Salesforce Connect = real-time, no data copied (external objects __x).
