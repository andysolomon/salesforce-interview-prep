Section 1

Application Lifecycle Management

§1.1 · Methodologies & risk

Choosing a development methodology

Match the methodology to project risk, requirement volatility, and the customer's appetite for iteration.

Waterfall

Sequential, fixed scope. Fits stable, well-understood, compliance-heavy requirements. Risk: late feedback, expensive change.

Agile (Scrum/Kanban)

Iterative, incremental, feedback-driven. Fits evolving requirements. Risk: scope drift without strong governance.

Hybrid / SAFe

Agile teams inside a planned governance shell. Scaled Agile Framework (SAFe) coordinates multiple teams via Agile Release Trains & PI planning. Fits large regulated enterprises.

Fed angle

The JD lists "SAFe highly desired." Be ready to say you've worked in PI planning and Agile Release Trains, delivering in increments while honoring enterprise change-management gates — agile execution, governed release.

§1.2 · Governance by maturity

Right-sizing governance to maturity

Governance should scale with the organization's ALM maturity. Over-governing a small shop kills velocity; under-governing an enterprise creates uncontrolled risk.

MaturitySymptomsRight-sized governance
LowChanges made in prod, no source control, no testsIntroduce version control, a single sandbox tier, basic deployment checklist
MediumSome CI, inconsistent standards across teamsCenter of Excellence (CoE), coding standards, PR + review, defined sandbox tiers
HighMultiple streams, packages, automated pipelinesArchitecture review board, release trains, automated quality gates, package strategy
A Center of Excellence (CoE) and a steering committee are the canonical Salesforce answers for "who owns governance." The CoE sets standards/patterns; the steering committee prioritizes and arbitrates.
Section 2

Planning

§2.1 · ALM maturity assessment

Assess people, process & technology

Before recommending anything, diagnose the three pillars.

People

Skills, roles (admin/dev/release manager/architect), team topology, who can deploy, training needs.

Process

Branching model, review gates, definition of done, change approval, release cadence, incident handling.

Technology

Source control, CI/CD tooling, sandbox inventory, packaging, static analysis, backup/monitoring.

Interview angle

When asked "where do you start with a messy org," lead with assessment: "I'd baseline ALM maturity across people, process, and tech before changing anything — you can't fix what you haven't measured." This signals architect-level judgment.

§2.2 · Environment risks & mitigation

Environment risks and how to mitigate them

RiskMitigation
Config drift (changes made directly in sandboxes/prod)Source control as the source of truth; regular drift detection; back-merge process
Stale sandboxes diverging from prodScheduled refresh cadence; seed with representative data on refresh
Sensitive data exposure in lower environmentsData masking / Salesforce Data Mask on Full/Partial sandboxes
Dependency conflicts between parallel streamsPackage boundaries, integration sandbox, trunk-based merges
Failed prod deploy (insufficient coverage)Validate-only deploys (check-only) with RunLocalTests before the window
§2.3 · Governance framework

Recommending a governance framework

  • Architecture Review Board — approves designs, enforces patterns, prevents tech debt.
  • Change Advisory Board (CAB) — approves what goes to prod and when (classic ITIL change control).
  • Release management role — owns the pipeline, environments, and the release calendar.
  • Standards & documentation — naming conventions, coding standards, the "paved road" patterns teams must use.

Fed angle

"Change-management controls, auditability, and release governance" is a verbatim JD requirement. The CAB + an audit trail of every deployment (who/what/when, tied to a ticket) is exactly the answer a regulated institution wants to hear.

§2.4 · Salesforce release strategy

Managing the three annual platform releases

Salesforce ships three major releases a year — Spring, Summer, Winter — automatically to every org. The JD calls this out: "Performs new Salesforce release evaluations and assess impact."

Preview windows

Sandboxes on preview instances get the new release weeks early — use them to test against the upcoming version before prod upgrades.

Release notes & readiness

Review release notes, the Release Readiness webinars, and the "Release Updates" / enforcement timeline in Setup.

Regression

Run automated regression (Apex + UI/Playwright) in a preview sandbox; triage any breaking changes and required updates.

Know the difference: Preview vs Non-Preview instances. Refreshing a sandbox at the right time determines whether it lands on the current or next release — a classic exam trap.
Section 3

System Design

§3.1 · Agile tooling

Tools that support an agile process

  • Work tracking — Jira, Azure DevOps, GitLab Issues: backlog, sprints, user stories with acceptance criteria.
  • Source & CI — Git provider (the JD uses GitLab) with merge requests and pipelines wired to stories.
  • Traceability — link commit → MR → story → deployment so every prod change is auditable back to a requirement.

Fed angle (GitLab)

Your résumé is GitHub Actions; they run GitLab CI. Same concepts, different file: .github/workflows/*.yml → .gitlab-ci.yml with stages: and jobs. Say that out loud — it shows you transfer the pattern, not just the tool.

Section 4

Building

§4.1 · Branching, versioning, merging

Source control branching models

GitFlow

main + develop + feature/* + release/* + hotfix/*. Strong control, more overhead. Fits scheduled enterprise releases.

GitHub Flow

main + short-lived feature/* merged via PR. Simple, continuous-delivery friendly.

Trunk-based

Tiny, frequent merges to trunk behind feature flags. Lowest merge pain, needs strong automated tests + flags.

Mapping branches to environments

# common enterprise pattern
feature/W-123  ──▶ scratch org / dev sandbox     (build & unit test)
develop        ──▶ integration sandbox            (continuous integration)
release/2026.6 ──▶ UAT / staging sandbox          (validate-only deploy)
main           ──▶ production                      (tagged release)
hotfix/*       ──▶ from main, fast-track to prod, then back-merge to develop
"Versioning" on Salesforce = package version numbers (1.2.0.NEXT) for unlocked packages, plus Git tags for releases. Merging discipline (rebase vs merge, conflict resolution on metadata XML) is a frequent exam theme.
§4.2 · Dev model: org-based vs package-based

Org-based vs package-based development

Org-based (org development model)Package-based (package development model)
Source of truthA sandbox/prod org's metadataSource control + versioned packages
EnvironmentSandboxesScratch orgs (ephemeral, source-defined)
Best forExisting, hard-to-modularize orgs; adminsModular, greenfield, multi-team, reuse
ToolingChange sets / MD API + source trackingsf CLI, scratch orgs, unlocked packages

Scratch orgs vs sandboxes

Scratch org

Ephemeral (≤30 days), source-driven, defined by a scratch-def.json with features/settings. Perfect for CI and clean-room builds.

Sandbox

Long-lived copy of a real org (with or without data). Needed when you must test against prod-like config/data.

§4.3 · Test data & unit tests

Building a test data & unit-test strategy

Quality code needs tests across four dimensions the exam names explicitly:

Positive

Valid inputs produce expected results.

Negative

Invalid inputs are handled — assert exceptions, error paths.

Permission-based

System.runAs() for personas; verify CRUD/FLS and sharing enforcement per profile/permission set.

Large data volume

Bulkified tests (200+ records) to prove no governor-limit failures.

@TestSetup
static void makeData(){
  // create once, shared by all test methods — avoids MIXED_DML and re-creation
  insert TestFactory.accounts(200);
}
@IsTest
static void sharesEnforcedForReadOnlyPersona(){
  User u = TestFactory.readOnlyUser();
  System.runAs(u){
    Test.startTest();
    // assert the persona cannot edit / cannot see restricted fields
    Test.stopTest();
  }
}

Fed angle

This is your VA/PSIP wheelhouse: persona-based, least-privilege testing with runAs, @TestSetup to kill MIXED_DML, and Security.stripInaccessible() in the code under test. Lead with it.

§4.4 · Code quality & static analysis

Ensuring delivery of quality code

Coding standards

Naming, trigger frameworks (one trigger/object), bulkification, no SOQL/DML in loops, separation of concerns (fflib service/selector/UoW).

Pull / merge requests

Required reviewers, CODEOWNERS, branch protection — no direct pushes to protected branches.

Code review

Human review for design & security; checklists for CRUD/FLS, sharing, exception handling.

Static analysis

Salesforce Code Analyzer (sf scanner run) wraps PMD, ESLint, RetireJS, plus the Graph Engine (DFA) for data-flow security (SOQL injection, missing CRUD/FLS). SonarQube for org-wide quality gates.

# run all engines, fail the pipeline on high-severity findings
sf scanner run --target force-app --engine pmd,eslint --severity-threshold 2
sf scanner run dfa --target force-app --projectdir .  # graph engine: security data-flow

Fed angle

"Ensure code quality through static analysis, unit testing and test automation" is a JD bullet. You ran SonarQube in production pipelines — pair that story with PMD + Graph Engine to show defense-in-depth on quality.

Section 5

Deploying

§5.1 · Metadata vs Tooling API

Metadata API vs Tooling API

Metadata APITooling API
PurposeMove metadata between orgs (deploy/retrieve) in bulkBuild dev tools; granular, per-component CRUD
GranularityWhole components / packagesIndividual fields, classes, members
ModeAsynchronous (deploy job), supports check-only & destructive changesFast, often synchronous, ideal for IDE-style edits
Used bysf CLI deploys, CI/CD, change sets (under the hood)VS Code extensions, code completion, debug
Not all metadata types are supported by the Metadata API — those gaps become manual pre/post-deploy steps (next slide).
§5.2 · Pre / post-deploy steps

Handling pre- and post-deployment steps

Some changes can't ride the API — plan them into a runbook.

Pre-deploy

Disable automations/jobs that would conflict; defer sharing recalculation for large changes; communicate downtime.

Manual / not API-supported

Some standard picklist value sets, certain settings, secrets/credentials, marking flows/processes active, post-install data.

Post-deploy

Activate Flows, re-enable jobs, run post-install scripts/data loads, smoke test, re-enable sharing recalculation.

Unlocked & managed packages support a post-install Apex script; for org deploys, encode manual steps in a versioned runbook so they're repeatable and auditable.
§5.3 · Technical reference data

Managing & deploying technical reference data

"Reference data" = configuration-as-data that the app depends on (rate tables, mappings, country codes).

Custom Metadata Types

Deploys like metadata — records travel with the package, are testable, and are visible in source control. The preferred home for config.

Custom Settings

List/Hierarchy. Data does not deploy with metadata — must be loaded per environment.

Record data

Use sf data tree, Data Loader, or the SFDMU plugin to seed reference records into each org.

Interview angle

"Where does configuration belong?" Strong answer: Custom Metadata Types — because the records deploy with the package, are environment-portable, and keep config out of code. Reserve Custom Settings for per-org or user/profile-specific values.

Fed angle

You introduced Playwright for browser E2E and set Jest standards with a templated guide — that's the full pyramid, unit → E2E. Use it to answer any "how do you ensure quality" question.

§6.2 · Execution & coverage rules

Test execution methodology & coverage

The 75% rule

Production deployments require ≥75% org-wide Apex coverage, and every trigger must have some coverage. (Coverage is a gate, not a quality measure — assert behavior, don't pad lines.)

Deployment test levels

NoTestRun (sandbox only) · RunSpecifiedTests · RunLocalTests (excludes managed-package tests) · RunAllTestsInOrg.

# validate-only ("check only") deploy with local tests before the release window
sf project deploy start --dry-run --test-level RunLocalTests --target-org prod
RunLocalTests is the usual production choice — it runs all your org's tests but skips installed managed-package tests you don't own.
§6.3 · Secure test data strategy

A unified, secure test-data strategy

Use representative data throughout the lifecycle without exposing sensitive records in lower environments.

Mask

Salesforce Data Mask anonymizes PII in Full/Partial sandboxes after refresh (replace, delete, or randomize).

Synthesize

Generate synthetic data via factories / SFDMU when real data is too sensitive to copy at all.

Subset

Partial Copy templates pull a representative slice rather than the full data set.

Fed angle

At a central bank, "representative data in a secure manner" is non-negotiable. Lead with Data Mask + synthetic factories so no production PII/financial data ever lands in a dev or QA sandbox.

Releasing

§7.1 · Package types compared

Managed vs unmanaged vs unlocked

TypeUpgradeable?IP protected?Editable in target org?Use case
UnmanagedNoNoYes (components unlocked)One-time templates, sample code, open distribution
Managed (2GP)YesYes (namespaced, code hidden)NoISV / AppExchange products

Interview angle

For an internal enterprise platform, the right answer is almost always unlocked packages — you get versioning, dependencies, and upgradeability without the IP-protection overhead of managed packages (which are for ISVs selling on AppExchange). Most candidates conflate these; you won't.

Fed angle

This is your "platform enablers / reusable components" story (last conversation's paved-road idea). Unlocked packages are the explicit APIs/abstractions the JD asks you to deliver to app teams.

§7.2 · Release management strategy

Mapping sandboxes to a release plan

A release strategy ties branching → environments → cadence, with separate lanes for features and hotfixes.

# release train model
Sprint work ─▶ develop ─▶ Integration sbx ─▶ release/* ─▶ UAT (Partial) ─▶ Staging (Full) ─▶ PROD
Urgent fix  ─▶ hotfix/* ─────────────────────────────────────────────────▶ Staging ─▶ PROD
                                                                              └─ back-merge to develop
  • Multiple project streams → feature branches + integration sandbox to surface conflicts early.
  • Training → a dedicated training sandbox refreshed to the release candidate.
  • Hotfixes → branch from prod state, fast-track, then back-merge so the fix isn't lost next release.
Section 8

Operating

§8.1 · Changes directly in prod

Implications of changing prod directly

  • Creates config drift — source control no longer matches reality, so the next deploy can overwrite the change.
  • Bypasses review, testing, and audit — unacceptable in a regulated environment.
  • Sometimes necessary (emergency hotfix, admin-only declarative tweaks) — but must be captured back into ALM.

Fed angle

"No cowboy deploys" is itself a feature at a central bank. The right posture: even emergency prod changes are logged, ticketed, and back-merged into source — drift is detected, not tolerated.

§8.2 · Reconciling drift into ALM

Integrating prod changes back into the lifecycle

  1. Detect — diff prod metadata against source control (scheduled sf project retrieve + diff, or a DevOps tool's drift report).
  2. Capture — retrieve the changed components into a branch.
  3. Reconcile — merge into develop so lower environments and the next release include the fix.
  4. Prevent — tighten who can edit prod; route changes through the pipeline.
The failure mode to name: a hotfix made only in prod gets silently reverted by the next scheduled deploy because source control never learned about it.

Exam detail

The Operating section specifically tests the Apex Metadata API — the ability to create/update metadata (e.g. records of Custom Metadata Types) programmatically from Apex, including in managed-package post-install scripts. Know that it's deploy-only (no retrieve) and runs asynchronously.

§8.3 · Multi-org release artifacts

Managing common artifacts across multiple orgs

  • Factor shared functionality into common unlocked packages with explicit version numbers.
  • Each org installs the same package version → guaranteed consistency, controlled upgrades per org.
  • Manage dependencies explicitly (a base "core" package others depend on) so upgrades roll out in order.
  • A central pipeline builds the artifact once and promotes it to each org's release lane.

Fed angle

This is the literal "platform" in Platform Engineer: a versioned core package every application team consumes — increasing adoption, consistency, and operational efficiency, exactly as the JD frames the role.

sf CLI quick reference

Reference · Exam strategy

Exam-day strategy (if you sit the cert)

Distilled from SalesforceBen's guide — these also double as good interview discipline.

Read scenarios twice

The answer options often reveal what's being tested. Identify the real constraint (volume? timing? risk?) before choosing.

Process of elimination

Salesforce plants answers that mix unrelated features or aren't best practice. Cut the obviously wrong, then decide between the survivors.

Prefer the standard feature

Curveballs look correct but aren't best practice. Favor a standard platform capability over a custom build when one exists.

Mark for review

Flag doubtful questions, finish the rest, then revisit — later questions often jog the answer.

  • Weightings are near-even (8–15%) — study all eight sections; don't bet on skipping one.
  • This is scenario-heavy and hands-on: examiners assume you've actually run SFDX, scratch orgs, and GitHub flows — which you have.
  • Retakes are half price, up to three attempts per release; reschedule fast so the material stays fresh.
  • Master revision list = the official Trailhead exam guide + the "Architect Dev Lifecycle & Deployment" trailmix.

Interview crossover

Even if you don't sit the exam before Thursday, these habits transfer: when they give you a scenario, name the constraint out loud, reason by elimination, and default to standard platform features. That's exactly how a senior architect thinks on their feet.
