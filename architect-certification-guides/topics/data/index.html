Section 1

Data Modeling

§1.1 · Relationships & design

Relationships & schema design

RelationshipBehavior
LookupLoose link; child can exist without parent; flexible sharing.
Master-DetailTight; child inherits owner & sharing from parent; enables roll-up summaries; cascade delete.
Junction (2× M-D)Resolves many-to-many between two parents.
HierarchicalSelf-lookup on User only (e.g. manager).
Trade-off: master-detail gives roll-ups & inherited sharing but couples the records tightly. Lookups are flexible but you implement roll-ups yourself (or via tools). Pick by sharing & lifecycle needs.
§1.2 · External IDs & keys

External IDs — the integration & migration linchpin

  • An External ID field holds the record's key from a source system; mark it Unique.
  • Enables upsert — match on the external key to insert-or-update, which is idempotent (safe to retry).
  • External ID fields are automatically indexed → keeps lookups selective at volume.
  • Critical for migration: load parents first, capture their IDs, then resolve child relationships by external key.

Fed angle

This ties your Integration story together: upsert-on-External-ID is how your Bulk API pipelines stay idempotent and how migrations re-run safely.

Section 2

Master Data Management

§2.1 · MDM & golden records

MDM: the single source of truth

System of Record

The authoritative source for a given data domain (e.g. the core banking system for accounts).

Golden Record

The consolidated, deduplicated, best-version record assembled from multiple sources.

MDM styles

Registry (index/point to sources), Consolidation (gather & clean), Centralized/Hub (master lives in one place), Coexistence (sync both ways).

Interview angle

Always establish which system owns which field. "Salesforce is system of record for X, the core system owns Y" prevents the bidirectional-sync wars that wreck integrations.

§2.2 · Dedup & data quality

Deduplication & data quality

  • Duplicate Management — Matching Rules + Duplicate Rules block or warn on dupes at entry.
  • Survivorship — rules deciding which field value wins when merging (most recent, most complete, source priority).
  • Standardization — normalize formats (phone, address) on the way in; validation rules + flows.
  • Profiling — measure completeness/accuracy; data quality dashboards & scorecards.
Section 3

Salesforce Data Management

§3.1 · Big Objects & archiving

Big Objects & archiving strategy

Big Objects

Store billions of records cheaply with a fixed schema. Queried via Async SOQL or a defined composite index — not normal SOQL.

Use for

Audit trails, historical/archived transactions, IoT/event history, regulatory retention.

Archiving pattern

Move aged records out of standard objects (which hit LDV problems) into a Big Object or external store; keep the live object lean.

Big Objects have no triggers, no standard SOQL, no sharing in the normal sense — they trade flexibility for massive scale. Define the index up front; you can't change it later easily.
§3.2 · Backup & restore

Backup & restore (JD: "backup" pattern)

Salesforce protects the platform, but you own your data's backup — a shared-responsibility reality every architect must state.

Native options

Scheduled Data Export (weekly/monthly), Salesforce Backup product, report exports, Recycle Bin (15 days, limited).

API / custom

Bulk API 2.0 extracts to external storage (e.g. S3) on a schedule — your pipeline.

Restore

Relationships & record IDs are the hard part on restore — re-link via External IDs; test the restore, not just the backup.

Fed angle

Your Bulk API 2.0 → Amazon S3 pipeline is a backup/DR pattern. Frame it as point-in-time export with downstream artifacts — exactly the "backup" the JD lists as a platform need.

Section 4

Data Governance

§4.1 · Governance & stewardship

Data governance & stewardship

  • Ownership & stewardship — named data stewards accountable per domain.
  • Classification — tag fields by sensitivity (public / internal / confidential / regulated) using Data Classification metadata.
  • Retention — policies for how long data lives, then archive/delete (ties to Big Objects).
  • Quality metrics — completeness, accuracy, timeliness tracked and reported.
§4.2 · Encryption & compliance

Protecting sensitive data (JD: "encryption")

Shield Platform Encryption

Encrypts data at rest while preserving key functionality. Deterministic encryption allows filtering; probabilistic is stronger but un-queryable.

Event Monitoring

Tracks who accessed/exported what — the audit trail a regulator expects.

Data Mask

Anonymizes PII in sandboxes so lower environments never hold real regulated data.

Classic encryption & FLS

Field-level security + CRUD as the first layer; encryption for data-at-rest beyond that.

Fed angle

Have a crisp Shield decision matrix ready: deterministic (filterable, weaker) vs probabilistic (stronger, not filterable), plus Event Monitoring for auditability. That trio answers "how do you protect sensitive data on platform" for a central bank.

Section 5

Large Data Volumes

§5.1 · LDV fundamentals

What changes at Large Data Volume

Past millions of records, naive patterns break. LDV is the most JD-relevant section here.

Selective queries

Queries must hit an index or they full-scan and time out. Selectivity is everything.

Sharing recalculation

Ownership/sharing changes on huge data sets are expensive; defer & batch them.

Skew

Too many child records under one parent/owner causes lock contention & slow recalcs.

Bulkification

Use Bulk API + batch Apex; never row-by-row at volume.

§5.2 · Indexing & selective queries

Indexing & query selectivity

  • Standard indexes — Id, Name, OwnerId, CreatedDate, External IDs, lookups/master-detail, unique fields.
  • Custom indexes — request from Salesforce for high-selectivity custom fields.
  • Selectivity thresholds — a filter is selective if it returns roughly <10% of records (first 1M) / <5% beyond, under index-specific caps.
  • Not indexed well — NULL values (standard indexes skip nulls), negative operators (!=, NOT, leading % wildcards), formula fields on non-deterministic data.
  • Skinny tables — Salesforce-created copies of frequently-queried fields (incl. some standard) to avoid joins; great for reports/list views at volume.
A two-column (composite) custom index helps common filter+sort pairs. Avoid filtering on non-selective fields or you force a full table scan.
§5.3 · Query Plan tool

The Query Plan tool

In the Developer Console (enable from preferences), Query Plan shows how the optimizer will execute a SOQL — your tuning instrument.

Cost

Relative cost; < 1.0 means it can use a selective index. Higher = trouble.

Leading operation type

Index (good), TableScan (bad at volume), Sharing, Other.

Cardinality

Estimated rows the leading operation returns — drives the cost.

Interview angle

"How do you fix a slow SOQL?" → "Run it through Query Plan, confirm it's hitting an index with cost < 1, and if it's a TableScan, make the filter selective or request a custom index." That's a concrete, senior answer.

§5.4 · Data skew

The three data skews

SkewCauseFix
Ownership skewOne user owns > ~10k records → slow sharing recalcsDistribute ownership; place owner high/outside role hierarchy
Account data skew> ~10k child records under one Account → lock contentionSpread children; "bucket" placeholder parents
Lookup skewHuge number of records point to one lookup valueDistribute values; reduce concurrency on that record
Skew shows up as record-locking errors (UNABLE_TO_LOCK_ROW) under concurrent updates. The number to remember is ~10,000.
Section 6

Data Migration

§6.1 · Migration strategy

Migrating data safely & at scale

  1. Profile & map source → target fields; cleanse before loading.
  2. Load order — parents before children; capture IDs / use External IDs to relate.
  3. Use Bulk API 2.0; consider deferring sharing recalculation & disabling non-essential automation during load.
  4. Validate — reconcile counts & checksums; spot-check relationships; re-enable automation.
  5. Idempotent — upsert on External ID so a re-run doesn't duplicate.
Turn off validation rules/triggers/workflows you don't need during bulk load to avoid row-by-row slowdowns & spurious failures — then re-enable and run a data-quality pass.
§6.2 · Data Cloud touchpoint

Data Cloud (JD: "preferred")

Salesforce's data platform / CDP — unify data from many sources into harmonized, queryable profiles. Know it at a conversational level.

Ingest

Data Streams pull from Salesforce, external systems, and files into the lake; zero-copy options federate to warehouses (Snowflake/BigQuery) without moving data.

Harmonize

Map sources to the Data Model; Identity Resolution stitches records into a unified profile.

Activate

Calculated Insights & segments feed analytics, personalization, and back into Salesforce/agents.

Fed angle

A one-paragraph answer is enough: "Data Cloud ingests via Data Streams (with zero-copy federation), harmonizes to a common model with identity resolution, and activates via Calculated Insights." For platform telemetry/logs, it's a strong cross-org analytics sink.

Bonus · Quick-Reference Cheatsheet

Quick-Reference Cheatsheet

Selective query rules

  • Selective ≈ filter returns <10% (first 1M) / <5% beyond, under index caps.
  • Standard indexes: Id, Name, OwnerId, CreatedDate, External IDs, lookups, unique fields.
  • Nulls aren't in standard indexes; !=, NOT, leading % kill selectivity.
  • Skinny tables & custom indexes = Salesforce-side fixes (log a case).

Query Plan

  • Cost < 1.0 = can use selective index. Leading op Index good, TableScan bad.

The ~10,000 number (skew)

  • Ownership skew (one owner >10k), Account data skew (>10k children), lookup skew → locking + slow recalc.

Scale storage

  • Big Objects — billions of rows, Async SOQL, no triggers/sharing, fixed index. Archive here.

Backup

  • You own it: Data Export / Salesforce Backup / Bulk API → external (S3). Test the restore.

Protect

  • Shield: deterministic (filterable) vs probabilistic (stronger). Event Monitoring = audit. Data Mask = sandboxes.

Migration

  • Parents first → External IDs → Bulk API → defer sharing/automation → reconcile → upsert = idempotent.
