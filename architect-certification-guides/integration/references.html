Authenticate Apps with OAuth Baseline concepts for app authentication against Salesforce APIs. Separate identity, authorization scope, token lifetime, and client trust model.
REST API: Understanding Authentication REST API authentication basics: Connected App setup, OAuth endpoints, OAuth flows, and access token use. Before API calls, define the connected app and flow, then protect tokens and scope access to the integration’s real needs.
OAuth Flows Choose the right OAuth flow for user, server-to-server, device, web, or integration contexts. Don’t pick “OAuth” generically — pick the flow based on actor, interactivity, and secret handling.
Connected Apps Overview Configure and govern integrations that need Salesforce API access or SSO/mobile policies. Connected Apps are the control plane for API access: scopes, policies, IP/session controls, and admin approval.
Connected App / OAuth Terminology Clarify terms such as client, resource owner, authorization server, scopes, tokens, callback URL, and connected app policies. Use precise vocabulary: authentication proves identity; authorization grants scoped access; a connected app governs the client.
OpenID Connect SSO Provider Use OIDC when Salesforce participates in standards-based single sign-on with identity claims over OAuth-style flows. OIDC answers “who is the user?”; OAuth answers “what can this app access?”
Salesforce as Identity Provider When Salesforce authenticates users and provides identity assertions/tokens to service providers. Be explicit whether Salesforce is IdP or SP; it changes where users authenticate and where trust is configured.
Just-in-Time Provisioning Create or update users during SSO based on incoming identity attributes. JIT turns identity claims into user lifecycle automation, but requires attribute mapping and governance.
Trailhead: Identity Protocols Plain-English comparison of SAML, OAuth 2.0, and OpenID Connect plus IdP/SP terminology. SAML is classic SSO, OAuth delegates API access, OIDC adds identity to OAuth-style flows.
Trailhead: Salesforce Identity Identity product features: SSO, external client apps, social sign-on, MFA, My Domain, centralized user management, and App Launcher. Identity architecture is user experience plus security policy: right people, right access, right time.
Security Overview Broader security posture reference for protecting access, sessions, credentials, users, and org configuration. Security requirements should become concrete controls: MFA, session policy, IP ranges, least privilege, monitoring, and audit.
Security Keys Understand stronger authentication factors and phishing-resistant auth options. For high-trust integrations/users, mention MFA/security keys and least-privilege connected app policy.

Fast answer template

“I’d start by classifying the integration: layer, direction, timing, volume, and ownership of the transaction. Then I classify the data: public/internal/confidential/restricted, PII, residency, retention, consent, and audit requirements. If Salesforce initiates a real-time process, I evaluate request/reply and its callout/governor limits; if it can be decoupled, I prefer events/queues/fire-and-forget. For external systems calling Salesforce, I look at Remote Call-In, REST/SOAP/Bulk/Composite API fit, API limits, idempotency with external IDs/upsert, and retry strategy. For data-change propagation, I compare Platform Events and CDC. For production readiness, I require monitoring, retry/dead-letter behavior, partial-failure handling, and resync plans. For auth and secrets, I avoid secrets in code, use Connected Apps/OAuth for inbound API access, and Named Credentials/External Credentials for outbound callouts.”
