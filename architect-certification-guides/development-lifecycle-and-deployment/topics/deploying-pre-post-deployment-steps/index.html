After studying this topic, you should be able to:

Page 4 · Introduction

Introduction

Salesforce deployments often require pre and post-deployment steps. Pre-deployment steps include important activities such as planning, sandbox testing, documentation of manual steps, freezing users, etc. It is necessary to perform these steps to ensure that no issues arise during or after the deployment.

Deployment activities include choosing a suitable tool, performing deployment validation, identifying the correct order of dependencies, and performing the deployment.

Post-deployment steps are necessary to make sure that the deployed components work as expected. Some important steps include reactivating deactivated features, such as validation rules and email deliverability, performing data migration in the correct order, monitoring the deployed features, etc.

Fed angle

At a regulated institution, every deployment — including pre and post steps — must be documented in a formal runbook approved before execution. The freeze-users / disable-automation / re-enable sequence maps directly to the change-control window in a Fed deployment plan. Regulators and internal audit teams will ask to see the runbook, evidence of validation, and sign-off records.

Deployment Steps

Page 7 · Pre-Deployment Steps (Planning, Testing, Audit Trail)

Pre-Deployment Steps

Pre-deployment steps are activities that are performed before a Salesforce deployment.

Planning

A Salesforce deployment should be well-planned. The deployment implications should be considered. Various positive and negative scenarios should be built and tested. All users should be notified and frozen or asked not to log in during the deployment timeframe.

Testing

A sandbox that is a true copy/replica of the production environment should be used to test the application before deployment.

Audit Trail

The audit trail in the production environment should be checked to ensure that no changes were made that would be overwritten.

Fed angle

Checking the audit trail before deploying is a critical segregation-of-duties control: it confirms no unauthorized changes were made directly in production since the last deployment. At the Fed, production changes outside the approved pipeline are a control deficiency. Freezing users during the deployment window is also an auditable change-control step — it prevents mid-deployment data writes that could corrupt migrated records.

Page 8 · Pre-Deployment Steps (Dependencies, Backup, Manual Steps)

Pre-Deployment Steps

Pre-deployment steps are activities that are performed before a Salesforce deployment.

Dependencies

Dependencies should be checked and all related components should be included in the package.

Backup

Data and metadata should be exported/backed up, especially for components that are being replaced or modified.

Manual Steps Documentation

Any manual steps required, such as data migration and feature activations, should be documented prior to the deployment.

Interview angle

Manual steps documentation is the key differentiator in this deck. When asked about unsupported metadata (e.g., org-wide email addresses, sharing settings), the answer is always: document the manual steps before deployment, perform them after the automated deployment completes. A well-structured runbook enumerates every manual step with owner, sequence, and verification criteria.

Page 9 · Pre-Deployment Steps (Automation, Test Scripts, Unsupported Components)

Pre-Deployment Steps

Pre-deployment steps are activities that are performed before a Salesforce deployment.

Automation

Validation Rules, Flows, and Apex Triggers that would prevent the deployment of new records or changes should be deactivated. Email deliverability should be disabled to ensure that mass changes do not trigger system emails and notifications.

Test Scripts & Training

Test Scripts to run after the deployment should be prepared. Training sessions should be organized for users in a sandbox environment.

Unsupported Components

Components not supported by the API, such as sharing settings and organization-wide email address, should be identified, and their manual deployment should be planned.

Unsupported components are a classic exam trap. The Metadata API and Tooling API do not cover everything — sharing settings and org-wide email addresses are the canonical examples. If the exam scenario mentions these, the answer is always: identify them pre-deployment, document the manual steps, and perform them post-deployment.

Fed angle

Disabling automation and email deliverability before bulk data operations is an important control to prevent alert fatigue and unintended notifications to customers or counterparties. In a regulated environment, an unplanned mass email to clients could trigger a supervisory inquiry. Documenting the disable/re-enable sequence in the runbook ensures no step is forgotten under deployment pressure.

Page 10 · Deployment

Deployment

Deployment steps are activities that are performed during a Salesforce deployment.

Deployment Tool

A suitable deployment tool, such as Change Sets or Metadata API, should be selected. The deployment package should be prepared accordingly.

Deployment Validation

Before performing the actual deployment, it should be validated. For example, when deploying a change set, it should first be validated to view the success or failure messages during the actual deployment.

Deployment Order

The correct order of deployment should be identified for the components with dependencies to ensure their successful deployment.

Deployment Execution

The deployment should be performed using the prepared deployment package and the selected deployment tool.

Interview angle

Validate-before-deploy is the standard exam answer for avoiding deployment surprises. After a successful validation of a Change Set, Salesforce allows a quick deployment that skips re-running Apex tests — a significant time saver for large orgs. Be prepared to articulate this distinction between a full deploy and a quick deploy after prior validation.

Page 11 · Post-Deployment Steps (Validation, Reactivation, Manual Changes)

Post-Deployment Steps

Post-deployment steps are activities that are performed after a Salesforce deployment.

Validation

Post-deployment testing should be performed to ensure that all deployed components and their interaction with existing components work as expected in the production environment.

Reactivation

Any features, such as validation rules, flows, and triggers, that were deactivated before the deployment should be reactivated. User accounts should be unfrozen. Email deliverability should be enabled to ensure that users can receive emails again.

Manual Changes

Any configuration changes that could not be automated via the API should be performed manually.

Fed angle

The reactivation checklist — rules, flows, triggers, user accounts, email deliverability — must be explicitly tracked in the deployment runbook with a responsible owner and a sign-off step for each item. At a Fed-regulated institution, leaving validation rules deactivated post-deployment is a data-integrity control gap that could surface in an audit. A formal post-deployment checklist with timestamped sign-offs is the control evidence.

Page 12 · Post-Deployment Steps (Data Migration, Monitoring, Additional Steps)

Post-Deployment Steps

Post-deployment steps are activities that are performed after a Salesforce deployment.

Data Migration

Data migration or updates should be performed if the deployment involves new fields or changes to data structures.

Monitoring & Support

The deployed features should be monitored to ensure that there are no issues. Support should be provided to end users who encounter issues.

Additional Steps

System documentation should be updated to ensure that it reflects the deployed changes. Changes should be communicated to end users and stakeholders. Training should be provided if necessary.

Interview angle

Data migration order is a critical post-deployment step when parent-child relationships exist. Parent records must be loaded before child records to avoid lookup errors (e.g., Accounts before Contacts, Products before Opportunities, Opportunities before Opportunity Line Items). Expect a scenario question that asks you to sequence a migration — the answer is always parent-first, following the object relationship hierarchy.

Business Scenario — Cosmic Green Innovations

Read the business scenario below and determine the most appropriate solutions for the company's requirements.

Scenario

Cosmic Green Innovations, a global leader in sustainable energy solutions, leverages Salesforce to manage its extensive client relations, project management, and analytics. The company's offerings range from renewable energy projects to environmental impact assessments, requiring sophisticated Salesforce customizations to meet diverse client needs.

With operations spanning North America and Europe, the company utilizes two primary Salesforce development teams. Despite their expertise, performing complex deployments across teams and ensuring consistent performance has been challenging. To streamline deployment processes and enhance application reliability, the company's Salesforce architect needs to analyze the existing deployment processes and recommend pre and post-deployment steps to improve the overall efficiency and consistency of Salesforce deployments.

Requirements & Solutions

Page 16 · Requirement 1

Requirement 1

Scenario

The development team in North America has been working on a new custom application for managing clients, sales opportunities, and energy solutions. The application utilizes accounts, contacts, leads, opportunities, opportunity line items, and products, which need to be migrated from an external system. In addition, it uses certain metadata components, such as an organization-wide email address, that are not supported by the Metadata API. The architect needs to recommend appropriate approaches to handle the deployment process, including the pre and post-deployment steps and the data migration order.

Page 17 · Solution 1

Solution 1

Solution

Prior to the deployment, it is a best practice to document the manual deployment steps for any components that cannot be deployed automatically, such as the steps required for setting up the organization-wide email address required by the application. A suitable deployment tool, such as Metadata API, should be utilized for deploying the application components. Once the deployment is complete, the manual deployment steps should be performed. This should be followed by the data migration of records in this order to ensure that parent records are loaded before the related records: Accounts, Contacts, Leads, Products, Opportunities, and Opportunity Line Items

Interview angle

This solution exemplifies the two-track deployment pattern: automated track (Metadata API) for supported components, manual track (runbook steps) for unsupported ones. The data migration order — Accounts → Contacts → Leads → Products → Opportunities → Opportunity Line Items — follows the parent-child relationship chain. Memorize this order; it appears frequently in scenario questions.

Fed angle

Documenting manual steps for API-unsupported components before deployment is the runbook discipline that a regulated institution demands. At the Fed, a deployment without a written, approved runbook covering manual steps would not be approved by the Change Advisory Board (CAB). The org-wide email address is a canonical example: it must be set manually, and the runbook must capture the before/after values with a verification step.

Page 18 · Requirement 2

Requirement 2

Scenario

The European development team is working on a custom data analytics application that focuses on customer engagement data. The application contains several custom dashboards with multiple running users. The team is planning to use Change Sets for the deployment of the application and would like to avoid possible delays during deployment. After the deployment, thousands of customer accounts, contacts, and cases will be migrated from an on-premises system. The architect must provide deployment-related considerations and identify the key areas that must be tested as part of the data migration process.

Page 19 · Solution 2 (Part 1)

Solution 2 (Part 1)

Solution

A few days before the planned deployment date, the Change Sets should be validated to view any success or failure messages that would occur during the actual deployment. After the validation, a quick deployment can be performed. For the deployment of the custom dashboards, it is important to note that user fields are preserved during a metadata deployment. Salesforce attempts to locate a matching user in the target org by comparing usernames during the deployment. If a username in the source org does not exist in the target org, Salesforce displays an error and the deployment stops until the username is resolved or removed.

Quick deployment is only available after a successful validation run that executed and passed all Apex tests. The test run results are reused, meaning the quick deploy skips test execution and deploys faster. This is the key mechanism for minimizing production downtime.

Interview angle

Dashboard running-user mismatches are a common real-world deployment blocker. The exam expects you to know: (1) user fields are preserved in metadata deployments, (2) Salesforce resolves users by username match between orgs, and (3) a missing username causes the deployment to halt. The fix is to either ensure matching usernames exist in the target org or remove the running user reference before deploying.

Page 20 · Solution 2 (Part 2)

Solution 2 (Part 2)

Solution

Some key areas that can be tested as part of the data migration include case association with the correct account and contact, case ownership along with associated entitlements and milestones, and data transformation against the on-premises system.

Fed angle

Data migration testing for a regulated institution goes beyond record counts. Verifying case ownership, entitlements, and milestones post-migration ensures that SLA commitments and access controls are correctly transferred. At the Fed, a data migration that incorrectly assigns ownership could result in unauthorized access to sensitive records — a compliance finding. Testing data transformation against the source system is the reconciliation step that satisfies audit requirements for data integrity.

High-Yield Exam Gotchas

  • Org-wide email address and sharing settings are NOT supported by the Metadata API — they must be set manually. Always document them in the pre-deployment runbook.
  • Quick deployment requires a prior successful validation — the validation must have run and passed Apex tests. Quick deploy then reuses those results.
  • Dashboard running users cause deployment failures if the username exists in the source org but not the target org. Resolve by matching usernames or removing the running user before deploying.
  • Re-enable email deliverability post-deployment — forgetting this is a common post-deploy oversight that leaves users unable to receive system emails.
  • Audit trail check is a pre-deployment step, not just a monitoring tool. It detects direct-in-prod changes that would be silently overwritten by the deployment.
  • Data migration order follows parent-child relationships. Accounts before Contacts, Products before Opportunities, Opportunities before Opportunity Line Items.
  • Data migration testing key areas: case association (correct account/contact), case ownership (with entitlements and milestones), and data transformation validation against the source system.

Fed angle — Tying it together

For a Federal Reserve platform engineer, the pre/post-deployment process is a change-control event with formal governance requirements. The pre-deployment runbook (including documented manual steps, automation disable/re-enable sequence, user freeze, and audit trail review) is the evidence package submitted to the Change Advisory Board for approval. The post-deployment checklist (reactivations, manual config steps, data migration, monitoring) must be completed with timestamped sign-offs by named owners. Any API-unsupported configuration (sharing settings, org-wide email addresses) must appear explicitly in the runbook with before/after values and a verification step — regulators and internal audit will ask for this evidence during change reviews and incident investigations.
