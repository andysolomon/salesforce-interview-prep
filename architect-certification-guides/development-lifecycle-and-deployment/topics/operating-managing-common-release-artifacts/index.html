Page 4 · Introduction

Introduction

In today's complex Salesforce environments, architects often face the challenge of managing common release artifacts across multiple Salesforce orgs. In a multi-org architecture, various approaches can be utilized for managing these shared components, which include custom fields, Apex classes, Lightning components, etc.

Salesforce architects should have the knowledge and tools to efficiently synchronize updates, maintain consistency, and ensure the seamless operation of business processes across different Salesforce orgs. Strategies for managing common release artifacts include source-driven development, Metadata API-based deployments, package-based deployments, and the use of change sets.

Fed angle

At a central bank with multiple Salesforce orgs (e.g., separate orgs per business line or regulatory boundary), having a single auditable source of truth for shared artifacts is a core control requirement. Drift between orgs — where one org's Apex class or configuration differs silently from another's — creates audit findings. The choice of deployment strategy (source-driven, Metadata API, packages, change sets) must be weighed against traceability and change-control obligations.

Page 5 · Managing Common Release Artifacts — Overview

Managing Common Release Artifacts

Four primary strategies exist for managing and deploying common release artifacts across Salesforce orgs, each with distinct strengths and trade-offs.

Source-Driven Development

A version control system (VCS) such as Git should be utilized as the source of truth for all artifacts, ensuring consistency across orgs.

Metadata API

The deploy() and retrieve() calls of Metadata API can be used to retrieve and deploy release artifacts across Salesforce orgs.

Package-Based Development

Managed, unmanaged, and unlocked packages can be created to deploy release artifacts or perform a metadata backup.

Additional Strategies

Additional strategies include creating a .zip file, using Salesforce CLI commands, evaluating third-party solutions, and using a Requirements Traceability Matrix (RTM).

Page 7 · Multi-Org Architecture & Release Artifacts

Multi-Org Architecture & Release Artifacts

When a company uses multi-org architecture, managing common release artifacts across multiple orgs presents certain challenges.

Artifacts

Common release artifacts that need to be synchronized across orgs include code, configurations, metadata components, and data.

Challenges

Managing common release artifacts across multiple orgs presents challenges in ensuring consistency, governance, and efficiency.

Approaches

Managing release artifacts in a multi-org architecture requires understanding of deployment methodologies, tools, and best practices.

Interview angle

When asked about multi-org challenges, anchor your answer to the three dimensions on this slide: consistency (same artifact version in every org), governance (who approves and tracks changes), and efficiency (how fast and reliably changes propagate). Then map each dimension to a specific tool or practice — VCS for consistency, change control process for governance, CI/CD pipeline for efficiency.

Page 8 · Source-Driven Development

Source-Driven Development

A version control system (VCS) such as Git should be utilized as the source of truth for all artifacts, ensuring consistency across orgs.

VCS at the Core

A VCS should be at the core of the release management process. It allows for version tracking, branching, and merging of development work across different orgs.

Salesforce DX, Git & Metadata API

Salesforce DX, Git, and the Metadata API can be used for maintaining consistency and governance across orgs, enabling collaborative development and helping to resolve conflicts in shared artifacts.

CI/CD Integration

CI/CD tools like Jenkins, Circle CI, and Travis CI can be integrated with Salesforce DX to automate the build, test, and deployment processes, ensuring consistent deployments across orgs.

Fed angle

For a central bank, source-driven development is the highest-assurance deployment strategy because every artifact change is traceable to a commit, author, and timestamp. CI/CD pipelines add automated testing gates before production deployment — exactly the kind of pre-approval control that regulators and internal audit look for. Branching strategies (e.g., GitFlow) also enforce segregation of duties between developers and release managers.

Page 9 · Metadata API

Metadata API

The deploy() and retrieve() calls in Metadata API can be used to retrieve and deploy release artifacts across Salesforce orgs.

Direct Control

Deployments based on Metadata API provide direct control over specific metadata components and are suitable for orgs with heavily customized metadata.

Salesforce CLI Commands

Salesforce CLI commands can be used to retrieve and deploy artifacts. The project retrieve start command is used to retrieve components. The project deploy start command is used to deploy components.

Zip File Deployment

The deploy() and retrieve() calls are used to deploy and retrieve a .zip file. The .zip file contains a project manifest (package.xml) that lists what to retrieve or deploy and XML components organized into folders.

Interview angle

The exam distinguishes between Metadata API methods precisely. Know that project retrieve start pulls metadata from an org into local source format, and project deploy start pushes it. The .zip + package.xml pattern is used when direct org access is unavailable — the package.xml manifest is the human-readable change list that gets handed to a release management team. This is the canonical answer for Requirement 1 in the scenario section.

Page 10 · Package Based Development

Package Based Development

Packages can be created to deploy release artifacts or perform a metadata backup.

Package Fundamentals

A package encapsulates a collection of metadata for easy deployment and supports versioning for iterative development. It can be distributed to other Salesforce users and orgs.

Package Types

Managed packages are less flexible for updates post-deployment. Unmanaged packages cannot be upgraded. Unlocked packages require the use of Salesforce DX.

Backup & Rollback

An unmanaged package can be created for metadata backup, the rollback of metadata changes and restoring data efficiently in the event of deployment issues or system bugs often requires more specialized solutions.

Unlocked packages are the modern, modular packaging option — they support source-driven development and can be versioned and upgraded, unlike unmanaged packages. Choose unlocked packages when you need the flexibility of modular releases with version control integration.
Page 11 · Change Sets

Change Sets

Change Sets can be utilized to deploy release artifacts between connected orgs.

Small Deployments

Change Sets offer a simple and intuitive method for small deployments and require no additional tools or setup. They can be easily used by Salesforce administrators.

Considerations

Using Change Sets is limited to orgs associated with the same production org (e.g., sandbox to production). It lacks the sophistication needed for managing complex dependencies.

Interview angle

Change Sets are the correct answer only for small, simple deployments between sandboxes and their associated production org. The exam frequently tests whether candidates know the limitations: no version control integration, no automated testing gates, no support for cross-org deployments (e.g., between two separate production orgs). For complex multi-org scenarios, Metadata API or source-driven development is always the stronger answer.

Page 12 · Additional Deployment Strategies for Release Artifacts

Additional Deployment Strategies for Release Artifacts

Additional strategies can be employed for managing deployments, data integrity, and system integration in Salesforce environments.

Zip File Deployment

For the deployment of artifacts when there is no direct access to the org, a .zip file containing a package.xml file and XML components can be utilized.

Validate Before Deploy

Deployment of artifacts can be validated prior to actual deployment using the Salesforce CLI project deploy validate command. The project deploy quick command quickly deploys a validated deployment.

Third-Party & AppExchange

Third-party and AppExchange products can be evaluated to implement metadata rollback and data recovery to comply with industry regulations.

Requirements Traceability Matrix

Comprehensive documentation, such as a Requirements Traceability Matrix, can be used to trace the development and purpose of code components.

Fed angle

The validate-then-quick-deploy pattern is especially valuable in regulated environments: running a full validation (including all Apex tests) in production without committing changes gives the release manager an auditable proof-of-deployability before the actual deployment window. This separates the approval gate from the execution step — a classic segregation of duties control. Third-party backup and rollback tools are often required to meet RTO/RPO obligations under financial regulators.

Requirements & Solutions

Page 16 · Requirement 1

Requirement 1

Scenario

A Salesforce consultant has been working on a customization project, but due to security concerns, the company cannot provide the consultant with direct access to the production org that requires the new features. A dedicated release management team will be responsible for performing the deployment to production. The architect needs to recommend suitable approaches for the proper communication of metadata components to the release management team as well as their validation and final deployment to the production environment using Salesforce CLI.

Fed angle

This scenario maps directly to a central bank's segregation of duties requirement: the developer who builds a change must not be the same person who deploys it to production. The .zip + package.xml hand-off is the auditable artifact that the release management team validates before touching the production org — creating a clear approval record that satisfies change control policy.

Page 17 · Solution 1

Solution 1

Solution

The consultant can use the retrieve() call of Metadata API for this requirement. They should retrieve all the project metadata and create a .zip file containing a project manifest (package.xml) file with all the associated metadata and send it to the release management team. The project manifest lists what to retrieve or deploy. One or more XML components are organized into folders in the .zip file. After receiving the .zip file, the release management team can use the project deploy validate command to validate the metadata deployment. After successful validation, it can use the project deploy quick command for the actual deployment.

Interview angle

The two-step deploy pattern — project deploy validate first, then project deploy quick — is the canonical exam answer for "how do you safely deploy when you cannot afford a failed production deployment." Validation runs all Apex tests and checks component integrity without committing; quick deploy then executes the pre-validated bundle, skipping the re-run of tests and drastically reducing the deployment window.

Page 18 · Requirement 2

Requirement 2

Scenario

A developer would like to utilize an existing Apex class for a new functionality but is unsure of its purpose. The class was defined by a different developer for a project that went live two years ago in a different Salesforce org. Comprehensive documentation is still maintained for that project. The architect must suggest a suitable approach to determine the purpose of the class.

This scenario highlights why maintaining comprehensive project documentation — including a Requirements Traceability Matrix — is not optional overhead. Code artifacts outlive their original authors and cross org boundaries; without an RTM, the provenance and intent of any artifact becomes archaeology.
Page 19 · Solution 2

Solution 2

Solution

Considering the project's documentation is still available, the developer can leverage the Requirements Traceability Matrix (RTM) to determine the purpose of the Apex class. It contains project specifications and artifacts, shows how requirements are related to the artifacts (such as an Apex class), and demonstrates that requirements have been met.

Fed angle

For a Federal Reserve Bank environment, the RTM is not just a developer convenience — it is a compliance artifact. It provides the evidence trail that a given code component was built to satisfy a documented, approved requirement. During audits or incident reviews, regulators will ask: "Why does this code exist and what requirement authorized it?" The RTM answers that question directly.

Page 20 · Requirement 3

Requirement 3

Scenario

The company is rolling out new infrastructure and strategies based on Salesforce DevOps for its production org in Europe. The new infrastructure should facilitate the rollback of metadata after a deployment and data backup and restore to help recover from deployment issues, bugs, or outages in the downstream environments. To remain compliant with industry regulations, the company must implement an appropriate strategy to recover and roll back from issues as soon as possible.

Interview angle

Rollback of metadata changes and data restore are two distinct problems. Native Salesforce (unmanaged packages) covers metadata backup, but efficient data restore and metadata rollback under regulatory time pressure typically requires third-party or AppExchange solutions. Know that this is the boundary where native tooling is insufficient and specialized products enter the picture.

Page 21 · Solution 3

Solution 3

Solution

The company should evaluate third-party and AppExchange solutions for this use case. Although Salesforce offers the creation of a metadata backup using an unmanaged package, the rollback of metadata changes and restoring data efficiently in the event of deployment issues or system bugs often requires more specialized solutions.

Fed angle

European regulatory environments (e.g., DORA — Digital Operational Resilience Act) impose strict requirements for recoverability, with mandated RTO and RPO targets. A regulated financial institution must have a tested, documented backup and rollback plan — an ad-hoc unmanaged package is not an auditable disaster-recovery strategy. Third-party solutions provide automated backups, point-in-time restore, and the audit logs that regulators require.

High-Yield Exam Gotchas

  • Change Sets only work between orgs connected to the same production org — they cannot deploy across two separate production orgs. For true multi-org scenarios, use Metadata API or source-driven development.
  • project deploy validate does not commit changes — it runs all Apex tests and checks component integrity in production. Only project deploy quick actually deploys. This two-step pattern is critical for zero-downtime deployments.
  • Unmanaged packages ≠ rollback solution — they can back up metadata, but efficient rollback and data restore under compliance pressure requires third-party/AppExchange tools.
  • The RTM is the answer when documentation is available — if comprehensive project documentation exists, the RTM is the fastest way to trace an artifact's purpose and the requirements it fulfills.
  • Unlocked packages require Salesforce DX — they are the modern modular packaging option. Managed packages are distribution-oriented (AppExchange ISVs); unmanaged are non-upgradeable snapshots.
  • CI/CD tools (Jenkins, Circle CI, Travis CI) integrate with Salesforce DX — not with Change Sets. If the scenario mentions automation or consistent deployments across orgs, source-driven development with CI/CD is the answer.
  • The RTM serves double duty: it traces requirements-to-artifacts AND provides the compliance evidence that a code component was built to satisfy an approved requirement — critical for audit.

Fed angle — Tying it together

For a central bank with multiple Salesforce orgs, the highest-priority controls are: (1) Source of truth in VCS — every artifact must be traceable to a version-controlled commit with author and timestamp; (2) Segregation of duties via release management — developers hand off .zip artifacts with package.xml manifests to a separate release team who validates and deploys; (3) Compliance-grade rollback — native unmanaged package backup is insufficient for RTO/RPO obligations, requiring specialized AppExchange or third-party tools; (4) RTM as audit evidence — every code component must be traceable to an approved, documented requirement. The validate-then-quick-deploy pattern and the RTM together create the paper trail that satisfies change-control audits and regulatory examinations.
