Page 4 · Introduction

Introduction

In the Salesforce landscape, a comprehensive testing approach is vital for ensuring applications meet both performance and business criteria. This approach includes unit testing to check individual components, integration testing for verifying component interactions, and system testing to assess the application as a whole. User Acceptance Testing (UAT) confirms the solution aligns with user expectations and business needs. Regression testing ensures new updates do not disrupt existing functionalities. On the performance front, performance testing, load testing, and stress testing evaluate how the application behaves under various loads and conditions. Collectively, these methodologies guarantee that Salesforce applications are robust, reliable, and ready for deployment.

Interview angle

When asked to describe your Salesforce testing approach, lead with the layered model: unit → integration → system → UAT → regression, with performance/load/stress as a parallel track for high-volume scenarios. Each layer catches a different category of defect. Architect-altitude means knowing which layer to invoke given a specific risk profile — not just listing all the types.

Page 5 · Salesforce Testing Methodologies Overview

Salesforce Testing Methodologies

Nine distinct testing methodologies can be utilized in Salesforce, each serving a specific purpose in the overall testing strategy.

Unit Testing

Focuses on verifying the functionality of the smallest testable parts of an application.

Integration Testing

Verifies the interactions between different components of an application.

System Testing

Focuses on testing the complete Salesforce system to ensure that everything works together as expected.

User Acceptance Testing

Performed by end users in a full copy sandbox.

Functional Testing

Ensures that features perform as expected according to technical specifications.

Regression Testing

Performed to ensure that existing features are not affected by new changes.

Production Testing

Performed in production to verify an implementation.

Performance Testing

Evaluates an application under different load conditions.

Load & Stress Testing

Load testing mimics expected data volume and/or user traffic. Stress testing pushes an application to its limits, and even beyond, to find potential breaking points.

Page 7 · Salesforce Testing Categories

Salesforce Testing Categories

Salesforce testing can be performed manually or automated using automation tools.

Manual Testing

In manual testing, tests are set up and executed manually using traditional methods with the minimum use of tools. It can be used for a variety of different test types and testing scenarios. However, it requires performing repetitive tasks, does not scale, and is prone to human error.

Automated Testing

Automated testing involves the use of automation tools to test Salesforce applications or features. Test scripts are executed automatically at scale. It avoids repetitive and error-prone manual testing activities. Examples are Selenium, Copado, Provar, ACCELQ, etc.

Fed angle

In a regulated environment, the repeatability and audit trail of automated testing are not optional. Manual testing cannot provide the evidence-of-execution artifacts that examiners expect for regression and release-gate testing. Automated test runs integrated into CI/CD pipelines generate timestamped, reproducible records — exactly the kind of control evidence that satisfies both internal audit and external regulators.

Page 8 · Salesforce Testing Categories — When to Use

Salesforce Testing Categories — When to Use Each

Salesforce testing can be performed manually or automated using automation tools.

Using Manual Testing

Manual testing is suitable for testing scenarios that require human judgment or subjective evaluation. It can be used to test one-off, non-repetitive scenarios that would be counter-productive to automate.

Using Automated Testing

Automated testing can be used to test repeatable test scenarios that would require considerable time and manual effort. It can be used for regression testing, data-driven testing with various input values, data sets, and data scenarios, integrating testing into the CI/CD pipeline, etc.

The decision to automate is an investment: setup cost is high but the payoff is in repeated runs and consistency. Automate what you run repeatedly; keep manual for exploratory and judgment-based scenarios.
Page 9 · Types of Salesforce Testing — Unit, Integration, System

Types of Salesforce Testing — Unit, Integration & System

Several different types of Salesforce testing can be utilized based on the testing requirements.

Unit Testing

Unit tests focus on verifying the smallest testable parts of an application, typically individual Apex methods, to ensure that they work correctly in isolation.

Integration Testing

Integration tests focus on verifying the interactions between different components, such as Apex classes and external APIs, to ensure that they work as expected.

System Testing

System testing focuses on testing the complete Salesforce system to ensure that all features, configurations, and customizations work together as expected.

Page 10 · Types of Salesforce Testing — UAT, Functional, Regression

Types of Salesforce Testing — UAT, Functional & Regression

Several different types of Salesforce testing can be utilized based on the testing requirements.

User Acceptance Testing

User Acceptance Testing (UAT) is performed by end-users to ensure that the system meets business needs and requirements. It is the final step before deployment.

Functional Testing

Functional testing is used to ensure that features perform as expected according to technical specifications. Each function is examined by providing input and comparing the output to functional requirements.

Regression Testing

Regression testing is performed after changes (new features, updates, enhancements, etc.) to the system to ensure that existing functionalities are not adversely affected.

Interview angle

UAT vs. functional testing is a common exam trap. Functional testing verifies against technical specifications — it is developer/QA-driven. UAT verifies against business requirements — it is end-user-driven and is the gate before go-live. Regression is the safety net run after any change, ensuring you haven't broken what was previously working.

Page 11 · Types of Salesforce Testing — Production, Performance, Load & Stress

Types of Salesforce Testing — Production, Performance & Load/Stress

Several different types of Salesforce testing can be utilized based on the testing requirements.

Production Testing

Production testing is performed in the production environment to ensure the successful implementation of all the code and configurations.

Performance Testing

Performance testing focuses on evaluating the performance, scalability, and responsiveness of a Salesforce application under different load conditions.

Load & Stress Testing

Load testing focuses on mimicking the expected user traffic to see how an application performs under that load. Stress testing pushes it to its limits, and even beyond, to find potential breaking points.

Performance testing can only be performed in a sandbox — it is NOT permitted in production. Load and stress testing require prior approval from Salesforce Support, submitted at least two weeks in advance.
Page 12 · Considerations for Unit Testing — Apex & Coverage

Considerations for Unit Testing

Unit testing involves testing individual components or units of code to ensure their correctness and functionality in isolation.

Apex Test Methods

Developers use unit testing to verify the behavior of Apex code. Apex test methods are usually very specific and can be used to test the behavior of individual Apex classes, triggers, Visualforce pages, or flows. Assertions can be used to verify the Apex code behavior.

Code Coverage

Salesforce requires a minimum of 75% code coverage for Apex code to ensure that most of the code is tested, which is crucial before deployment to production.

Fed angle

The 75% Salesforce platform minimum is a floor, not a target. In a regulated financial institution deploying custom Apex, internal quality gates should enforce higher coverage thresholds (often 85–90%+) as a release-control. Code coverage metrics should be tracked, trended, and reported as part of the change-control package submitted to the release manager and audit.

Page 13 · Considerations for Unit Testing — Test Classes & Mocks

Considerations for Unit Testing

Unit testing involves testing individual components or units of code to ensure their correctness and functionality in isolation.

Test Classes & Methods

Apex test classes and methods use the @isTest annotation. Test classes don't count toward the limit of 6 MB of Apex code in each org.

Considerations

Test methods cannot send emails or make callouts to external services. A mock object is needed whenever Apex code needs to make an HTTP callout. A mock can also be used to bypass the dependencies of other objects, methods, states, or behaviors.

@isTest is load-bearing: only methods annotated with @isTest (or @testSetup) count as test code. Forgetting the annotation means the method runs as production code and counts against the 6 MB limit — an easy mistake with real consequences.
Page 14 · Considerations for User Acceptance Testing

Considerations for User Acceptance Testing

User Acceptance Testing (UAT) is conducted by end-users before deployment to production to ensure that an application can handle the required tasks in real-world scenarios.

Validation

UAT is critical for validating an application's usability and functionality from the user's perspective, ensuring it aligns with business processes.

RTM

A Requirements Traceability Matrix (RTM) can be used to ensure that all the requirements have test cases associated with them so that no functionality is left untested during user acceptance testing.

Interview angle

The RTM is the architect's tool for proving completeness of test coverage at the requirement level — not code coverage, but requirements coverage. In regulated environments, the RTM becomes an audit artifact: it demonstrates that every business requirement was validated before go-live, which is the definition of defensible change control.

Page 15 · Considerations for Performance Testing — Objectives & Approval

Considerations for Performance Testing

Performance Testing simulates real-world usage conditions to identify potential performance bottlenecks and optimize an application's performance before it affects end-users.

Objectives

Performance Testing determines areas of the application where performance issues might occur, assesses how well it can scale with an increasing number of users or data volume, verifies that it remains stable under various stress conditions, and provides insights into optimization.

Approval

Performance tests must be submitted for approval to Salesforce Support at least two weeks in advance of the testing date. Unapproved testing is subject to throttling or blocking. The business case or scenario and business justification must be provided for performance testing.

Fed angle

The two-week advance approval requirement is a hard constraint, not a suggestion. For a regulated institution, this must be built into the release schedule — a missed approval window delays the entire release. Project plans for high-volume integrations should account for this lead time explicitly in the test planning phase.

Page 16 · Considerations for Performance Testing — Test Plan & Monitoring

Considerations for Performance Testing

Performance Testing simulates real-world usage conditions to identify potential performance bottlenecks and optimize an application's performance before it affects end-users.

Test Plan

A test plan can be generated and a testing window can be scheduled with the Performance Assistant. The test plan can be created based on the scenarios that need to be tested and their success criteria.

Monitoring

Salesforce Support does not design or interpret customer performance test results. Its role is strictly to monitor test activity to ensure that there are no issues with Salesforce services.

Salesforce Support monitors your test to protect the multi-tenant platform — they are not your QA team. You own the test design, execution, and results interpretation. Understand this boundary clearly before entering a performance testing conversation.
Page 17 · Considerations for Performance Testing — Sandbox & Constraints

Considerations for Performance Testing

Performance Testing simulates real-world usage conditions to identify potential performance bottlenecks and optimize an application's performance before it affects end-users.

Sandbox Only

Performance testing, including load and stress testing, can only be performed in a sandbox. It is not permitted in production environments since Salesforce is a multi-tenant platform.

Other Considerations

Performance testing must take governor limits into account. Built-in monitoring tools, such as the Developer Console, Lightning Usage App, and Salesforce Optimizer, can be used to monitor and analyze performance metrics.

Fed angle

The production testing prohibition protects all Salesforce tenants on shared infrastructure — an important concept for a central bank, which must also protect its own internal tenants from resource contention. Governor limits in this context are analogous to resource-consumption controls in a shared computing environment: they are guardrails, not obstacles, and testing against them in a sandbox reveals the real capacity envelope before you put production workloads at risk.

Page 18 · Considerations for Automated Testing

Considerations for Automated Testing

Automated testing tools can be utilized for unit testing, integration testing, functional testing, regression testing, performance testing, and UI testing.

Continuous Integration

Test automation can be run for different types of tests, especially unit and functional tests, as part of a continuous integration strategy. This is useful to prevent regression, ensuring that newly released features do not break other previously existing and stable functionality.

Merging

When using an automated testing tool to help manage deployments between Salesforce environments, automated tests should be run when branches are merged.

Fed angle

For a Fed platform engineer, automated tests run on branch merge in a GitLab CI pipeline are not just a developer convenience — they are a release-control. They enforce the principle that no untested code advances toward production. This is directly analogous to segregation of duties: the pipeline is the control that prevents a developer from self-approving a deploy without passing tests. Regulators and internal audit view this as a key automated control in the SDLC.

Business Scenario — Cosmic Retail Group

Read the business scenario below and determine the most appropriate solutions for the company's requirements.

Scenario

Cosmic Retail Group, a rapidly growing retail chain, leverages Salesforce for customer engagement and various internal operations. It utilizes Sales Cloud for sales processes, Service Cloud for customer interactions, and various custom applications on the Lightning platform for retail operations. With an expanding footprint and the need for innovative features to enhance its business processes and streamline operations, there's a pressing need for new custom applications in Salesforce.

The development teams have embarked on multiple Salesforce projects for the development of new functionalities, which require robust testing methodologies to ensure efficiency and reliability. The company's Salesforce architect needs to analyze the given technical requirements and recommend appropriate testing methodologies.

Page 22 · Requirement 1 (Part 1)

Requirement 1 (Part 1)

Scenario

A development team has started working on a custom application for order management in Salesforce. The team has the following technical requirements:

  1. A custom REST web service has been developed. It processes orders and order line items received from an external system. It is expected to receive more than 150,000 orders per day, and each order can have up to 20 line items. An inbound request can contain only one order and its corresponding line items. The architect needs to recommend testing methodologies to ensure that users don't face platform slowdowns during peak business hours.
Page 23 · Requirement 1 (Part 2)

Requirement 1 (Part 2)

Scenario

  1. HTTP callouts are used in Apex code to send processed order information to an external system. The architect must provide relevant considerations for writing Apex test classes for testing HTTP callouts.
  2. The development team is considering the use of an automated testing tool in a Continuous Integration (CI) workflow to manage deployments between environments. A suitable testing strategy is required to prevent regression.
  3. When the application components have been deployed in a UAT environment, the team wants to ensure that no functionality is left untested during user acceptance testing.
Page 24 · Solution 1 (Part 1)

Solution 1 (Part 1)

Solution

  1. To ensure that users don't experience slowdowns during peak business hours, performance testing should be conducted in a full copy sandbox. Load testing can be performed using the expected load of 150,000 orders and 20 line items per order.
  2. To test HTTP callouts in Apex test classes, mock objects are required. An HTTP response mock can be created by defining a class that extends the HttpCalloutMock interface.
  3. When using an automated testing tool for deployments, automated tests should be run when branches are merged. Unit and functional test automation can be utilized as part of the continuous integration strategy to prevent regression and ensure that the new features do not break any existing and stable functionality.

Interview angle

This scenario is a three-part testing question in a single requirement — a common exam pattern. Match each sub-requirement to its methodology: high-volume inbound → performance/load testing in sandbox; HTTP callouts in Apex → HttpCalloutMock; CI deployment management → automated tests on branch merge. The architect demonstrates mastery by mapping each risk precisely to the right tool, not by naming all testing types generically.

Page 25 · Solution 1 (Part 2)

Solution 1 (Part 2)

Solution

  1. A Requirements Traceability Matrix (RTM) document can be used to map user requirements to test cases. It can be used to ensure that all the requirements have test cases associated with them and no functionality is left untested during user acceptance testing.

Fed angle

The RTM is a critical governance artifact in regulated change management. At the Federal Reserve, every deployment to production requires documented evidence that all requirements were tested. The RTM provides that linkage in an auditable, traceable format — not as a developer's checklist, but as a formal change-control deliverable reviewed by the release manager before go-live approval.

Requirement 2

Scenario

A custom application comprising multiple Lightning web components has been created for case management. The components use validation rules and flows defined on the Case object. It will be used by support agents to handle inbound customer service calls. The architect must recommend testing methodologies to ensure that the application does not experience slowdowns under high call volume. Any considerations related to testing must also be described.

Page 27 · Solution 2

Solution 2

Solution

Performance testing and load testing can be performed in a full copy sandbox to ensure that the application does not experience slowdowns during high call volume. The request for performance testing must be submitted to Salesforce Support for approval at least two weeks in advance. A business justification must be provided. Salesforce monitors test activity to ensure that there are no issues with Salesforce services. It is important to note that Salesforce does not permit performance testing in production since it's a multi-tenant environment with shared resources.

Two separate scenarios in this deck (Req 1 and Req 2) both arrive at the same answer: performance/load testing in a full copy sandbox with pre-approval. This repetition is intentional — it is the canonical answer pattern for any "ensure no slowdowns under load" scenario question on the exam.

High-Yield Exam Gotchas

  • 75% code coverage is the platform minimum — not the organizational target. Architects should enforce higher thresholds (e.g., 85–90%) via CI gates for regulated or high-risk deployments.
  • Performance/load/stress testing is SANDBOX ONLY. It is never permitted in production — Salesforce is multi-tenant and shared resources protect all customers.
  • Two-week advance approval from Salesforce Support is required for performance testing. This must be factored into the project release schedule — missing the window delays go-live.
  • Salesforce Support monitors your test; they do NOT design or interpret your results. The customer owns test design and analysis.
  • Test methods cannot make real HTTP callouts. Always use a class implementing HttpCalloutMock. Forgetting the mock causes test failures that block deployment.
  • @isTest annotation is mandatory. Test classes do NOT count toward the 6 MB Apex code limit per org.
  • UAT ≠ Functional Testing. Functional testing is driven by technical specifications (QA/developer); UAT is driven by end-users validating business needs — it is the final gate before production.
  • RTM = completeness insurance for UAT. It ensures every business requirement has at least one test case — no gaps, auditable by design.
  • Automated tests should run on branch merge in a CI/CD pipeline. This is the canonical answer for "prevent regression in a deployment workflow" scenarios.
  • Regression testing triggers: any change to the system — new features, updates, enhancements, bug fixes. It is not a one-time activity; it runs after every change.

Fed angle — Tying it together

For a Federal Reserve platform engineer, testing is not just a quality gate — it is a control. The full testing lifecycle maps directly to the SDLC controls that regulators examine: unit tests with enforced coverage thresholds demonstrate that developers cannot merge untested code; automated regression in CI pipelines enforces that no change advances without passing tests (a segregation-of-duties analog); performance testing approval processes align with change-advisory board reviews for high-risk changes; and the RTM provides the audit artifact demonstrating that every business requirement was verified before go-live. Together, these form a defensible, documented, repeatable evidence package — exactly what examiners and internal audit ask for during a technology audit cycle.
