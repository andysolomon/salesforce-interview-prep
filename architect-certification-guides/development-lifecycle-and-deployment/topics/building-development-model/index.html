3 / 33 · Learning Objectives

After studying this topic, you should be able to:

  • Describe the main features of the org development and package development models.
  • Explain how scratch orgs, sandboxes, and development orgs are used for Salesforce development.
  • Identify the design factors that should be considered when choosing a Salesforce development model and a development environment.
  • Describe the appropriate development model and environment for the given business requirements.
4 / 33 · Introduction

Introduction

The org development model and package development model are two models that are often used for Salesforce development. The org development model leverages sandboxes and a source control system for development. On the other hand, in the package development model, metadata and code for applications and customizations are organized into manageable packages.

Scratch orgs are temporary orgs that can be spun up quickly for development. Sandboxes are copies of the production environment that are used for development, testing, and training. Individual development orgs and partner development orgs are also available for application development. Partner development orgs offer higher API and storage limits and more licenses.

Interview angle

When asked to compare the two models, lead with the key distinction: org model = sandboxes + manual change tracking; package model = modular packages + source-driven, automated CI/CD. The environment choice (scratch org vs sandbox) follows directly from which model you pick.

Development Models

7 / 33 · Org Development Model — Sandboxes & Source Control

Org Development Model

The Org Development Model features sandboxes and source control for the development process.

Sandboxes

The Org Development Model leverages sandboxes at various stages of the development lifecycle, including development, integration, testing, and training.

Source Control

A source control system is used to manage changes and ensure consistency across environments. A central repository is used to store all the code and metadata, which can also be stored on the local machine.

Salesforce DX

Salesforce DX tools are used to streamline the development workflow.

Fed angle

At the Federal Reserve, the org development model maps naturally to an existing change-control posture: sandboxes are controlled environments approved through IT governance, and a central Git repository (GitLab) provides the immutable audit trail regulators require. Salesforce DX tooling enables automated deployment pipelines that replace ad-hoc change sets.

8 / 33 · Org Development Model — Tools & Change Management

Org Development Model

The Org Development Model features sandboxes and source control for the development process.

Tools

Salesforce Extensions for VS Code and Salesforce CLI are used to enhance the development efficiency, from code retrieval to deployment. Automated processes can be created for testing and deployment.

Change Management

The development model ensures a robust change management process using tools for tracking changes, managing deployments, and facilitating real-time collaboration among team members.

Changes

Changes must be tracked manually. Sets of changes are deployed to sandboxes and then to the production org.

The key limitation of the org development model is that changes must be tracked manually — there is no automatic source-tracking. This is the primary pain point the package development model addresses.
9 / 33 · Package Development Model — Modular Dev & Version Control

Package Development Model

The Package Development Model uses packages to organize and manage components.

Modular Development

Metadata and code for applications and customizations are organized into manageable packages for modular development. This modularity supports better organization and reuse of functionality across multiple projects or orgs.

Version Control

Each package version is immutable once created, which allows precise version tracking and control over what is deployed. This facilitates easier rollback and upgrades.

Fed angle

Immutable package versions are a significant advantage in a regulated environment: each release artifact is a fixed, auditable unit. Change-control boards can approve a specific package version (e.g., v1.3.0.2) and that exact artifact — nothing more, nothing less — gets installed in production. This eliminates the "drift" risk inherent in change-set deployments.

10 / 33 · Package Development Model — Dependency & Isolation

Package Development Model

The Package Development Model uses packages to organize and manage components.

Dependency Management

Packages can declare dependencies on other packages, enabling complex applications to be built from smaller, interdependent modules. This simplifies updates and maintenance.

Isolation

Development in isolated environments (scratch orgs) is encouraged, minimizing the risk of conflicts and ensuring that development activities do not impact the production org directly.

Interview angle

Dependency management is often overlooked in exam answers. When explaining package development, mention that explicit package dependencies allow architects to reason about deployment order and version compatibility — a key concern when multiple teams share a Dev Hub.

11 / 33 · Package Development Model — Source-Driven Development

Package Development Model

The Package Development Model uses packages to organize and manage components.

Source-Driven Development

The model uses source tracking, source control, and continuous integration and deployment. Changes are tracked on the local machine and in the default development environment.

Source Tracking

Source tracking can be turned on in the source (production) org so that Developer and Developer Pro sandboxes automatically track changes between sandboxes created from it and Salesforce DX projects. It is enabled by default for scratch orgs. Only metadata changes that are not yet supported by source tracking need to be tracked manually.

Fed angle

Source-driven development is the core enabler of repeatable, audited builds in a regulated context. With source tracking and GitLab CI/CD, every metadata change is captured in a commit, every deployment is triggered by a pipeline, and every release has a traceable lineage from developer workstation to production. This is the story to tell when discussing how the Fed's Salesforce platform meets FISMA and internal IT controls.

12 / 33 · Package Development Model — Dev Hub & Salesforce DX

Package Development Model

The Package Development Model uses packages to organize and manage components.

Dev Hub

To create and manage scratch orgs and packages, Dev Hub must be enabled in the production org. To use packages, Enable Unlocked Packages and Second-Generation Managed Packages must be selected on the Dev Hub page in Setup.

Salesforce DX

For development, a Salesforce DX project can be created. A scratch org can be created and set as the default org for development. Source can be pushed and pulled to keep the local environment and the default development org in sync.

Dev Hub is the control plane for both scratch orgs and second-generation packages. Enabling it in production does not affect end users but it must be enabled before any sfdx scratch org or package work can begin.
13 / 33 · Package Development Model — CLI & Advantages

Package Development Model

The Package Development Model uses packages to organize and manage components.

Salesforce CLI

Salesforce CLI can be used to manage Salesforce DX projects, create scratch orgs, push and pull metadata, and run unit tests. It can also be used as part of build automation scripts to create and access environments, deploy source, install packages, and run tests.

Advantages

The package development model offers various benefits, such as improved team development and collaboration, facilitating automated testing and integration, greatly reducing the need for manual change tracking, more efficient and agile release cycles, etc.

Interview angle

When justifying the package development model to a skeptical stakeholder, anchor on three things: (1) automated testing via CLI in CI pipelines replaces error-prone manual testing, (2) immutable package versions eliminate "what exactly went to production?", and (3) agile release cycles mean smaller, lower-risk deployments more frequently.

Development Environments

15 / 33 · Scratch Orgs — Temp Orgs, Packages, Automation

Scratch Orgs

Scratch orgs are temporary Salesforce orgs that can be quickly spun up for development.

Temporary Orgs

Scratch orgs are fully configurable, disposable, and source-driven. They allow developers to emulate different Salesforce editions with different features and settings.

Packages

Scratch orgs are ideal for the development and testing of packages, especially unlocked packages.

Automation

Scratch orgs are suitable for automated testing and continuous integration pipelines.

Fed angle

Scratch orgs' disposable, source-driven nature is exactly what a CI/CD pipeline needs: a clean environment is spun up, automated tests run, results are recorded, and the org is deleted. There is no persistent environment state to manage or secure — each pipeline run starts from a known-good definition file checked into source control.

16 / 33 · Scratch Orgs — Use Cases

Scratch Orgs

Scratch orgs are temporary Salesforce orgs that can be quickly spun up for development.

Use Cases

A scratch org can be spun up for the following:

  1. Start a new project.
  2. Start a new feature branch.
  3. Test a new feature.
  4. Start automated testing.
  5. Perform development tasks directly in an org.
  6. Start from 'scratch' with a fresh new org.

Interview angle

The exam often presents a scenario where sandbox licenses are limited. The correct answer is always scratch orgs — they consume no sandbox license quota, are ephemeral, and can be created on demand. Memorize the six use cases; they map directly to the scenarios in the requirements section.

17 / 33 · Sandboxes

Sandboxes

Sandboxes are copies of the production environment that allow development, testing, and training.

Development

Sandboxes allow isolated customization and development work until changes are ready to be deployed to production.

Testing

Changes can be tested against copies of the production data and users.

Training

A sandbox can be used as a training environment for end users.

Coordination

Individual changes can be coordinated into one deployment to production.

Sandboxes are tied to the production org — they inherit its metadata and (depending on type) its data. Unlike scratch orgs, they persist and must be refreshed to stay in sync with production.
18 / 33 · Developer Edition Org — Usage, Sign-Up, Storage

Developer Edition Org

An individual Developer Edition org is a full-featured copy of Salesforce that can be used indefinitely.

Usage

A Developer Edition org can be used to keep up with the newest features, build custom apps, and test functionalities before purchasing them. Partners can use it for initial development and prototyping.

Sign-Up

One can sign up for a free Developer Edition org. However, it expires after 1 year of inactivity.

Storage & API

A Developer Edition org has a storage limit of 20 MB and an API call limit (per 24 hours) of 15,000.

19 / 33 · Developer Edition Org — Licenses & Beta Testing

Developer Edition Org

An individual Developer Edition org is a full-featured copy of Salesforce that can be used indefinitely.

Licenses & Limits

The org offers a limited number of user, feature and permission set licenses. It is not possible to submit feature/license/limit requests. For example, only 2 Salesforce user licenses are available.

Managed Beta Testing

A Developer Edition org supports managed beta testing.

The 2-user license limit makes individual Developer Edition orgs unsuitable for team development. For team work, use a Partner Developer Edition org (20 licenses) or sandboxes.
20 / 33 · Partner Developer Edition Org — Usage & Storage

Partner Developer Edition Org

A Partner Developer Edition org is a free org available for ISVs and consulting partners.

Usage

A Partner Developer Edition org is typically used by partners for application development and initial testing.

Sign-Up

The Environment Hub is used to create and log in to a Partner Developer Edition org. However, it expires after 1 year of inactivity.

Storage & API

A Developer Edition org has a storage limit of 250 MB and an API call limit (per 24 hours) of 50,000.

21 / 33 · Partner Developer Edition Org — Licenses & Beta Testing

Partner Developer Edition Org

Licenses & Limits

A Partner Developer Edition org offers a higher number of user, feature and permission set licenses, compared to an individual Developer Edition org. It is also possible to submit feature/license/limit requests. For example, 20 Salesforce user licenses are available.

Managed Beta Testing

A Partner Developer Edition org supports managed beta testing.

Design Factors

23 / 33 · Choosing Development Model & Environment

Choosing Development Model & Environment

Various design factors are necessary to consider for choosing an appropriate development model and environment.

Project

Larger, more complex projects benefit from package-based development and the use of sandboxes or scratch orgs depending on the testing needs.

Team

Org-based development is suitable for smaller teams. Package-based development is appropriate for larger, more collaborative teams.

Release

Package-based development with scratch orgs is ideal for sophisticated release management and continuous integration.

Longevity

For long-term projects requiring frequent updates and maintenance, sandboxes should be considered for development for stability and ease of integration.

Fed angle

For the Federal Reserve, the relevant factors skew toward package-based: large, multi-team platform with long lifecycle, continuous delivery requirements, and sophisticated release management via GitLab pipelines. The "longevity + frequent updates" factor makes sandbox-based environments the practical complement for integration testing of releases, while scratch orgs handle feature development in isolation.

Interview angle

The exam will give you a scenario and ask you to pick a model and environment. Map the scenario signals directly: large team → package; simple internal app → org; CI/CD pipeline → scratch orgs; need production-data testing → sandboxes; ISV app for AppExchange → package + scratch orgs.

25 / 33 · Business Scenario — Cosmic Digital Frontiers

Business Scenario

Read the business scenario below and determine the most appropriate solutions for the company's requirements.

Scenario

Cosmic Digital Frontiers, an innovative leader in virtual reality (VR) entertainment and educational platforms, develops immersive VR experiences for a global audience. Spanning markets in the Americas, Europe, and Asia, the company leverages Salesforce to streamline customer interactions, sales processes, and content delivery mechanisms. As the demand for VR content skyrockets, the company is at a crucial juncture, needing to efficiently manage the development of new features, address technical issues, and roll out updates to stay ahead in the highly competitive VR industry. The company seeks to implement a development strategy that not only accelerates innovation but also promotes effective collaboration among its globally dispersed teams. To achieve this, it requires a seasoned Salesforce architect to recommend the most suitable development model and environment that aligns with its vision for delivering unparalleled VR experiences.

Requirements & Solutions

27 / 33 · Requirement 1

Requirement 1

Scenario

Most of the Salesforce development teams of the company have been using the org development model for custom applications and customizations in Salesforce. A Sales Cloud development team has developed various extensions that are being used by internal users. The company recently acquired a software development company that develops extensions of an AppExchange app. The CTO would like both development teams to use the same Salesforce org to work on separate projects while following the same set of processes. The architect needs to recommend a suitable development model and environment.

28 / 33 · Solution 1

Solution 1

Solution

The development teams should adopt the package development model so that they can develop and build release artifacts that can be tested and released independently from artifacts for other projects. It offers various advantages, including improved team development and collaboration, facilitating automated testing and integration, and greatly reducing the need for manually tracking changes. Dev Hub must be enabled in the org to allow developers to create and manage scratch orgs and packages. In addition, to allow development using packages, Enable Unlocked Packages and Second-Generation Managed Packages must be selected on the Dev Hub page in Setup.

Fed angle

Independent release artifacts are especially important in a regulated org where two teams have different change-control approvers. Package development lets each team maintain its own release cadence and approval chain — the Sales Cloud customizations team and the AppExchange extensions team each produce versioned, independently installable packages. This preserves segregation of duties between teams without requiring separate orgs.

29 / 33 · Requirement 2 (Part 1)

Requirement 2 (Part 1)

Scenario

The company uses a highly customized repository that contains a lot of different custom applications. For most of its Salesforce development needs, it is trying to shift from the org development model to the package development model. Currently, each developer works within their own personal sandbox. The architect needs to recommend a suitable development environment strategy for the package development model and provide considerations related to change tracking.

30 / 33 · Requirement 2 (Part 2)

Requirement 2 (Part 2)

Scenario

Furthermore, the company recently became a Salesforce partner and would like to develop and launch a one-of-a-kind VR application that provides training to sales reps. It plans to use the org development model for developing the application. The architect needs to recommend a suitable development environment for this requirement.

31 / 33 · Solution 2 (Part 1)

Solution 2 (Part 1)

Solution

For development using the package development model, the company's developers should start using scratch orgs. A developer can spin up a scratch org to start a new project or feature branch, test a new feature, perform automated testing, etc. Source Tracking allows automatic tracking of changes between scratch orgs and Salesforce DX projects. It is enabled by default for scratch orgs. However, changes to metadata components that are not yet supported by source tracking need to be tracked manually.

Interview angle

This is the canonical "migrating from org to package model" answer. The environment shift is: personal sandboxes → scratch orgs per feature/project. Source tracking is the key change-tracking mechanism — but always note the caveat that some metadata types still require manual tracking. That nuance shows architect-level awareness, not just textbook recall.

32 / 33 · Solution 2 (Part 2)

Solution 2 (Part 2)

Solution

For the VR application, the company should use a Partner Developer Edition org for development. Compared to an individual Developer Edition org, it offers higher API call limit, more storage, and a greater number of licenses.

The trigger for choosing Partner Developer Edition over individual Developer Edition is Salesforce partner status. Partners get access to the Environment Hub to create Partner DE orgs, which are substantially more capable (50K vs 15K API calls, 250 MB vs 20 MB storage, 20 vs 2 user licenses).

Key Setup Steps for Package Development Model

  • Enable Dev Hub in the production org.
  • Select Enable Unlocked Packages and Second-Generation Managed Packages on the Dev Hub page in Setup.
  • Create a Salesforce DX project and scratch orgs as the default dev environment.
  • Use sf push / sf pull to keep local and scratch org in sync.
  • Note: some metadata types not yet supported by source tracking must be tracked manually.

High-Yield Exam Gotchas

  • Package version immutability is the exam's favourite advantage of the package model — once created, a version cannot change, enabling precise rollback.
  • Source tracking is automatic in scratch orgs but must be explicitly enabled (in the production org settings) for Developer and Developer Pro sandboxes.
  • Dev Hub lives in production — enabling it does not affect end users but it is a prerequisite for everything in the package model.
  • Individual Developer Edition: 2 licenses; Partner Developer Edition: 20 licenses — this is the exam's way to force the partner scenario answer.
  • Org model ≠ no source control — it uses source control too, but changes must be tracked manually (no source tracking by default).
  • Scratch orgs consume no sandbox license quota — always the answer when the scenario mentions "limited sandbox licenses."
  • Both Dev Edition and Partner Dev Edition expire after 1 year of inactivity — not on a fixed date.

Fed angle — Tying it together

For the Federal Reserve Bank of Chicago Salesforce Platform Engineer role, the package development model is the target state: source-driven builds, immutable release artifacts, GitLab CI/CD pipelines using Salesforce CLI, and scratch orgs for isolated feature development. Each package version represents an auditable, repeatable deployment artifact that can be approved by change control boards and traced back to a Git commit. Sandboxes remain relevant for integration testing (especially Full/Partial Copy types with production-like data), and source tracking on Developer/Developer Pro sandboxes can bridge the gap during a model migration. This combination — packages for delivery, sandboxes for integration, scratch orgs for development — is the architecture story that satisfies both Salesforce best practices and Federal Reserve IT governance requirements.
