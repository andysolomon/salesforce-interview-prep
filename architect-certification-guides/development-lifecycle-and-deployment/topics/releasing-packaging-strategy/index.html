Page 4 · Introduction

Introduction

In the Salesforce ecosystem, the deployment and distribution of custom applications and functionalities can be effectively managed through different types of packages: managed, unmanaged, and unlocked packages. Each package type serves distinct use cases, from distributing applications on the AppExchange, sharing open-source projects, to deploying modular customizations within an organization.

Managed packages are ideal for ISVs to distribute and sell applications with upgrade paths and license management. Unmanaged packages are suitable for one-time distributions where the recipient may need to modify the source code. Unlocked packages provide more flexibility for iterative development and release management within Salesforce DX, offering a balance between controlled deployment and customization capability. Understanding when and how to use each package type is crucial for Salesforce developers and architects to ensure efficient, secure, and scalable application lifecycle management.

Fed angle

For a regulated organization like a central bank, the packaging model chosen directly affects how metadata changes are versioned, audited, and rolled back. Managed 2GP and unlocked packages both produce immutable, versioned artifacts — the kind of traceable deployment record that satisfies change-control and audit requirements in a GitLab CI/CD pipeline.

Managed, Unmanaged, and Unlocked Packages

I · Managed Package Use Cases

Managed packages are used by Salesforce partners to create apps and distribute them to customers via the AppExchange marketplace.

The same namespace can be assigned to multiple managed packages. Public Apex classes and methods can be shared across packages in the same namespace.

Page 6 · Section

Managed Packages

Page 7 · Managed Packages — Overview

Managed Packages

Managed packages are used by Salesforce partners to create apps and distribute them to customers via the AppExchange marketplace.

Container

A package is a container that holds a set of related features, customizations, and schema. It can include many different metadata components and allows packaging a single component, app, or library.

Capabilities

Managed packages allow partners to distribute, license, pilot features of, troubleshoot, and monetize their offerings.

Types

Salesforce offers first-generation managed packages (managed 1GP) and second-generation managed packages (managed 2GP). Going forward, Salesforce recommends the use of managed 2GP.

Interview angle

When asked about managed packages, lead with the ISV distribution story: AppExchange listing, IP protection, upgrade paths, and license management. Then differentiate 1GP vs 2GP — 2GP is source-driven and CLI-first, making it the current recommendation. This shows both conceptual breadth and awareness of platform evolution.

Page 8 · Managed 2GP & Lifecycle

Managed Packages — Managed 2GP & Lifecycle

Managed packages are used by Salesforce partners to create apps and distribute them to customers via the AppExchange marketplace.

Managed 2GP

Managed 2GP offers benefits such as source-driven development, minimal interaction with Salesforce orgs, API- and CLI-first model, flexible versioning, namespace sharing across packages, declarative dependencies, and simplified patch versioning.

Lifecycle

Each package follows a distinct lifecycle. Whenever metadata is changed, added, or removed in a package, a new package version is created. Each package version has a version number and is an immutable artifact. When a new version is released, customers can upgrade to the latest package version or an upgrade can be pushed to them.

Fed angle

Immutable package versions are the packaging equivalent of a signed release artifact. In a regulated pipeline, every promotion from dev to staging to production should reference a specific, unmodifiable package version — not a living branch. This provides the traceable, auditable change history that examiners require.

Page 9 · Managed Packages — Metadata & AppExchange

Managed Packages — Metadata & AppExchange

Managed packages are used by Salesforce partners to create apps and distribute them to customers via the AppExchange marketplace.

Metadata

Features, customizations, and schema that comprise an app can be added to a package. Examples of metadata components include Apex classes, custom objects, flows, etc. The Metadata Coverage Report can be viewed for a complete list of metadata components that can be added.

AppExchange

When a completed app has been packaged up, and the packaged app has been through the security review, it can be listed on the AppExchange for marketing and distribution.

Page 10 · Managed Packages — Namespace & Continuous Integration

Managed Packages — Namespace & Continuous Integration

Managed packages are used by Salesforce partners to create apps and distribute them to customers via the AppExchange marketplace.

Namespace

A namespace is an alphanumeric identifier that can be created, registered, and associated with one or more packages. The same namespace can be assigned to multiple managed 2GPs. Code can be easily shared across packages in the same namespace.

Continuous Integration

End-to-end automation can be created using continuous integration (CI) jobs. For example, a CI job can be launched when a pull request against the source repository is created. The job can create a package version and a scratch org, and then install the package in the org.

Interview angle

The CI integration story is the architect-level answer to "how do you ensure package quality?" — a PR triggers a CI job that creates a new package version, spins up a scratch org, installs the package, runs Apex tests, and reports results. This is a concrete, repeatable pipeline that maps cleanly to any DevOps framework.

Page 11 · Managed Packages — Code Sharing & Flexible Versioning

Managed Packages — Code Sharing & Flexible Versioning

Managed packages are used by Salesforce partners to create apps and distribute them to customers via the AppExchange marketplace.

Code Sharing

Public Apex classes and methods can be shared across all packages in the namespace. The @namespaceAccessible annotation can be added to an Apex class, making it available to all packages in the namespace.

Flexible Versioning

An ancestor needs to be specified for each new package version. A package version can be abandoned if it does not need to be built on, but only if customers haven't been upgraded to it yet. Moreover, when creating a package version, it can be tagged with the name of the branch in the source control system.

The @namespaceAccessible annotation is the exam-specific mechanism for controlled code sharing across packages in the same namespace. Without it, public Apex in one package is not automatically callable from another package in the same namespace.
Page 12 · Managed Packages — Parallel Development & Tools

Managed Packages — Parallel Development & Tools

Managed packages are used by Salesforce partners to create apps and distribute them to customers via the AppExchange marketplace.

Parallel Development

Two or more development teams can build new features in parallel for the same package and then merge them when appropriate. Features can be built and tested without taking over the main branch. Unreleased versions can be easily abandoned.

Tools

The key tools used for building a managed 2GP are as follows:

  • Salesforce Extensions for VS Code
  • Salesforce CLI
  • Dev Hub org
  • Source Control System
Page 13 · Managed Packages — Dev Hub & Package Configuration

Managed Packages — Dev Hub & Package Configuration

Managed packages are used by Salesforce partners to create apps and distribute them to customers via the AppExchange marketplace.

Dev Hub

The Dev Hub setting can be enabled for a Salesforce org to make it the Dev Hub org, which is the designated place to find and manage all the managed 2GP packages, scratch orgs, and namespaces.

Package Configuration

A Salesforce DX project directory contains one or more package directories. The sfdx-project.json configuration file describes the configuration for each package. It specifies information such as package namespace, API version, and the path, version name, description, definition file, and dependencies of each package.

Fed angle

The sfdx-project.json file is the source-of-record for package structure and dependencies — analogous to an infrastructure-as-code manifest. In a regulated pipeline, this file (stored in source control) provides the configuration audit trail: every change to package membership, dependency declaration, or API version target is a reviewable commit.

Page 14 · Managed Packages — Version Numbering & Scripts

Managed Packages — Version Numbering & Scripts

Managed packages are used by Salesforce partners to create apps and distribute them to customers via the AppExchange marketplace.

Version Numbering

Package version numbers use the semantic versioning format. Each package version has major version, minor version, patch version, and build number (e.g., 4.1.7.NEXT). The build number can be NEXT, LATEST, or RELEASED.

Scripts

Continuous integration scripts can automate package development steps. For example, a script can be written to create a package version, create a scratch org, install the package version in the scratch org, run Apex tests, and email the test results to the release manager.

Build number keywords: NEXT creates the next sequential build, LATEST references the most recently created version, and RELEASED references the most recently promoted (released) version. These are exact values that appear in exam questions.
Page 15 · Managed Packages — Customization, Apex Settings & Developer Edition Orgs

Managed Packages — Customization, Apex Settings & Developer Edition Orgs

Managed packages are used by Salesforce partners to create apps and distribute them to customers via the AppExchange marketplace.

Customization

Each metadata component in a package has certain rules that determine whether the developer or the subscriber can make changes to the component or remove it after the package version is installed.

Apex Settings

To enable deployment of metadata from Apex code in a package that is not yet certified, Deploy Metadata from Non-Certified Package Versions via Apex can be enabled on the Apex Settings page in Setup.

Developer Edition Orgs

A partner can use a Developer Edition or Partner Developer Edition org for the development of a managed package.

Page 16 · Managed 2GP Development Workflow

Managed 2GP Development Workflow

The six-step workflow for building and releasing a managed second-generation package.

  1. Create a Salesforce DX Project
  2. Develop an App
  3. Configure and Create a Package
  4. Create a Package Version
  5. Install and Test the Package Version in a Scratch org
  6. Promote and Release the Package Version

Interview angle

This six-step workflow is a high-yield exam and interview item. Note that "Install and Test in a Scratch org" comes before "Promote and Release" — the scratch org is the gating quality check, not an afterthought. Promoting a version marks it as released and makes it available for production installs; you cannot un-release a promoted version.

Unmanaged Packages

Page 18 · Unmanaged Packages — Customization & Best Practice

Unmanaged Packages

Unmanaged packages are used to distribute open-source projects to developers or for one-time upload of applications that require customization after installation.

Customization

The components installed from an unmanaged package can be edited in the org they're installed in. The developer who created and uploaded the package has no control and cannot change or upgrade them.

Best Practice

An unmanaged package should not be used to migrate metadata from a sandbox to production. Furthermore, it should only be installed if the org used to upload the package still exists.

Unmanaged packages are not for sandbox-to-production metadata migration — that is a common wrong-answer trap. Use change sets, Salesforce CLI, or unlocked packages for that workflow.
Page 19 · Unmanaged Packages — Creation & Upload

Unmanaged Packages — Creation & Upload

Unmanaged packages are used to distribute open-source projects to developers or for one-time upload of applications that require customization after installation.

Creation

An unmanaged package can be created and uploaded on the Package Manager page in Setup. The Components tab can be used to add components to the package.

Upload

Once all the components have been added to an unmanaged package, it can be uploaded. An email with an installation link is sent once the package is uploaded successfully.

Page 20 · Unmanaged Packages — Uninstallation & Components

Unmanaged Packages — Uninstallation & Components

Unmanaged packages are used to distribute open-source projects to developers or for one-time upload of applications that require customization after installation.

Uninstallation

Any dependencies on metadata in another package must be removed before attempting to uninstall an unmanaged package.

Components

Components can be added either explicitly or implicitly to an unmanaged package. Explicit components must be included directly in the package, while implicit components are added automatically when another dependent component, such as a custom object, is added.

Page 21 · Unmanaged Packages — Automatic Renaming & Conversion

Unmanaged Packages — Automatic Renaming & Conversion

Unmanaged packages are used to distribute open-source projects to developers or for one-time upload of applications that require customization after installation.

Automatic Renaming

Some components, such as Report and Dashboard, support automatic renaming if a naming conflict occurs during installation. For other components, the installation is blocked if a naming conflict occurs.

Conversion

An unmanaged package can be converted into a managed package on the Package Manager page in Setup after registering a namespace.

Not all components handle naming conflicts gracefully. Reports and Dashboards auto-rename; most other component types block the install entirely. Know this distinction for scenario questions.

Unlocked Packages

Page 23 · Unlocked Packages — Use Cases & Modular Development

Unlocked Packages — Use Cases & Modular Development

Unlocked packages are designed for customers and partners to organize and deploy metadata and business logic using modular development.

Use Cases

Unlocked packages are suitable for iterative development and release of applications within customers orgs or distributing apps not intended for AppExchange. It can be used to organize existing metadata, package an app, extend an AppExchange app, or package new metadata.

Modular Development

Unlocked packages facilitate modular app development, which provides benefits such as better ownership of functionality, more efficient change management, more efficient development processes, and decreased cost to deliver new features.

Fed angle

For an internal platform team (like a central bank's Salesforce center of excellence), unlocked packages are the recommended pattern: each business domain or product team owns its package, changes are source-driven and versioned, and the version control system — not the org — is the source of truth. This is directly analogous to microservices release ownership and maps well to a DevSecOps governance posture.

Page 24 · Unlocked Packages — Source-Driven Development & Dependencies

Unlocked Packages — Source-Driven Development & Dependencies

Unlocked packages are designed for customers and partners to organize and deploy metadata and business logic using modular development.

Source-Driven Development

Unlocked packages utilize a source-driven development model. The source of truth of the metadata contained in an unlocked package is the version control system rather than what's in the org.

Dependencies

Unlocked packages allow declaring multi-level dependencies on one or many managed and unlocked packages.

Interview angle

The "source of truth is version control, not the org" statement is the conceptual cornerstone of Salesforce DX. For unlocked packages, this means that a developer should never edit metadata directly in the org and call it done — the VCS is authoritative, and the org is just a deployment target. This is the answer that distinguishes an architect from a developer in an interview.

Page 25 · Unlocked Packages — Package Evolution & Installation

Unlocked Packages — Package Evolution & Installation

Unlocked packages are designed for customers and partners to organize and deploy metadata and business logic using modular development.

Package Evolution

An unlocked package has a distinct life cycle. While a package continually evolves, each package version is an immutable artifact that contains specific metadata and features associated with it at the time it was created. As a developer adds, removes, or changes the packaged metadata, they create many package versions.

Installation

A package version can be installed in a scratch, sandbox, trial, developer edition, or production org. It has a version number, and subscribers can install a new package version through a package upgrade.

Page 26 · Unlocked Packages — Namespace & Requirements

Unlocked Packages — Namespace & Requirements

Unlocked packages are designed for customers and partners to organize and deploy metadata and business logic using modular development.

Namespace

An unlocked package can include a namespace for isolation or be namespace-free for more seamless integration with org metadata.

Requirements

Development of unlocked packages requires enabling Dev Hub and Second-Generation Managed Packaging and installing Salesforce CLI. A Salesforce DX project is created for development.

Unlocked packages can be namespace-free, unlike managed packages which always require a namespace. Namespace-free unlocked packages blend more naturally with org-specific metadata, which is often preferable for internal-only customization deployments.

Requirements & Solutions

Page 30 · Requirement 1

Requirement 1

Scenario

The company has developed a managed package for AppExchange. It includes Apex classes to create and customize some metadata components. The package is in the testing phase and has not been certified yet. During testing in a sandbox, the Apex code fails. The architect needs to ensure that the Apex classes are able to access the metadata in the org. Once the testing is complete, the package will be submitted for Salesforce security review. However, the product manager is concerned about the errors from the Checkmarx code scanner and requires a suitable approach to proceed.

Page 31 · Solution 1

Solution 1

Solution

To ensure that Apex classes in the managed package are able to access the metadata in the sandbox to perform operations, Deploy Metadata from Non-Certified Package Versions via Apex should be enabled on the Apex Settings page in Setup. With regard to the errors returned by the Checkmarx code scanner, they should be reviewed thoroughly. If there is no need to fix them, they should be marked as false positive, an explanation should be attached, and then the package should be submitted for review.

This is an exact exam scenario: uncertified managed package + Apex metadata access failure. The answer is always the Apex Settings toggle, not a code change. Similarly, Checkmarx false positives must be explicitly marked and explained — you cannot simply ignore them and submit.
Page 32 · Requirement 2

Requirement 2

Scenario

Two development teams have started working on two separate projects. Team A is working on an application for learning management, while Team B is working on an admin console for managing various administrative tasks. Both teams will be using second-generation managed packages (managed 2GPs) for development. Team A needs to use certain Apex code that will be developed by Team B. The architect must ensure that Team A only uses the methods exposed by Team B and no other team is able to use the same Apex code.

Page 33 · Solution 2

Solution 2

Solution

Two second-generation packages should be created with the same namespace for the given requirements. In the package being developed by team B, the @namespaceAccessible annotation should be added to the Apex methods that should be shared with team A.

Interview angle

This is the canonical use case for @namespaceAccessible: controlled, selective code sharing between 2GP packages in the same namespace without making the entire class globally accessible. The answer is not "use a global class" — that would expose the code to all orgs with the package installed. @namespaceAccessible scopes sharing to within the namespace boundary only.

Page 34 · Requirement 3

Requirement 3

Scenario

The company recently acquired a small business named Northern Lights Solutions, which became a Salesforce partner not long ago. Its development team needs to work on an AppExchange solution and would like the architect to recommend suitable development environments for creating a managed package for the solution. Also, the sales leadership team of Cosmic Learning Solutions recently had hands-on experience with a sales analytics app used by Northern Lights Solutions and would like to add it to the main Salesforce org in the shortest possible time.

Page 35 · Solution 3

Solution 3

Solution

Northern Lights Solutions' development team can use a Developer Edition or Partner Developer Edition org to develop the managed package. An unmanaged package can be created for the sales analytics app used by Northern Lights Solutions and deployed in the main Salesforce org used by Cosmic Learning Solutions.

The unmanaged package is the right choice here specifically because the goal is "shortest possible time" and the recipient may need to customize the components post-install. There is no ongoing upgrade relationship needed — just a fast, one-time distribution.
Page 36 · Requirement 4

Requirement 4

Scenario

The company has three orgs in different regions. Its business processes are standardized but used globally, but each region needs the flexibility to be able to understand the standardized code and customize some of its aspects for the region. The architect needs to suggest a suitable package development model for this use case and provide best practices and considerations for change management.

Page 37 · Solution 4

Solution 4

Solution

Unlocked packages can be used to deploy the global code to different Salesforce orgs. Each region can be allowed to create its customized unlocked package extensions. For an agile and efficient release cycle, a modular development process should be utilized with a source control system as the source of truth for the metadata in unlocked packages. Developed packages should be tested in sandbox environments before installing to production. The metadata coverage report should be consulted to identify features supported by packages. Package versioning and the ability to specify multi-level dependencies should help with change management.

Fed angle

This multi-org scenario is analogous to a central bank with regional operations (e.g., district banks, international offices). Unlocked packages with regional extension packages provide global standardization with local flexibility — and every deployment is traceable via package versions in a source control system. Testing in sandbox before production mirrors the dev → staging → production pipeline governance that regulated organizations require.

Page 38 · Requirement 5

Requirement 5

Scenario

The company wants to release an application that can be installed in partner Salesforce environments. The application is designed to allow the partners to publish training modules without leaving their Salesforce environment. The partners should be able to build on top of the application with flows and Apex triggers for integration with their own business processes. The architect needs to recommend a suitable mechanism for developing and releasing the application, considering the company wants to keep the application up to date in various environments.

Page 39 · Solution 5

Solution 5

Solution

The company should use a managed package for developing and releasing the application. Managed packages allow for version control, easy updates, and package upgrades, which are crucial for keeping the application up to date across partner Salesforce environments. Additionally, managed packages provide IP protection and namespace isolation, which helps prevent conflicts with the partners' existing customizations. Partners can still build on top of the application with flows and Apex triggers, making this a seamless and scalable solution for distribution.

Interview angle

The decision driver here is "distribute to partner orgs and keep up to date" — that is the managed package use case, not unlocked. Unlocked packages are for internal org-source management. Managed packages provide the upgrade path (push upgrades or subscriber self-upgrade) and IP protection needed when distributing to external parties. Partners can still extend with flows and triggers because managed packages allow subscriber-side additions on top of the package layer.

Page 40 · Requirement 6

Requirement 6

Scenario

A development team is using two second-generation managed packages for developing a custom application for managing opportunities. Both packages have the same namespace. Package A contains two Apex classes named OpportunityController and OpportunityControllerTest, but they are used only in package B. The architect needs to recommend a suitable approach for moving these classes to package B for better organization and control.

Page 41 · Solution 6

Solution 6

Solution

In package B, any references to the Apex classes in package A should be removed, and a new package version should be created for package B. After removing all the references, the Apex classes should be removed from package A, and a new version of package A should be created.

The order matters: remove the references from package B first (creating a new B version), then remove the classes from package A (creating a new A version). Reversing this order would cause a compile error in the new package B version because it would still reference classes that no longer exist in A.

High-Yield Exam Gotchas

  • Unmanaged packages are NOT for sandbox-to-production migration — use change sets, Salesforce CLI, or unlocked packages instead.
  • Unmanaged package components are fully editable — the original developer has no control after install. This is a feature, not a bug, for open-source distribution.
  • Managed 2GP is Salesforce's current recommendation over 1GP — it is source-driven, CLI-first, and supports namespace sharing across packages.
  • @namespaceAccessible controls cross-package Apex sharing within the same namespace — not global access, which would expose code to all installs.
  • Version number format is major.minor.patch.build — build values NEXT, LATEST, RELEASED have precise meanings; RELEASED refers to the most recently promoted version.
  • Unlocked packages can be namespace-free — managed packages cannot. Namespace-free unlocked packages integrate seamlessly with org metadata, preferred for internal use.
  • Removing components from a 2GP package requires version sequencing: remove references first (new version), then remove the component (another new version). Order matters to avoid compile errors.
  • Unlocked package source of truth = VCS, not the org — direct org edits outside the package workflow are an anti-pattern.
  • Checkmarx false positives must be marked and explained — you cannot submit for security review while leaving scanner errors unaddressed; they must be acknowledged with justification.
  • Dev Hub is required for both managed 2GP and unlocked packages — it manages scratch orgs, namespaces, and package records.

Fed angle — Tying it together

For a central bank platform engineer, package strategy is fundamentally a change-control and audit story. Managed 2GP and unlocked packages both produce immutable, versioned artifacts that satisfy the "every production deployment is traceable to a specific, reviewed, approved artifact" requirement of regulated change management. Unlocked packages are the right internal tool: source-driven (VCS is auditable), modular (teams own their domains), and versioned (rollback is deterministic — reinstall the prior version). Managed packages are right when distributing to external partners with IP protection and upgrade governance. Unmanaged packages should appear in your architecture only for fast one-time transfers where no ongoing control is needed — their lack of upgrade governance makes them unsuitable for anything on a regulated change-advisory board's radar.
