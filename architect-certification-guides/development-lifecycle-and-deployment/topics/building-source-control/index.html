Introduction

Using a source control system like Git for Salesforce development allows tracking and managing changes to code and configuration over time. It allows developers to revert to previous versions, compare changes, and merge updates from multiple sources.

Git keeps track of changes in a project over time while GitHub is a collaboration platform that hosts Git repositories. There are various branching strategies available for Git workflows, including Centralized Workflow, GitHub Flow, Gitflow Workflow, Forking Workflow, and Trunk-Based Development.

A commit represents a snapshot of a project at a specific point in time. A merge conflict should be resolved to merge two branches successfully. It occurs when two developers have changed the same lines in a file or if a developer deleted a file while another developer was modifying it.

Fed angle

At the Federal Reserve Bank of Chicago, every code change must be traceable to an approved work item and an auditable commit history. Git's immutable SHA-based history plus GitLab merge requests with required approvals satisfy both the version-tracking and segregation-of-duties controls that regulators examine.

Git

Repositories

A repository is a collection of source files used to compile the project.

GitHub

GitHub is a collaboration platform that hosts Git repositories and acts as a remote source of truth for the shared work of developers.

Issues

Issues are threaded discussions about the project. They can be used to track bugs and feature requests and assigned to specific team members.

Pull Requests

Branching Strategies

15 / 53

Branching Strategy

When choosing a suitable branching strategy for a GitHub workflow, various considerations apply.

Short-Lived Branches

Generally, branches should be short-lived and created to accomplish a specific function. They should be deleted once they are merged to prevent confusion, encourage up-to-date code, and facilitate iterative improvements to projects.

Long-Lived Branches

A long-lived branch is suitable for a development branch or a situation that requires multiple levels of deployment-level code. However, there are challenges with a long-running branch, such as not having the most up-to-date version of each branch and needless merge conflicts.

16 / 53

Branching Strategy

When choosing a suitable branching strategy for a GitHub workflow, various considerations apply.

Branching Elements

Some important aspects to consider for creating branches include naming conventions, labels, assignees, milestones, project boards, templates for issues and pull requests, sign-off process, users responsible for merging pull requests, etc.

Factors

Some important factors to consider for choosing a suitable branching policy are team size, team structure and complexity, desired release cadence, and existing workflow.

Interview angle

When asked to recommend a branching strategy, frame your answer around these four factors — team size, structure, release cadence, and existing workflow — before naming a strategy. This signals you are reasoning from requirements, not just reciting a preference.

Centralized Workflow

The Centralized Workflow is a GitHub workflow that uses a single central repository.

Clone the central repository

A developer clones the central repository, creating a local copy of the entire project.

Make changes locally

The developer makes changes to the local repository by adding, editing, and deleting files.

Make commits

Changes are staged and committed to track modifications in the local project.

Push changes to the main branch

After finalizing and committing the local changes, they are pushed to the main branch of the central repository.

Centralized Workflow

The Centralized Workflow is straightforward and easy to understand, making it suitable for small teams looking for simplicity.

Small Teams

It is best for small teams or individual developers when tightly coordinated development efforts are required, minimizing the risk of conflicting changes.

Simple Collaboration

It is ideal when a project has simple collaboration needs and does not require a complex branching strategy for features or releases.

Transition

It is suitable for teams that are moving from a centralized version control system to Git, offering a familiar structure and easing the transition process.

GitHub Flow

The GitHub flow is a lightweight, branch-based workflow used to collaborate on projects.

Create a branch

To work on a new feature or fix a bug, a new branch is created from the main branch. Any changes made are only reflected in the branch.

Make commits

Changes made to files on the new branch are committed using descriptive message. After the commit, the changes are pushed to the branch.

Create a pull request

A pull request is created to discuss the proposed changes. It can include a summary of the changes made and what problem they solve.

Collaborate

Reviewers can leave comments, questions, and suggestions on the proposed changes. Further changes can be committed and pushed in response.

Merge the pull Request

Once the pull request is approved, the changes are deployed to the target environment, and the pull request is merged with the main branch.

Delete the branch

After the pull request is merged, the branch is deleted, which indicates that the work is complete and prevents users from accidentally using it.

22 / 53

GitHub Flow

The GitHub Flow is typically used in projects that prioritize a simple, clear workflow with a continuous integration/deployment model.

Rapid Iterations

It is ideal for projects that aim for continuous integration/continuous delivery (CI/CD), where changes need to be deployed quickly and efficiently after passing automated tests.

High Collaboration

It is suitable for teams that value collaboration and fast feedback loops with stakeholders. It facilitates easy code reviews and discussions via pull requests.

Simplified Workflow

It is suitable when a streamlined workflow is required without the overhead of managing multiple branches or complex merging strategies.

Gitflow Workflow

The Gitflow Workflow is a branching model that uses two primary branches and feature branches.

StepAction
1Create 'main' and 'develop' branches from the repository
2Create a feature branch from 'develop'
3Merge feature branch into 'develop'
4Create a release branch from 'develop'
5Merge the release branch into 'main' and 'develop'
6Create hotfix branches from 'main' to fix critical issues
24 / 53

Gitflow Workflow

The Gitflow Workflow is a branching model that uses two primary branches and feature branches.

Create primary branches

The repository is cloned and two primary branches called 'main' and 'develop' are established.

Create a feature branch

A feature branch is created from the 'develop' branch to work on a new feature.

Merge with the develop branch

After feature completion, the feature branch is merged into the 'develop' branch.

Create a release branch

A release branch is created from 'develop' when ready for a new release.

Merge with develop and main

When the release is complete, the release branch is merged with 'develop' and 'main'.

Create hotfix branches

Hotfix branches are created from 'main' to work on urgent fixes. They are merged back into 'main' and 'develop' after completion.

25 / 53

Gitflow Workflow

The Gitflow Workflow is typically used to manage larger projects for parallel development of features, preparation for upcoming releases, and quick fixes.

Scheduled Releases

It is ideal for projects with defined release schedules that require a structured approach for managing development, releases, and hotfixes.

Complex Projects

It is suitable for complex projects that require maintaining multiple versions in production, staging, and development environments.

Collaboration

It provides an organized, standard methodology that clearly defined roles and responsibilities for managing large-scale projects.

Fed angle

Gitflow maps naturally to the Fed's release governance model: the develop branch maps to the integration/UAT environment, the release branch represents the change freeze window before production deployment, and hotfix branches give auditors a clear record of emergency fixes applied directly to production. This branch topology makes change-control evidence straightforward to produce.

Forking Workflow

In the Forking Workflow, a developer has a private local repository and a public server-side repository.

Fork the repository

A personal copy of the repository is created on the server side.

Clone the fork

The fork is cloned to the local machine for development work.

Create a new branch

In the local repository, a new branch is created to work on new features or bug fixes.

Commit and push changes

Changes are committed regularly to the new branch and pushed to the fork.

Submit a pull request

A pull request is created from the fork to the original repository to propose the changes for integration.

Review and merge

The pull request is reviewed. Once approved, the changes are merged.

Control

When external contributions need to be reviewed and vetted thoroughly, project maintainers can control what gets merged and when.

Large Teams

It is suitable for large teams that are distributed geographically, allowing each contributor to work independently.

30 / 53

Trunk-Based Development (TBD)

In Trunk-Based Development (TBD), small, frequent updates are merged into the trunk or main branch.

Clone the central repository

The central repository is cloned to start with a fresh clone of the main codebase.

Work directly in trunk

Work is performed directly in the core trunk or main branch. Alternatively, it is performed in a short-lived branch.

Commit and push frequently

Small, incremental changes are made and pushed at least daily to minimize divergence from the trunk.

Use feature toggles

Incomplete features can be hidden from users without removing them from the 'main' branch.

Merge quickly

If using a short-lived branch, it is merged quickly into the 'main' branch after a quick review process.

31 / 53

Trunk-Based Development (TBD)

Trunk-Based Development (TBD) is suitable for teams that prioritize rapid delivery and wish to avoid the complexity of long-lived branches.

Rapid Release Cycles

It is suitable for teams that are committed to CI/CD practices and want to focus on rapid release cycles, minimizing branch management overhead and integration challenges.

Agile & Lean Practices

It is ideal when teams want to focus on agile development practices to build, test, and release software in short, iterative cycles, promoting a faster feedback loop.

Minimizing Conflicts

Frequent commits to the main branch are encouraged, reducing the scope and complexity of merge conflicts by avoiding long-lived branches.

TBD requires strong automated testing gates — committing directly to trunk is only safe when CI catches regressions immediately. For Salesforce, this means Apex test coverage gates in the pipeline before any merge to trunk.

Commits & Merging

33 / 53

Commits

A commit represents a snapshot of the project that contains a lot of information.

SHA-1 Hash

Each file in a snapshot is given a unique SHA-1 hash called a blob. The blobs are referenced by a tree, which is referenced by the commit. As changes are made to a file and new commits are made, a new SHA-1 hash is applied to the file, which references the previous hash as the parent.

Commit History

Each new commit references the previous commit as the parent. This parent-child relationship creates a consistent history and allows Git to merge branches together.

34 / 53

Commits

A commit represents a snapshot of the project that contains a lot of information.

Semantic Versioning

Semantic Versioning can be used in commit messages to track the evolution of code and configurations with clear version numbers that indicate the nature of changes (major, minor, or patch).

Release Tags

Tags can be used in Git to mark releases or significant changes, making it easier to deploy specific versions to Salesforce orgs or rollback if necessary.

Interview angle

Semantic versioning (MAJOR.MINOR.PATCH) is the exam-preferred answer for versioning strategy. Pair it with Git tags to show you understand how to create a persistent, queryable reference to any deployed version — which is how you enable rollback to a named release.

Commits

A commit represents a snapshot of the project that contains a lot of information.

Commit History

Git can be used to display a list of all the commits on the current branch. The project history can also be accessed on GitHub.

Comparisons

When working on a commit, versions of files can be compared. The differences between what is currently in the working directory and the staging area can help add the right files to the commit.

36 / 53

Commits

A commit represents a snapshot of the project that contains a lot of information.

Undoing Changes

Git can be used to undo a change by creating a new commit with changes that are the opposite of the changes in the original commit. It also allows making a modification to the last commit, which alters the commit history of the project.

Rewinding

Git can be used to rewind the history of the project, which also alters the commit history. It is only recommended when commits have not been pushed to the remote branch.

Never rewrite history on a shared/protected branch. Rewinding (git reset --hard) should only be done locally before pushing. On shared branches, use a revert commit to safely undo changes while preserving the audit trail.
37 / 53

Merge Strategies

Git uses two primary methods for merging changes: Recursive Merge and Fast-Forward Merge.

Recursive Merge

When the feature branch doesn't have the latest version of code in the target branch (usually main), recursive merge is used. When a pull request is created and changes are merged, a merge commit is created, which combines the changes in the two branches.

Fast-Forward Merge

When there are no new commits other than the ones in the feature branch, fast-forward merge is used. In this case, Git does not create a new merge commit. The tip of the target branch is fast-forwarded to include the changes in the feature branch.

Interview angle

Know which merge type produces a merge commit (recursive) and which does not (fast-forward). In regulated environments, recursive merges are preferred because the merge commit itself is part of the audit trail — it records who merged what and when, which fast-forward merges lose.

38 / 53

Merge Conflicts

Merge conflicts occur when two developers have changed the same lines in a file or if a developer deleted a file while another developer was modifying it.

Conflict

A merge conflict only affects the developer who conducts the merge. The file is marked as conflicted and the merge process is halted. The developer must then resolve the conflict.

Resolution

There are various command-line tools available in Git to resolve merge conflicts. Many third-party tools support streamlined merge conflict support features.

Fed angle

At the Fed, merge conflict resolution must be documented — the resolution is itself a change to the codebase and must go through the same review process as any other change. GitLab protected-branch rules ensure that even conflict-resolved merges require a fresh approval, preventing the conflict resolution from bypassing the four-eyes control.

Requirements & Solutions

42 / 53

Requirement 1

Scenario

The company has multiple development teams that work on separate streams of work, with different timelines and releases. Each team typically works on different code and configurations. The company is exploring the use of a source control system to track code and configuration changes and minimize the risk of unwanted changes. The architect needs to outline the benefits of using a source control system for the company's requirement. Also, a suitable branching strategy is needed to manage the complexity of releases efficiently.

43 / 53

Solution 1

Solution

A source control system like Git is suitable for the company's requirement since it allows distributed teams to work in isolation. It would also allow the teams to back up code and configuration changes, enabling rollbacks in case of unwanted changes. The GitHub Flow can be used as the branching strategy for the source control workflow. It allows the use of multiple feature branches which can be deployed independently. This suits the company's need for handling multiple release timelines. The development teams can work on feature branches and merge them into the main branch when they are ready for deployment.

Interview angle

This is the canonical "multiple teams, multiple timelines" answer: Git for isolation + GitHub Flow for independent feature branches. The key selling points to articulate are: isolation (teams don't block each other), rollback (failed deployments revert cleanly via Git history), and independent release cadence per feature branch.

Requirement 2

Scenario

Following the architect's recommendation, the company has started using Git as the source control system. Salesforce Extensions for VS Code is used with Salesforce CLI to update various sandboxes from source control. A development team in Australia uses multiple sandboxes and is considering the use of Gitflow as its branching strategy. The strategy emphasizes the use of two main branches called Master and Develop. There are also three supporting branches called Feature, Release, and Hotfix. The architect needs to recommend a suitable approach for development using this branching strategy.

46 / 53

Solution 2

Solution

When using the Gitflow workflow, each developer should work off of a Feature branch, which is pulled from the Develop branch, and then the Feature branch should be merged back into the Develop branch. This allows for continuous integration and testing in the Develop branch, which aligns with agile development practices. It is important to note that using feature branches would allow tracking each feature or change separately and maintain a history of changes made by each developer. However, code reviews should be performed before merging branches.

Fed angle

The requirement for code reviews before merging Feature branches into Develop is the four-eyes principle in action. In GitLab, this is enforced through protected branch rules and required approvers on merge requests — a key control that satisfies both IT governance and audit requirements at a central bank.

Requirement 3

Scenario

A development team working on an Experience Cloud project has completed a sprint and would like to deploy the changes made in the sprint after business approval. However, the team will also immediately begin the next sprint. The architect needs to recommend a suitable strategy to handle the deployment. In addition, two developers are currently working on the Case object and the same Apex classes that reference the Case object. One of them has finished their work early and merged the changes into the Develop branch. The architect needs to provide any related considerations.

49 / 53

Solution 3 (Part 1)

Solution

For the given requirement, a Release branch can be created from the Develop branch for the completed sprint. After business approval, the changes made in the sprint can be deployed from the Release branch. For the new sprint, development can be started in new Feature branches. After the completion of each feature, its Feature branch can be merged into the Develop branch for integration and testing. This would allow continuous development and staging of features for release.

50 / 53

Solution 3 (Part 2)

Solution

The second developer working on the Case object and the same Apex classes could potentially see a merge conflict when they create a pull request for merging changes in their Feature branch into the Develop branch. They would need to resolve the conflict using Git commands to merge the two branches successfully.

Interview angle

This is the classic exam scenario combining release branching with conflict resolution. The two-part answer pattern — Release branch for the completed sprint + Feature branches for the new sprint, plus flagging the merge conflict risk for the second developer — demonstrates architect-level awareness of both the workflow and the operational risks.

51 / 53

Requirement 4

Scenario

A development team in the United States is working on the next development phase of a Sales Cloud customization project that requires a lot of development work. The project has 15 Apex developers building new functionality and fixing bugs. The architect needs to recommend a suitable branching strategy that mitigates the risk of developers overwriting each others' changes. Also, the project manager is concerned about critical production issues occurring in the middle of development. A suitable strategy is required to address the issues.

52 / 53

Solution 4

Solution

For the branching strategy, developers should build new functionality in new branches and merge their changes into a common branch for testing. This would isolate each developer's work until it's ready for integration, reducing the risk of conflicts. To address critical production issues immediately without affecting the ongoing development work, separate branches should be created for current development and production bug fixes. Once the production fix is tested and ready, it can be merged and deployed without waiting for the current development cycle to complete.

Fed angle

This is the hotfix-branch pattern from Gitflow applied to an emergency production fix. At the Fed, this scenario would additionally require an emergency change request and expedited approval from the Change Control Board before deployment — the branch strategy enables the technical isolation, but the governance layer still applies even for urgent production fixes.

High-Yield Exam Gotchas

  • GitHub Flow ≠ Gitflow. GitHub Flow is lightweight (main + feature branches only). Gitflow has five branch types and is for scheduled releases with hotfix capability.
  • Short-lived branches are the default. Delete branches after merging to prevent stale branch proliferation and needless conflicts.
  • Trunk-Based Development requires strong CI. Without automated test gates, direct commits to trunk are risky — do not recommend TBD unless the team has a mature CI/CD pipeline.
  • Recursive merge preserves the audit trail; fast-forward does not. In regulated/audited contexts, prefer merge commits over fast-forward.
  • Rewinding history alters commit history. Only safe before pushing to a remote. On shared branches, use a revert commit instead.
  • Hotfix branches in Gitflow solve the "critical production issue while development is in progress" scenario — they are created from main, not develop.
  • Source-driven development = VCS is source of truth, not the org. Deployments push FROM Git TO the org.

Fed angle — Tying it together

For the Federal Reserve Bank of Chicago, the highest-priority source-control concerns are: (1) auditable commit history — every change is traceable to a person, ticket, and timestamp; (2) protected branches with required approvals in GitLab — enforces the four-eyes principle and segregation of duties; (3) merge requests with automated CI gates — Apex test coverage and static analysis must pass before any merge to develop or main; (4) emergency change process — hotfix branches must still go through an expedited change-request approval, not bypass change control. Gitflow maps most naturally to this governance model, but any strategy can satisfy audit requirements if protected-branch rules and merge-request approvals are configured correctly.
