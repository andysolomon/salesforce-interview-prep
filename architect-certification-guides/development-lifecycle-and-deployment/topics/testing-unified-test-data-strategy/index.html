Page 4 · Introduction

Introduction

A unified test data strategy is necessary to ensure the usage of consistent, reliable, and secure test data that is representative across all stages of the Salesforce development lifecycle.

For reliable test data generation, data factory methods and scripts can be used. Tools such as Data Loader can be used for bulk data operations in non-production environments. Salesforce Data Mask can be used to automatically mask sensitive production data in sandbox environments. Mock data that mimics production data shape and volume can be generated.

Batch Apex can be used to delete test data on a regular basis. Automated test data loading can be used for reliable results and when no human oversight is required. Multiple related records can be inserted in a single call or transaction using REST API composite requests or sObject tree requests.

Fed angle

At the Federal Reserve, every environment that touches financial or personally identifiable data falls under strict access controls and audit requirements. The core principle — that test data must be representative yet never contain real production PII or financial records — is a direct regulatory obligation. Salesforce Data Mask and mock data generation are the two primary controls that satisfy this requirement and should be the first tools named when a Fed examiner asks how non-production environments are secured.

Unified Test Data Strategy — Overview

A unified test data strategy spans five interconnected pillars, each addressing a distinct aspect of keeping test data representative and secure across the development lifecycle.

Representative & Secure Test Data

Test data should adhere to the regulations and accurately reflect the production environment's complexity and variability without exposing sensitive information.

Data Masking

Salesforce Data Mask can be utilized to automatically mask sensitive production data in sandbox environments to comply with regulations.

Sandboxes & Data Refresh

Different sandbox types can be utilized to test with representative data at various stages of the development lifecycle.

Test Data Creation

Representative test data can be created by using data factory methods and scripts or using tools such as Bulk API for bulk data operations.

Considerations

To delete a large volume of test data, a batch Apex job can be used. Automated test data loading can be used for reliable results. REST API composite requests and sObject tree requests can be used for inserting related records.

Interview angle

When asked to describe a unified test data strategy, frame it around these five pillars. An architect-altitude answer covers all five simultaneously rather than treating them as isolated decisions. Lead with the security dimension (masking, regulations) to signal that you understand the compliance context before discussing the mechanics of data creation and refresh.

Page 7 · Representative Data & Security & Compliance

Unified Test Data Strategy — Representative Data & Security

A unified test data strategy ensures consistent, reliable, and secure test data is used across all stages of the development lifecycle, from development to testing, and staging to production.

Representative Data

Test data should accurately reflect the production environment's complexity and variability without exposing sensitive information.

Security & Compliance

Test data should adhere to data protection regulations (e.g., GDPR, HIPAA, etc.). Data masking, anonymization, or pseudonymization techniques should be implemented to secure sensitive and personally identifiable information (PII).

Fed angle

For the Federal Reserve, the applicable regulations are not limited to GDPR and HIPAA — they include GLBA, OCC and Fed internal data governance policies, and IT examination frameworks (FFIEC). The requirement to mask or anonymize PII before it reaches any non-production environment is an examiner-visible control. Being able to demonstrate an automated, auditable mechanism (Salesforce Data Mask with a documented masking configuration) is stronger than a manual process, because it is repeatable and leaves an evidence trail.

Developing a Unified Test Data Strategy — Test Data Creation & Masking

For the development of a unified test data strategy, clear guidelines should be established for test data management, including test data creation, storage, usage, and disposal policies.

Test Data Creation

Data factory methods and scripts can be used to generate test data that mimics real-world scenarios. Tools such as Data Loader can be used for bulk data operations in non-production environments.

Data Masking

Data masking techniques can be implemented to obscure sensitive data while maintaining its usability for testing purposes. Salesforce Data Mask can automatically mask data in sandbox environments.

Fed angle

Salesforce Data Mask is the canonical tool answer for this requirement. It should be called out by name in any Fed interview discussion about sandbox data security. The combination of documented masking configurations (which fields are masked, with which technique) plus an audit log of when masking jobs ran constitutes the evidence package that satisfies both internal audit and external examiner review. Data Loader for bulk creation in non-production environments is acceptable only when the source data is already masked or synthetic — never raw production records.

Page 9 · Developing a UTDS — Mock Data & Sandbox Environments

Developing a Unified Test Data Strategy — Mock Data & Sandbox Environments

For the development of a unified test data strategy, clear guidelines should be established for test data management, including test data creation, storage, usage, and disposal policies.

Mock Data

If regulations prohibit the use of production data for testing, mock data that mimics production data shape and volume can be generated.

Sandbox Environments

Different types of sandboxes (Developer, Developer Pro, Partial Copy, and Full) can be leveraged to manage and test with representative data at various stages.

Know the four sandbox types and what each carries: Developer and Developer Pro have no production data copy; Partial Copy brings a sampled subset; Full copies all data. Only Partial Copy and Full can carry real (masked) production data into a lower environment. When regulations prohibit production data entirely, mock data is the answer regardless of sandbox type.

Interview angle

The exam frequently tests the distinction between "use Salesforce Data Mask on a refreshed sandbox" versus "generate mock data from scratch." The decision tree is: does the regulation allow any form of production data in lower environments (even masked)? If yes, use Data Mask on a Partial Copy or Full sandbox. If no, generate synthetic mock data that matches the production schema's shape and volume using data factory methods.

Page 10 · Developing a UTDS — Data Refresh & Monitoring

Developing a Unified Test Data Strategy — Data Refresh & Monitoring

For the development of a unified test data strategy, clear guidelines should be established for test data management, including test data creation, storage, usage, and disposal policies.

Data Refresh

Regularly refreshing test data in sandbox environments from production ensures that it remains representative. Sandbox refresh strategies can be used to manage how and when data is updated in test environments.

Monitoring & Auditing

Monitoring should be implemented to track usage and access to test data, ensuring compliance with data policies. Periodic audits should be conducted to validate adherence to the test data strategy and data protection regulations.

Fed angle

Monitoring and auditing of test data access is precisely what Fed examiners look for when reviewing a platform's data governance posture. At a central bank, "we refresh sandboxes from production and then mask them" is not sufficient on its own — you must also demonstrate that (a) the masking step always runs before any developer accesses the refreshed sandbox, and (b) there is an audit trail showing who accessed what test data and when. Salesforce Event Monitoring combined with a documented sandbox refresh runbook satisfies both requirements.

Page 11 · Considerations for Test Data Management

Considerations for Test Data Management

Certain considerations are applicable for the management of test data in a unified test data strategy.

Test Data Deletion

If test data needs to be deleted on a regular basis, an Apex batch job can be utilized.

Automation

Automated test data loading can be used for reliable results and when no human oversight is required.

Related Data

To load multiple related records in a single call or transaction, REST API composite request or sObject tree request can be utilized.

REST API composite request vs. sObject tree request: a composite request is a single POST representing a series of REST API requests (up to 25 sub-requests); an sObject tree request creates a collection of nested parent-child records with a single root record. Use sObject tree for hierarchical related records; use composite for mixed operations across multiple object types.

Interview angle

The architect-altitude answer for nightly test data cleanup is a scheduled Apex batch job — not a manual admin process or a sandbox refresh. Batch Apex processes records in chunks, handles governor limits gracefully, and can be scheduled via the Apex Scheduler or a cron expression, making it auditable and repeatable. This is the pattern to cite when asked how a team maintains a "fresh state" sandbox at scale.

Business Scenario — Cosmic Wellness

Read the business scenario below and determine the most appropriate solutions for the company's requirements.

Scenario

Cosmic Wellness, a rapidly expanding healthcare solutions provider, leverages Salesforce to manage patient records, appointments, and interactions across its global network of clinics and hospitals. As part of its commitment to provide exceptional patient care and ensure data privacy, the company faces the challenge of testing new Salesforce features and customizations with data that accurately reflects real-world use cases without compromising patient confidentiality.

Given the sensitive nature of healthcare data, including personal health information (PHI) that must comply with strict regulatory standards like HIPAA in the U.S. and GDPR in Europe, the company needs a strategic approach to manage test data in a representative and secure manner across its development lifecycle. The company's architect needs to recommend appropriate strategies for requirements related to the same.

Fed angle

The Cosmic Wellness scenario maps directly to the Fed's situation: a regulated institution handling sensitive records (financial data at the Fed; PHI here) must test against representative data without exposing real records in lower environments. The HIPAA/GDPR compliance requirement in this scenario mirrors GLBA and Fed IT security policies. Every solution recommended here — masking, mock data, batch deletion — is the same pattern you would apply in a central bank Salesforce environment.

Page 15 · Requirement 1

Requirement 1

Scenario

A Salesforce development team of the company is working on a large customization project and is in the process of refining its testing strategies. It would like to introduce large data volume testing using representative data to resolve performance defects earlier in the development lifecycle. However, regulations prohibit the use of sensitive production data in non-production environments. Furthermore, the team wants a suitable approach to delete 2 GB of test data in a partial copy sandbox every night, setting the sandbox to a fresh state for the next day's testing.

Page 16 · Solution 1

Solution 1

Solution

The development team can utilize Salesforce Data Mask to automatically mask sensitive production data in sandbox environments. Another option is generating and loading mock data that mimics production data shape and volume. To delete the test data in the partial copy sandbox every night, a batch Apex job can be executed at a specific time.

Fed angle

This is the highest-relevance scenario in the deck from a Fed examiner's perspective. The two-option structure is important: Salesforce Data Mask is preferred when a masked copy of production data is permissible and provides better representativeness; mock data generation is the fallback when regulations absolutely prohibit any production data — even masked — from leaving the production environment boundary. At the Fed, the latter is often the case for the most sensitive data categories. Document which approach is approved for each data classification in your test data policy.

Batch Apex for 2 GB nightly deletion is the canonical exam answer. A sandbox refresh would accomplish the same goal but takes hours and consumes the sandbox's refresh allocation. Batch Apex is targeted, schedulable, and does not touch metadata — only the records you specify. It is the right tool for high-frequency, high-volume test data cleanup.
Page 17 · Requirement 2

Requirement 2

Scenario

A small team of Salesforce developers is working on a custom application for managing patient information. Various features of the application are already in the testing stage. The team wants a suitable strategy to insert test data that represents records of multiple related objects that mimic real patient interactions, medical records, and appointment scheduling. In addition, the team is considering automated test data loads and would like the architect's assistance in choosing automated test data loading over manual loading.

Page 18 · Solution 2

Solution 2

Solution

For the loading of test data that represents records of multiple related objects, REST API composite requests or REST API sObject tree requests can be utilized. A composite request is a single POST request that represents a series of REST API requests. An sObject tree request comprises a collection of nested, parent-child records with a single root record. Automated test data loading is useful for reliable results and when no human oversight is required for loading test data.

Interview angle

The architect question here is choosing between composite and sObject tree. The decision rule: if you need to create a parent object and multiple levels of children (e.g., Patient → Medical Record → Appointment) in one atomic call, use sObject tree — it handles the full hierarchy. If you need to perform a mix of operations (insert Account, then insert Contact referencing that Account's new ID, then insert a Case) where each step may depend on the prior step's result, use composite requests with reference IDs. The exam distinguishes these by the word "hierarchy" vs. "cross-object dependency."

Fed angle

Automated test data loading over manual loading is not just a convenience — it is a control. Automated loading is deterministic, version-controlled (the loading scripts live in source control), and leaves no room for an individual developer to manually insert real production data "just this once." At the Fed, any process that removes human discretion from a data-handling step strengthens the control posture and is easier to defend in an audit.

High-Yield Exam Gotchas

  • Salesforce Data Mask ≠ Shield Platform Encryption. Data Mask obscures data in sandbox copies for testing safety. Shield Platform Encryption encrypts data at rest in production (and potentially other environments). These solve different problems.
  • Mock data is the answer when regulations prohibit ALL production data — even masked data. If the rule is "no production data of any kind in non-production environments," Data Mask is not sufficient and mock data generation is the correct approach.
  • Partial Copy sandbox carries a sampled subset of production data; Full sandbox carries all data. Developer and Developer Pro sandboxes do NOT copy production data. Know which sandbox types are relevant when the scenario mentions data volume or representativeness.
  • Apex batch job for deletion ≠ sandbox refresh. A refresh resets the entire environment (metadata + data) and is rate-limited. A batch Apex deletion targets only test records and can run nightly without affecting metadata or consuming the refresh entitlement.
  • sObject tree request is for a single hierarchy (one root, multiple levels of children). Composite request is for a series of independent REST API sub-requests that can reference each other by ID. Do not conflate them.
  • Automated test data loading is both a quality control and an audit control — it eliminates the risk of a developer manually loading real data "just this once" and creates a version-controlled, repeatable evidence trail.
  • A unified test data strategy requires documented guidelines for creation, storage, usage, AND disposal — disposal (deletion policy) is frequently overlooked and is specifically called out in the deck.

Fed angle — Tying it together

For a Federal Reserve platform engineer, the unified test data strategy is one of the highest-visibility governance artifacts. Examiners specifically ask: "How do you ensure that production financial data never appears in your development or test environments?" The complete answer has three layers: (1) technical controls — Salesforce Data Mask running automatically post-refresh, with mock data generation as the fallback when masking is insufficient; (2) process controls — documented sandbox refresh runbooks, nightly batch Apex cleanup jobs, and version-controlled data loading scripts; and (3) audit controls — Event Monitoring to track test data access, periodic audits to validate adherence to the strategy, and masking job execution logs as evidence. All three layers together constitute a defensible, examiner-ready posture.
