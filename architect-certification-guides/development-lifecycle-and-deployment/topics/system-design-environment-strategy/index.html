Page 3 · Learning Objectives

After studying this topic, you should be able to:

  • Describe the main features of Salesforce sandboxes.
  • Describe the features of the four types of sandboxes.
  • Identify the refresh intervals and storage limits available for the four types of sandboxes.

Page 4 · Introduction

Introduction

A Salesforce sandbox is a separate, isolated environment that contains some or all of the data and metadata from production. Sandboxes can be used for development, testing, staging, and training. There are four types of sandboxes, namely: Developer, Developer Pro, Partial Copy, and Full. Each type of sandbox is used for specific use cases.

A new sandbox is created with the metadata and data (depending on the sandbox type) from the production org. Refreshing a sandbox updates its metadata from the resource org. If the sandbox is a clone or uses a sandbox template, the process updates the org's data and its metadata. Sandboxes have different refresh intervals and storage limits.

Fed angle

At the Federal Reserve Bank of Chicago, the sandbox hierarchy is a core element of change-control governance. Every configuration or code change must be developed and validated in a sandbox before production deployment — this is both a Salesforce best practice and a regulatory requirement for systems touching financial data. The choice of sandbox type directly determines what data reaches lower environments, which is an audit-relevant decision.

Page 5 · Sandbox Strategy Overview

Sandbox Strategy

Each of the four sandbox types fills a distinct role in the development lifecycle.

Developer Sandbox

A Developer sandbox can be used for development and testing in an isolated environment.

Developer Pro Sandbox

A Developer Pro sandbox can be used for quality assurance, integration testing, and user training.

Partial Copy Sandbox

A Partial Copy sandbox can be used for user-acceptance testing, integration testing, and testing.

Full Sandbox

A Full sandbox can be used for performance testing, load testing, and staging.

Interview angle

The strategy diagram is the architect's mental model for sandbox selection. If an interviewer presents a scenario, map each requirement to its lowest-cost sandbox that satisfies the data fidelity need: Developer for isolated dev, Developer Pro for QA/training when larger data sets are needed, Partial Copy for UAT/integration with a data sample, Full only for staging/performance/load (most expensive, 29-day refresh). Avoid over-provisioning — recommending Full when Partial Copy suffices is a red flag.

Page 7 · Salesforce Sandboxes — Usage & Development/Testing

Salesforce Sandboxes

A Salesforce sandbox is a separate, isolated environment that contains some or all of the data and metadata from production.

Usage

Sandboxes can be used for development, testing, staging, and training, without affecting the data and metadata in the production org.

Development & Testing

Sandboxes allow isolated customization and development work until changes are ready to be deployed. Changes can also be tested against copies of the production data and users.

Page 8 · Salesforce Sandboxes — Training & Deployment

Salesforce Sandboxes

A Salesforce sandbox is a separate, isolated environment that contains some or all of the data and metadata from production.

Training

A sandbox can be used as a training environment for end users before an application is deployed to production.

Deployment

Individual changes from administrators and developers can be coordinated and deployed to production.

Sandboxes serve four distinct purposes — development, testing, training, and deployment coordination. An exam question that asks "what sandbox is used for training end users?" is asking about a use case, not just data volume. Developer Pro is the lowest-cost option that supports user training with larger datasets.
Page 9 · Sandbox Types

Sandbox Types

There are four types of Sandboxes.

Developer

A Developer sandbox includes a copy of the production org's metadata. It is typically used for isolated development and testing.

Developer Pro

A Developer Pro sandbox includes a copy of the production org's metadata and can host larger datasets. It is typically used for more development and quality assurance tasks, integration testing, and user training.

Partial Copy

A Partial Copy sandbox includes a copy of the production org's metadata and a sample of production data defined by a sandbox template. It is typically used for user acceptance testing, integration testing, and training.

Full

A Full sandbox is a replica of the production org and includes all data and metadata. It is used for performance testing, load testing, and staging.

Fed angle

For a regulated financial institution, the distinction between Partial Copy and Full is a data-governance decision, not just a capacity one. Bringing all production data into a Full sandbox requires the same data-masking and access controls that apply in production. The Fed's internal security policies will require documented justification for using a Full sandbox — default to Partial Copy unless full data fidelity is a documented, approved requirement.

New Sandbox

Additional Sandboxes

If a sandbox option is not visible or more licenses are needed, Salesforce should be contacted to order additional sandboxes.

Page 11 · Creating Sandboxes — Purchased Sandboxes & Templates

Creating Sandboxes

Creating a sandbox copies the metadata and data (depending on the sandbox type) from the production org to the new sandbox org.

Purchased Sandboxes

If the number of purchased sandboxes is reduced, the number of sandboxes should be matched to the purchased number. For example, if there are two Full sandboxes but only one was purchased, a Full sandbox cannot be created.

Sandbox Template

For Partial Copy and Full sandboxes, a template can be selected for the data to include. For a Full sandbox, all data can be included; the amount of field history tracking data to be included can be selected, and whether to copy Chatter data can be selected.

If sandbox count exceeds what was purchased — for example after a license reduction — you cannot create new sandboxes of that type until the count is brought in line. Deleting the unused sandbox resolves the block. This is exactly the pattern tested in Requirement 2 of this deck.
Page 12 · Creating Sandboxes — Options & Processing Time

Creating Sandboxes

Creating a sandbox copies the metadata and data (depending on the sandbox type) from the production org to the new sandbox org.

Additional Options

To run scripts after each create and refresh for the created sandbox, an Apex class created for the SandboxPostCopy interface can be specified. A public user group that contains the users that require access to the sandbox can be selected.

Processing Time

The process of creating a sandbox takes from several minutes to several days, depending on the size and type of the sandbox. When the sandbox is ready, a notification email is sent.

Interview angle

The SandboxPostCopy interface is a high-signal answer when an interviewer asks how you automate post-refresh setup (e.g., masking PII, resetting integration credentials, reassigning users). Mentioning it demonstrates you understand the full sandbox lifecycle, not just creation. In a regulated environment, a SandboxPostCopy class that automatically masks sensitive fields is a key control.

Page 13 · Refreshing Sandboxes — How & Options

Refreshing Sandboxes

A sandbox can be refreshed to update its metadata from the resource org. If the sandbox is a clone or uses a sandbox template, the process updates the org's data and its metadata.

Refreshing a Sandbox

Sandboxes that can be refreshed are visible on the Sandboxes page in Setup. A Refresh link appears next to the name of a sandbox that can be refreshed.

Options

Name, Description, and Create From values can be reviewed and edited. If the sandbox is not a clone, the type of sandbox environment required can be selected.

Page 14 · Refreshing Sandboxes — Data & Auto-Activation

Refreshing Sandboxes

A sandbox can be refreshed to update its metadata from the resource org. If the sandbox is a clone or uses a sandbox template, the process updates the org's data and its metadata.

Data

The data that should be copied can be selected. For partial copy and full sandboxes, template-based data can be selected. For a Full sandbox, the amount of field history tracking data to be included can be selected, and whether to copy Chatter data can be selected.

Auto-Activation

The sandbox can be auto-refreshed after refreshing it by selecting Auto Activate. An activation email is not sent if this option is selected.

Page 15 · Refreshing Sandboxes — Activation & Discarding

Refreshing Sandboxes

A sandbox can be refreshed to update its metadata from the resource org. If the sandbox is a clone or uses a sandbox template, the process updates the org's data and its metadata.

Activation

A refreshed sandbox must be activated before it can be used. The 'Activate' link next to the name of a sandbox can be selected.

Discarding

The refreshed sandbox can also be discarded. A discarded sandbox cannot be recovered, and discarding a refreshed sandbox reverts to its previous version, deleting the new version.

Discarding is irreversible — the new refresh is permanently deleted and you revert to the old version. This is particularly dangerous for Full sandboxes where a refresh takes up to several days. Activate before doing any validation to preserve the option to discard only as a last resort.
Page 16 · Sandbox Refresh Intervals & Storage Limits

Sandbox Refresh Intervals and Storage Limits

Different sandbox environments can be created based on the needs for storage, configuration, and frequency of refresh.

Sandbox Type Refresh Interval Storage Limit
Developer 1 day 200 MB data storage and 200 MB file storage
Developer Pro 1 day 1 GB data storage and 1 GB file storage
Partial Copy 5 days 5 GB data storage and file storage same as production
Full 29 days Data storage and file storage same as production

Interview angle

These numbers are high-frequency exam targets. Memorize: Developer/Developer Pro refresh daily (1 day); Partial Copy every 5 days; Full every 29 days. The Partial Copy training scenario in this deck exploits the 5-day interval — a weekly training cycle maps cleanly to a weekend refresh. If someone asks why Full is not used for weekly training, the 29-day refresh interval is the technical disqualifier.

Fed angle

The 29-day Full sandbox refresh cycle is a significant operational constraint for regulated environments that need to test against current production configurations after each monthly release window. Plan the UAT/staging refresh schedule to align with the Fed's change-control calendar — a stale Full sandbox can give false confidence that production-equivalent testing was completed.

Scenario

Cosmic Healthcare, a leader in health technology solutions, is enhancing its Salesforce platform to support expansive growth and the integration of advanced health applications. It currently manages its operations using Sales Cloud, Service Cloud, and Experience Cloud. Its development teams are currently working on multiple projects. It is in the process of introducing new applications and services, making the need for the optimized use of Salesforce sandboxes critical.

The Salesforce architect of the company is tasked with crafting environment strategies for the company's requirements by utilizing the correct sandbox types for aspects such as multiple project streams, training, staging, and hotfixes.

Requirements & Solutions

Page 20 · Requirement 1 (Part 1)

Requirement 1 (Part 1)

Scenario

The company needs to manage multiple concurrent development projects for Sales Cloud and Service Cloud. The development teams face challenges in environment management due to upcoming major releases and differing release timelines for Sales and Service Cloud enhancements. The Sales Cloud development team uses a Developer Pro sandbox for development and testing. The Service Cloud development team needs to use a part of the Sales Cloud work from the sandbox. The company requires an effective sandbox strategy to accommodate these development efforts without compromising the quality or timeline of either project.

Page 21 · Requirement 1 (Part 2)

Requirement 1 (Part 2)

Scenario

In addition, to ensure that end users are properly trained to use the new features and enhancements, the company would like to conduct weekly training sessions. Each training session will last for five days and train a new set of trainees on suitable samples of production data. All the training data should be deleted at the end of the week. The architect must suggest an optimal sandbox strategy for the training sessions.

Page 22 · Solution 1

Solution 1

Solution

A new Developer Pro sandbox can be created for the Service Cloud development team by cloning the existing sandbox currently used by the Sales Cloud development team. This approach would allow both teams to work independently on their requirements without interference.

For the training sessions, a Partial Copy sandbox can be used. It can be refreshed every weekend. An appropriate sandbox template can be selected to include a sample of training data from production.

Interview angle

Two key patterns in one solution: (1) sandbox cloning to spin up an independent stream from an existing environment — the clone inherits the current state so the Service Cloud team gets a baseline without waiting for a full production refresh; (2) Partial Copy + weekend refresh for training — the 5-day refresh interval aligns with a weekly cycle, the template controls which data is included, and the refresh at week-end clears training data. This is the canonical sandbox strategy answer for concurrent streams + training.

Fed angle

For a central bank, the sandbox template used for training must be reviewed to ensure it does not expose actual PII or sensitive financial data. A SandboxPostCopy Apex class should be deployed to mask regulated fields after each weekend refresh. The weekly data lifecycle (load, train, purge) should be documented in the change-control system as a recurring operational procedure.

Page 23 · Requirement 2

Requirement 2

Scenario

The company would like to perform thorough batch data testing and a final review of new features and enhancements before deployment to production. The sandbox strategy for batch testing should consider the production data required. Furthermore, there are currently two Full sandboxes. One is used for user acceptance testing, and the other was used for performance testing in the past but is no longer used. A Salesforce administrator has reported that none of the sandboxes can be refreshed. The architect needs to recommend a suitable action to resolve the issue.

Page 24 · Solution 2

Solution 2

Solution

A Full sandbox can be used for staging. The same can be used for batch data testing if the testing scenarios require all the production data. A Partial Copy sandbox can be utilized for testing scenarios that require only a subset of production data.

The current sandbox utilization should be reviewed to resolve the issue with sandbox refreshes. The Full sandbox that was previously used for performance testing and is no longer being used should be deleted to align the organization's sandbox usage with its license entitlements and restore the ability to refresh sandboxes as needed.

When a sandbox count exceeds purchased license entitlements, ALL sandboxes of that type are blocked from refresh — not just the excess one. Deleting the unused sandbox brings the count back in line and unblocks refresh for the remaining one. This is a common exam trap: admins assume only the "extra" sandbox is affected.

Fed angle

At the Fed, unused sandboxes represent an attack surface — they contain copies of production metadata and potentially data. A governance process should require periodic inventory of all active sandboxes with documented owners and purposes. Sandboxes that have not been used within a defined retention window (e.g., 90 days) should be deleted as part of the change-control hygiene process. This directly prevents the license-entitlement blocking scenario described here.

Page 25 · Requirement 3

Requirement 3

Scenario

A development team that works on the company's Experience Cloud site has identified the need for a hotfix environment to resolve urgent production issues. In addition, the team regularly needs to test its integrations between the site and multiple enterprise systems, including an HRIS. The sandbox required for testing integration performance should contain up to 10,000 records of each object. The architect needs to suggest the sandbox types and workflow that should be used for these two use cases.

Page 26 · Solution 3

Solution 3

Solution

A Developer sandbox can be set up to work on urgent bug fixes. Once development and unit testing have been completed in this sandbox, changes can be pushed to a Full sandbox for user-acceptance testing, and then deployed to production. Once a fix has been deployed to production, it can be merged with the downstream environments to maintain a complete codebase.

For the purpose of testing integrations with enterprise systems, a Partial Copy sandbox can be created using a sandbox template with all the objects required for testing.

Interview angle

The hotfix workflow is a classic three-stage pipeline: Developer (fix + unit test) → Full UAT → Production, then merge back down. The key insight is that a hotfix stream is separate from the main development stream — it must not wait for in-flight development work to complete. After deploying the hotfix to production, merging it back into downstream Developer sandboxes keeps all environments current. This avoids the scenario where a prior hotfix is inadvertently reverted by a later deployment.

Page 27 · Solution 3 — Hotfix Flow Diagram

Solution 3 — Hotfix Workflow

The hotfix flow isolates urgent fixes from normal development streams while ensuring the fix is propagated back downstream.

Stage Environment Sandbox Type Action
1. Fix & Unit Test Hotfix Environment Developer Sandbox Develop and unit test the urgent fix in isolation
2. UAT UAT Environment Full Sandbox Push changes for user-acceptance testing against full production data replica
3. Release Production — Deploy to production after UAT sign-off
4. Merge Development Environment Developer Sandbox Merge hotfix back into the main development environment to maintain a complete codebase

Fed angle

At the Federal Reserve Bank of Chicago, a hotfix deployment requires an expedited change-control review — not a bypass of it. The Developer → Full UAT → Production pipeline maps to the emergency change request process: the hotfix Developer sandbox serves as the development evidence artifact, the Full sandbox UAT provides the test evidence, and both must be documented before production deployment. The merge step generates the updated release package that satisfies the "back-out plan" requirement of the change record.

Page 28 · Requirement 4

Requirement 4

Scenario

The current development lifecycle used by the company starts with Developer sandboxes and moves to a Developer Pro sandbox for integration testing, a Partial Copy sandbox for QA testing, a Full sandbox for UAT, and then production. The company's CTO would ask the architect to recommend a sandbox refresh plan that the development teams can use as a reference. It should describe how often each type of sandbox should be refreshed.

Page 29 · Solution 4

Solution 4

Solution

A sandbox should be refreshed when it is necessary to update its metadata from the source org. For example, a Developer sandbox can be refreshed to replicate several configuration updates made to the production org as a result of a separate development stream. If a sandbox is a clone or uses a sandbox template, the refresh process updates the data and metadata of the sandbox.

Developer and Developer Pro sandboxes can be refreshed every day. A Partial Copy sandbox can be refreshed once every 5 days. A Full sandbox can be refreshed once every 29 days.

Interview angle

The architect-altitude answer is not just "here are the intervals" — it's "refresh when the source org has changed in ways that affect your work." Blanket scheduled refreshes waste capacity and reset in-progress work. The guidance is: Developer/Dev Pro daily-capable (refresh when production config changes affect your stream); Partial Copy before each major test cycle (but no more than every 5 days); Full sandbox refresh aligned to the monthly release cycle (29-day minimum means roughly once per sprint-end or release window).

Cheatsheet — Environment (Sandbox) Strategy

Sandbox Types — Quick Reference

Type Data Copied Refresh Interval Storage Primary Use Cases
Developer Metadata only 1 day 200 MB data / 200 MB file Isolated development, unit testing, hotfix development
Developer Pro Metadata + larger datasets 1 day 1 GB data / 1 GB file QA, integration testing, user training
Partial Copy Metadata + sample of production data (sandbox template) 5 days 5 GB data / same as production file UAT, integration testing with sample data, training with weekly refresh
Full All data + metadata (replica) 29 days Same as production Performance/load testing, staging, UAT with full production data

Environment Strategy Decision Matrix

Requirement Recommended Sandbox Key Reasoning
Multiple concurrent dev streams (e.g., Sales Cloud + Service Cloud) Developer Pro (cloned) Cloning gives each team an independent baseline; no interference between streams
Weekly end-user training with sample production data Partial Copy (refresh every weekend) 5-day refresh interval aligns with weekly cycle; template controls data included
Staging / final review before production deployment Full Full replica of production ensures true pre-production validation
Batch data testing requiring all production data Full Only Full sandbox contains complete production data volume
Batch/integration testing requiring subset of data Partial Copy More cost-effective; sandbox template specifies required objects/data
Urgent hotfix (production down) Developer → Full → Production → Merge back Developer for speed; Full for UAT sign-off; merge to keep downstream current
Integration testing with enterprise systems (up to 10K records/object) Partial Copy (with sandbox template) Template includes required objects; 5 GB limit accommodates the volume

High-Yield Exam Gotchas

  • Refresh interval is a minimum wait, not a schedule. You can refresh less frequently — the interval is the earliest you are allowed to refresh again after the last refresh.
  • Exceeding purchased sandbox count blocks ALL refreshes of that type — not just the excess sandbox. The fix is to delete the unused sandbox to match the licensed count.
  • A clone refresh updates both data and metadata; a non-clone refresh updates only metadata unless a template is applied.
  • Auto Activate suppresses the activation email — teams relying on that email as a deployment trigger will not receive it.
  • Discarding a refreshed sandbox is irreversible — the new version is permanently deleted and the old version is restored.
  • Developer Pro is the right choice for user training when sample data is not needed — Partial Copy is needed only when a production data sample is required for training.
  • Full sandbox for training is over-engineered and costly — the 29-day refresh makes it impractical for weekly training cycles.
  • SandboxPostCopy Apex class is the correct mechanism to automate post-refresh steps (data masking, credential reset, user reassignment).
  • Hotfix merging downstream is often omitted in answers but is architecturally required — a hotfix not merged back will be overwritten by the next full deployment.

Fed angle — Tying it together

At the Federal Reserve Bank of Chicago, every sandbox in the inventory is a data-governance artifact. The environment strategy must be documented, reviewed, and approved as part of the system design process — not decided ad hoc per project. Key Fed-specific controls: (1) Partial Copy templates must be reviewed for PII/financial data before each training or testing use; (2) SandboxPostCopy masking classes are a required control, not optional, for any sandbox receiving production-derived data; (3) unused sandboxes must be deleted within the change-management system's retention policy to prevent license blocking and reduce attack surface; (4) the hotfix pipeline must map to the emergency change request process — no production deployment without documented test evidence from the Developer and Full sandbox stages; (5) the 29-day Full sandbox refresh must be aligned to the monthly release calendar so staging always reflects the current production state before a deployment window opens.
