Page 4 · Introduction

Introduction

Integrating changes directly into a production environment in Salesforce presents unique challenges and considerations. It is important to manage these changes within the broader context of Application Lifecycle Management (ALM). Such changes have implications on the development lifecycle, from potential disruptions to workflow, system integrity, and compliance issue, making it necessary to utilize strategies for effectively incorporating them into the ALM process. The risks associated with direct production changes need to be mitigated, ensuring seamless integration, and maintaining the balance between rapid deployment needs and the necessity for rigorous testing and validation processes. Architects should be able to make informed decisions with the aim of upholding system stability and user experience while accommodating urgent business requirements.

Fed angle

At the Federal Reserve Bank of Chicago, any change to a production Salesforce org touches a regulated, audited system. The tension between "urgent business need" and "rigorous validation" is never abstract — regulators expect every production change to carry a documented rationale, approval chain, and post-change validation record. Architects who can articulate the ALM integration steps are demonstrating the change-control maturity that examiners require.

Risks of Direct Changes in Production

Making direct changes in production without performing testing has certain risks.

Testing Protocol Bypass

Bypassing established testing protocols can introduce errors into the live environment, complicating diagnosis and rectification.

Conflicts & Instability

Direct changes risk conflicting with other ongoing updates or integrations, potentially causing system instability or failure.

Regulatory & Compliance

Regulatory and compliance issues may arise if changes affecting data security or user privacy haven't been rigorously validated.

Interview angle

The exam will present a scenario where a direct production change broke something. The three-risk pattern — testing bypass → errors; conflict → instability; unvalidated security/privacy → compliance — maps precisely to the three canonical risks. Identify which risk category the scenario falls into, then name the matching mitigation.

Page 8 · Best Practices for Direct Changes in Production

Best Practices for Direct Changes in Production

Certain best practices can be utilized for managing direct changes in production.

Emergency Hotfixes

A dedicated process should be established for emergency hotfixes, clearly defining what constitutes an emergency change that warrants direct updates in production.

Review & Authorization

Close collaboration should be fostered between developers, QA teams, and stakeholders to ensure changes are thoroughly reviewed and authorized before implementation.

Fed angle

Segregation of duties is a foundational internal-control requirement at any central bank. The "review & authorization" best practice directly implements that control: no single person approves and executes a production change. A written emergency-hotfix policy provides the documented procedure auditors will ask for during IT general-controls reviews.

Page 9 · Tools for Direct Changes in Production

Tools for Direct Changes in Production

Release management tools offered by Salesforce can be utilized for direct changes in production.

Tools

Deployment tools offered by Salesforce and sandbox refresh cycles can be leveraged to plan and execute changes methodically, minimizing disruptions to the development lifecycle. Changes should be thoroughly documented and follow a standard cadence.

Sandboxes

Salesforce sandboxes should be used for testing significant changes to ensure they don't negatively impact live data. Direct changes should be reserved for minor, low-impact updates after assessing all potential effects.

The sandbox-first rule is absolute for significant changes — only truly minor, low-impact updates (e.g., picklist value additions, simple field label changes) should bypass the sandbox. When in doubt, use the sandbox. The standard cadence and thorough documentation requirements ensure every change is traceable.
Page 10 · Integrating Direct Changes into ALM

Integrating Direct Changes into ALM

Direct changes in production should be integrated into Application Lifecycle Management.

Strategy

For direct changes made in production, a strategy should be developed to retroactively incorporate these changes into the ALM process. Downstream environments should be updated to ensure that they reflect the changes made in production.

Validation

Retrospective analysis and testing should be conducted in sandbox environments even after direct changes to production, to validate their impact and ensure they align with broader system functionalities.

Interview angle

This is the canonical answer for "what do you do after a direct production change?": (1) retroactively update downstream environments so sandboxes match production, (2) run retrospective analysis and testing in sandbox to validate impact, (3) ensure the change is captured in version control / source of truth. An architect who stops at "it's already in production" has failed the ALM integration step.

Fed angle

Reconciling drift back into the version-control source of truth is an audit imperative. If production diverges from the documented baseline, the next examiner review will surface it as a finding. Retroactively incorporating changes — and refreshing downstream sandboxes — closes that gap and keeps the ALM pipeline the authoritative record of what is actually running in production.

Page 11 · Communication & Training

Communication & Training

Proper communication and training should be conducted for any direct changes in production.

Communication

Communication should be prioritized with the team and stakeholders about any direct changes made in production, ensuring there is a clear understanding of the reasons and expected outcomes.

Training

Training or briefing sessions should be conducted for users affected by the direct changes to ensure smooth adoption and minimize operational disruptions.

Communication is often the overlooked step. A technically perfect production change that surprises end users or downstream teams creates its own incident. The communication step is part of the change management process, not an optional courtesy.
Page 12 · Monitoring & Coordination

Monitoring & Coordination

Ongoing monitoring, adjustment, and coordination are essential for direct changes in production.

Monitoring & Adjustment

After implementing direct changes in production, the system should be continuously monitored for any unforeseen impacts or issues that may arise. Further adjustments should be made if needed.

Coordination

Sandboxes should be used for testing whenever possible, especially for high-impact changes. Direct production changes should be reserved for situations where sandbox testing is not feasible or the change urgency justifies it.

Interview angle

The coordination card contains the exam-critical rule: direct production changes are the exception, not the default. The only valid justifications are (a) sandbox testing genuinely not feasible or (b) urgency so extreme it outweighs the risk. Any scenario where sandbox testing is available and time permits should route through the normal pipeline.

Requirements & Solutions

Page 16 · Requirement 1

Requirement 1

Scenario

The company is considering the implementation of a minor change policy for low-risk user stories that are commonly handled by a Salesforce administrator. It would allow the administrator to make these changes directly in production. The production environment is highly regulated and audited. The development workflow currently does not utilize continuous integration/continuous delivery (CI/CD). The architect must suggest best practices that the company should follow for the new change policy.

Page 17 · Solution 1

Solution 1

Solution

For the new change policy, minor changes should be thoroughly documented and follow a standard cadence. Before making any changes in production, they should be reviewed against compliance requirements, regulations, and security principles, and explicit stakeholder approval should be obtained. After making the changes, the downstream environments should be updated, and the changes should still be tested in sandbox environments using the normal development workflow.

Fed angle

In a highly regulated, audited environment like a central bank, the three-step pattern here is mandatory: document + approve before, execute with authorization, then back-propagate and validate after. Regulators will ask for evidence of each step. "Explicit stakeholder approval" is not a courtesy — it is the segregation-of-duties control that prevents an individual from both requesting and approving a production change.

Interview angle

Solution 1 is the complete lifecycle for a direct minor change: document → review against compliance → get approval → make change → update downstream → test retroactively. Memorize this six-step sequence. The exam will test whether you know that "done" doesn't mean the change is deployed — it means the sandboxes are updated and retrospective testing is complete.

Page 18 · Requirement 2

Requirement 2

Scenario

A developer has noticed that Apex unit tests are failing in production during deployments, but they still function as expected in the other environments. It has been revealed that a Salesforce consultant has been making minor changes in production while disregarding the need to add dependent components. One of the developers is working in a Developer sandbox on a Lightning web component that utilizes Opportunity fields. The consultant has added a new custom field in production. The architect must provide suggestions to discover the failing unit tests earlier and assist the developer.

This scenario illustrates production drift: the consultant's untracked direct changes have made production diverge from the downstream sandboxes, causing test failures that only surface at deployment time — exactly the risk the ALM integration steps are designed to prevent.
Page 19 · Solution 2 (Part 1)

Solution 2 (Part 1)

Solution

To help the company discover failing unit tests earlier and manage changes in production more effectively, the consultant should be trained to make changes in a special sandbox, followed by their deployment to production. Also, a daily metadata backup should be committed to a source control system and the differences should be published so that the development team can easily spot discrepancies and potential causes for test failures before they affect the production environment.

Fed angle

Daily metadata backup to source control is the mechanism that surfaces production drift before it becomes an audit finding. Publishing diffs gives the team a living audit trail of every change made outside the standard pipeline. At a regulated institution this pattern also satisfies the requirement to maintain an authoritative, versioned record of the system configuration.

Page 20 · Solution 2 (Part 2)

Solution 2 (Part 2)

Solution

To assist the developer in the development process after the addition of a new custom field to production, the consultant should refresh the Developer sandbox to ensure that changes made in production are reflected in the sandbox that the developer is using to work on the Lightning web component. Another option is using a Change Set to deploy the changes from production to the sandbox.

Interview angle

Two valid mechanisms to propagate production changes back to a sandbox: (1) sandbox refresh — gets all org metadata but takes longer and disrupts in-progress work; (2) Change Set from production to sandbox — surgical, deploys only the specific components needed. The exam may ask which is more appropriate given constraints. If the developer has significant in-progress work, a Change Set is less disruptive than a full refresh.

High-Yield Exam Gotchas

  • Direct production changes are the exception, not the rule. The only valid justifications are: sandbox testing not feasible, or urgency so extreme it outweighs the risk.
  • "Done" does not mean deployed. A direct production change is only complete when downstream environments are updated and retrospective testing is finished.
  • Daily metadata backup to source control is the mechanism that surfaces drift and enables early detection of test failures — not a nice-to-have, but a core ALM hygiene practice.
  • Sandbox refresh vs. Change Set: refresh = full parity but disruptive; Change Set = surgical but partial. Pick based on developer's in-progress work.
  • Segregation of duties: the person making the change must not be the person approving it. Explicit stakeholder approval is the control, not just a process step.
  • Retroactive validation in sandbox is required even after a direct production change — the fact that the change is already live does not eliminate the need to validate its impact against the broader system.
  • Communication and training are part of the change process, not optional. Users surprised by a production change create their own incidents.

Fed angle — Tying it together

For a central bank platform engineer, the highest-stakes implication of direct production changes is audit exposure. Every un-documented, un-approved, un-backported production change is a potential IT General Controls finding. The ALM integration steps in this deck — document, approve, execute, communicate, update downstream, validate retroactively, monitor — are not suggestions; they are the control evidence package that satisfies internal audit and regulatory examiners. The daily metadata backup to source control closes the audit trail loop by making any production drift immediately visible and attributable.
