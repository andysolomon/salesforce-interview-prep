Page 4 · Introduction

Introduction

In Salesforce, a test execution methodology is essential for a structured approach to executing tests, ensuring comprehensive coverage and alignment with best practices. Various tools are available for the execution of Apex unit tests, including Apex Classes page, Developer Console, and VS Code.

When using Metadata API for a deployment, a subset of tests can be run using the RunSpecifiedTests test level. Using a mock object is necessary to test Apex code that performs HTTP callouts. The startTest() and stopTest() methods can be used to reset governor limits in Apex unit tests.

For testing Lightning components, the Jest framework can be utilized. Aura component accessibility tests can be run in two environments: JavaScript and WebDriver.

Fed angle

At the Federal Reserve Bank of Chicago, structured test execution with documented methodology is not optional — it is a release-control requirement. Code coverage gates enforced during CI/CD deployments (e.g., GitLab pipelines) provide the automated, auditable evidence that every production change met the minimum quality bar before it was promoted. The 75% coverage floor is the statutory floor; a mature regulated org raises that bar further.

Four interconnected areas define the Salesforce test execution and coverage landscape.

Test Execution Methodology

A test execution methodology should focus on aspects such as a test plan, types of testing, test scripts, code coverage, automation, monitoring, and stakeholder engagement.

Apex Test Execution

Testing Lightning Components

Lightning web components and Aura components can be tested using the Jest framework. Apex controller can be tested using test classes. Aura accessibility tests can be run in JavaScript and WebDriver.

Test Execution Methodology

A test execution methodology should emphasize a structured approach to executing tests within Salesforce environments, ensuring comprehensive coverage and alignment with best practices.

Test Plan

A test execution methodology should be based on defining a clear test plan, which should align with the customer's business processes, Salesforce configuration, and customization.

Types of Testing

The test plan should detail the types of testing to be conducted, such as unit, integration, system, UAT (User Acceptance Testing), and performance testing.

Interview angle

The architect-altitude answer on test methodology always starts with the test plan — it is the governance document that links every test to a business process or requirement. When asked to describe an appropriate testing strategy, open with: test plan first, then test types, then coverage thresholds, then automation tooling. This shows breadth and prevents the conversation from jumping straight to implementation details.

Apex Test Execution

Page 11 · Executing Apex Unit Tests — Steps

Executing Apex Unit Tests

Running Apex unit tests involves creating test data, calling the test methods, and then verifying the results. Data is not committed, so it does not need to be deleted.

1 · Prepare Data

Create valid test data for testing.

2 · Execute Methods

Execute the methods to be tested.

3 · Verify Results

Verify the expected results using assertions.

Test data is rolled back automatically — no cleanup code is needed. This is one of the exam's favorite subtle facts: Apex test data is never committed to the database, so delete statements at the end of test methods are unnecessary.
Page 12 · Executing Apex Unit Tests — Tools

Executing Apex Unit Tests

Various options and considerations apply to the execution of Apex unit tests in Salesforce.

Tools

Apex unit tests can be run using these tools:

  • Apex Test Execution Page
  • Apex Classes Page (Run All Tests)
  • Developer Console
  • Visual Studio Code
  • Code Builder
  • API (SOAP API, Tooling REST API, etc.)

Interview angle

When an interviewer asks how you run tests in a CI/CD pipeline, the answer is the API — specifically the Tooling REST API or Metadata API invoked by your pipeline tool (GitLab, GitHub Actions, etc.). The UI tools are for ad-hoc developer use. An architect must know the distinction: human-driven vs. pipeline-driven test invocation has very different auditability and repeatability properties.

Page 13 · Executing Apex Unit Tests — Groupings & Options

Executing Apex Unit Tests

Various options and considerations apply to the execution of Apex unit tests in Salesforce.

Groupings

Salesforce allows executing these groupings of unit tests:

  • Some or all methods in a test class
  • A predefined suite of test classes
  • Some or all methods in a set of test classes
  • All unit tests in an org

Test Options

When validating or deploying a change set, four test options are available:

  • Default
  • Run Local Tests
  • Run All Tests
  • Run Specified Tests
Page 14 · Executing Apex Unit Tests — Subset & Deployment Requirement

Executing Apex Unit Tests

Various options and considerations apply to the execution of Apex unit tests in Salesforce.

Subset of Tests

When using Metadata API for a deployment, the RunSpecifiedTests test level can be set on the DeployOptions object to run a subset of tests and shorten the deployment time to production. Each test class (and not individual test methods) needs to be specified in the DeployOptions object, which is then passed as an argument to the deploy() call.

Deployment Requirement

A deployment fails if the code coverage of an Apex component in the deployment is less than 75%. It also fails if one of the specified tests fails. Code coverage is computed individually for each Apex class and trigger and is different from the overall code coverage percentage.

Fed angle

The 75% code coverage requirement is Salesforce's built-in release gate — it is not optional and cannot be waived in a production deployment. For the Fed, this functions as a policy control: no Apex component reaches production without documented test coverage. In a mature CI/CD pipeline (GitLab), the RunSpecifiedTests + DeployOptions pattern gives teams the ability to run only the tests relevant to a given changeset, which keeps pipeline duration manageable while still enforcing the per-component coverage gate.

Page 15 · Executing Apex Unit Tests — Email & Callouts

Executing Apex Unit Tests

Various options and considerations apply to the execution of Apex unit tests in Salesforce.

Outbound Email

Apex unit tests cannot send outbound emails. When a unit test includes Apex code that sends an email message, it may run successfully, but no email is actually sent out from the org.

Apex Callouts

Apex unit tests cannot perform HTTP callouts. In order to test Apex code that performs callouts, a mock object needs to be created by defining a class that implements the HttpCalloutMock interface. The Test.setMock() method is used to set the mock object.

This is a high-frequency exam trap: if a test class exercises code that makes a callout and no mock is set up, the test throws an error — Methods defined as TestMethod do not support Web service callouts. The fix is always HttpCalloutMock + Test.setMock().
Page 16 · Executing Apex Unit Tests — Limits & Production Data

Executing Apex Unit Tests

Various options and considerations apply to the execution of Apex unit tests in Salesforce.

Limits Methods

The Limits methods can be used to return the specific limit for a particular governor, such as the number of callouts that have been processed or the amount of heap size remaining.

Resetting Limits

The startTest() and stopTest() methods can be used to reset governor limits in Apex unit tests. A new set of governor limits is assigned to any code that executes after startTest() and before stopTest().

Production Data

It is a best practice to not use the @IsTest(SeeAllData=true) annotation since the test results can differ depending on which data is available in the organization. Unit tests should generate their own test data.

Fed angle

Avoiding @IsTest(SeeAllData=true) is especially critical in a regulated environment: if tests access real production data, test outcomes become non-deterministic (dependent on what data exists at the time), and test runs in lower environments may behave differently from production. This directly undermines the auditability goal. Self-contained test data is a prerequisite for reproducible, auditable test results.

Page 17 · Using a Mock Object

Using a Mock Object

The following shows an example of a mock object and how it is used in a test method.

// A mock class that simulates the response of a successful enrollment of a student:
public class EnrollHttpCalloutMock implements HttpCalloutMock {
    public HttpResponse respond(HTTPRequest req) {
        HttpResponse res = new HttpResponse();
        res.setHeader('Content-Type', 'application/json');
        res.setBody('{"success":true,"studentId":12345,"courseId":67,"yearLevel":3}'); // create fake response
        res.setStatusCode(200);
        return res;
    }
}

// Example code contained and executed inside a test method:
Test.startTest();
Test.setMock(HttpCalloutMock.class, new EnrollHttpCalloutMock());  // Test.setMock() called after Test.startTest() and before the callout
StudentApplicationWrapper application = generateStudentApplication(); // some helper method
Enrollment erm = StudentController.enroll(application); // invoke the method to test

// verify new record created from fake data
System.assertEquals(erm.ExternalStudentId__c, 12345);
System.assertEquals(erm.YearLevel__c, 3);
System.assertEquals(erm.CourseId__c, 67);
Test.stopTest();
Test.setMock() should be called after Test.startTest() and before the callout. The mock object is passed as an argument. This ordering is required — calling setMock() outside of the startTest/stopTest block will not properly intercept the callout.
Page 18 · Section

Code Coverage

Page 19 · Code Coverage — Overview

Code Coverage

Code coverage numbers are generated for Apex code every time one or more tests are executed.

Covered Apex Code

Code coverage indicates the number of executable lines of code in Apex classes and triggers that have been exercised by test methods.

Coverage Requirements

Apex unit tests enable meeting the code coverage requirements for deploying or packaging Apex code. The tests must cover at least 75% of the Apex code and pass, every trigger must have some test coverage, and all classes and triggers must compile successfully.

Code Quality

Code coverage does not guarantee test effectiveness. Unit tests should assert all the expected behaviors and ensure code quality.

Fed angle

The 75% coverage floor is a hard release gate enforced by the Salesforce platform itself — no workarounds exist at deploy time. For a regulated institution, this is a floor, not a target. The Fed's own change-control posture should set internal thresholds higher (e.g., 85–90%) and enforce them in CI before the deploy even reaches Salesforce's own gate. The "coverage does not guarantee test effectiveness" caveat is critical: an org can hit 80% coverage with vacuous tests that assert nothing. Acceptance criteria quality is the complement to coverage quantity.

Page 20 · Code Coverage — Inspection & Discrepancies

Code Coverage

Code coverage numbers are generated for Apex code every time one or more tests are executed.

Inspection

Code coverage information can be viewed in the Tests tab of the Developer Console.

Refresh

Tests need to be rerun to refresh code coverage numbers. They aren't refreshed automatically when Apex code is updated.

Discrepancies

There can be discrepancies in code coverage numbers between a development or sandbox environment and production due to reasons such as test failures, data dependencies, metadata dependencies, etc.

A common gotcha: a team sees 80% coverage in their sandbox and is surprised when a deployment to production fails with sub-75% coverage on a specific component. The cause is almost always data dependencies — tests that pass in sandbox because certain records exist there, but not in production. The fix is @IsTest with self-contained test data generation.
Page 21 · Code Coverage — Percentage Formula

Code Coverage — Percentage Formula

Code Coverage Percentage, which is computed when running tests, uses the formula:

CCP = [(number of covered lines) / (number of covered lines + number of uncovered lines)] * 100

What is NOT counted

The following are not counted and do not impact code coverage percentage:

  • Code comments
  • Class name definition
  • Lines that only contain brackets
  • System.debug statements

Only the lines highlighted in blue (executable statements) are included in the code coverage computation.

// this is a class used for controlling a vehicle
public class Vehicle {                               // not counted — class name definition

    static Integer maxCapacity = 4;                  // COUNTED — executable

    // add passengers to vehicle                    // not counted — comment
    public static void addPassengers(List<Contact> contacts) {  // COUNTED
        System.debug('passenger count: ' + contacts.size()); // not counted — System.debug
        if (contacts.size() > maxCapacity) {          // COUNTED
            System.debug('Too many passengers!');    // not counted — System.debug
        } else {                                      // not counted — bracket
            notifyPassengers(contacts);               // COUNTED
        }
    }

    // send email to vehicle passengers
    public static void notifyPassengers(List<Contact> contacts) {  // COUNTED
        System.debug('alert passengers..');          // not counted — System.debug
    }
}

Testing Lightning Components

Page 23 · Testing Lightning Web Components — Jest

Testing Lightning Web Components

Jest is a testing framework that can be used to write unit tests for Lightning web components.

Running Jest Tests

Jest tests can be run in the command line or the IDE. They don't run in the browser or connect to an org, and they give immediate feedback while coding when run in watch mode.

Test Cases

Jest tests can be written to test a component in isolation, its public API, basic user interaction (clicks), DOM output, firing of events, etc.

Using Jest

Jest and its dependencies can be installed in a Salesforce DX project. Jest tests can be written in local JavaScript files. They can be run from VS Code or the command line.

Interview angle

Jest for LWC is a pure JavaScript, offline test framework — it does not make Salesforce API calls and does not require an org. This makes it ideal for a CI pipeline step that runs before any deployment: fast, isolated, no org credentials required. The architect answer is: Jest runs in CI, Apex unit tests run during deployment — two separate gates, both required.

Page 24 · Testing Lightning Web Components — Test File & Blocks

Testing Lightning Web Components

Jest is a testing framework that can be used to write unit tests for Lightning web components.

Test File

Each test file must import both the component to test and the createElement method from 'lwc'. A describe block should be defined to create a test suite within the test file.

Test Blocks

An it or test block should be defined to create a single functional unit test. The DOM should be reset at the end of each unit test using the afterEach() method.

Create Instance

Inside the unit test, the imported createElement method can be used to create an instance of the component for testing. It should be appended to the body of the document using the appendChild() method.

Page 25 · Testing Lightning Web Components — ShadowRoot & Promises

Testing Lightning Web Components

Jest is a testing framework that can be used to write unit tests for Lightning web components.

ShadowRoot

When creating a unit test, the shadowRoot property of the element under test should be used to access the shadow tree. It can be used to select a particular element.

Promises

Asynchronous DOM updates such as a property change can be tested by using a Promise in the unit test.

Other Considerations

To test the wire service, the @salesforce/sfdx-lwc-jest test utility can be utilized. A JSON file can be created to define the Salesforce data expected by a component. The npm run test:unit:watch command can be used to run tests continuously during development.

Page 26 · Testing Aura Components

Testing Aura Components

One of the testing frameworks that can be used to perform automated testing of Aura components.

Testing Tools

Some popular testing tools that can be used to test Aura components are Jest, UTAM, Jasmine, Mocha, Selenium, and WebdriverIO.

Accessibility Tests

Salesforce's test tools can be utilized to check for common accessibility issues (such as images without alt attributes and th element without a scope attribute) in Aura components. Aura accessibility tests can be called in two environments: JavaScript and WebDriver.

Apex Controller

Server-side logic in the component's Apex controller must be tested separately using an Apex test class.

A common exam trap: Jest tests for LWC/Aura do NOT cover the Apex controller — server-side logic must be tested with a separate Apex test class. Always mention both layers when describing a comprehensive Lightning component test strategy.

Page 28 · Business Scenario

Business Scenario — Cosmic Web Solutions

Read the business scenario below and determine the most appropriate solutions for the company's requirements.

Scenario

Cosmic Web Solutions manages its customer relationships and operations using separate Salesforce instances for its branches in Asia and South America. The company has encountered difficulties in maintaining a consistent quality assurance process, leading to disparities in customer experience and operational efficiency between the regions. Recognizing the need for better testing and quality control methodologies, the company turns to a Salesforce architect for guidance.

The architect is charged with evaluating the existing testing strategies employed by the two divisions and suggesting appropriate test execution methodologies and coverage needs for the company's requirements. The goal is to establish consistent, high-quality testing practices across both divisions, enhancing the reliability of deployments.

Page 29 · Section

Requirements & Solutions

Page 30 · Requirement 1 (Part 1)

Requirement 1 (Part 1)

Scenario

The development team of the company's Asian division has certain requirements related to testing and quality assurance:

  1. The Salesforce instance has 85% overall code coverage. A test plan is created for each sprint, but the number of defects is still large. The architect needs to suggest a suitable approach to reduce the number of defects.
  2. Automated browser tests are used to verify the functionality of Lightning web components. The team is concerned about the impact of Salesforce releases and needs to identify the type of changes that would require updating the tests.
Page 31 · Requirement 1 (Part 2)

Requirement 1 (Part 2)

Scenario

  1. A developer has written a test class to test a method that involves a web service callout. However, the test method fails and this error message is returned: Methods defined as TestMethod do not support Web service callouts
  2. The team has written test classes to unit test certain Apex classes and triggers. When executed in the sandbox, all the test methods pass and all the classes meet the minimum code coverage requirement. But a few of these test methods are failing when deploying the associated Apex components to production.
Page 32 · Solution 1 (Part 1)

Solution 1 (Part 1)

Solution

  1. To reduce the number of defects, code coverage should be increased and the acceptance criteria should be more detailed.
  2. Any DOM changes introduced in a Salesforce release could require updating the automated browser tests.
  3. To avoid the error message, a mock object should be used to test the web service callout. The following steps should be performed within the test class:
    1. Create an Apex class that implements the HttpCalloutMock interface.
    2. In the test method, call the Test.startTest() method.

Interview angle

This scenario demonstrates the architect's diagnostic pattern: the team has 85% coverage but still has many defects. The diagnosis is not "more coverage" alone — it is "more detailed acceptance criteria." Coverage measures how much code is exercised; it does not measure whether the tests are actually asserting the right behaviors. An architect who gives only "raise coverage" misses the key insight that test quality (assertions, edge-case scenarios) matters as much as test quantity.

Page 33 · Solution 1 (Part 2)

Solution 1 (Part 2)

Solution

  1. Set the mock object using the Test.setMock() method.
  2. Call the Apex method that contains the web service callout.
  3. Verify the behaviors using assertions.
  4. Call the Test.stopTest() method.

4. The test methods are most likely failing because of the @IsTest(SeeAllData=true) annotation and the presence of different data in production. Test methods should not use this annotation to ensure that test data is not dependent on the org's data. They should generate their own test data.

Fed angle

The @IsTest(SeeAllData=true) problem is exactly the kind of environment-to-production discrepancy that causes deployment failures at regulated institutions. Production data is different from sandbox data — always. Tests that depend on pre-existing records will fail unpredictably. Self-contained test data generation is the control that makes test results deterministic and therefore auditable across all environments, including a Fed production org.

Page 34 · Requirement 2

Requirement 2

Scenario

The development team in South America is facing certain challenges related to testing. The developers have built new features for the sales team, but while testing the Apex classes, they are constantly hitting the governor limits. Various Aura components are utilized by these new features, but the team is unsure how to test these components. They also need to perform accessibility tests for these Aura components. In addition, the team lead would like to shorten the deployment time to production and would like considerations related to running specific tests during deployments using Metadata API.

Page 35 · Solution 2 (Part 1)

Solution 2 (Part 1)

Solution

While testing the Apex classes, the governor limits can be reset using the Test.startTest() and Test.stopTest() methods. Apex methods that need to be tested should be called after Test.startTest() and before Test.stopTest().

The JavaScript code in Aura components can be tested using a suitable testing framework such as Jest. Server-side logic in Apex controllers should be tested using Apex test classes. Salesforce's test tools can be utilized to check for common accessibility issues in Aura components. Aura accessibility tests can be called in two environments: JavaScript and WebDriver.

Page 36 · Solution 2 (Part 2)

Solution 2 (Part 2)

Solution

The deployment time to production can be shortened by running a subset of tests. The RunSpecifiedTests test level can be set on the DeployOptions object. The test classes to be executed should be specified in DeployOptions; specifying test methods is not supported. The object should be passed as an argument to the deploy() call.

Fed angle

RunSpecifiedTests is the pattern that enables fast, targeted deployments in a CI/CD pipeline — for example, a GitLab pipeline that deploys only a small changeset can run only the tests relevant to that change, dramatically reducing pipeline duration without sacrificing the per-component 75% gate. At the Fed, where change windows may be constrained, shorter deployment pipelines directly reduce risk. The constraint that only test classes (not individual methods) can be specified is an important implementation detail to know for the exam and for pipeline design.

High-Yield Exam Gotchas

  • 85% coverage with many defects? The issue is not coverage quantity — it is acceptance criteria quality. Detailed acceptance criteria + more coverage together reduce defects.
  • "Methods defined as TestMethod do not support Web service callouts" — always means you need HttpCalloutMock + Test.setMock().
  • Tests pass in sandbox, fail in production? Almost always @IsTest(SeeAllData=true) and data differences. Fix: remove the annotation, generate own test data.
  • DOM changes in a Salesforce release can break automated browser tests for LWC — this is the release-impact that requires test updates.
  • RunSpecifiedTests requires test classes specified on DeployOptions — you cannot specify individual test methods.
  • Jest tests do NOT cover Apex — server-side logic in Aura/LWC Apex controllers requires a separate Apex test class.
  • Code coverage is computed per class and trigger — an org with 90% overall coverage can still fail a deployment if one specific class in the changeset is below 75%.
  • System.debug statements do NOT count toward code coverage — you cannot inflate coverage by adding debug statements.
  • Coverage numbers do not refresh automatically — always rerun tests after modifying Apex code to get accurate numbers.

Fed angle — Tying it together

For a Federal Reserve Bank of Chicago Platform Engineer, the most important themes in this deck are: (1) Code coverage as a release gate — the 75% Salesforce floor is the minimum; a mature regulated org enforces a higher internal threshold in CI (e.g., GitLab) before the change even reaches the Salesforce deploy step. (2) CI test automation — API-driven test execution in GitLab pipelines removes human discretion from the "did we test?" question, creating an auditable, repeatable quality control artifact for every production change. (3) Self-contained test data — avoiding @IsTest(SeeAllData=true) ensures tests are deterministic across all environments, which is a prerequisite for audit-grade evidence that a change was properly tested. These three controls together form the testing pillar of a defensible change management posture — exactly what Fed examiners and senior leadership expect to see documented in an architect's release governance framework.
