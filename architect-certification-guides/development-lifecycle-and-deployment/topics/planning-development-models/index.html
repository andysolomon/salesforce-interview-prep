Page 4 · Introduction

Introduction

Application Lifecycle Management (ALM) typically involves a specific process utilized for developing Salesforce applications. There are three development models available to implement an ALM process: the Change Set Development Model, the Org Development Model, and the Package Development Model.

Each model necessitates the use of certain features or tools. For instance, the Org Development Model is source-driven and employs a source control system for tracking changes, while the Package Development Model utilizes unlocked packages and scratch orgs.

Various key roles are integral to the ALM process, including architects, developers, QA testers, project managers, release managers, and business analysts, among others. These roles play crucial functions in ensuring the success and efficiency of the application development lifecycle.

Page 5 · ALM Overview — Processes, Tools & Roles

ALM Processes, Tools, and Roles

Processes

To implement an application lifecycle management process, three development models are available. These are change set development model, org development model, and package development model.

Tools

The change set development model focuses on the use of change sets. The org development model utilizes a source control repository and can benefit from a project management tool. The package development model involves the use of unlocked packages and scratch orgs.

Roles

Key people and roles in an application lifecycle management process include architect, developers, QA testers, project manager, release manager, business analyst, and stakeholders such as executive leadership and end users.

Processes & Tools

Page 7 · ALM Processes — Change Set & Org

Application Lifecycle Management Processes

Three development models are available for managing the lifecycle of Salesforce applications.

Change Set Development

In the Change Set Development Model, change sets are used to deploy changes between related Salesforce environments. Changes can be made in a non-production org, such as a developer sandbox, and then sent to another org for review and deployment.

Org Development Model

In the Org Development Model, a source control repository is used to track and manage changes. Tools including Git, Salesforce CLI, and Salesforce Extensions for Visual Studio (VS) Code are utilized to migrate changes from one environment to another.

Interview angle

When asked to compare models, anchor your answer on source of truth: Change Set = the org itself is the source of truth (risky, manual). Org Model = source control is the source of truth (better). Package Model = versioned artifact in source control is the source of truth (best for maturity). Each step up the ladder increases repeatability and auditability.

Page 8 · ALM Processes — Package Development

Application Lifecycle Management Processes

Three development models are available for managing the lifecycle of Salesforce applications.

Package Development Model

In the Package Development Model, modular units of functionality called packages are created. The version control system represents the source of truth. Developers use scratch orgs for the development of unlocked packages. CI/CD tools are typically used for continuous integration and deployment.

Fed angle

The Package Development Model maps directly to the Fed Platform Engineer JD: versioned, modular artifacts in Git, CI/CD pipelines (GitLab), and scratch orgs for clean-room builds. When a regulated environment needs full auditability of every component version deployed to production, package versions provide that chain of custody automatically.

Change Set Development Model

Page 10 · Change Set — Develop & Test · Build Release

Change Set Development Model

The Change Set Development model allows the use of change sets to send customizations between Salesforce orgs that are affiliated with a production org.

Develop and Test

Developer sandboxes can be used to create and test customizations. A Developer sandbox contains no production data and can be used to keep changes isolated until they are ready to be integrated.

Build Release

After development and testing, customizations can be sent from each Developer sandbox to a shared Developer Pro sandbox for integration. Developer Pro sandboxes also do not contain production data.

Change sets only move between orgs that share a production org — you cannot use change sets between completely unrelated orgs.
Page 11 · Change Set — Test Release · Release

Change Set Development Model

The Change Set Development model allows the use of change sets to send customizations between Salesforce orgs that are affiliated with a production org.

Test Release

After integrating the changes, they can be sent to a Full sandbox, which is a complete replica of production. It can be used for user-acceptance testing (UAT).

Release

After user-acceptance testing, the changes can be validated and deployed to the production org for final release. The Full sandbox can be used to train users without exposing production data.

Page 12 · Change Set — Manual Changes & Change-Tracking

Change Set Development Model

The Change Set Development model allows the use of change sets to send customizations between Salesforce orgs that are affiliated with a production org.

Manual Changes

Changed metadata components that are not supported in Metadata API need to be migrated manually. The Metadata Coverage report can be accessed to view the supported metadata types.

Change-Tracking

To track changes, developers can use a custom tool to log each change they make. It can contain fields for essential information about each change in a release. The information can include who made the change, whether manual migration is required, the component impacted by the change, the orgs that have the change, and when the change was made.

Fed angle

Manual change-tracking (who/what/when/which-org) is the change-set equivalent of an audit trail. At the Fed, this kind of structured log — even if manual — satisfies the "auditability" requirement. However, it is labor-intensive and error-prone: this is the strongest argument for graduating to the Org or Package model where Git commit history provides an automatic audit trail.

Page 13 · Change Set — Deleting, Renaming & Profiles

Change Set Development Model

The Change Set Development model allows the use of change sets to send customizations between Salesforce orgs that are affiliated with a production org.

Deleting and Renaming

Change sets do not allow deleting or renaming components. Deletion must be performed manually in the target org. A component can be renamed after first deleting it in the target org and then sending the new component in a change set.

Profiles and Permission Sets

Permission sets or profile settings can be used to specify permissions and other access settings in a change set. However, there are several related considerations.

No deletes and no renames via change sets are classic exam traps — always remember: deletion = manual work in the target org.

Interview angle

If asked about limitations of change sets, lead with: no version control, no deletes, no rollback after a successful deploy, and manual-only for unsupported metadata types. These are the exact pain points that motivate moving to the Org or Package model.

Page 14 · Change Set — Outbound Change Set & Deployment Connection

Change Set Development Model

The Change Set Development model allows the use of change sets to send customizations between Salesforce orgs that are affiliated with a production org.

Outbound Change Set

When changes are ready to be moved to another org, an outbound change set containing new and changed metadata components can be created in the source org. It must contain all the components necessary for the change, including dependencies.

Deployment Connection

To allow a target org to receive inbound changes, a deployment connection needs to be authorized in the target org. This can be done on the Deployment Settings page in Setup by selecting Allow Inbound Changes.

Page 15 · Change Set — Upload & Inbound Change Set

Change Set Development Model

The Change Set Development model allows the use of change sets to send customizations between Salesforce orgs that are affiliated with a production org.

Upload

After authorizing the deployment connection, the outbound change set can be uploaded from the source org to the target org. For example, the upload can be performed in a Developer sandbox by selecting a Developer Pro sandbox as the target.

Inbound Change Set

In the target org, the inbound change set uploaded in the source org can be deployed. If a deployment is unsuccessful for some reason, it is rolled back. If it succeeds, the changes are committed and the deployment cannot be rolled back.

Once a change set deployment succeeds, it is permanent — there is no undo. This is a critical operational difference from package installs, which can be removed.
Page 16 · Change Set — Validation & Rollout

Change Set Development Model

The Change Set Development model allows the use of change sets to send customizations between Salesforce orgs that are affiliated with a production org.

Validation

Before deployment to production, it is a best practice to validate an inbound change set, which shows the success or error messages that would occur during an actual deployment. After successful validation, the change set might qualify for a quick deploy.

Rollout

The change set is finally deployed to a production org at the scheduled rollout time. Manual changes are performed after the deployment.

Fed angle

Validation (check-only deploy) before the release window is mandatory practice in a regulated environment — it ensures the deployment will succeed before touching production. The "quick deploy" window (within 96 hours of a successful validation) is a useful operational detail: it lets you run full tests ahead of a maintenance window, then deploy quickly when the window opens.

Org Development Model

Page 18 · Org Development Model — Environments & Salesforce DX

Org Development Model

The Org Development Model is a source-driven development process that utilizes a source control repository to store and track changes.

Environments

The Org Development Model uses the same development and testing environments that are applicable to the Change Set Development Model. These include Developer sandboxes for development and testing, a Developer Pro sandbox for integration, and a Full sandbox for user-acceptance testing.

Salesforce DX

A Salesforce DX project contains the source and files that represent the changes in an org. It is used to manage and collect the changes that need to be sent from one org to another. It contains a configuration file named sfdx-project.json.

Interview angle

The Org Development Model is the most common model for existing, brownfield orgs. The key differentiator from Change Sets: source control becomes the authoritative record — not the org itself. Every change is retrievable, diffable, and reviewable as code before it hits any environment.

Page 19 · Org Development Model — Manifest File & Source Control

Org Development Model

The Org Development Model is a source-driven development process that utilizes a source control repository to store and track changes.

Manifest File

After changes have been tested, a manifest file named package.xml is created. It is a release artifact that lists all the components that need to be deployed to a target org.

Source Control System

A source control system is used to merge and store all the changes. It contains the Salesforce DX project. A popular example is GitHub.

package.xml is the deployment manifest for the Org Development Model — it declaratively lists every component to be deployed. This is the counterpart to a package version in the Package Development Model.
Page 20 · Org Development Model — Salesforce CLI & VS Code Extensions

Org Development Model

The Org Development Model is a source-driven development process that utilizes a source control repository to store and track changes.

Salesforce CLI

Salesforce CLI is a command-line interface that can be used to authorize sandboxes, create and manage DX projects, import and export test data, retrieve and deploy metadata, and run and automate tests.

Salesforce Extensions for VS Code

Built on top of Salesforce CLI and VS (Visual Studio) Code, Salesforce Extensions for VS Code is an integrated development environment for custom development on the Lightning platform. It includes these VS Code extensions: Salesforce CLI integration, Apex, Apex Replay Debugger, Aura Components, and Visualforce.

Fed angle

Salesforce CLI is the backbone of any CI/CD pipeline — all the sf commands you run interactively are the same commands your GitLab CI stages will run. The ability to authorize named credentials in pipelines (using JWT bearer flow, not interactive login) is essential for automated deployments in a regulated environment where human intervention should be minimized.

Page 21 · Org Development Model — Change Management Tools

Org Development Model

The Org Development Model is a source-driven development process that utilizes a source control repository to store and track changes.

Change Management Tools

A developer can use a change list (list, table, or spreadsheet) to track the changes they made in their own dev org. They can use a deployment run list to list any manual changes required pre- and post-deployment. In addition, project management tools such as Jira and Agile Accelerator can be used to track requirements, feature work, and bugs. They can also be used to manage sprints and groom the backlog.

Interview angle

A deployment run list is your operational runbook — it captures the human steps that can't be automated (activating flows, loading seed data, toggling settings). Naming this explicitly in an interview shows operational maturity beyond just "we ran sf project deploy."

Page 22 · Org Development Model — Source Code Repository & Dev Branch

Org Development Model

The Org Development Model is a source-driven development process that utilizes a source control repository to store and track changes.

Source Code Repository

A code repository can be created in the source control system to organize the source files for a development project. A Salesforce DX project can be created and added to the repository. It can be committed and pushed to the default branch, such as main.

Development Branch

A developer can clone the source code repository and create their own branch for the changes they need to work on and deploy.

Page 23 · Org Development Model — Develop, Retrieve & Commit

Org Development Model

The Org Development Model is a source-driven development process that utilizes a source control repository to store and track changes.

Develop, Retrieve & Deploy

A developer can make changes in the local DX project. For example, they can create an Apex class for a new feature. Changes made in the Developer sandbox, such as a new custom object, can be retrieved to the local repository. Changes made in the local repository can be deployed to the Developer sandbox.

Commit Changes

After all the changes have been made, they can be committed to the source control repository. A pull request can be created and reviewers can be assigned to it for review and approval. Once it is approved, the changes can be merged with the main branch.

Fed angle

Pull request review with required approvers is the technical implementation of your change approval process. In a regulated environment, the PR approval (with audit log in Git) replaces or supplements the manual CAB — every change to production has a named approver, a timestamp, and a diff. This is exactly the "auditability" the JD requires.

Page 24 · Org Development Model — Build Release Artifact & UAT

Org Development Model

The Org Development Model is a source-driven development process that utilizes a source control repository to store and track changes.

Build Release Artifact

After developing all the changes and committing them to the source control repository, the final release artifact (a manifest file named package.xml) can be built for all the components that need to be deployed to sandbox and production orgs.

User Acceptance Testing

The release artifact can be deployed to a partial sandbox for user-acceptance testing (UAT).

Page 25 · Org Development Model — Staging & Release

Org Development Model

The Org Development Model is a source-driven development process that utilizes a source control repository to store and track changes.

Staging

A Full sandbox can be used for staging and regression testing. Before deploying to production, validation can be performed, which verifies the results of tests and ensures that there's no missing or invalid metadata.

Release

Before releasing the changes to production, pre-deployment tasks are completed and a validation is performed. The validation sets up the quick deploy, which can be performed within 10 days. After the quick deploy, post-deployment steps are completed.

Interview angle

The full Org Model pipeline is: Dev sandbox → Dev Pro (integration) → Partial (UAT) → Full (staging + validation) → Production (quick deploy). Being able to describe this end-to-end flow fluently, including the purpose of each environment tier, is a strong signal of hands-on experience.

Package Development Model

Page 27 · Package Development Model — Package & Version Control

Package Development Model

The Package Development model focuses on creating modular units of functionality called packages.

Package

In the Package Development Model, a release artifact called package is created. It is a group of related code and customizations. For example, a package can contain Lightning web components, Apex classes, custom objects, and custom fields for a custom application in an org.

Version Control System

All the source and metadata for the packages is stored in a source control repository, which represents the source of truth.

Fed angle

Packages are the explicit "platform components" and "reusable abstractions" the Fed Platform Engineer JD describes. Each package is a versioned, independently installable unit — one package per bounded domain (e.g., a core utilities package, a case management package). Application teams consume specific versions, giving the platform team full control over what ships to production.

Page 28 · Package Development Model — Scratch Orgs & Package Release

Package Development Model

The Package Development model focuses on creating modular units of functionality called packages.

Scratch Orgs

A developer can quickly spin up a scratch (development) org from the source to work specifically on a package. It can be configured with just the edition, features, and preferences needed for the package and used for declarative development.

Package Release

Teams can develop separately and build towards a release of the package. This allows more frequent, independent releases. The goal is to create packages that are versionable, easy to maintain, update, install, and upgrade.

Interview angle

Scratch orgs are ephemeral (up to 30 days), defined entirely by source — they are the closest Salesforce equivalent to a Docker container. Each CI build spins up a fresh scratch org, pushes source, runs tests, and tears it down. This eliminates "works in my sandbox" problems and is the strongest signal of a mature Salesforce DevOps practice.

Page 29 · Package Development Model — Unlocked Packages & Salesforce CLI

Package Development Model

The Package Development model focuses on creating modular units of functionality called packages.

Unlocked Packages

Unlocked packages are suitable for internal business applications. An unlocked package can be used to organize existing metadata, package an app, extend an app, or package new metadata.

Salesforce CLI

Salesforce CLI can be used to manage DX projects, create scratch orgs, push and pull metadata to and from a scratch org, and run unit tests. It can also be used as part of build automation scripts to create and access orgs, deploy source, install packages, and run tests.

Fed angle

Unlocked packages are the right choice for internal enterprise platform development — not managed packages (those are for ISV/AppExchange). Every sf package command in a GitLab CI pipeline (create version → promote → install) is automatable, auditable, and repeatable. This is the "automation for deployments to reduce manual processes" the JD describes.

Page 30 · Package Development Model — VS Code Extensions & Sandboxes

Package Development Model

The Package Development model focuses on creating modular units of functionality called packages.

Salesforce Extensions for VS Code

Salesforce Extensions for VS Code is an integrated development environment that can be used to create projects for package development and interact with the Salesforce CLI.

Sandboxes

While scratch orgs are used for package development, sandboxes are used as targets/destinations for testing the installation of the package version. They can be used for user acceptance testing, staging, and continuous delivery testing.

Key distinction: in the Package model, scratch orgs are for development/build; sandboxes are for testing and validating the package install — they simulate what will happen in production.
Page 31 · Package Development Model — Salesforce DX Project & Synchronization

Package Development Model

The Package Development model focuses on creating modular units of functionality called packages.

Salesforce DX Project

When a new Salesforce DX project is created, a default 'package' directory is created. The project directory stores the metadata in source format. Multiple packages can be organized into a single DX project.

Synchronization

Salesforce DX tracks local changes as well as any changes made in the scratch org. Using Salesforce CLI, a list of changes can be viewed, local changes can be pushed, and changes in the scratch org can be pulled.

Page 32 · Package Development Model — DX Source Format & CI Testing

Package Development Model

The Package Development model focuses on creating modular units of functionality called packages.

Synchronization — DX Source Format

In the DX project format, large source files are broken down to make them more digestible and easier to manage with a version control system. The source structure makes it easy to find what needs to be updated. It also results in fewer merge conflicts during development.

Testing

To perform manual or exploratory testing, metadata is pushed into a separate scratch org. Continuous Integration (CI) is used to automate consistent test runs against every set of merged changes. Package versions are created and installed in each testing environment for release testing or continuous delivery automation.

Fed angle

CI running against every merge is the automated quality gate that replaces manual pre-deploy checks. In a GitLab CI pipeline: push triggers a scratch org build → tests run → if green, a new package version is created and promoted. The combination of fewer merge conflicts (DX source format) and automated CI makes the Package model the most scalable for a platform team managing 33+ repos.

Page 33 · Package Development Model — Continuous Delivery & Deployment

Package Development Model

The Package Development model focuses on creating modular units of functionality called packages.

Continuous Delivery

For continuous delivery, the process for deployment and release to production is tested. Testing is performed with the package created in the build phase. It is installed in a sandbox that is the best representation of production. The steps used to release to production are replicated and tested in the sandbox.

Deployment

After creating and testing the app or customizations, the deployment artifact is created. A package version is installed in the production environment.

Interview angle

The Package model's deployment story is clean: one artifact (the package version), installed identically in each environment in sequence. Compare to the Org model where you might have different package.xml manifests per environment. This consistency is what "repeatable, auditable deployment" means in practice — and it is the strongest exam/interview answer for "how do you ensure prod gets exactly what was tested?"

Key Roles in Application Lifecycle Management

In a typical application lifecycle management process for Salesforce development, various key people and roles are involved.

Project Manager

A project manager is responsible for planning, executing, and finalizing projects according to strict timeline and budget.

Release Manager

A release manager manages the release process and oversees the development, testing, and deployment phases of the release cycle.

Interview angle

When they ask "what's your role in the ALM process," you span multiple of these: you architect the DX/pipeline design, you act as release manager owning the pipeline and environments, and you collaborate with PMs on sprint cadence. Demonstrating multi-role coverage at the platform-engineer level signals seniority.

Page 38 · Stakeholder Groups

Stakeholder Groups

There are various stakeholder groups who participate in the application lifecycle management process.

GroupDescription
Executive Leadership Includes executive sponsors and the steering committee. They communicate key information to leaders and end users and receive recurring updates on the readiness status.

Page 40 · Business Scenario — Cosmic Technology Group

Business Scenario

Read the business scenario below and determine the most appropriate solutions for the company's requirements.

Scenario

Cosmic Technology Group, a multinational corporation, specializes in providing complex Salesforce solutions to a diverse range of clients. The company's portfolio includes large-scale Salesforce integrations, custom application development, and system overhauls.

Two regional teams provide Salesforce development services. The EMEA team focuses on clients in Europe, and the APAC team serves the Asia-Pacific market, but they often work together on some projects. Given the complexity and scale of their projects, the company faces challenges in maintaining consistency, quality, and efficiency across the teams.

A Salesforce architect is brought on board to assess the maturity of their current ALM processes, evaluate the existing people, technology, and processes utilized by the two regional teams, and recommend improvements.

Page 42 · Requirement 1

Requirement 1 — Large-Scale Banking Implementation

Scenario

The two regional teams need to work together on a large-scale Salesforce implementation project for a multinational banking corporation. This project involves initial system design, integration with legacy banking systems, and implementation of advanced security protocols. Given the project's complexity, there's a need for a sophisticated application lifecycle management process that supports rigorous testing and quality control and aligns with the organization's high maturity level. This process must involve a tool to manage requirements and defects and facilitate seamless communication and collaboration.

Fed angle

This scenario is structurally identical to the Fed's environment: a large regulated institution, multiple teams, legacy system integrations, security protocols, and a demand for rigorous quality control. The answer pattern here (Org model + Git + project management tool + layered sandbox strategy) is exactly the answer you would give for the Fed's Salesforce platform.

Page 43 · Solution 1 (Part 1) — Org Development Model & Sandbox Strategy

Solution 1 (Part 1)

Solution

For the large-scale Salesforce implementation project, the teams should adopt the org development model. A source control system like Git should be integrated with the development lifecycle for effective code management and version control. The developers of the two regional teams should work within separate Salesforce Developer sandbox environments, which would promote focused development while maintaining project alignment. Developed features can be integrated in a Developer Pro sandbox. A Partial sandbox can be used for user-acceptance testing. A Full sandbox can be used for staging and training.

Page 44 · Solution 1 (Part 2) — Project Management Tool

Solution 1 (Part 2)

Solution

A project management tool, such as Jira or Agile Accelerator, should be implemented to manage requirements, track development tasks, and log defects across teams. Regular cross-regional coordination meetings should be scheduled to ensure synchronicity in development efforts and address any emerging issues.

Page 46 · Requirement 2 — EMEA Complex Financial Services Project

Requirement 2 — EMEA Complex Financial Services Project

Scenario (Part 1)

The EMEA team needs to work on a complex Salesforce project. It involves the development of a series of complex, interrelated applications for a financial services client. These include a custom financial tracking tool, a human capital management application, and data analytics capabilities. Given the sophistication of these applications and the client's expectation for seamless integration and upgradability, a high degree of coordination and control is required throughout the development lifecycle.

Scenario (Part 2)

The requirement is for an Application Lifecycle Management (ALM) process that aligns with the company's high maturity level, leveraging the package development model for modular development, scratch orgs for isolated testing environments, and a source control system for versioning, along with the appropriate tools and roles to support these processes.

Fed angle

The triggers here — interrelated applications, upgradability, high maturity — are exactly the conditions that justify the Package Development Model over the Org model. At the Fed, with multiple application domains (case management, integrations, data platforms), a package-per-domain architecture ensures teams can upgrade one domain without destabilizing others. This is the highest-value architectural decision in the Fed Platform Engineer role.

Page 47 · Solution 2 (Part 1) — Unlocked Packages & Scratch Orgs

Solution 2 (Part 1)

Solution

The project should be broken down into smaller, manageable packages using the package development model. Each module (financial tool, HCM app, and analytics) should be developed as an independent unlocked package, allowing for easier maintenance and upgradability. A source control system like Git, integrated with Salesforce DX, should be used for version control. Each development stream should have its own branch, ensuring clean separation of code and configurations. Scratch orgs should be utilized by individual developers and testers. They can provide isolated environments to develop and test each module without impacting other development streams.

Page 48 · Solution 2 (Part 2) — Roles & CI/CD

Solution 2 (Part 2)

Solution

The ALM process should consist of various key roles and people. Salesforce Developers should be assigned to coding and configuration tasks within their respective packages. QA Testers can use scratch orgs for testing each package, ensuring functionality and interoperability. Project Managers can oversee the project, track progress, and coordinate using an ALM tool like Jira or Agile Accelerator. In addition, CI/CD tools can be utilized to automate the build and deployment process for efficiency and reduced error rate. A Release Manager can assist in creating a unified plan for releases and also identify and assure use of technical deployment tooling (such as CI/CD tools).

Interview angle

This solution describes a platform team structure: each functional domain has dedicated developers, QA testers validate package interoperability (not just individual packages), and the Release Manager owns the CI/CD toolchain. The Release Manager role is the one most closely aligned to the Fed Platform Engineer JD — it spans architecture, automation, and governance simultaneously.

Cheatsheet — Planning: Development Models

Three Development Models — Decision Matrix

ModelSource of TruthDev EnvironmentsKey ToolsBest For
Change Set The org itself Developer sandboxes → Dev Pro → Full Salesforce Setup (change sets) Low maturity, simple teams, no coding required
Org Development Source control (Git) + package.xml Developer sandboxes → Dev Pro → Partial → Full Salesforce CLI, VS Code Extensions, Git, Jira Existing brownfield orgs, mixed admin/dev teams, moderate maturity
Package Development Source control + versioned package Scratch orgs → Scratch (CI) → Dev Pro + Partial → Full → Production Salesforce CLI, VS Code, Git, CI/CD tools, unlocked packages High maturity, modular greenfield, multi-team, internal platform engineering

Change Set Limitations (exam traps)

  • Change sets cannot delete components — deletion must be done manually in the target org.
  • Change sets cannot rename components directly — delete in target, then send new name in a change set.
  • Once deployed successfully, a change set cannot be rolled back.
  • Some metadata types are not supported in Metadata API — use the Metadata Coverage report; these require manual migration.
  • Change sets only work between orgs affiliated with the same production org.
  • No version control, no audit trail beyond manual tracking — weakest on auditability.

High-Yield Exam Points

  • Change Set → Org → Package is a maturity progression: each step adds auditability, repeatability, and scalability.
  • The Org Development Model uses package.xml as the release artifact; the Package model uses a package version.
  • Scratch orgs are used for development in the Package model; sandboxes are used as install targets for testing the package version.
  • Validation (check-only deploy) qualifies for quick deploy within 10 days — lets you run tests before the release window, then deploy fast during it.
  • For complex, interrelated applications with upgradability requirements → Package Development Model with unlocked packages.
  • For multi-team large-scale projects where an existing org must be source-controlled → Org Development Model.
  • A Release Manager's key function is owning the pipeline AND the toolchain — not just scheduling; this is the Fed Platform Engineer core function.
