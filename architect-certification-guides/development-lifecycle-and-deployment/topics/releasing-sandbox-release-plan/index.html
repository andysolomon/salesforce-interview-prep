Page 4 · Introduction

Introduction

In today's dynamic Salesforce development environment, aligning a sandbox strategy with a comprehensive release plan is essential for project success. This involves meticulous planning across multiple project streams, each with its distinct development and deployment timelines. A well-thought-out sandbox strategy ensures that various teams can work in parallel without interference, while also accommodating training needs for end-users on new features or updates. Additionally, having a dedicated environment for staging allows for thorough validation of features and updates before production deployment, ensuring that each release enhances the system's functionality and stability. Moreover, the strategy must include provisions for urgent hotfixes to address any unforeseen issues promptly.

Fed angle

At a regulated institution, every stream in the release plan — development, SIT, UAT, training, staging, hotfix — must be mapped to a named sandbox with a documented purpose and refresh cadence. This separation of environments directly satisfies segregation-of-duties and change-control requirements that regulators and internal audit will examine.

Page 6 · Sandbox Strategies Overview

Sandbox Strategies

Multiple Project Streams

Developer or Developer Pro sandboxes can be assigned to each project team when there are multiple project streams.

Training Requirements

A Partial Copy or Full sandbox can be utilized for facilitating training using realistic datasets. If required, sensitive data can be anonymized using Salesforce Data Mask.

Staging

Staging refers to validating the release prior to its deployment in the production environment. A full sandbox can be utilized for staging.

Hotfixes

A hotfix addresses an urgent issue impacting day-to-day business. It can be developed in a Developer sandbox and tested in a Partial Copy or Full sandbox.

Page 7 · Sandbox Types

Sandbox Types

There are four different sandbox types used for specific use cases.

Developer

Developer sandboxes are ideal for individual developers working on separate project streams.

Developer Pro

Developer Pro sandboxes can handle more development and quality assurance tasks and for integration testing or user training.

Partial Copy

Partial Copy sandboxes are suitable for user acceptance testing, integration testing, and training sessions.

Full

A Full sandbox is a full replica of production that can be used for staging, performance testing, load testing, and user acceptance testing.

There are exactly four sandbox types — Developer, Developer Pro, Partial Copy, and Full. Do not conflate them or invent additional types. Each has a specific use-case fit that the exam will test.
Page 8 · Project Streams Management

Project Streams Management

Dedicated sandboxes can be utilized when there are multiple project streams.

Isolated Development

Developer or Developer Pro sandboxes can be assigned to each project team to prevent overlap and ensure isolated development efforts.

Source Control

Source-driven development and version control (with tools like Salesforce DX) can be used to merge development work from various streams for integrated testing in a Partial Copy or Full Sandbox.

Interview angle

When asked how you manage parallel development streams without interference, the pattern is: one Developer or Developer Pro sandbox per team + a source-control merge strategy (Salesforce DX / SFDX) that feeds a shared integration sandbox (Partial Copy or Full) for combined testing. This demonstrates both environment isolation and the integration-merge discipline expected of an architect.

Page 9 · Training Requirements

Training Requirements

Special sandbox considerations are applicable when user training is required.

Realistic Datasets

A Partial Copy or Full sandbox can be utilized for training to provide realistic datasets without impacting production data. It can be regularly refreshed to align with current business processes.

Anonymization

Sensitive data can be anonymized to comply with privacy standards, ensuring training environments are secure and up-to-date. Salesforce Data Mask can be utilized.

Fed angle

At a regulated financial institution, using real production data in a training sandbox without masking it is a compliance violation. Salesforce Data Mask is the control that satisfies privacy requirements (e.g., PII, PCI, financial account data) while still giving trainees realistic records to work with. Auditors will ask specifically whether training environments are masked.

Page 10 · Staging

Staging

Staging refers to validating the release prior to its deployment in the live environment.

Final Validation

Final validation can be conducted in a Full sandbox that simulates the production environment. This step is critical to identify and mitigate any last-minute issues.

Regular Refreshes

Regular Full sandbox refreshes should be scheduled to ensure that the staging environment closely reflects the production setup for accurate testing.

Staging always uses a Full sandbox — only a Full sandbox is a complete replica of production. Partial Copy sandboxes are for UAT and integration testing, not for final pre-production validation.
Page 11 · Hotfix Development and Deployment

Hotfix Development and Deployment

A hotfix is a simple change that addresses an urgent issue impacting day-to-day business.

Rapid Fixes

A Developer sandbox can be reserved for hotfix development to allow for rapid fixes to critical issues without disturbing the main development and release cycle.

Hotfix Testing

Hotfixes can be tested in a Partial Copy or Full sandbox before they are deployed to production to ensure that they don't introduce new issues.

Interview angle

The key architectural point on hotfixes is isolation: a dedicated Developer sandbox means the hotfix work never pollutes the in-progress feature branch or the main deployment train. The architect must also define when to test in a Partial Copy (faster, less data fidelity) vs. a Full sandbox (slower refresh, but production-equivalent) — the severity and data sensitivity of the issue drives that choice.

Page 12 · Sandbox Refresh and Data Management

Sandbox Refresh and Data Management

An appropriate sandbox refresh strategy should be utilized for different release cycles.

Sandbox Refresh

The sandbox refresh schedule should align with major and minor release cycles and the project requirements, ensuring that environments are reset and ready for new development work post-release.

Data Masking

A data masking strategy can be implemented for training and testing environments to protect sensitive information while maintaining the utility of real-world data scenarios.

Fed angle

Tying refresh cadence to the release calendar is a change-control practice, not just an operational one. A regulated org should document which sandboxes are refreshed when, approved by whom, and what data masking policy applies to each — this is the evidence trail auditors expect to see in a sandbox management procedure document.

Page 13 · Sandbox Preview Considerations

Sandbox Preview Considerations

A preview sandbox provides early access to features in a new Salesforce release in advance, allowing testing of configurations before the production upgrade.

Non-Preview Refresh Before Cut-Off

A non-preview sandbox can be refreshed before the cut-off date (the day before the preview starts) to ensure that they are upgraded to the next major release. It moves the sandbox to a preview instance.

Sandbox Preview Guide

The Sandbox Preview Guide can be used to determine if each of the sandboxes is on a preview or non-preview instance and what to do to either move to the next release or stay on the current release.

Preview Sandbox Refresh After Cut-Off

If a preview sandbox is refreshed after the cut-off date, it is moved to a non-preview instance and reverts to the current release. If a non-preview sandbox is refreshed after the date, it remains on a non-preview instance.

Preview/non-preview refresh timing is a classic exam gotcha. Refreshing after the cut-off date moves a preview sandbox back to non-preview (current release). Refreshing before cut-off moves a non-preview sandbox to preview (next release). The direction of the move depends on both the sandbox's current state and the timing relative to cut-off.

Business Scenario — Cosmic Technology Solutions

Read the business scenario below and determine the most appropriate solutions for the company's requirements.

Scenario

Cosmic Technology Solutions is preparing for multiple Salesforce updates aimed at enhancing user interfaces, automating administrative tasks, and integrating third-party analytics tools. The development teams are working on several projects, including the development of new features, customization of existing applications, and critical bug fixes. Additionally, the company plans to roll out training for end users to familiarize them with the updates. The company's Salesforce architect must analyze various business requirements and recommend sandbox strategies for specific release plans. These strategies should accommodate aspects such as parallel development, staging environment, planned training sessions, and rapid deployment of hotfixes. These activities must be orchestrated seamlessly, ensuring that all updates are delivered efficiently and effectively without compromising the platform's integrity or user experience.

Requirements & Solutions

Page 17 · Requirement 1

Requirement 1

Scenario

A development team works on four types of releases: daily, minor, major, and urgent. It has finished working on a major project and is about to begin its release using a deployment train consisting of several sandboxes, which are on preview and non-preview instances. The project manager is concerned about the impact of the upcoming Salesforce release. The team also needs to work on urgent fixes for bugs found in production. Furthermore, a user has submitted an urgent request for a new report. The architect must recommend suitable sandbox strategies that align with these releases.

Page 18 · Solution 1 (Part 1)

Solution 1 (Part 1)

Solution

For the release of the major project, all non-preview sandboxes should be refreshed before the cut-off date to ensure that they are upgraded to the new release. This is to ensure that new features are tested and any potential issues with the project are identified in relation to the upcoming Salesforce release.

A full sandbox can be utilized for the urgent analysis and fixing of bugs found in production. Before any deployment in production, the same process must be performed in the full sandbox to identify and address potential issues before they affect the production environment. The sandbox should be refreshed after the deployment of each hotfix in production.

Fed angle

Refreshing non-preview sandboxes before cut-off is a deliberate, documented release-coordination action — exactly the kind of scheduled, approved change that a regulated institution's release calendar must capture. The requirement to run the same process in a Full sandbox before any production deployment mirrors the segregation-of-duties control: no change goes to production without validated staging evidence.

Page 19 · Solution 1 (Part 2)

Solution 1 (Part 2)

Solution

The daily release process can be utilized to create the report directly in a full sandbox and then deploy it to production. The daily release process is typically designed for quick changes that need to be deployed rapidly to address immediate needs or fix minor issues. Creating the report in a full sandbox first would allow testing and validation in an environment that mirrors production.

Even a simple report request should go through a full sandbox before production — this is because a full sandbox mirrors production data structure and configurations. Bypassing validation for "quick" changes is an anti-pattern the exam tests against.
Page 20 · Requirement 2 (Part 1)

Requirement 2 (Part 1)

Scenario

The European division of the company wants to implement a release strategy with major releases every four weeks and minor releases every week. Major releases should go through development, system integration testing (SIT), user acceptance testing (UAT), and training. Minor releases should go through development and user acceptance testing (UAT). The architect must suggest a suitable sandbox strategy for UAT.

Also, the division is planning for a new Service Cloud implementation project for a large support center, which will require extensive training and change management.

Page 21 · Requirement 2 (Part 2)

Requirement 2 (Part 2)

Scenario

The implementation has dependencies on the existing Sales Cloud implementation. A suitable sandbox strategy that utilizes an appropriate release plan is required for the implementation. The architect must also provide considerations related to the use of a staging environment for the development lifecycle.

Page 22 · Solution 2

Solution 2

Solution

Considering the required release timelines, minor releases should use a partial copy sandbox and major releases should use a full sandbox for user acceptance testing (UAT). For the Service Cloud implementation project, the major release process should be utilized. User acceptance testing (UAT) and extensive training should be performed in a full sandbox before deployment to production. A separate full sandbox can be used as the staging environment for the release. A staging sandbox is typically a full replica of production when it is created or refreshed.

Interview angle

The UAT sandbox choice — Partial Copy for minor, Full for major — is driven by data fidelity requirements. Minor releases need basic representative data; major releases and large implementations need a full production replica to surface data-volume and configuration issues before go-live. When the exam gives you a release cadence scenario, always match the sandbox tier to the stakes of the release.

Cheatsheet — Sandbox Strategy for a Release Plan

Sandbox Type Selection Matrix

Use CaseSandbox TypeKey Reason
Development (per team / stream) Developer or Developer Pro Isolated, prevents overlap between parallel project streams
Integration Testing (merged streams) Partial Copy or Full Combined work from multiple streams tested together via source control merge
UAT — Minor Release Partial Copy Representative data sufficient for weekly minor changes
UAT — Major Release Full Full production replica needed to surface volume/config issues
Training Partial Copy or Full Realistic dataset; use Salesforce Data Mask to anonymize sensitive data
Staging (final pre-prod validation) Full Must mirror production exactly; regularly refreshed
Hotfix Development Developer Isolated from main release cycle; dedicated for urgent rapid fixes
Hotfix Testing Partial Copy or Full Validates hotfix doesn't introduce new issues before production deploy
Daily Release / Quick Change Full Even quick changes need a production-mirror for testing before deploy

Preview vs. Non-Preview Refresh Behavior

Sandbox TypeRefreshed Before Cut-OffRefreshed After Cut-Off
Non-Preview Sandbox Moved to preview instance (next major release) Remains on non-preview instance (current release)
Preview Sandbox Stays on preview instance (next major release) Moved to non-preview instance (reverts to current release)

High-Yield Exam Gotchas

  • Full sandbox = staging. Only a Full sandbox is a complete replica of production. Never use Partial Copy for final staging validation.
  • Partial Copy vs. Full for UAT is driven by release size: minor releases use Partial Copy, major releases use Full.
  • Hotfix development is isolated in a dedicated Developer sandbox — it must never pollute the main release train sandboxes.
  • Data Mask is required for training sandboxes containing real production data — exposing PII/sensitive data in training environments is a compliance violation.
  • Refreshing a non-preview sandbox before cut-off upgrades it to the next release; after cut-off it stays on the current release.
  • Refreshing a preview sandbox after cut-off reverts it to the current release (moved to non-preview instance).
  • Sandbox refresh cadence must align with the release calendar — not ad hoc. Document who approves each refresh and when.
  • Daily release process uses a Full sandbox even for simple changes like new reports — testing in a production-mirror before deploy is non-negotiable.
  • Source control (Salesforce DX) is the merge mechanism for multiple project streams — it feeds combined work into a shared integration sandbox, preventing "last one to deploy wins" conflicts.

Fed angle — Tying it together

For a central bank platform engineer, the sandbox strategy is not an operational convenience — it is a change-control artefact. Every sandbox must have a documented purpose, owner, refresh cadence, and data masking policy. The staging Full sandbox (refreshed regularly, used as the final gate before production) maps directly to the pre-production validation stage required by change advisory board (CAB) governance. The hotfix Developer sandbox — isolated from the main train — satisfies the segregation-of-duties requirement that emergency fixes cannot short-circuit the normal pipeline without a distinct, auditable approval track. Preview/non-preview management ensures that Salesforce platform upgrades are tested before they hit production, which is the Salesforce-specific equivalent of patch management controls that regulators expect.
