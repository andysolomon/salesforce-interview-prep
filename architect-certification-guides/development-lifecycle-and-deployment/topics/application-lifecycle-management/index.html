Page 4 · Introduction

Introduction

Application Lifecycle Management (ALM) is the process of managing the life of an application. It manages an application's development, from design to final release. It establishes a framework for fixing bugs and delivering feature enhancements over time. It consists of these phases: Plan Release, Develop, Test, Build Release, Test Release, and Release.

Various development methodologies are available to manage the development of a Salesforce application. These include waterfall, agile, and hybrid. Furthermore, the principles of frameworks such as Scrum, Lean, or Kanban can also be applied to a Salesforce development project.

It is also important to consider the establishment of governance strategies for a development methodology to manage and track changes effectively.

Application Lifecycle Management

Page 7 · ALM Definition

Application Lifecycle Management

Application Lifecycle Management (ALM) refers to the process of managing the life of an application and focuses on the steps and policies to build the application smoothly.

Stages

The ALM cycle consists of the following stages that apply to any Salesforce development project: Plan Release, Develop, Test, Build Release, Test Release, and Release.

Process & Framework

ALM defines the process of managing an app's development, from design to final release. It also establishes a framework for fixing bugs and developing feature enhancements over time.

Fed angle

At a regulated institution like the Federal Reserve, ALM is not optional — it is the governance structure that provides the audit trail from requirement through release. Every stage maps to a control: Plan Release = change request, Develop = controlled environment, Test = quality gate, Release = change advisory board sign-off.

Page 8 · Plan Release & Develop

ALM Stages: Plan Release & Develop

Application Lifecycle Management (ALM) refers to the process of managing the life of an application and focuses on the steps and policies to build the application smoothly.

Plan Release

A development project should start with a plan. At this stage, requirements should be gathered and analyzed. The product manager creates design specifications. The development and testing environments are identified.

Develop

At this stage, based on the design specifications, the development work is done in an environment containing a copy of the production org's metadata. An appropriate combination of declarative and programmatic tools is used for development.

Interview angle

"Plan Release" is where architects add the most value — defining sandbox strategy, identifying tooling, and establishing the governance model before a single line of code is written. Frame your answer around "what do you do before you build?"

Page 9 · Test & Build Release

ALM Stages: Test & Build Release

Application Lifecycle Management (ALM) refers to the process of managing the life of an application and focuses on the steps and policies to build the application smoothly.

Test

The changes made in the previous step are tested to ensure they work as intended before they are integrated with other people's work. Testing is done in the same type of environment that was used for development.

Build Release

The customizations that need to be deployed to production are aggregated into a single-release artifact.

Testing at the same environment type as development avoids environment-parity surprises. This is a key reason why the sandbox tier strategy matters: developer sandboxes for Develop, same tier (or integration sandbox) for Test.
Page 10 · Test Release & Release

ALM Stages: Test Release & Release

Application Lifecycle Management (ALM) refers to the process of managing the life of an application and focuses on the steps and policies to build the application smoothly.

Test Release

The release artifact is tested in a staging environment that mimics production. Regression and performance tests are run at this stage. The release is tested with a small set of experienced people who provide feedback, called user acceptance testing (UAT).

Release

After completing the testing and meeting the quality benchmarks, the release artifact containing the customizations is deployed to production. Employees and partners are trained to ensure that they understand the changes, and if necessary, a separate environment is created for training if the release has a significant user impact.

Fed angle

UAT in a Full sandbox mirroring production is the standard answer for regulated deployments. The "training environment" step is often overlooked in interviews — mention it to show operational maturity. At the Fed, training documentation and sign-off are part of the change record.

Page 11 · ALM Cycle

The ALM Cycle — Six Stages

The six stages of ALM form a continuous cycle, enabling iterative delivery and ongoing improvement.

#StageKey activity
1Plan ReleaseGather & analyze requirements; create design specs; identify environments
2DevelopBuild in a sandbox copy of production metadata using declarative & programmatic tools
3TestValidate changes in the same environment type; ensure integration with other work
4Build ReleaseAggregate all customizations into a single release artifact
5Test ReleaseRegression & performance tests in staging; UAT with key stakeholders
6ReleaseDeploy to production; train employees & partners
The cycle repeats — after Release, the next Plan Release begins, incorporating feedback and new requirements. This is how ALM supports both waterfall (one large cycle) and agile (many short cycles) methodologies.
Page 12 · Benefits of ALM (1)

Benefits of Application Lifecycle Management

Using Application Lifecycle Management (ALM) for application development has many benefits.

Avoids Defects

Using ALM improves the quality of the application and ensures that defects, such as functional bugs, usability issues, and logic errors, are not deployed to production.

Increases Efficiency

It increases the efficiency and productivity of teams by standardizing processes and facilitating the reuse of resources.

Improves Consistency

It enables systematic planning, development, and deployment, leading to more consistent and predictable release schedules.

Page 13 · Benefits of ALM (2)

Benefits of Application Lifecycle Management (continued)

Using Application Lifecycle Management (ALM) for application development has many benefits.

Faster Delivery

It can accelerate the development process, enabling teams to deliver features to customers faster.

Reduces Cost

It can significantly reduce costs by improving efficiency, reducing rework, and preventing defects.

Maintenance

It provides a framework for ongoing maintenance and support of the application, ensuring long-term stability and usability.

Interview angle

When asked "why does ALM matter?", lead with the cost angle: defects found in production cost 10–100x more than defects caught in development. The "reduces cost" and "avoids defects" bullets are your evidence. Pair it with a real example of catching a bug in a sandbox before it hit prod.

Development Methodologies

Page 15 · Development Methodology

Development Methodology

A development methodology is the structured approach or set of practices that Salesforce developers and teams follow to build, test, deploy, and maintain applications within the Salesforce platform.

Processes & Strategies

The development methodology encompasses the processes and strategies used to manage the lifecycle of custom Salesforce solutions, through initial planning and design through development, deployment, and ongoing maintenance.

Key Aspects

The key aspects of a development methodology are planning and analysis, design, development, testing, deployment, maintenance and support, and governance.

Page 16 · Waterfall Methodology (1)

Waterfall Methodology

Waterfall is a traditional development methodology with a linear sequence of defined steps. Each step is completed fully before moving on to the next.

Stable Requirements

The requirements are well-defined and typically very stable.

Documentation Focus

There is a focus on extensive planning and documentation.

Single Outcome

There is a single outcome or result of the development process.

Stakeholder Engagement

Stakeholders engage in planning and at key milestones.

Page 17 · Waterfall Methodology (2)

Waterfall Methodology (continued)

Waterfall is a traditional development methodology with a linear sequence of defined steps. Each step is completed fully before moving on to the next.

Time & Cost Planning

Time and cost are determined in the planning stage of the project.

Early Risk Definition

The project risks are defined early in the project.

Change Control

Changes are carefully managed and controlled.

Fed angle

Waterfall's upfront planning, extensive documentation, and managed change control map directly to the Federal Reserve's IT governance requirements. Change requests must be documented, risk-assessed, and approved before work begins — that is Waterfall governance by default. For well-understood, compliance-driven projects, Waterfall remains the safer and more auditable choice.

Page 18 · Risks of Waterfall

Risks of Waterfall Methodology

The Waterfall development methodology has various risks.

Inflexibility

There is a lack of flexibility and the changes must be formally reviewed and approved.

Change Resistance

Change is avoided and new or unplanned risks are not easily accommodated.

Documentation Overhead

The documentation is time-consuming and doesn't provide value to the customer.

Limited Stakeholder Feedback

Stakeholder involvement is minimal, so there is limited feedback.

Upfront Planning Required

Accurate and complete planning is required to determine the project time and cost.

Customer Dissatisfaction Risk

There is a risk of customer dissatisfaction with the final outcome.

Interview angle

The exam often presents a scenario where requirements change mid-project under Waterfall — the correct answer is that Waterfall does not accommodate this well, and the change must go through a formal Change Control Board. That rigidity is both a risk and, in regulated environments, a feature.

Page 19 · Agile Methodology (1)

Agile Methodology

Agile is a less traditional development methodology that focuses on an iterative and flexible approach where the project is divided into small parts called sprints.

Evolving Requirements

The requirements are progressively elaborated.

Iterative Planning

The focus is on iterative planning and execution.

Incremental Delivery

There is incremental delivery of outcome.

Continuous Stakeholder Engagement

Stakeholders engage throughout the project.

Page 20 · Agile Methodology (2)

Agile Methodology (continued)

Agile is a less traditional development methodology that focuses on an iterative and flexible approach where the project is divided into small parts called sprints.

Time & Cost Refinement

As the requirements are elaborated, the time and cost are defined and refined.

Ongoing Risk Definition

Project risks are defined and refined throughout the project.

Change Embrace

Changes are expected and incorporated during planning and execution.

Page 21 · Risks of Agile

Risks of Agile Methodology

The Agile development methodology has various risks.

Scope Creep

Projects can suffer from scope creep due to the iterative nature and frequent feedback loops.

Quality Compromise

Rapid development can sometimes compromise the quality of software.

Insufficient Documentation

Prioritizing working software can lead to insufficient documentation.

Constant Changes

Excessive customer input can derail the project focus or lead to constant changes in requirements.

Underestimation

Lack of detailed upfront planning can cause underestimation of time and effort.

Integration Challenges

Integration can be challenging if multiple teams are working on different parts of a larger system.

Fed angle

In a regulated environment, "insufficient documentation" is not just a risk — it is a compliance failure. Agile at the Fed requires explicit guardrails: definition-of-done that includes documentation, compliance review at sprint boundaries, and a Release Management role that maintains the audit trail across sprints.

Page 22 · Agile Methodologies

Agile Methodologies

The three most common Agile methodologies are Scrum, Lean, and Kanban.

Scrum

An iterative framework based on time-boxed sprints, defined roles (scrum master, product owner, development team), and five core values.

Lean

Applies manufacturing principles of efficiency and value delivery — waste elimination, continuous learning, just-in-time decisions.

Kanban

A visual workflow framework that manages work in progress (WIP) and improves flow through the development pipeline.

Page 23 · Scrum

Scrum

Scrum is an agile framework used for the iterative delivery of project outcomes and results. It is an easy to follow and scalable method often used for software development.

Incremental

Working software is delivered incrementally. Time-boxed iterations known as sprints typically last for 2–4 weeks.

Roles

Stakeholders and team are highly collaborative. Roles include scrum master, product owner, and development team.

Meetings

Scrum features meetings such as sprint planning, daily stand-ups, sprint review, and sprint retrospective.

Artifacts

Major artifacts include product backlog, sprint backlog, burndown charts, and increment.

Interview angle

Know the difference between sprint review (show stakeholders what was built) and sprint retrospective (team reflects on how they worked). Interviewers test this distinction. The product owner prioritizes the backlog; the scrum master removes impediments — these are distinct roles, not interchangeable.

Page 24 · Scrum Values

Scrum Values

The Scrum framework is built on five core values that guide team behavior and decision-making.

Focus

Team members concentrate on the overall goals and work of the sprint. They prioritize the work that contributes to the sprint goals and avoid distractions.

Courage

Team members have the bravery to do the right thing. They are bold in the face of challenges and do not hesitate to speak up, experiment, or innovate.

Openness

The team and stakeholders are transparent about all the work and any challenges. They share ideas, concerns, and mistakes. They are open to change, feedback, and learning.

Commitment

Team members are committed to the success of the project and the goals of the sprint. They are dedicated to the necessary time and effort to complete tasks.

Respect

Team members recognize each member's expertise, perspective, and contribution. They treat each other with dignity, work together as equals, and value their input.

Mnemonic: FCORE — Focus, Courage, Openness, Respect… wait — COFOR. Better: remember "A Competent Focus Opens Respect" (Commitment, Focus, Openness, Respect) + Courage. The exam tests all five by name.
Page 25 · Lean

Lean

Lean is a framework that applies the manufacturing principles of efficiency and value delivery to software development.

Waste Elimination

Lean focuses on maximizing value while minimizing waste associated with unproductive tasks.

Efficiency & Quality

There is an efficient use of team resources. The focus is on quality at every step.

Knowledge

Constant learning and adaptation are encouraged for continuous improvement.

Just-in-Time Decisions

Decisions are made at the last responsible moment. Up-front decisions are avoided.

Page 26 · Lean Principles

Lean Principles

The five principles of Lean guide how value flows from development to the customer.

Identify Value

The focus is on determining what is valuable to the customer by understanding their needs and preferences through engagement.

Map the Value Stream

Value stream mapping focuses on identifying the activities and processes necessary to deliver a feature and eliminating waste.

Create Flow

Creating a flow involves reorganizing work processes, equipment, and teams to get value to flow to customers at a steady pace. Value-creating steps are performed in a tight sequence.

Establish Pull

Features are only made in response to customer demand. This means not delivering features unless there is a clear need or request.

Seek Perfection

The final characteristic of Lean is the continuous pursuit of perfection. It emphasizes continually seeking ways to improve processes and eliminate waste.

Interview angle

Lean's "just-in-time decisions" directly opposes Waterfall's upfront planning. When an exam scenario describes a team that wants to delay architectural decisions until they have more information, Lean (not Agile generically) is the precise answer. Pair with the value stream — waste in Salesforce dev includes unused features, unnecessary approvals, and environments that drift.

Page 27 · Kanban

Kanban

Kanban is an agile framework that focuses on managing and improving workflows.

Visual Workflow

Work is made visible, typically using a Kanban board. The workflow is divided into columns, each representing a different stage.

Limits

Limitations are placed on how many work items are in progress at a time in each workflow stage.

Changes

Kanban allows teams to embrace smaller and more changes along the workflow.

Metrics

Metrics such as cycle time and throughput are used to determine and predict progress.

Page 28 · Kanban Traits

Kanban Traits

Four key traits distinguish Kanban from other frameworks.

Visualize Workflow

Work is divided into smaller pieces that are represented on cards that move from left to right on a Kanban board, which visually maps out each stage of the workflow.

Limit Work in Progress (WIP)

WIP limits are set at each stage of the workflow to prevent overloading the team and to ensure the smooth flow of work through the process. Current tasks are completed before starting new ones.

Incremental & Evolutionary Change

Teams using Kanban are more open to taking last-minute requests. When a work item is finished, they move to the next highest-priority task.

Kanban Metrics

Cycle time is used to determine the number of days to complete a work item once work starts on it. Throughput is used to measure the amount of work completed in a single period of time.

Kanban vs Scrum: Kanban has no sprints, no fixed roles, and no ceremonies — it is a continuous-flow model. Scrum has time-boxed sprints and defined ceremonies. Kanban suits ongoing operational support work (e.g., bug fixes, admin tasks); Scrum suits project-based delivery with a defined scope.
Page 29 · Hybrid Methodology (1)

Hybrid Methodology

A hybrid development methodology combines the elements of both Waterfall and Agile methodologies by leveraging their strengths and mitigating their weaknesses.

Structured Phases

Structured phases, such as detailed upfront planning, are combined with the flexibility of Agile, such as iterative development.

Detailed Initial Planning

Initial planning and requirement gathering are done in a detailed and structured manner.

Iterative Implementation

Planning is followed by the use of iterative development cycles for implementation.

Regular Feedback

Regular feedback is incorporated while maintaining defined milestones and deliverables.

Page 30 · Hybrid Methodology (2)

Hybrid Methodology (continued)

A hybrid development methodology combines the elements of both Waterfall and Agile methodologies by leveraging their strengths and mitigating their weaknesses.

Balanced Documentation

Comprehensive documentation is balanced with minimal but essential documentation to ensure clarity without overburdening.

Dual Risk Approach

Risk assessment in early phases is combined with the ability to adapt to risks as they arise.

Best-of-Both Application

Waterfall techniques are often used for the predictive aspects. Agile techniques are applied to uncertain parts.

Fed angle

Hybrid is the natural model for the Federal Reserve: regulatory and compliance phases use Waterfall governance (documented, signed off, change-controlled), while feature development within a release uses Agile sprints. This is essentially SAFe — Agile Release Trains within a PI planning governance shell.

Page 31 · Risks of Hybrid

Risks of Hybrid Methodology

The Hybrid development methodology has various risks.

Complexity & Confusion

Balancing the practices of the two methodologies can be complex and lead to confusion.

Methodology Conflicts

The different nature of the two methodologies can lead to conflicts.

Administrative Overhead

Implementing both the methodologies can increase the administrative overhead and strain resources.

Unclear Guidelines

If the guidelines are unclear, teams may struggle to determine when to apply Agile principles and Waterfall practices.

Adoption Difficulty

Teams accustomed to one methodology may find it challenging to adopt a combined approach.

Suboptimal Outcomes

Combining the two methodologies can lead to suboptimal outcomes due to potentially diluted benefits.

Governance Strategies

Page 33 · Governance — Definition

Governance

Governance refers to putting a structure in place to effectively handle and track changes to all the aspects that control how applications work.

Application

Governance can apply to the development of custom applications by the business in Salesforce and the introduction of release updates three times a year by Salesforce.

Need

To adapt to the changing business climate, organizations need consistent tweaks to how changes are managed. It can be a new system or process to implement, or a new dataset to track.

Page 34 · Governance — Focus & Benefits

Governance (continued)

Governance refers to putting a structure in place to effectively handle and track changes to all the aspects that control how applications work.

Focus

Governance frameworks generally focus on aspects such as release management, prioritization of change requests, approval of changes, release schedule, communication process, etc.

Benefits

Benefits of using governance strategies include increased efficiency due to better resource utilization, improved security and compliance, greater collaboration and transparency, etc.

Interview angle

When asked "how do you govern a Salesforce org?", structure your answer around these pillars: who approves changes (CAB/steering committee), how changes are tracked (ticketing + source control), when they deploy (release calendar), and how quality is assured (testing gates). That is a governance framework answer, not just a tooling answer.

Page 35 · Waterfall Governance Strategies

Waterfall Development Governance Strategies

Governance strategies for the Waterfall development methodology include the establishment of a Change Control Board (CCB) and setting up Milestone Reviews.

Change Control Board (CCB)

A Change Control Board (CCB) is a formal group that assesses and approves changes to the project scope, ensuring that they align with the original goals and objectives.

Milestone Reviews

Meetings can be scheduled regularly to review progress and ensure that the project stays on track with its timeline and budget.

Fed angle

The CCB is the Waterfall governance mechanism that most directly maps to the Federal Reserve's change management requirements. In a regulated environment, the CCB is not optional — it is the control that prevents unauthorized changes and provides the audit trail required by internal audit and external regulators.

Page 36 · Agile Development Governance Strategies

Agile Development Governance Strategies

When using the Agile development methodology, some governance practices include prioritization, daily stand-ups, sprint reviews, and retrospectives.

Work Prioritization

The product owner prioritizes work items and ensures alignment with customer needs and organizational goals.

Daily Stand-Ups

Teams can use short, daily meetings to report progress and raise issues.

Reviews & Retrospectives

Regular meetings are conducted at the end of each sprint to review work and discuss ways to improve processes.

Interview angle

Agile governance is lightweight by design, but in enterprise or regulated settings it must be supplemented: add a release manager role, a definition of done that includes compliance checkpoints, and sprint-gate approvals for deployments to UAT/staging. "Agile with guardrails" is the answer for most large-org scenarios.

Page 42 · Solution 1 (Part 1)

Solution 1 — Waterfall Rationale

Solution

The Waterfall development methodology should be adopted for this project for several reasons. It uses a linear and sequential approach that provides a clear structure and a defined pathway from project initiation to completion, which aligns with the client's preference for a structured methodology. The project's well-defined requirements and scope are ideal for this methodology. The extensive documentation required in Waterfall can meet the client's compliance needs. The fixed deadline and limited availability for engagement also align well with the Waterfall approach of set timelines and deliverables.

Page 43 · Solution 1 (Part 2)

Solution 1 — Risk Mitigation

Solution

However, some risks are associated with using the Waterfall methodology, but they can be mitigated using some strategies. It can be challenging to incorporate changes late in the project, which can be avoided through exhaustive requirement gathering and stakeholder sign-off before proceeding to development. A feasibility study and architectural evaluation should be conducted early in the project to mitigate late testing and integration risks. In addition, milestone review meetings should be conducted to ensure that there are no gaps in expectations.

Solution 1 — Waterfall Development Flow

The Waterfall Development Methodology follows a strict linear sequence of phases.

The chief executives value flexibility, as they anticipate their needs evolving quickly due to their fast-paced and dynamic market. Page 47 · Solution 2 (Part 1)

Solution 2 — Agile Rationale

Solution

The Agile development methodology is suitable for the evolving needs of the startup, as it allows for frequent reassessment and adaptation of requirements. The iterative nature of Agile enables the delivery of work in small, manageable increments, allowing the startup to begin using functionalities sooner and provide ongoing feedback. Moreover, Agile emphasizes collaboration between the development team and the client, ensuring that the final product closely aligns with the client's expectations and needs.

Page 48 · Solution 2 (Part 2)

Solution 2 — Risk Mitigation

Solution

However, certain risks and related mitigation strategies need to be considered for using the Agile methodology. If not managed carefully, the flexibility offered by Agile can lead to scope creep. A robust backlog prioritization process should be implemented, and changes in scope should be systematically evaluated and agreed upon. Since Agile requires active client involvement, it must be ensured that the client is committed to this level of participation. Regularly scheduled meetings and demos can facilitate this. Rapid delivery can compromise the depth of initial planning, which can be mitigated by sprint planning sessions that clearly outline goals and deliverables for each iteration.

Page 49 · Solution 2 (Part 3)

Solution 2 — Agile Development Cycle

The Agile Development Methodology follows a repeating iterative cycle — each sprint passes through all phases before the next sprint begins.

PhaseWhat happens
PlanSprint planning: select user stories from backlog, estimate effort, commit to sprint goal
DesignTechnical design and breakdown of selected stories into tasks
DevelopBuild the agreed features/fixes within the sprint timebox
TestUnit tests, integration tests, and QA within the sprint
DeployRelease increment to staging/UAT; demo to stakeholders
ReviewSprint review (show work) + retrospective (improve process); feed learnings into next sprint
LaunchProduction release at cadenced intervals (end of sprint or release train)

Solution 3 — Hybrid Rationale

Solution

The Hybrid development methodology should be adopted for the project since it provides the structured planning and clear milestones of Waterfall, which are essential for complex system integration, while also incorporating the flexibility and adaptiveness of Agile for gathering and implementing user feedback. The combination of early risk identification and mitigation and ongoing risk assessment would be beneficial for integrating Salesforce with multiple enterprise systems. Agile practices can be gradually introduced, ensuring stakeholder comfort and buy-in. Agile sprints can be employed for the development of custom features and for gathering user feedback.

Solution 3 — Risk Mitigation

Solution

On the other hand, mixing the two methodologies can lead to confusion and conflict, which can be avoided by providing training to the team and clearly defining which parts of the project will use Waterfall and which will use Agile. There's a risk that this methodology can use more resources, so careful planning and resource management are necessary to ensure that the project stays within the budget and time constraints. Regular meetings and clear communication should be used for a smooth transition between Waterfall and Agile phases. Additionally, phase-gate reviews should be implemented at major milestones for quality and progress checks.

Scrum's Five Values (memorize)

  • Commitment — dedicated to sprint goals and project success.
  • Courage — bold enough to speak up, experiment, innovate.
  • Focus — concentrate on sprint work, avoid distractions.
  • Openness — transparent about work, challenges, and mistakes.
  • Respect — recognize each member's expertise and contribution.

Lean's Five Principles (memorize)

  • Identify Value — what does the customer actually need?
  • Map the Value Stream — eliminate waste-generating activities.
  • Create Flow — organize work so value moves at a steady pace.
  • Establish Pull — build features only in response to demand.
  • Seek Perfection — continuously improve and eliminate waste.

Key Gotchas for the Exam

  • Waterfall: each step is fully completed before the next begins — no overlap.
  • Agile: requirements are progressively elaborated, not frozen upfront.
  • Scrum sprints are time-boxed (typically 2–4 weeks); Kanban has no sprints — it is continuous flow.
  • Lean decisions are made at the last responsible moment — not upfront.
  • Hybrid applies Waterfall to predictive/integration phases and Agile to uncertain/feature phases.
  • Governance must be right-sized: over-governing a small shop kills velocity; under-governing an enterprise creates uncontrolled risk.
  • The CCB is the Waterfall governance mechanism; the product owner is the Agile prioritization mechanism.
  • ALM applies to both waterfall and agile — it is the overarching framework, not a methodology itself.
