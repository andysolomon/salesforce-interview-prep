Page 4 · Introduction

Introduction

Salesforce releases new features and enhancements three times a year during the Spring, Summer and Winter seasons. A preview sandbox can be used to test new features before they are released in the production environment. The location of a sandbox (preview or non-preview instance) depends on the timing of its most recent refresh.

Release Notes should be reviewed to identify the different types of features in a release. Change management principles should be followed for the implementation of new features. Various types of testing, such as unit testing, functional testing, and regression testing, can be conducted in a preview sandbox prior to a release.

Page 7 · Upgrades & Release Cycle

Salesforce Releases — Upgrades & Release Cycle

Salesforce releases new features and enhancements three times a year during the Spring, Summer, and Winter seasons.

Upgrades

Each release brings automatic, seamless upgrades with minimal scheduled maintenance, ensuring all customers run on the same, latest version of Salesforce.

Release Cycle

The release cycle starts approximately 3 months before live production, with sandbox instances upgraded 4–6 weeks prior to the production release.

Because upgrades are automatic, every org in your estate — including production — will receive the release. The 4–6 week sandbox preview window is your only opportunity to catch regressions before they hit production users.
Page 8 · Salesforce Trust & Lightning Experience

Salesforce Releases — Trust & Lightning Experience

Salesforce releases new features and enhancements three times a year during the Spring, Summer, and Winter seasons.

Salesforce Trust

Release dates are published up to a year in advance on the Salesforce Trust website, allowing for early planning.

Lightning Experience

Lightning Experience is the focus of innovation in Salesforce releases, bringing productivity boosts and new features not available in Salesforce Classic.

Interview angle

When asked about release planning: lead with "I'd subscribe to Salesforce Trust release calendar notifications a year in advance and incorporate seasonal release windows into our internal PI planning calendar." This signals proactive governance, not reactive scrambling.

Page 9 · Sandbox Preview — Early Access & Non-Preview

Sandbox Preview — Early Access

Sandboxes allow previewing and testing new Salesforce features before their general release.

Early Access

Preview sandboxes provide early access to new features about 4–6 weeks before the production upgrade, enabling evaluation and user communication.

Non-Preview

Not all sandboxes are eligible for early upgrades; 'non-preview' sandboxes receive updates later, sometimes after production release.

Not every sandbox automatically becomes a preview sandbox. Whether a sandbox is on a preview or non-preview instance depends entirely on when it was last refreshed relative to the preview cut-off date.
Page 10 · Sandbox Preview — Location

Sandbox Preview — Location & the Cut-off Date

Sandboxes allow previewing and testing new Salesforce features before their general release.

Sandbox Location

The location of a sandbox (preview or non-preview instance) depends on the timing of its most recent refresh. If a sandbox is refreshed during the sandbox preview period, it is moved to a non-preview instance.

Preview Access

Refreshing a sandbox before the sandbox preview cut-off date sends it to a preview instance. To ensure access, the sandbox should be maintained without refreshing it after the cut-off date.

Classic exam trap: a sandbox refreshed during the preview window lands on a non-preview instance and therefore does NOT get the early upgrade. Refresh before the cut-off, then leave it alone.

Interview angle

Interviewers love this gotcha: "How do you ensure you have a preview sandbox for the upcoming release?" Answer: "Refresh the sandbox you want as a preview sandbox before the sandbox preview cut-off date, then do not refresh it again until after production goes live. I'd also consult the Sandbox Preview Guide to confirm which instances are preview vs non-preview."

Page 11 · Sandbox Preview — Guide & Recommendations

Sandbox Preview — Guide & Recommendations

Sandboxes allow previewing and testing new Salesforce features before their general release.

Preview Guide

The Salesforce Sandbox Preview Guide can be used to ensure access to a preview sandbox that gets an early upgrade.

Recommendations

Each sandbox instance can be looked up in the guide to see if it's a preview or non-preview instance. Recommendations can be followed to ensure that there's at least one sandbox on a preview instance.

Fed angle

A large enterprise org estate will have many sandboxes on multiple instances. The Fed requires having at least one Full or Partial sandbox on a preview instance dedicated to release impact assessment — this becomes a standing item on the quarterly release readiness checklist, just like a CAB entry. Documenting this in a runbook satisfies the auditability requirement.

Page 12 · Release Notes — Feedback & Communication

Release Notes — Feedback & Communication

Release Notes filters can be used to identify features that are automatically enabled (Quick Wins) and those that need minimal admin action (Low-hanging Fruit).

Feedback

Super users can be engaged for feedback on Quick Wins and Low-hanging Fruit to ensure user relevance and facilitate training.

Communication

Upcoming release details should be communicated to users and stakeholders, focusing on benefits and incorporating feedback for phased rollouts. Communication channels include in-app notifications, customized help menu, email, newsletters, cheat sheets, lunch and learns, virtual meetings, and webinars.

Interview angle

Automatically enabled features ("Quick Wins") are the release readiness risk most often overlooked. The exam expects you to know: filter release notes by "Automatically On" to find changes that will affect users on go-live day with zero admin action — those are the ones that could break existing behavior silently. Always review these first.

Page 13 · Release Notes — Sections & Process

Release Notes — Sections & Repeating Process

Release Notes filters can be used to identify features that are automatically enabled (Quick Wins) and those that need minimal admin action (Low-hanging Fruit).

Sections

The various sections in the release notes can be used as reference or to check for updates. It is possible to drill down by cloud as well as cloud-independent areas such as Analytics.

Process

This process should be repeated every three months: mark calendar dates, engage with community, preview in sandbox, review Release Notes, and prepare users.

Fed angle

The five-step cadence — mark dates, engage community, preview, review notes, prepare users — is a textbook change management loop. At the Fed this maps directly onto a quarterly CAB submission: a formal impact assessment submitted before each seasonal release window, with a testing sign-off before production is upgraded. The "every three months" cadence aligns perfectly with Salesforce's release schedule.

Page 14 · Pre-Release Org

Pre-Release Org

A pre-release org allows getting the earliest possible look at new features in action.

Availability

Sign-up for a pre-release org is available 3–4 weeks before the sandbox preview starts.

Customizations

A pre-release org does not contain any of the customizations, but they can be used to get a sneak peek at what's coming.

Pre-release orgs are completely separate from your production org — no customizations, no data. They're useful for exploring new standard features but cannot substitute for testing against your own org's custom code and configuration.
Page 15 · Benefits of New Features

Benefits of New Features

There are several benefits of new features released by Salesforce.

New Functionality

New functionality is delivered to users without custom code or third-party apps.

Improvements

Existing customizations are improved by eliminating workarounds or limitations.

Reduced Technical Debt

Unnecessary complexity or technical debt is removed, reducing time to deploy.

Simplified Backlog

Customizations in the backlog are simplified or enhanced.

Interview angle

When asked "why invest time evaluating every seasonal release?", the answer is not just "to avoid regressions." Releases also deliver value — new native functionality can replace custom-built workarounds, reducing technical debt and backlog size. Platforms engineers who evaluate releases proactively surface those opportunities; those who don't leave money on the table.

Page 16 · Implementation of New Features

Implementation of New Features

New features should be implemented by following change management principles.

Forward Planning

Forward planning should be used to ensure that the needed technical resources are available. Planning can be started two months before the release in production (early December, April, and August).

Roles, Responsibilities & Processes

Roles, responsibilities, and processes should be defined. Several individuals or teams may be responsible. Examples include product owners, subject matter experts, and technical experts.

Advanced Tools

Advanced tools such as the Release Matrix and a Release Management custom object can be used to manage release updates and make it easier to collaborate around prioritization and deployment.

Fed angle

Starting planning two months early (December, April, August) maps directly to a standing quarterly review in a regulated environment. A Release Matrix tracking feature-by-feature impact (auto-enabled vs admin action required, risk level, testing needed) is the kind of artifact that satisfies an internal audit or a CAB: it's auditable, assignable, and version-controlled. Build it in a Release Management custom object or a GitLab wiki — either way it's trackable.

Page 17 · Testing of New Features

Testing of New Features

The testing approach for new features depends on the complexity of the Salesforce org. The three change management principles should be considered.

Time & Resources

Time for testing activities should be factored in ahead of a Salesforce release deployment. The required people and testing environments should be considered. Other Salesforce project schedules may need to be adjusted.

User Experience & Code

New features that impact the user experience, such as changes to the user interface, and any existing custom code, should be tested. Tests should be conducted in a sandbox preview upgraded with the new Salesforce release.

Automated Testing (CI)

Automated testing tools, called CI (Continuous Integration) tools, can be used when there are multiple developers or complex custom code. Considerations such as cost, in-house expertise, and compatibility are applicable.

Interview angle

The slide explicitly calls out CI tools for multi-developer orgs with complex custom code. This is the opening to describe your automated regression suite: "I'd run the existing CI pipeline against the preview sandbox instance, catching any test failures surfaced by the new release before we're in the non-preview window."

Page 18 · Types of Testing

Types of Testing

There are five main types of testing that can be utilized for testing new features.

TypeWhat it tests
Unit testsSmallest bits of custom code — used to catch bugs early.
Integration testsCode interactions with anything not native in the org (external systems, APIs).
Functional testsVerify that features work as defined in the technical requirements.
User-acceptance testing (UAT)Allows end users to accept or reject the final feature delivery.
Performance testingEvaluates system response when large volumes of records or operations are being handled.
All five types can be conducted in a preview sandbox during the 4–6 week window before the production upgrade. The order matters: run unit → integration → functional → UAT → performance, so bugs are caught at the cheapest possible layer.
Page 19 · Testing Considerations

Testing Considerations

There are various considerations for testing new features before a release.

Sandbox Management

One or more sandboxes need to be created for testing. Reliable re-execution of tests requires a refresh or reset.

Test Data

Test data needs to be generated using a suitable approach in developer sandboxes since they do not contain any production data.

Integration Testing

Integration with third-party systems requires running tests on both sides of the integration.

API & UI Testing

API tests should be used instead of UI tests wherever possible since UI testing is costly to maintain. A dedicated UI tool should be used.

Performance Testing

It is necessary to ensure that governor limits are not reached during performance tests. Performance tests should not be automated.

Salesforce Classic Testing

Some tests built for Salesforce Classic won't run in Lightning Experience, so it may be necessary to rebuild them.

Fed angle

Three of these six considerations map directly to Fed-context risks: integration testing (the Fed's Salesforce integrates with core banking, Oracle, and middleware — third-party tests must be coordinated), API over UI testing (aligns with your Playwright work — reserve UI tests for genuine UX journeys, not API behavior), and performance testing not automated (a common oversight — governor-limit failures at scale must be caught manually in a Full sandbox with representative data volumes before release day).

Business Scenario — Cosmic Innovations

Scenario

Cosmic Innovations is a global enterprise with a vast Salesforce implementation spanning multiple business units, including sales, customer service, and marketing. The company leverages Salesforce for a wide range of processes and custom applications, making the regular Salesforce seasonal releases (Spring, Summer, and Winter) crucial for the organization.

A Salesforce architect has been hired to recommend the appropriate strategies based on the company's requirements.

Requirements & Solutions

Page 23 · Requirement 1

Requirement 1 — Release Calendar Misalignment

Scenario

The CTO of the company has noticed that the misalignment of release cycles between Salesforce seasonal releases and internal major and minor releases is leading to inefficiencies and increased risk. An upcoming major release will be deployed one week after Salesforce updates the production org. The current deployment plan does not account for the Salesforce Spring release and the time required for refreshing the full sandbox, potentially delaying the deployment of critical updates.

Page 24 · Solution 1

Solution 1 — Establish a Release Calendar

Solution

The company should establish a comprehensive release calendar that aligns Salesforce seasonal releases with the internal release cycles. This calendar should be used to train and align all relevant teams, ensuring everyone is prepared for upcoming releases. In addition, the deployment plan should account for the production environment update and sandbox refresh time. To ensure seamless testing and deployment, the full sandbox should be refreshed approximately six weeks before go-live to ensure that it is on a preview instance for the purpose of testing. Once testing is complete and Salesforce has updated the production environment, the changes can be deployed to production.

Interview angle

This is the canonical exam answer for "release calendar + sandbox timing": refresh the Full sandbox ~6 weeks before go-live (which places it in the preview window), complete testing there, wait for prod to upgrade, then deploy. The mistake Cosmic Innovations made was not accounting for this lead time in their deployment plan — a classic gotcha.

Page 25 · Solution 1 — Release Timeline

Solution 1 — Release Window Timeline

Visual representation of the sandbox preview vs non-preview windows relative to the production release cycle.

PhaseDurationWhat happens
Current Production Release → Blog Post Reminder~8 weeksSandbox Preview Window is open. Sandboxes refreshed in this window land on a preview instance and will receive the early upgrade.
Blog Post Reminder → Sandbox Preview Upgrade~4 weeksStill within the preview window. The blog post reminder signals the preview upgrade is coming. Ensure your test sandbox has already been refreshed (before the cut-off).
Sandbox Preview Upgrade → Next Production Release~4 weeksSandbox Non-Preview Window. Sandboxes refreshed now go to a non-preview instance. Preview-enabled sandboxes have the new release for testing. Production upgrade occurs at the end of this window.
Key takeaway: the Sandbox Preview Upgrade happens approximately 4 weeks before the Next Production Release. To have a preview sandbox, you must refresh it before the Sandbox Preview Upgrade date — i.e., during the first 8-week window.

Fed angle

Translating this to operational practice: enter all three annual preview cut-off dates into the team's change management calendar as hard deadlines. Missing the cut-off means you lose your preview window — no early regression testing — which violates the spirit of the "Performs new Salesforce release evaluations and assess impact" JD requirement. Automate a Jira/GitLab ticket creation rule to fire 10 weeks before each seasonal release, kicking off the sandbox refresh checklist.

Page 26 · Requirement 2

Requirement 2 — Sandbox Version Mismatch

Scenario

A development team is facing issues while deploying metadata from a developer pro sandbox to a partial copy sandbox used for user-acceptance testing. The UAT sandbox is not recognizing some new Salesforce metadata types. There was no issue while deploying the same metadata from a developer sandbox to the developer pro sandbox. With several ongoing development projects, the company needs a robust strategy to prepare for the Salesforce release without impacting these projects.

Page 27 · Solution 2 — Sandbox Version Alignment

Solution 2 — Sandbox Version Alignment

Solution

The discrepancy between the two sandbox environments is most likely because the developer pro sandbox is on a preview release but the partial copy sandbox is not. It is important to ensure that both environments are on the same Salesforce release version to facilitate smooth metadata deployment. Additionally, the release strategy should include thoroughly reviewing the release notes for automatically-enabled features, features that require manual intervention, and areas of testing, refreshing a sandbox during the release preview window to test the upcoming release, and running regression tests in an upgraded sandbox to detect any issues.

Root cause: version mismatch between sandboxes. New metadata types introduced in the preview release are not recognized by the non-preview sandbox, because the non-preview sandbox is running the older version. Always verify all pipeline environments are on the same release before deploying.

Interview angle

This is a high-value exam scenario. The diagnostic question is: "Are all sandboxes in my deployment pipeline on the same Salesforce release version?" If developer sandboxes are on a preview instance and downstream UAT sandboxes are on non-preview, new metadata types will fail to deploy downstream. The fix is version alignment — not fixing metadata — and the prevention is a release strategy that controls which sandboxes are on preview vs non-preview.

Fed angle

At the Fed, a sandbox version mismatch mid-sprint could block a critical deployment. The mitigation is an environment inventory (a simple table of sandbox name → instance → current release version, updated each release cycle) and a policy that downstream UAT/Staging sandboxes are kept at the same release as developer sandboxes until a controlled cut-over. This inventory becomes an audit artifact showing the release evaluation process was followed.

Cheatsheet — Planning: Salesforce Releases

The three releases (memorize the timing)

ReleaseGeneral timingPlan start (2 months early)
SpringJanuary–FebruaryEarly December
SummerMay–JuneEarly April
WinterSeptember–OctoberEarly August

Preview sandbox timing (the most tested concept)

If you refresh…Sandbox lands on…Gets early upgrade?
Before preview cut-off datePreview instanceYes — 4–6 weeks early
During / after preview cut-offNon-preview instanceNo — may be after prod
Trap: refreshing a sandbox during the preview period moves it to a non-preview instance. Leave the sandbox untouched after the cut-off to keep it on preview.

Pre-release org vs preview sandbox

  • Pre-release org — available 3–4 weeks before sandbox preview; no customizations; sneak peek only.
  • Preview sandbox — your own org's sandbox on a preview instance; includes customizations; use for regression/functional/UAT testing.

Release Notes filter taxonomy

  • Automatically On (Quick Wins) — enabled on release day with no action; highest risk of silent regressions.
  • Low-hanging Fruit — minimal admin action required; engage super users for feedback first.
  • Drill down by cloud or cloud-independent area (Analytics, etc.) to scope the review.

Five types of testing (in recommended order)

  1. Unit — smallest custom code bits, catch bugs early.
  2. Integration — code interactions with non-native systems; test both sides.
  3. Functional — verify behavior matches technical requirements.
  4. UAT — end users accept or reject final delivery.
  5. Performance — governor limits under large volume; do NOT automate.

Testing considerations (six gotchas)

  • Sandbox management — reliable re-execution requires refresh or reset.
  • Test data — developer sandboxes have no prod data; generate synthetic data.
  • Integration testing — run tests on both sides of every integration.
  • API over UI — UI tests are expensive to maintain; use a dedicated UI tool when you must.
  • Performance tests — verify governor limits are not hit; these should NOT be automated.
  • Classic vs Lightning — some Classic UI tests won't run in Lightning; rebuild them.

Implementation checklist (change management)

  1. Mark calendar: subscribe to Salesforce Trust release dates ~1 year in advance.
  2. Start planning 2 months before production release (Dec / Apr / Aug).
  3. Refresh at least one sandbox before the preview cut-off date.
  4. Review release notes: filter for "Automatically On" features first.
  5. Engage super users; communicate to stakeholders via multiple channels.
  6. Run full test suite (unit → integration → functional → UAT → performance) in preview sandbox.
  7. Build and maintain a Release Matrix — assign owners to each feature/risk item.
  8. After production upgrade: deploy internal changes; run regression; sign off.
