Introduction

There are various methods that can be utilized to ensure the delivery of quality code in Salesforce. These include the creation of coding conventions and standards, the integral process of pull requests in Git-based workflows, the practice of code review for quality assurance, and the technique of static code analysis for the examination of code. These methods can be used to improve code consistency, enhance code security, catch bugs, and significantly improve the overall integrity of the codebase.

Fed angle

All four quality pillars map directly to the Federal Reserve Bank of Chicago's engineering standards: coding conventions enforce consistency across teams with high turnover; pull requests (merge requests in GitLab) enforce segregation of duties — no developer merges their own code; code review is a mandatory peer gate before any merge to main; and static analysis runs automatically in the CI pipeline, providing an auditable quality record before deployment to regulated environments.

Coding Standards

Coding conventions/standards are guidelines for styling and structuring code to add consistency and ensure team adherence to the same principles.

Code Quality

Coding conventions help maintain the clarity and quality of code in Salesforce orgs as they grow and become more complex.

Conventions

Coding conventions cover naming conventions for Salesforce elements, frameworks for making code reusable and maintainable, and best practices for Apex coding.

Benefits

Benefits of coding conventions include standardization, easier debugging and maintenance, fewer bugs, and ultimately, higher quality Salesforce solutions leading to increased customer satisfaction.

Interview angle

When asked how you enforce code quality across a multi-team org, lead with coding conventions as the foundation. Conventions create the shared mental model that makes code reviews faster and static analysis rules meaningful. Without them, every review degenerates into style debates rather than substantive quality checks.

Coding Standards — Naming & Conventions

Coding conventions/standards are guidelines for styling and structuring code to add consistency and ensure team adherence to the same principles.

Team Agreement

Implementing coding conventions requires no specific tools or software, just team agreement and commitment to follow these guidelines.

Success Cloud Conventions

Success Cloud Naming Conventions offer guidelines for naming common Salesforce entities, aiming to standardize component identification.

Apex Classes

For Apex classes, naming conventions suggest using PascalCase, including a namespace prefix (if applicable), the class name, and an optional suffix indicating the class type (e.g., Controller, Extension). For example, SCT_NewOrderController.

Fed angle

At a central bank, consistent naming conventions are not just developer ergonomics — they are required for traceable change management. When auditors ask which Apex class implements a particular business rule, a predictable naming scheme (namespace + class name + suffix) lets the ops team answer immediately without consulting the original developer. That traceability expectation is baked into Fed IT governance requirements.

Coding Standards — Frameworks

Coding conventions/standards are guidelines for styling and structuring code to add consistency and ensure team adherence to the same principles.

Framework

A framework is a reusable, highly optimized structure that acts as a building block, offering common functionality for developers to adapt to their needs, enhancing development speed, code clarity, and debugging.

Trigger Framework

A trigger framework is essential for structured, efficient trigger management in Salesforce.

Good Trigger Framework

A good trigger framework is scalable, traceable, reusable, atomic (ability to bypass specific triggers), and optimized (minimal SOQL calls, prevention of recursion, and shared result sets).

The five attributes of a good trigger framework — scalable, traceable, reusable, atomic, optimized — are a favourite exam list. Atomic (bypassable) is the one candidates most commonly forget; it is critical for data migration and integration scenarios where triggers must be suppressed for specific operations.

Coding Standards — Trigger & Error Logging Frameworks

Coding conventions/standards are guidelines for styling and structuring code to add consistency and ensure team adherence to the same principles.

Recommended Trigger Framework

Kevin O'Hara's SFDC Trigger Framework is recommended for large-scale projects. It features an abstract TriggerHandler base class to handle execution and prevent recursion, with child classes overriding specific trigger context methods.

Error Logging Framework

An error logging framework records errors in a structured manner, aiding in debugging and maintaining Salesforce orgs. Implementations should log errors to a custom object, enabling actions such as email notifications or task creation based on errors.

Interview angle

Interviewers will probe your trigger architecture stance. The correct answer at architect altitude is: one trigger per object, delegating to a handler class via a framework. Kevin O'Hara's pattern is the most commonly cited. Pair it with an error logging framework (log to a custom object, not just debug logs) and you demonstrate operational maturity — errors survive the transaction and are actionable by ops staff.

Coding Standards — Bypass Patterns, Test Data & Tools

Coding conventions/standards are guidelines for styling and structuring code to add consistency and ensure team adherence to the same principles.

Bypass Patterns

Hierarchical custom settings or custom permissions can be utilized to temporarily disable configurations (like validation rules or triggers) for specific users, profiles, or the entire org.

Test Data Factory

A test data factory contains reusable methods for generating test data, speeding up development and enhancing the reliability of unit tests.

Tools

Various tools can be utilized to manage code quality. These include source control system like Git, Salesforce Extensions for VS Code, Salesforce CLI, and CI/CD tool.

Fed angle

Bypass patterns are a change-control concern at regulated institutions. Using hierarchical custom settings to suppress triggers/validation rules for specific integration users is the auditable, reversible pattern — it leaves a configuration trail. Using a hard-coded boolean flag deep in a class is not auditable and will fail a code review. The Fed's IT risk team will want to see that bypass capability exists, is documented, and is controlled by access management (permission sets / custom permissions), not by ad hoc code edits.

Coding Standards — Apex Best Practices & TDD

Coding conventions/standards are guidelines for styling and structuring code to add consistency and ensure team adherence to the same principles.

Using Apex

Apex code should only be used for high performance batch processing needs or highly sophisticated implementation logic.

Apex Best Practices

There are various best practices that apply to the use of Apex code. These include bulkifying DML statements, using the built-in Limits methods, writing comments with a good balance between quality and quantity, avoiding SOQL queries and DML statements within loops, etc.

Using TDD

Test-Driven Development can be utilized for more modularized, flexible, and extensible code.

Interview angle

Governor limits are the Salesforce platform's hard ceiling — bulkification and avoiding SOQL-in-loops are the two most commonly cited violations in code reviews and static analysis scans. At architect level, the answer is not just "avoid them" but "enforce avoidance via static analysis (PMD rules) and code review checklists so the pipeline catches violations before they reach the sandbox."

Pull Requests — Comparison, Review & Standards

In Git-based workflows, a pull request is a proposal to merge changes from one branch into another.

Comparison

A pull request displays the differences between the content in the source branch and the content in the target branch. It represents a change to the code (adding, modifying, or deleting files) on a branch that the author would like to incorporate in another branch.

Review

In a pull request, collaborators can review and discuss the proposed set of changes before integrating them with the main codebase. Team members can be invited to comment and complete code reviews.

Quality & Standards

Every pull request should be reviewed by at least one other developer for code quality and adherence to standards.

Fed angle

At the Federal Reserve Bank of Chicago, GitLab merge requests serve as the mandatory segregation-of-duties control — a developer cannot merge their own feature branch to main. The "at least one other reviewer" requirement is a compensating control that satisfies both the bank's internal IT risk framework and external examination findings around code change governance. This is not a nice-to-have; it is a required control.

15 / 39

Pull Requests — Conversations, Testing & Information

In Git-based workflows, a pull request is a proposal to merge changes from one branch into another.

Conversations

A pull request gives a platform for having extended conversations about the changes between two branches.

Automated Testing

Pull requests help write better software by facilitating code review and showing the status of any automated tests.

Information

In a pull request, a summary of the proposed changes can be added, the changes made by commits can be reviewed, labels, milestones, and assignees can be added, and individual contributors or teams can be @mentioned.

Interview angle

The combination of automated test status + human code review inside a pull request is the canonical architect answer for "how do you prevent defects from reaching production?" The pipeline fails the merge if tests fail; the peer reviewer catches logic and standards issues the automated scan misses. Both gates must pass before merge — this two-layer model is what examiners and interviewers want to hear.

Code Review — Purpose & Preparation

Code review, also called peer review, is a quality assurance activity in which one or more people check the source code to catch bugs and ensure code quality and adherence to best practices.

Purpose

The purpose of code review is to enhance code quality and maintainability, detect bugs and issues early, and facilitate knowledge sharing across the development team.

Preparation

The goals of the code review process should be identified. A review checklist should be prepared. Code should be documented clearly to explain the logic and decisions.

Fed angle

In a regulated environment, code review documentation is part of the change record. The review checklist becomes an attestation artifact — the reviewer is certifying that the code meets specific quality and security criteria. Storing that checklist result in the GitLab merge request comment thread provides the audit trail that examiners look for when tracing a production incident back to the change that introduced it.

18 / 39

Code Review — Checklist & Effective Reviews

Code review, also called peer review, is a quality assurance activity in which one or more people check the source code to catch bugs and ensure code quality and adherence to best practices.

Review Checklist

A code review should check whether the code follows standards and best practices, including the use of naming conventions, correct formatting, and frameworks. Furthermore, the code should be scalable, performant, secure, easy to understand, and easily maintainable.

Effective Reviews

Code should be reviewed for logical correctness, efficiency, and alignment with project requirements. It should be checked for compliance with Salesforce best practices, including governor limits and bulkification. Tools like GitHub can be used for facilitating code reviews and discussions.

Governor limits and bulkification appear explicitly in the Salesforce code review checklist — this is an exam favourite. Any Apex code that performs SOQL or DML inside a loop, or that does not use collections for bulk operations, should fail the review.

Code Review — Automation & Common Issues

Code review, also called peer review, is a quality assurance activity in which one or more people check the source code to catch bugs and ensure code quality and adherence to best practices.

Automation & Resolution

The code review process should be automated as much as possible using tools such as static code analysis tools and automated testing tools. If issues are found and need to be resolved, changes should be committed to source control and run through CI/CD processes.

Issues

When evaluating the code in a Salesforce org, some issues that can be expected include multiple triggers on the same object, duplicated logic across Apex classes and Visualforce pages, existence of redundant Apex code that is no longer required due to new Salesforce features, etc.

Fed angle

Automating as much of the review as possible via CI pipeline gates is essential in a regulated org — it removes subjectivity and provides a consistent, documented enforcement record. At the Fed, "we ran static analysis and all findings were resolved or accepted with documented rationale" is the kind of attestation that satisfies the change advisory board. Manual review alone is insufficient evidence for an audit.

20 / 39

Code Review — Communication & Incorporating Feedback

Code review, also called peer review, is a quality assurance activity in which one or more people check the source code to catch bugs and ensure code quality and adherence to best practices.

Communication

During code reviews, specific, actionable feedback focused on code improvement should be provided. All feedback should maintain a positive and respectful tone. Developers should be encouraged to explain their decisions and reasoning when necessary.

Incorporating Feedback

Code should be revised based on review feedback, prioritizing critical changes. Disagreements or misunderstandings should be discussed and resolved collaboratively. Changes should only be merged after all critical issues are addressed and the code meets project standards.

Interview angle

The "only be merged after all critical issues are addressed" rule is the merge gate. In practice this means the pull request cannot be approved until all review threads are resolved — a feature enforced by GitLab/GitHub branch protection rules. As an architect you define the branch protection policy; as a lead you model the tone of constructive, actionable feedback that makes reviews a learning exercise, not a gatekeeping exercise.

21 / 39

Code Review — Evaluation

Code review, also called peer review, is a quality assurance activity in which one or more people check the source code to catch bugs and ensure code quality and adherence to best practices.

Evaluation

The effectiveness of the code review process should be regularly evaluated. Feedback should be solicited from team members on how to improve code reviews. Changes should be implemented to the code review process based on feedback and assessments.

Treating the code review process itself as something to be continuously improved — not just the code — is the maturity marker that distinguishes an architect mindset from a developer mindset. Tracking metrics like review turnaround time, defect escape rate, and recurrent findings enables data-driven process improvement.

AppExchange Security Review

The Salesforce security team conducts reviews before green-lighting solutions for the AppExchange.

Partner Commitment

Partners are responsible for leveraging the platform to protect customer data, with the security review process ensuring high standards.

Security Threats

Partners are responsible for protecting their solutions from the most common web security threats, such as injection, sensitive data exposure, session hijacking, and cross-site scripting.

Salesforce-Specific Security

CRUD/FLS must be considered when designing a solution since it is related to how objects interact within the solution. Failure to properly enforce CRUD/FLS security is the most common reason prospect AppExchange solutions fail the security review.

Interview angle

CRUD/FLS enforcement is the #1 AppExchange security review failure — memorize this. In code reviews and static analysis, PMD's Apex security category and the Salesforce Code Analyzer specifically flag CRUD/FLS violations. Enforcing it in code review means checking that every SOQL query and DML operation is preceded by an appropriate access check (Schema.sObjectType.isAccessible(), WITH SECURITY_ENFORCED, or the Security.stripInaccessible() pattern).

Static Code Analysis — Overview & Benefits

Static code analysis examines the code without executing it to identify potential vulnerabilities, coding errors, and adherence to coding standards.

Importance

Static code analysis ensures code quality, security, and performance within Salesforce applications.

Benefits

It detects code issues early in the development cycle, saving time and reducing costs, improves code security by identifying vulnerabilities that could be exploited, and ensures compliance with Salesforce best practices and coding standards.

Tools

Various Salesforce-specific tools are available for static code analysis. These include PMD, CodeScan, Clayton, and Salesforce CLI Scanner.

Fed angle

Static analysis in the CI pipeline is the automated quality gate that a regulated institution relies upon to produce a consistent, repeatable, documented code quality record for every change. When examiners ask "how do you know the code deployed to production meets your standards?" the answer is: "our GitLab CI pipeline runs PMD/Salesforce Code Analyzer on every merge request; the pipeline fails if critical findings exceed our defined threshold, and all findings are stored in the merge request record as evidence."

Static Code Analysis — PMD, CodeScan & Clayton

Static code analysis examines the code without executing it to identify potential vulnerabilities, coding errors, and adherence to coding standards.

Apex PMD

PMD is an open-source static code analysis tool that supports Apex and Visualforce. It finds common programming flaws like unused variables, empty catch blocks, unnecessary object creation, and so forth.

CodeScan

CodeScan is a comprehensive code analysis tool specifically designed for Salesforce, covering Apex, Visualforce, and Lightning components.

Clayton

Clayton is a cloud-based code quality tool tailored for Salesforce, offering automated reviews and coding standards enforcement.

PMD is the most exam-relevant tool because it is free, open-source, and widely referenced in Salesforce documentation and the Salesforce Code Analyzer (which bundles PMD under the hood). CodeScan and Clayton are paid commercial alternatives with broader Salesforce-native coverage.
26 / 39

Static Code Analysis — Salesforce CLI Scanner & Implementation

Static code analysis examines the code without executing it to identify potential vulnerabilities, coding errors, and adherence to coding standards.

Salesforce CLI Scanner

Salesforce CLI Scanner is a plugin for Salesforce CLI that leverages PMD and ESLint to scan Apex, Visualforce, Lightning Web Components (LWC), and Aura components.

Implementation

Salesforce DX can be used for a seamless integration of a static code analysis tool into the development workflow to routinely check the code.

Configuration

Static code analysis tools can be configured to match the project's coding standards and security policies.

Fed angle

The Salesforce CLI Scanner (sf scanner run) is the tool that slots into a GitLab CI job step. Because it wraps PMD and ESLint in a single CLI invocation, it can be configured once in the pipeline YAML and produces machine-readable output (JSON/CSV) that can be parsed to fail the build on critical violations. Configuring it to match the org's security policies — e.g., requiring CRUD/FLS checks — makes the pipeline a security gate, not just a style gate.

Static Code Analysis — CI/CD Integration

Static code analysis examines the code without executing it to identify potential vulnerabilities, coding errors, and adherence to coding standards.

Review & Address

Findings from the static code analysis tool can be reviewed and addressed as part of the code review process. The development team can be educated on common issues identified by the tool to prevent them in future coding.

CI/CD

Static code analysis can be automated as part of CI/CD pipelines to ensure consistent code quality and security checks before deployment. Tools like Jenkins, GitLab CI, and GitHub Actions can be configured to run static code analysis tools automatically on code commits.

Interview angle

The complete quality pipeline answer: (1) developer runs scanner locally before pushing; (2) GitLab CI job runs scanner on every commit to the feature branch; (3) merge request requires passing scan + passing tests + at least one approved peer review; (4) findings are stored in the MR as evidence. This end-to-end story demonstrates shift-left quality and gives regulators the documented control chain they require.

Requirements & Solutions

31 / 39

Requirement 1

Scenario

The company has multiple teams working on different projects. During code reviews, several inconsistently named variables and lack of best practices have been identified. The number of bugs has been increasing after each sprint. They need more time to understand the code and make changes after each sprint, which often delays the delivery of new features and updates. The architect must recommend methods and practices to face these challenges and improve the performance of the teams.

32 / 39

Solution 1

Solution

In order to improve code quality and consistency, the teams should define and follow coding standards. The standards should be enforced using a static code analysis tool. The performance of the teams can be improved by implementing a sprint review process that involves code reviews. The static code analysis tool should be used before the manual reviews. Also, development standards should be created, and the teams should be trained in those standards.

Fed angle

This solution pattern — define standards, enforce with static analysis, then human review — is exactly the layered control approach that a regulated institution's change advisory board expects. Static analysis removes the subjective and repetitive findings so that human reviewers can focus on business logic correctness, security, and architectural alignment. Training on standards ensures the feedback loop closes: findings become learning, not just blockers.

33 / 39

Requirement 2

Scenario

Most of the development teams have been using a CI/CD pipeline. The CTO would like to incorporate quality assurance techniques into the CI/CD processes to minimize defects in the applications, improve code quality, and also improve code security. In addition, the company has acquired code review software licenses to help the developers with code quality. The architect needs to recommend practices for secure code reviews.

34 / 39

Solution 2

Solution

Static code analysis and automated testing should be incorporated into the CI/CD pipelines to minimize defects in the applications. Before deployment to the testing sandbox, static code analysis and manual code review should be performed. For the improvement of code security, pull requests can be utilized for secure code reviews. Human efforts can be combined with automated checks by the code review software. A code review checklist should be generated to ensure consistency of reviews.

Interview angle

This solution illustrates the "shift-left" principle: quality gates run as early as possible in the pipeline (static analysis on commit, before reaching the sandbox). The checklist is what makes the human review consistent and auditable — reviewers attest to specific criteria, not just "looks good to me." This pattern directly maps to the exam scenario of "how do you improve code security in a CI/CD context."

Requirement 3

Scenario

The company's employees in France use a separate Salesforce org to manage its operations. It was implemented several years ago by a Salesforce Systems Integration Partner. Since then, various changes have been made to its Apex classes and Visualforce pages in response to customer requirements. The architect needs to evaluate the code and identify issues that should be addressed. In addition, the company wants to build a continuous integration process for the org to help manage code quality. All the developed code should be reviewed, tested, and validated in the upstream deployment process.

36 / 39

Solution 3

Solution

When evaluating the code in the org, the architect can expect various code quality issues, such as multiple triggers on the same object, duplicated logic across Apex classes and Visualforce pages, and obsolete Apex classes that are no longer required due to the introduction of new functionality by Salesforce. For the continuous integration process, a source control system such as Git, a CI/CD tool, Salesforce Extensions for VS Code, and Salesforce CLI can be utilized. Automated testing and test-driven development should be incorporated into the process. Development teams should perform code reviews to improve code quality.

Fed angle

The three expected code issues — multiple triggers, duplicated logic, obsolete classes — are the signature of an org that has grown organically without governance. Identifying them systematically (via PMD scan + architectural review) and then building a CI process around Git + pipeline + code review closes the governance gap. For a Fed context: the source control system provides the immutable audit trail of every change; the pipeline enforces quality gates; and code review provides human attestation before anything reaches the production org.

Apex Best Practices — Quick Reference

  • Use Apex only for high-performance batch processing or highly sophisticated logic (prefer declarative otherwise).
  • Bulkify DML statements — collect records in lists, perform a single DML at the end.
  • Never SOQL or DML inside a loop — violates governor limits; caught by PMD and code review.
  • Use Limits methods to monitor consumption at runtime.
  • Write comments with a balance of quality and quantity.
  • Use TDD for more modularized, extensible code.

Trigger Framework — Five Attributes

Scalable

Handles growing volume without architectural rework.

Traceable

Execution path is visible and debuggable.

Reusable

Logic shared across triggers via handler classes.

Atomic (Bypassable)

Specific triggers can be suppressed per user/profile/org via custom settings or custom permissions.

Optimized

Minimal SOQL calls, recursion prevention, shared result sets.

High-Yield Exam Gotchas

  • CRUD/FLS failure is the #1 AppExchange security review failure — always check object/field access before every SOQL and DML.
  • Static analysis runs before manual code review — automated checks first so human reviewers focus on logic, not style.
  • PMD is open-source and Apex/VF focused; Salesforce CLI Scanner wraps PMD + ESLint for LWC/Aura too.
  • Pull request = merge request in GitLab — same concept, different platform terminology. The "at least one reviewer" rule enforces segregation of duties.
  • Kevin O'Hara's SFDC Trigger Framework is the recommended framework for large-scale projects; abstract TriggerHandler base class, child classes override context methods.
  • Bypass patterns use hierarchical custom settings or custom permissions — not hard-coded booleans. Custom settings/permissions are auditable, reversible, and access-controlled.
  • Error logging to a custom object (not just debug logs) is the production-grade pattern — errors survive the transaction and can trigger notifications or tasks.
  • TDD produces more modularized, flexible, extensible code — exam may ask why TDD is recommended for Apex.

Fed angle — Tying it together

For the Federal Reserve Bank of Chicago Salesforce Platform Engineer role, every quality pillar maps to a specific control requirement: Coding standards ensure consistency and traceability across team changes; pull/merge requests enforce segregation of duties (no self-merge) and provide the change record; code review with a formal checklist provides the human attestation that change-advisory boards require; and static analysis in the CI pipeline produces an automated, objective, repeatable quality record for every commit — the kind of documented evidence that satisfies examiners during audits and IT risk reviews. When you can describe the full chain from coding standard to pipeline gate to merge approval to deployment, you are speaking at the architect altitude the role requires.
