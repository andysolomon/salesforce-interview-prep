Page 4 · Introduction

Introduction

For a successful deployment strategy, it is important to consider various components and tools. Deployment components include metadata components, data components, governance, change management, test plans and scripts, and rollback strategy.

On the other hand, there are various native and third-party deployment tools. They include Salesforce DX, Salesforce CLI, Metadata API, Ant Migration Tool, Change Sets, packages, automated testing tools, and CI/CD tools.

Fed angle

This deck is the closest to a Federal Reserve DevOps engineer's daily work. The Fed role requires GitLab CI/CD pipelines for automated Salesforce deployments. Every concept here — governance, change management, automated testing gates, rollback strategy — maps directly to the Fed's change-control framework and IT risk management requirements. Master this deck cold.

Page 5 · Deployment Components Overview

Deployment Components

The three pillars of a successful Salesforce deployment strategy.

Metadata & Data

Metadata components are building blocks of customizations that are moved between Salesforce environments. Data components are records of Salesforce objects that are migrated between orgs.

Governance & Change Management

A governance framework is a set of policies and procedures that guide how changes are managed and deployed. It includes tracking, reviewing, and approving changes.

Test & Rollback Strategies

Test plans and scripts are used to ensure that a deployment does not negatively affect functionality. A rollback strategy can be used to revert changes if a deployment causes issues in production.

Interview angle

When asked "what tools do you use to deploy Salesforce changes?", don't just name one. The architect answer maps tool to scenario: Change Sets for small declarative changes between affiliated orgs; Metadata API / Ant for scripted multi-stage pipelines; Salesforce DX + unlocked packages for source-driven, version-controlled builds; CI/CD (Copado, Jenkins, GitLab) for automated, auditable release pipelines.

Deployment Components

The components of a successful Salesforce deployment strategy focus on aspects such as metadata, data, governance, testing, and rollback.

Metadata Components

Metadata components are the building blocks of Salesforce customization, such as custom objects, custom fields, Apex classes, Lightning web components, Visualforce pages, etc.

Data Components

Data components represent records of Salesforce objects that need to be migrated between environments.

Metadata and data are separate concerns in a deployment plan. Metadata moves via deployment tools (CLI, change sets, packages); data moves via data migration tools (Data Loader, Dataloader.io). Conflating the two is a common exam trap.
Page 9 · Governance & Change Management

Deployment Components

The components of a successful Salesforce deployment strategy focus on aspects such as metadata, data, governance, testing, and rollback.

Governance

A governance framework is a set of policies and procedures that guide how changes are managed and deployed across different environments.

Change Management Process

A change management process focuses on establishing procedures for tracking, approving, and deploying changes, ensuring that all stakeholders are aligned and informed.

Fed angle

At the Federal Reserve, governance is not optional — it is mandated by the Fed's IT Risk Management Policy and FISMA. Every deployment must be traceable: who requested the change, who approved it, what was tested, when it was deployed, and what the rollback plan is. A GitLab pipeline that requires merge-request approvals from two reviewers before triggering a deployment stage directly implements this governance framework in code.

Page 10 · Test Plans & Rollback Strategy

Deployment Components

The components of a successful Salesforce deployment strategy focus on aspects such as metadata, data, governance, testing, and rollback.

Test Plans & Scripts

Test plans and scripts are detailed documents used to ensure that a deployment does not negatively impact the existing functionality.

Rollback Strategy

A contingency plan is necessary to revert changes if a deployment causes unexpected issues in the production environment.

Interview angle

Interviewers testing architect-level judgment will ask: "What is your rollback plan if a production deployment fails?" The answer must go beyond "we'll re-deploy the old code." Walk through: (1) pre-deployment sandbox backup as a restore point, (2) destructiveChanges.xml to remove new components, (3) Quick Deploy of a validated package to speed re-deployment. This demonstrates you have thought through the failure path, not just the happy path.

A GitLab pipeline replaces Copado/Flosum for teams that build on open-source tooling: stages are defined in .gitlab-ci.yml, the Salesforce CLI runs in pipeline jobs to deploy metadata, and merge-request approval rules (protected branches) enforce the approval gate that change management requires. Automated test execution in the pipeline produces the artifact evidence package regulators expect.

Page 16 · Salesforce DX — Deep Dive

Salesforce DX

Salesforce Developer Experience (DX) supports building and deploying applications on the Salesforce platform in a more efficient, flexible, and controlled manner.

Source-Driven Development

Salesforce DX enabled source-driven development. Source code and metadata exist in a version control system.

CI/CD Integration

It facilitates continuous integration and delivery using tools such as CircleCI, Jenkins, and Travis CI.

Salesforce CLI

Salesforce CLI automates various tasks, from org management to data import/export, streamlining the deployment process.

Metadata API

Metadata API can be used to retrieve and deploy changes using the development workflow called the org development model.

Unlocked Packages

Unlocked packages can be used to organize existing metadata, package an app, extend an app, or package new metadata.

Interview angle

When asked about source-driven development, explain the two models: the org development model (Metadata API retrieves from a persistent org, changes live in the org first) vs. the package development model (source is the truth, scratch orgs are spun up from source, unlocked packages version the artifact). For regulated environments, the package model provides a stronger audit trail because the package version is an immutable, versioned artifact.

Page 17 · Salesforce CLI — Deep Dive

Salesforce CLI

Salesforce CLI is a command-line tool that is part of Salesforce DX.

Environment & Deployment Automation

Salesforce CLI streamlines various tasks, such as creating and managing Salesforce environments, pushing and pulling source code, executing tests, and deploying metadata.

Data & Metadata Commands

The CLI provides commands for working with data and metadata, which allow for the automation of deployment processes.

CI Integration

Salesforce CLI commands make it easier to integrate with Continuous Integration (CI) systems for automated testing and deployment.

Fed angle

In a GitLab pipeline, the Salesforce CLI is invoked directly in pipeline job scripts: sf project deploy start to deploy metadata, sf apex run test to run Apex tests, sf org create scratch to spin up ephemeral test environments. Each CLI command produces exit codes and structured output that the pipeline captures as job artifacts — the machine-readable evidence trail that audit and compliance teams require.

Page 18 · Metadata API — Deep Dive

Metadata API

Metadata API can be used to move metadata between orgs during the development lifecycle and deploying large metadata changes from development.

Production → Local

Metadata can be moved from production to the local file system to make development changes.

Scratch Org Integration

Metadata changes can be moved to and from a scratch org, which can be used along with the local file system for development and testing.

Sandbox Integration

Metadata can be moved to sandboxes for integrating changes, testing, and collaboration.

Source Control → Production

In the final step of the development cycle, metadata can be moved from a source control system such as Git to production.

Large-Scale Changes

Metadata can be moved for large changes, such as splitting or merging production orgs.

The Metadata API is the underlying engine that the Salesforce CLI, Ant Migration Tool, and Change Sets all use. Understanding the API is what lets you troubleshoot when those higher-level tools fail.
Page 19 · Ant Migration Tool — Deep Dive

Ant Migration Tool

The Ant Migration Tool is a Java/Ant-based command-line utility used for moving metadata between a local directory and a Salesforce org.

Populating Test Environments

The tool can be used for development projects that require populating a test environment with a lot of Setup changes.

Scripted Multi-Stage Releases

It can be used for scripted retrieval and deployment of components, making multi-stage release processes much more efficient.

Repetitive Deployments

It can be used for repetitive deployments using the same parameters. The same process for deploying changes can be reused.

Scripting Environments

It can be used for deployments in a scripting environment, such as for migrating changes from staging to production.

Scheduled Batch Deployments

Batch deployments can be scheduled. For example, a deployment can be scheduled for midnight or changes can be pulled every day.

Interview angle

The Ant Migration Tool is increasingly superseded by the Salesforce CLI for new projects, but it remains relevant for legacy orgs and teams that have existing Ant-based scripts. On the exam and in interviews, the key differentiator vs. Change Sets is: Ant supports automation and scripting; Change Sets do not. If a scenario requires automation or multi-stage release scripting and does not involve a CI/CD platform, Ant Migration Tool is the answer.

Page 20 · Change Sets — Part 1

Change Sets

Change Sets can be used to move customizations between Salesforce orgs that are affiliated with a production org.

Outbound Change Set

Once a deployment connection is created, an outbound change set can be created and uploaded to send changes to another org.

Component Selection

When selecting components for an outbound change set, dependent components and profile settings can be added.

Inbound Change Set

The receiving org sees the outbound change set as an inbound change set, which must be deployed for the changes to take effect.

Validation

A change set can be validated before deploying changes. Validation allows viewing success or failure messages received with an actual deployment.

Deployment Status

The deployment of change sets can be tracked on the Deployment Status page. The change set detail page shows completed deployments.

Page 21 · Change Sets — Part 2

Change Sets

Change Sets can be used to move customizations between Salesforce orgs that are affiliated with a production org.

Authorizing Inbound Changes

Inbound changes from an org can be authorized by selecting Allow Inbound Changes on the Deployment Settings page in Setup.

Cannot Be Automated

The use of change sets cannot be automated based on metadata differences in an org.

Org Locking During Validation/Deploy

The originating org is locked while validating an outbound change set. The target org is locked while deploying an inbound change set. When locked, it is possible to read and write data, but any Setup changes that would modify the metadata are not possible.

Flow Version Limitation

Only one version of a flow can be included in a change set. If there is no active version, the latest inactive version is used.

Change Sets cannot be automated — this is the most-tested Change Set limitation. If a scenario requires automation, CI/CD, or scripting, Change Sets are disqualified as the answer regardless of other factors.

Fed angle

The org-locking behavior of Change Sets is a critical operational risk in a regulated environment: validating or deploying a change set locks the org, blocking all Setup changes from other team members. For a central bank with concurrent development streams, this is unacceptable during business hours. This is a concrete, defensible reason why the Fed's DevOps practice should use Salesforce CLI + GitLab pipeline rather than Change Sets for anything beyond trivial one-off moves.

Page 22 · Packages — Deep Dive

Packages

Unlocked packages can be utilized to organize and deploy metadata for internal business applications across different environments.

Package Lifecycle

Each unlocked package has a distinct life cycle. A new package version is created after adding, removing, or changing package metadata. A package version is an immutable artifact that contains specific metadata and features.

Multi-Environment Installation

A package version can be installed in various Salesforce environments, including sandboxes and scratch orgs, facilitating testing and staging before deployment to production.

Version Control Integration

Unlocked packages can be integrated with a version control system like Git. Version control allows deploying updates and rolling back changes with greater precision.

Interview angle

The immutable artifact property of unlocked package versions is the key differentiator from other deployment methods. Once a package version is created, it cannot be changed — only superseded by a new version. This gives you a reliable rollback target: if v1.3 causes a production issue, you deploy v1.2. No destructiveChanges.xml needed. This is the gold-standard deployment pattern for teams that operate multiple production orgs or have strict change-control requirements.

Page 23 · Automated Testing Tools — Deep Dive

Automated Testing Tools

Many third-party automation tools, such as Selenium, are available for Salesforce testing. They standardize testing processes and reduce the risk of human error.

Identify Issues Before Production

Automated testing tools ensure that deployments are successful by identifying potential issues before they affect users. They automate the testing process, allowing for quicker deployment.

Common Test Types

The common types of tests that can be automated include unit tests, functional tests, integration tests, regression tests, load tests, and UI tests.

Advantages

Advantages of automated testing include increased test coverage, early bug detection, time and cost savings, cleaner existing code, reliable deployments, and reduced human errors.

Fed angle

In a regulated environment, automated testing is a control, not a convenience. At the Fed, Apex test execution at the RunSpecifiedTests or RunLocalTests level during deployment is a required gate — not optional. Running Selenium or a Salesforce-specific UI testing framework (e.g., Provar) in a GitLab pipeline stage produces a test results artifact that can be attached to the change ticket as evidence of pre-production validation, satisfying IT audit requirements.

Page 24 · CI/CD Tools — Part 1

CI/CD Tools

Third-party CI/CD tools streamline development workflows and are crucial for continuous integration, continuous deployment, and continuous delivery.

Continuous Integration (CI)

Continuous Integration (CI) focuses on automatically moving work items through a release pipeline. Packages are combined and tested before being promoted to production, ensuring that no issues arise upon release.

Continuous Deployment (CD)

Continuous Deployment (CD) focuses on automatically deploying changes to a downstream environment. A change is deployed as soon as it has been approved and merged into version control, ensuring the latest changes.

Continuous Delivery

Continuous Delivery is the ultimate goal of CI/CD. It focuses on releasing added value and new functionalities as soon as possible.

Interview angle

Know the CI vs. CD distinction precisely. CI = automatically running tests when code is merged (validating the build). CD = automatically deploying the artifact to a downstream environment after CI passes. Continuous Delivery adds a human approval gate before the final production push — this is the variant most regulated organizations implement, since full Continuous Deployment to production without human approval is rarely acceptable in a change-controlled environment.

Page 25 · CI/CD Tools — Part 2

CI/CD Tools

Options for continuous integration and continuous deployment include standard automation tools and Salesforce-specific DevOps platforms.

Reduces Manual Work

CI/CD automates repetitive, error-prone manual processes, increases development velocity, and significantly saves developer time.

Version Control as Source of Truth

A successful CI/CD process is usually rooted in version control as the source of truth for new development work.

Pipeline Automation

Automation is used to validate deployment packages, carry out tests, and promote work items along the pipeline.

Standard Automation Tools

Standard automation tools include CircleCI, Jenkins, and Travis CI. Major Git hosting platforms also offer CI/CD capabilities.

Salesforce-Specific Platforms

Salesforce-specific tools like Copado and Flosum offer CI/CD as part of their DevOps solutions.

Fed angle

The Federal Reserve Chicago uses GitLab, which falls under "major Git hosting platforms that also offer CI/CD capabilities." A GitLab .gitlab-ci.yml pipeline for Salesforce deployments would define stages such as: validate (run sf project deploy validate), test (run Apex tests via CLI), deploy-uat (deploy to UAT sandbox, gated by manual approval), and deploy-prod (deploy to production, gated by two required approvers matching the change management policy). Each stage produces a job artifact for the audit trail. This is Continuous Delivery — not full Continuous Deployment — because the production gate is human-approved.

Business Scenario — Cosmic Tech Solutions

Read the business scenario below and determine the most appropriate solutions for the company's requirements.

Scenario

Cosmic Tech Solutions, a leading software development company that specializes in cloud-based applications, is undergoing a strategic shift to enhance its deployment processes across its Salesforce environments. The company currently utilizes a diverse set of Salesforce clouds, including Sales Cloud for CRM, Service Cloud for customer service management, and custom applications built on the Lightning platform to cater to specific business needs.

With a growing global presence and an increasing number of complex projects requiring frequent releases, the company faces the challenge of streamlining its deployment strategy to ensure efficient, error-free releases that align with business objectives and technical requirements.

The company's Salesforce architect is required to evaluate the existing deployment processes and recommend the components and tools for various business requirements to establish a successful deployment strategy.

Page 28 · Section

Requirements & Solutions

Page 29 · Requirement 1

Requirement 1

Scenario

The company would like to streamline and automate the deployment of customizations to various sandbox environments during the build phase. Once user acceptance testing is complete in the UAT environment, the deployment to the production org should also be automated.

Also, metadata changes need to be tracked in Salesforce throughout the development lifecycle across various environments. Furthermore, the company is looking for ways to reduce the deployment time and wants a rollback strategy for new features deployed to production.

Page 30 · Solution 1 — Part 1

Solution 1 (Part 1)

Solution

In order to streamline and automate the deployment of customizations to various sandbox environments during the build phase, a CI/CD tool such as Jenkins or a DevOps platform such as Copado should be utilized. A release pipeline can be built to deploy to sandboxes and production.

The CI/CD tool can automatically move work items through the release pipeline, combining and testing changes. It can also automatically deploy a change to a downstream environment once it has been approved and merged into version control. Metadata changes can be tracked in Salesforce using a third-party tool available in the AppExchange marketplace.

Fed angle

Mapping this solution to a GitLab pipeline: a .gitlab-ci.yml defines the pipeline stages (dev sandbox → integration sandbox → UAT → production). Each promotion between stages is triggered by a merge to a protected branch, which requires a passing CI stage and at minimum two approvals. The "approved and merged into version control" trigger is GitLab's merge-request workflow. Metadata tracking can be handled by tools like Gearset or Copado's metadata comparison feature installed from AppExchange.

Page 31 · Solution 1 — Part 2

Solution 1 (Part 2)

Solution

Before the deployment of a new feature to production, a sandbox can be created from production for a backup of the existing metadata. After the deployment of the new feature, if a rollback is required, destructiveChanges.xml can be used to delete the new components, and metadata from the sandbox can be deployed from the sandbox to production.

To reduce the deployment time, recent deployment validations and the Quick Deploy feature can be utilized. Also, specific tests can be run for deployments by using the RunSpecifiedTests test level.

Interview angle

Three distinct deployment time-reduction techniques are on this slide — learn all three: (1) Quick Deploy: if a validation passed within the last 10 days, you can deploy without re-running tests, saving significant time for large orgs. (2) RunSpecifiedTests: only run the tests relevant to the components being deployed, rather than all local tests. (3) Sandbox backup as rollback baseline: a full-copy or partial sandbox refreshed from production just before a release gives you a known-good restore point. Each technique addresses a different constraint (test time, time-to-revert) — an architect answer names the right one for the right constraint.

Page 32 · Requirement 2

Requirement 2

Scenario

The company has set up two new regional production instances for its operations in APAC and EMEA. A development team in the United States has created a custom application for managing different types of software solutions that needs to be deployed to the new production instances. The regional development teams should be able to maintain and modify the application metadata.

Also, the company wants to establish a deployment plan for releasing simple configuration changes and enhancements, such as a new flow. The architect needs to recommend a suitable tool while outlining its benefits and any valid considerations related to automation and deployment.

Page 33 · Solution 2 — Part 1

Solution 2 (Part 1)

Solution

Deployment tools such as the Ant Migration Tool or Salesforce Extensions for VS Code can be utilized to deploy the custom application metadata to the new production instances.

For simple configuration changes, such as a new flow, change sets can be used to migrate the metadata between different environments. They offer an easy and declarative way of deploying components, including dependent components, between orgs that are affiliated with a production org. To use change sets, a deployment connection must be established. An org that needs to receive customizations through a change set must allow inbound changes from the source org.

Interview angle

This solution pairs two tools to address two different requirements: Ant / VS Code Extensions for the initial large metadata deployment to new orgs (one-time, complex migration) and Change Sets for ongoing simple changes (recurring, declarative, low-complexity). The architect answer always matches the tool to the constraint. Change Sets are recommended here because the changes are simple and the orgs are affiliated with the same production — not because they are the best tool in general.

Page 34 · Solution 2 — Part 2

Solution 2 (Part 2)

Solution

There are other important considerations for using change sets, especially for migrating a flow. The use of change sets cannot be automated based on metadata differences in an org. Only one version of a flow can be included in a change set, and if there is no active version, the latest inactive version is used.

Although changes sent using a change set can be validated, the originating org is locked while validating an outbound change set. The target org is locked while deploying an inbound change set. When an org is locked, it is possible to read and write data, but any Setup changes that would modify the metadata are not possible.

This slide is the exam "gotcha cluster" for Change Sets: (1) cannot be automated, (2) only one flow version, (3) org locking during validate and deploy. Any one of these limitations, if present in a scenario, may disqualify Change Sets as the recommended tool.

High-Yield Exam Gotchas

  • Change Sets ≠ automation — the moment a scenario says "automated" or "CI/CD," Change Sets are off the table.
  • Unlocked package versions are immutable — this is the gold-standard rollback mechanism; no need for destructiveChanges.xml.
  • Quick Deploy requires a passing validation within 10 days — it skips test execution, not deployment itself.
  • RunSpecifiedTests — runs only the tests you name; requires 75% code coverage on the components being deployed.
  • Metadata API is the engine under the hood — CLI, Ant, and Change Sets all call Metadata API; direct API use gives you the most control.
  • Data migration ≠ metadata deployment — never mix these in an architecture answer; they use different tools and different failure modes.
  • org development model vs. package development model — key distinction for DX questions: org model = Metadata API as source of truth; package model = VCS as source of truth.
  • CI = validate/test; CD = deploy after approval — in regulated environments, full Continuous Deployment to production (no human gate) is usually not permitted; Continuous Delivery (with approval gate) is the acceptable pattern.

Fed angle — Tying it together

For the Federal Reserve Chicago DevOps / platform engineer role, the deployment strategy answer is: Salesforce CLI + GitLab CI/CD pipeline + unlocked packages + approval gates. Here is how the components map: (1) Metadata Components are tracked in a GitLab repo as the source of truth. (2) Governance & Change Management is enforced by GitLab protected branches + required merge-request approvals (two approvers = four-eyes principle). (3) Test Plans are executed as a mandatory test pipeline stage via sf apex run test — job artifacts are the evidence. (4) Rollback Strategy: unlocked package versioning provides the cleanest rollback (redeploy prior version); for org-model deploys, a pre-production sandbox backup + destructiveChanges.xml is the documented contingency. (5) Auditability: every pipeline run is logged, every merge is attributed to a person, every approval is timestamped — this is the audit trail regulators require. Change Sets have no place in this architecture because they cannot be automated and they produce no machine-readable audit artifact.
