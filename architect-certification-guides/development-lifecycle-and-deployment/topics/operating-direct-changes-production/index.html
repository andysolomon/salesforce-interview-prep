Page 4 · Introduction

Introduction

Organizations leveraging Salesforce must navigate the delicate balance of implementing urgent updates in their production environment against the backdrop of ensuring operational stability and security compliance. It is important to understand the critical considerations and implications of directly incorporating requests in a production environment.

Appropriate strategies must be adopted for addressing immediate issues in Salesforce-driven operations. Salesforce architects need to make informed decisions about making changes directly in production. Urgent fixes should enhance system functionality without compromising data integrity or user experience. Furthermore, best practices should be considered for managing direct changes in production, emphasizing the importance of thorough testing, stakeholder communication, and compliance with industry standards.

Fed angle

At a central bank, every change to a production system — even a low-impact field addition — sits within a formal change-management process. The tension described here (urgency vs. stability) is the core of any regulated institution's change-control policy. "Urgent updates" must still be traceable, authorized, and documented; skipping those steps is an audit finding, not a shortcut.

Page 5 · Incorporating Requests Directly in Production

Incorporating Requests Directly in Production

Four lenses frame the decision to make a change directly in production versus in a sandbox.

Changes in Sandbox

A sandbox is a risk-free testing environment that should be used for changes that require extensive testing or could impact system-wide operations, such as new workflow steps.

Changes in Production

Direct changes in production should be approached with caution by utilizing steps such as double-checking, clear communication, phased release, and training.

Implications

Implications of direct changes in production include the possibility of errors, conflicts with other concurrent updates or integrations, and regulatory and compliance risks.

Strategies

Certain strategies can be utilized for direct changes in production, including a dedicated process for hotfixes, review and authorization, and using release management tools.

Interview angle

The exam frequently presents a scenario and asks which type of change can or cannot be made directly in production. Know the hard rule: Apex code (and other metadata requiring a sandbox deploy) can never be written or edited directly in production. Low-impact declarative changes (custom fields, picklist values, reports, dashboards) can be made in production with precautionary steps.

Page 7 · Direct Changes in Production — Sandbox, Accuracy & Assessment

Direct Changes in Production

Organizations typically have a production org with live data and one or more sandbox environments for development and testing, ensuring changes do not affect live data or disrupt business operations.

Risk-Free Testing

A sandbox serves as a risk-free testing environment, separate from the live production org, which enables safe simulation of changes.

Accuracy

Sandboxes mirror the production org's tools and functionality and facilitate accurate testing and development without risking live environment integrity.

Assessment

Before making a change in a sandbox or directly in the live environment, the nature of the change and its potential impacts should be assessed.

Fed angle

A central bank's sandbox strategy is a control in its own right. Auditors expect evidence that changes were tested in an environment that mirrors production metadata (not just a partial copy) before being promoted. Sandbox type selection — Developer, Developer Pro, Partial, Full — should be part of the formal change ticket, not an ad hoc decision.

Page 8 · Direct Changes in Production — Coding, High & Low Impact Changes

Direct Changes in Production

Organizations typically have a production org with live data and one or more sandbox environments for development and testing, ensuring changes do not affect live data or disrupt business operations.

Coding Changes

Coding changes require a sandbox since code cannot be written directly in a production org.

High Impact Changes

For changes that require extensive testing or could impact system-wide operations, such as new workflow steps or global feature implementations, sandboxes should be used for development and testing.

Low Impact Changes

Many low impact changes, such as new custom fields, picklist values, reports, and dashboards, can be made in production after taking precautionary steps to avoid any unforeseen changes.

Interview angle

This slide contains a hard exam fact: Apex code cannot be written directly in a production org — ever. Any scenario that asks whether a developer can "quickly fix a bug directly in production" has one correct answer: no. The fix must go through a sandbox and be deployed via a change set or deployment tool.

Page 9 · Direct Changes in Production — Caution, Double-Checking & Communication

Direct Changes in Production

Organizations typically have a production org with live data and one or more sandbox environments for development and testing, ensuring changes do not affect live data or disrupt business operations.

Direct Changes

Direct changes in the production org should be approached with caution. Steps should be taken to ensure adoption and avoid negative impacts.

Double-Checking

Thorough double-checking should be performed to make sure that the change does not have any unwanted direct or indirect impact and no one else is using the change for other purposes.

Clear Communication

Changes should be clearly communicated to the team before they are made. Users in the organization should not be surprised with changes.

Double-checking for indirect dependencies is especially important in mature orgs with many automations — a picklist value rename, for example, can silently break formula fields, workflow criteria, and report filters that reference the old value.
Page 10 · Direct Changes in Production — Phased Release & Training

Direct Changes in Production

Organizations typically have a production org with live data and one or more sandbox environments for development and testing, ensuring changes do not affect live data or disrupt business operations.

Phased Release

The change should be validated by other admins, superusers, or the change requester before it is released to the rest of the organization.

Training

User training can be provided to get users on board with the change, explaining the change and how best to apply it.

Fed angle

Phased release and superuser validation are lightweight change-control practices that satisfy segregation of duties even for low-impact production changes. At a central bank, even a picklist addition should have at least a second pair of eyes sign off before general availability — this is exactly the kind of lightweight control that bridges the gap between "too small for a full change ticket" and "completely uncontrolled."

Page 11 · Implications of Direct Changes in Production

Implications of Direct Changes in Production

Before making a direct change in production, the implications should be considered.

Errors

Direct modifications bypass critical testing, leading to errors that are harder to diagnose and rectify without affecting users.

Conflicts

Changes might conflict with other concurrent updates or integrations, causing unexpected behavior or system failures.

Risks

Regulatory and compliance risks may increase if changes impact data security or user privacy without undergoing rigorous validation.

Interview angle

The three implications — errors, conflicts, risks — map to three exam question patterns: (1) why is direct production change dangerous operationally? (errors bypass testing); (2) what technical risk exists in a busy org? (conflicts with concurrent changes/integrations); (3) what risk matters most in regulated industries? (regulatory and compliance exposure when changes touch data security without validation).

Fed angle

Regulatory and compliance risk is not abstract at a central bank. Any change that touches access controls, encryption settings, or data visibility without a documented approval trail is a potential SR 11-7 or OCC finding. The cost of a direct-production shortcut can be a formal supervisory action — far exceeding the cost of doing it through proper channels.

Page 12 · Strategies for Direct Changes in Production

Strategies for Direct Changes in Production

Certain strategies can be utilized for making direct changes in production.

Hotfixes

A dedicated process can be established for emergency hotfixes, including criteria for what constitutes an emergency change warranting direct production updates.

Review

Close collaboration should be fostered between developers, QA team, and stakeholders to ensure changes are thoroughly reviewed and authorized.

Execution

Salesforce's release management tools, including deployment tools, and sandbox refresh cycles should be utilized to plan and execute changes methodically.

The hotfix process requires pre-defined criteria — not every urgent request qualifies. A documented threshold (e.g., P1/Sev-1 impacting revenue or data integrity) prevents "emergency" from becoming a loophole that bypasses normal change control for convenience.

Page 16 · Requirement 1

Requirement 1

Scenario

A developer has discovered a serious defect in production. Thousands of customer account records will be affected, resulting in incorrect data and causing major brand damage. A Salesforce consultant has suggested replacing the defective text field with a new picklist field directly in production. The page layout will also need to be modified accordingly. The architect needs to provide urgent assistance to resolve the issue.

Page 17 · Solution 1

Solution 1

Solution

The architect should collaborate closely with the consultant to review and implement the changes carefully in the production environment. This pragmatic approach allows for real-time problem-solving and damage control, minimizing the impact on the brand while ensuring that changes are made thoughtfully and with oversight.

Interview angle

This scenario tests whether you know that replacing a text field with a picklist field and modifying a page layout are both declarative (non-code) changes — they fall into the low-impact category and can be made directly in production. The key architect behavior is oversight and collaboration, not necessarily routing through a sandbox. The exam rewards recognizing this distinction.

Fed angle

Even for a low-impact direct-production change at a regulated institution, the architect's presence as a second reviewer satisfies segregation of duties. The "thoughtfully and with oversight" language is not just good practice — at the Fed it is a control requirement. Document who reviewed, who approved, and what was changed, even for a picklist field addition.

Page 18 · Requirement 2

Requirement 2

Scenario

The company operates in a strict regulatory environment with dedicated teams for development, quality assurance, security, and release management. One of the Salesforce development teams is midway through a large enterprise project. It follows the agile development methodology and has four-week sprints. A severe production issue has been identified at the start of a sprint. The root cause is a bug in an Apex class deployed to production two months ago. Dozens of users use the production org regularly. The architect needs to recommend a suitable approach to address the bug.

Page 19 · Solution 2

Solution 2

Solution

Since the serious production issue is tied to a bug in Apex code, understanding the scope and effect of the bug on existing data is crucial. Investigating potential data impacts would help assess the severity of the issue and effectively plan the necessary corrective actions. A hotfix branch should be created for the swift isolation and resolution of the bug without disrupting the current sprint's workflow. However, due to the strict regulatory environment, stakeholder approval should be obtained for implementing the hotfix to ensure compliance and transparency. Also, it is important to note that Apex code cannot be written or updated directly in production.

Interview angle

This is the canonical contrast to Solution 1: an Apex bug cannot be fixed directly in production — full stop. The correct approach is hotfix branch + stakeholder approval + deployment via sandbox. In a regulated agile team, a hotfix branch isolates the fix from the active sprint, preventing sprint contamination while enabling the rapid deployment path. Know this three-step pattern cold.

Fed angle

In a strict regulatory environment, "stakeholder approval" is not a formality — it is the authorization record that satisfies change-control audit requirements. The hotfix must have a change ticket, an approver, and a deployment log. The fact that Apex code cannot go directly to production is also a built-in platform control that regulators appreciate: it forces the four-eyes principle by requiring a sandbox intermediate step and a deployment action.

High-Yield Exam Gotchas

  • Apex code cannot be written or updated directly in production — this is a hard platform constraint, not just a best practice. Any scenario suggesting a developer "fix the bug in production" is wrong.
  • Picklist fields, custom fields, reports, and dashboards are low-impact changes that can be made in production — but only after double-checking dependencies and communicating to the team.
  • Phased release means having admins, superusers, or the change requester validate the change before it goes to all users — it is not the same as a full sandbox-to-production promotion cycle.
  • Double-checking for indirect impact is critical: renaming a picklist value can silently break formulas, workflow criteria, and report filters that reference the old value.
  • In a regulatory environment, stakeholder approval is mandatory for hotfixes — even when urgent. The approval is the audit record; skipping it turns a hotfix into a compliance violation.
  • Hotfix branch ≠ hotfix in production: a hotfix branch is created in version control (or a sandbox), the fix is developed there, then deployed. It is not synonymous with editing production directly.
  • The architect's role during a direct production change is oversight, not execution — ensure changes are reviewed, thoughtfully made, and documented.

Fed angle — Tying it together

For a central bank platform engineer, the highest-risk pattern is an "urgent" fix that bypasses all controls. The platform's own constraint (no direct Apex editing in production) is an ally — it forces the four-eyes / sandbox-deploy path for all code changes. For declarative changes, the architect must supply the control discipline: double-check, communicate, phase, document. Every production change — regardless of size — should leave an audit trail: who requested it, who reviewed it, who approved it, and what changed. That trail is the evidence package regulators and senior leadership require during audits and incident post-mortems.
