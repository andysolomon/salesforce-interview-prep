Page 4 · Introduction

Introduction

In Salesforce, technical reference data is used to categorize other data, standardize terminology, and ensure consistency across systems. It serves as a reference within applications, such as picklist values, configuration settings, or other standardized data sets.

Custom Metadata Types are typically used to store and manage technical reference data that can be deployed across Salesforce environments.

Various considerations are applicable to the management and deployment of technical reference data. For example, when using Salesforce objects to store the data and use it in Apex, object relationships and governor limits should be considered.

Fed angle

At a regulated institution, technical reference data (rate tables, product codes, service tier definitions) must move between environments in a controlled, auditable way. Custom Metadata Types are the preferred vehicle precisely because they travel with metadata deployments — subject to the same change-control review and GitLab CI/CD pipeline gates that govern code. Object-stored reference data requires a separate data-loading step, adding operational complexity and audit burden.

Technical Reference Data

Using Technical Reference Data

Technical reference data serves as a reference within applications, such as picklist values, configuration settings, or other standardized data sets. It is used for application functionality and not user-generated content.

Custom Metadata Types

A custom metadata type and its records can be created to store and manage technical reference data such as configuration settings for an application. Metadata API or Change Sets can be used for deployment.

Considerations

Important considerations for the management and deployment of technical reference data are related to the use of a source of truth, governance, data loading, object relationships, and governor limits.

Page 8 · Technical Reference Data — Custom Metadata Types & Picklists

Technical Reference Data

Technical reference data refers to data used across the organization to categorize other data, standardize terminology, and ensure consistency across systems.

Custom Metadata Types

Custom Metadata Types can be leveraged to store and manage technical reference data that can be deployed across environments.

Picklist Values

Picklist values are used to ensure data consistency and integrity by restricting field values to a set of predefined options. Picklist values can be added or edited in a custom picklist field. A picklist field can also use values from a global picklist value set, which can be edited.

Custom Metadata Types travel with the metadata deployment and do not require a separate data-loading step — unlike custom objects. This is the key exam differentiator when a question asks about deploying reference data "automatically" across environments.
Page 9 · Technical Reference Data — Objects & Deployment

Technical Reference Data

Technical reference data refers to data used across the organization to categorize other data, standardize terminology, and ensure consistency across systems.

Objects

Salesforce objects are often used to store and manage technical reference data. However, object relationships and limitations, such as governor limits, should be considered when using them in Apex.

Deployment

Metadata API can be utilized for the deployment of complex or large volume of technical reference data like custom metadata types and records. Change Sets can be utilized for simple deployments.

Fed angle

In a regulated environment, Metadata API–driven deployments (scripted, version-controlled, pipeline-gated) are strongly preferred over manual Change Sets for anything beyond trivial changes. Change Sets leave no audit trail in source control and cannot be reviewed as a diff. For Fed-grade change control, the deployment artifact should be a commit in GitLab — Metadata API supports that; Change Sets do not.

Data Loader

Large volumes of reference data in a Salesforce object can be imported or exported using Data Loader.

Governance

Strict governance policies and version control can be implemented to manage changes to reference data effectively.

Testing

Thorough testing and validation of reference data should be performed before deployment to production.

Fed angle

All three pillars here — Data Loader (for bulk object-stored reference data), governance/version control, and pre-production validation — map directly to Federal Reserve IT change-management requirements. A data-load step that bypasses the deployment pipeline must still be documented, approved, and logged. Version-controlling Data Loader CSV files alongside metadata in Git closes that audit gap and enables rollback if a reference data change causes downstream failures.

Requirements & Solutions

Page 14 · Requirement 1

Requirement 1

Scenario

The company is looking to implement a large number of features using an AppExchange product. The product allows the use of multiple related custom objects to store and configure important business logic within a custom application used for healthcare solutions. An administrator can create records of the custom objects to define the necessary business logic. The architect needs to recommend a suitable source of truth for managing this reference data and provide any relevant considerations related to loading a large volume of this data and using the data in Apex.

Page 15 · Solution 1 (Part 1)

Solution 1 (Part 1)

Solution

Salesforce can be used as the source of truth for the technical reference data stored in custom objects. The data can be stored in production and sandbox environments. For the metadata that defines the structure of these custom objects, a version control system such as Git can be used as the source of truth. Data Loader can be used to load a large volume of these records.

However, it is important to note that circular relationships become a concern in a data model that utilizes multiple related objects. It can lead to challenges in data integrity, updates, and navigation between related technical reference records. The records could indirectly reference each other in a loop, complicating updates and queries.

Fed angle

Using Git as the source of truth for object metadata structure while Salesforce stores the records creates a clean audit split: schema changes are code-reviewed and pipeline-approved; data changes (record loads) are tracked via Data Loader logs and CSV files committed to the repo. Circular relationships in a reference data model are not just a technical risk — they are an integrity risk that can produce inconsistent outputs, which is an audit finding waiting to happen in a regulated org.

Page 16 · Solution 1 (Part 2)

Solution 1 (Part 2)

Solution

Another important consideration is that Salesforce imposes governor limits on the depth of nested relationships that can be accessed in a single SOQL query in Apex. When managing technical reference data across multiple objects, it's important to ensure that Apex transactions do not exceed these limits. Excessive nesting can hinder the ability to effectively utilize the reference data, impacting user experience.

SOQL relationship queries in Apex are limited in the depth of nested relationships that can be traversed in a single query. When an AppExchange product uses many related custom objects, architects must verify that data retrieval patterns stay within these limits — especially for bulk operations that could multiply the query depth impact.

Interview angle

When asked about using object-stored reference data in Apex, give a two-part answer: (1) circular relationships break data integrity and make bulk-load ordering indeterminate, and (2) deeply nested SOQL traversals hit governor limits. The clean architect move is to flatten the model or use Custom Metadata Types (which avoid both issues) when object relationships are not truly needed for the use case.

Page 17 · Requirement 2

Requirement 2

Scenario

The company's service department recently started using Salesforce. It would like to store and manage service centers, which are independent business units where customer service operations are performed. They are only required for reference and should be searchable in various web forms on the company's website and a custom application used for service management. The architect needs to recommend approaches for storing the service centers as technical reference data and their deployment.

Page 18 · Solution 2

Solution 2

Solution

A custom metadata type can be defined in Salesforce for the service centers. Records of this custom metadata type can be created to store and manage various service teams that should be searchable on web forms and the custom application used for service management. Metadata API or Change Sets can be utilized to deploy the custom metadata type and its records.

Fed angle

This is the canonical use case for Custom Metadata Types: read-only reference data (service centers) that must be available across environments and searchable at runtime. Because CMT records deploy with the metadata package, there is no separate data-loading step — the deployment pipeline covers both type definition and data. For the Fed, this means a single, auditable deployment artifact in GitLab covers the entire change, satisfying change-control and segregation-of-duties requirements in one step.

Interview angle

When a scenario describes reference data that is "read-only for applications" and "must move between environments," the answer is almost always Custom Metadata Types. The distinguishing factor from Custom Settings is that CMT records deploy via Metadata API (source-trackable, pipeline-friendly); Custom Settings records do not deploy the same way. Know this distinction cold.

Cheatsheet — Deploying Technical Reference Data

Storage Mechanism Decision Matrix

MechanismBest ForDeployment MethodKey Consideration
Custom Metadata Types Config settings, reference lookups, data that must deploy with metadata Metadata API or Change Sets (records travel with deployment) No separate data-loading step; source-trackable in Git
Custom Objects Large-volume reference records with complex relationships Schema via Metadata API; records via Data Loader Watch for circular relationships and SOQL governor limits in Apex
Picklist / Global Value Sets Field-level constrained values, standardized terminology Metadata API or Change Sets Global value sets allow reuse across multiple fields/objects

Deployment Approach Decision Matrix

ApproachUse WhenAuditability
Metadata API Complex or large-volume deployments; CI/CD pipelines; Git-driven releases High — commit-traceable, reviewable as diff
Change Sets Simple deployments; small teams without DevOps tooling Low — no source-control artifact; manual, point-in-time
Data Loader Bulk-loading records into custom objects (not CMT records) Medium — CSV logs; pair with version-controlled CSVs in Git for full traceability

Key Considerations for Object-Stored Reference Data

RiskImpactMitigation
Circular Relationships Data integrity failures, load-order issues, infinite loops in navigation Flatten the data model; avoid bidirectional lookup chains
Governor Limits on SOQL nesting Apex queries exceeding relationship depth limits; runtime errors at scale Design queries to stay within limits; test with production-scale data volumes
Separate data-load step Deployment pipeline gaps; reference data out of sync with metadata Version-control Data Loader CSVs in Git; automate load as post-deploy step

High-Yield Exam Gotchas

  • Custom Metadata Type records deploy with the metadata package — no separate data-load step is needed. This is the key differentiator from Custom Object records.
  • Custom Settings records do NOT deploy via Metadata API the same way CMT records do — when a question asks about deployable reference data, the answer is Custom Metadata Types, not Custom Settings.
  • Change Sets cannot be rolled back and leave no source-control artifact — Metadata API is the correct answer whenever auditability, repeatability, or pipeline integration is mentioned.
  • Circular relationships in custom objects break Data Loader ordering — if Object A references Object B and B references A, you cannot load both in a single pass without placeholder records.
  • Governor limits apply to SOQL relationship depth in Apex — deeply nested multi-object reference data models may be queryable in Setup but fail at runtime in Apex transactions.
  • Data Loader is the answer for large-volume custom object records; it is not used for Custom Metadata Type records (those load via deployment tooling).
  • A version control system stores metadata structure; Salesforce stores the data — the single-source-of-truth pattern splits these responsibilities deliberately for both object and CMT approaches.

Fed angle — Tying it together

For a Federal Reserve platform engineer, the entire reference data management topic reduces to one principle: every change to reference data must be traceable, reviewable, and reversible. Custom Metadata Types achieve this most cleanly because the type definition and its records travel together in a single Metadata API deployment that can be code-reviewed in GitLab, gated by an approval workflow, and rolled back by reverting a commit. Object-stored reference data is workable but requires additional discipline: schema changes via pipeline, record loads via version-controlled Data Loader scripts, and governance policies enforced through strict change-control procedures. Whichever mechanism is chosen, the deployment artifact in source control is the evidence package that satisfies examiners — the pipeline is the audit trail.
