4 / 31 · Introduction

Introduction

In Salesforce, creating test data for Apex tests is necessary to ensure that tests do not depend on production data and are repeatable. Test data can be created using brute force, a test setup method, a test data factory, or a CSV data file uploaded as a static resource.

Various unit testing strategies are available for Apex unit tests. Positive tests are used to return expected results when a valid input is provided. Negative tests are used to ensure that code handles invalid data and unexpected user input correctly. Permission-based tests ensure that code behaves as expected when it is run as a user with or without specific permissions. Mocks and stubs facilitate unit testing by simulating real objects and methods, allowing developers to test code in isolation from external dependencies.

Fed angle

At the Federal Reserve Bank of Chicago, Apex test quality is a deployment gate — Salesforce requires 75% code coverage for production deploys, but a regulated environment should aim for meaningful test coverage (positive, negative, and permission-based), not just line-count coverage. GitLab CI/CD pipelines can enforce minimum coverage thresholds and test-result artifacts as evidence for change-control audits.

Test Data Strategies

7 / 31 · Test Data — Importance & Behavior

Test Data

Creating isolated unit test data ensures that tests do not depend on production data and are repeatable.

Importance

Creating test data for unit tests ensures that tests are consistent across runs and not dependent on production data.

Data Dependency

Dependency on production data can lead to deployment issues due to data differences across environments.

Transient Behavior

Data inserted by an Apex unit test does not persist after the test finishes execution, ensuring that data cleanup is not required.

Interview angle

When asked why you isolate test data, lead with two points: (1) production data varies across orgs, causing intermittent failures in CI/CD pipelines; (2) Apex auto-rolls back DML after each test, so cleanup is free — but only if you never annotate with @IsTest(SeeAllData=true). Frame it as a deployment-reliability concern, not just a coding preference.

8 / 31 · Test Data — Default Access & Org Data

Test Data

Creating isolated unit test data ensures that tests do not depend on production data and are repeatable.

Default Access

By default, Apex tests do not have access to pre-existing data in an org. Exceptions are setup and metadata objects, such as User and Profile.

Org Data

A test class or method can be annotated with @IsTest(SeeAllData=true) to open up data access to records in the org. However, the best practice is to run tests with data silo using the @IsTest(SeeAllData=false) annotation.

Data Queries

The @IsTest(SeeAllData=true) annotation applies to data queries only. New, updated, and deleted records are rolled back in Apex unit tests.

Even when SeeAllData=true is used, DML changes (inserts, updates, deletes) are still rolled back after the test. The annotation only affects SOQL reads against existing org data.
9 / 31 · Creating Test Data — Methods

Creating Test Data

Several methods are available for creating test data for unit tests.

Brute Force

Records are created and inserted manually on each unit test. But this can lead to lengthy tests, especially when generating related records or when records contain a lot of field details.

Test Setup

A test setup method that creates test data can be created using the @TestSetup annotation. This method is called before every test method in the Apex class. The test data is reset between each and every test method's execution.

Test Data Factory

A reusable Apex class called Test Data Factory can be used to model the creation of records of one or more objects. A number of open-source data factories are available online.

CSV Data File

A CSV data file can be created and uploaded as a static resource. Test data can be generated directly from the CSV file. This useful when a large data volume is required for testing.

Fed angle

In a regulated deployment pipeline, the @TestSetup pattern is strongly preferred over brute-force because it keeps test classes concise and maintainable — reducing the cognitive load during code reviews and making it easier to update test data when schema changes. CSV-via-static-resource is the go-to for LDV (Large Data Volume) regression tests that must prove bulk-processing limits are respected.

10 / 31 · Test Setup Method (@TestSetup)

Test Setup Method

The following example shows the use of @TestSetup to define a method for creating test data.

@isTest
public class ServiceLevelAgreementTest {
  // Test Data Creation
  @TestSetup
  static void dataSetup() {
    Account a = new Account(Name='AccountDemo', Active__c='True', SLA_Status__c='Premium');
    insert a;
    Contract c = new Contract(AccountId=a.Id, Status='Draft', StartDate=Date.today(), ContractTerm=12);
    insert c;
  }
  @isTest
  static void testOpportunity() {
    // Test Data Retrieval
    Account a = [SELECT Id, SLA_Status__c FROM Account LIMIT 1];
    Contract c = [SELECT Id, ContractTerm FROM Contract LIMIT 1];
    Opportunity o = new Opportunity(Name='SLA', StageName='Closed Won', CloseDate=Date.today(), ContractId=c.Id, AccountId=a.Id);
    insert o;
    Opportunity r = [SELECT Id, CloseDate FROM Opportunity LIMIT 1];
    Date contractExpiry = r.CloseDate.addMonths(c.ContractTerm);
    // Result Verification
    System.assertEquals(r.Contract_Expiry__c, contractExpiry);
    System.assertEquals(r.Service_Status__c, a.SLA_Status__c);
  }
}
The @TestSetup method runs once before the first test method in the class, and the data state is restored (rolled back and re-inserted) before each subsequent test method. This means each test gets a clean, known data state without re-writing setup code.
11 / 31 · Test Data Factory

Test Data Factory

The following is an example of a Test Data Factory class that creates and returns test accounts.

/* The test utility class 'TestDataFactory' is used here to create and return
 * account records based on the number of accounts required by test method. */

@isTest
public class TestDataFactory {
  public static List<Account> createAccounts(Integer numAccounts) {
    List<Account> accounts = new List<Account>();

    for(Integer i=0;i<numAccounts;i++) {
      Account acc = new Account(Name='Test Account ' + i);
      accounts.add(acc);
    }
    insert accounts;

    return accounts;
  }
}

Interview angle

A Test Data Factory is the architect-level answer to "how do you scale test data across dozens of test classes?" Point out that it centralises record construction, so when a required field is added to an object, you fix one factory method rather than hunting across every test class. Mention that the class itself is annotated @isTest so it never counts against production code coverage metrics.

Unit Testing Strategies

14 / 31 · Positive Tests

Positive Tests

Positive unit tests are tests that return expected results when valid input data is provided.

Importance

Positive testing ensures that well-written code performs as expected with correct inputs.

Pattern

The pattern for writing positive unit tests uses the following steps:

  1. Generate or load test data
  2. Make assertions to validate data
  3. Call Test.startTest()
  4. Execute the code being tested
  5. Call Test.stopTest()
  6. Make assertions about output

Interview angle

The Test.startTest()/Test.stopTest() bracket is not optional ceremony — it resets governor limits for the code under test, which is critical for proving that your production code fits within its own governor budget. Assertions before startTest validate your setup data; assertions after stopTest validate your results. This two-phase assertion structure is the canonical Apex test pattern.

15 / 31 · Positive Tests — Code Example

Positive Tests

The following example shows the positive test behavior of a class when valid input is provided.

@isTest
private class OpportunityUpdateClassTest {
  @isTest
  public static void positiveTest() {
    // Test Data Creation — Valid Input
    List<Opportunity> opportunities = new List<Opportunity>();
    for (Integer i = 1; i <= 300; i++) {
      Opportunity opp = new Opportunity(Name='Test Opportunity '+i,CloseDate=Date.newInstance(2020, 07, 15),StageName='Closed Won');
      opportunities.add(opp);
    }
    insert opportunities;

    // Method Execution
    OpportunityUpdateClass.processRecords(opportunities);

    // Test Result Verification
    for (Sales_Order__c s : [SELECT Name, Opportunity__r.Name, Status__c, Opportunity__r.Notes__c FROM Sales_Order__c]) {
      System.assertEquals(s.Opportunity__r.Name + ' Order', s.Name);
      System.assertEquals('New', s.Status__c);
      System.assertEquals('A sales order has been created', s.Opportunity__r.Notes__c);
    }
  }
}
16 / 31 · Negative Tests

Negative Tests

Negative unit tests ensure that code handles invalid data and unexpected user input correctly.

Importance

Negative testing ensures that the code is fault-tolerant and ensures that the code gracefully handles exceptions, preventing failures in batch processes or other operations.

Pattern

The pattern for writing negative unit tests uses the following steps:

  1. Generate or load test data
  2. Start a try/catch block
  3. Call Test.startTest()
  4. Execute the code that is expected to throw an exception
  5. Call Test.stopTest()
  6. Add an assertion that fails if no exception is thrown
  7. Catch the expected exception

17 / 31 · Negative Tests — Best Practices

Negative Tests

Negative unit tests ensure that code handles invalid data and unexpected user input correctly.

Best Practices

Test data can be modified to induce specific exceptions and validate error handling. Both the exception type and error message should be checked in the catch block to avoid false positives.

Example

In a batch process, if the code fails on the first record in the batch, and it does not gracefully handle exceptions, the remaining records are not processed. Negative tests avoid such situations.

Fed angle

In a central-bank payment processing context, a batch job that silently drops records due to an unhandled exception is a regulatory incident. Negative tests that verify graceful exception handling — and assert on both exception type and message — are the automated proof that your error-handling logic meets the bank's fault-tolerance requirements. These test results belong in the deployment evidence package.

18 / 31 · Negative Tests — Code Example

Negative Tests

The following example shows the negative test behavior of a class when invalid input is provided.

@isTest
private class OpportunityUpdateClassTest {

  @isTest
  public static void negativeTest() {
    // Test Data Creation — Invalid Input
    List<Opportunity> opportunities = new List<Opportunity>();
    for (Integer i = 1; i <= 300; i++) {
      Opportunity opp = new Opportunity(Name='Test Opportunity '+i,CloseDate=Date.newInstance(2020, 07, 15),StageName='Closed Lost');
      opportunities.add(opp);
    }
    insert opportunities;

    // Test Method Execution
    OpportunityUpdateClass.processRecords(opportunities);

    // Test Result Verification
    for (Opportunity o : [SELECT Id, Notes__c, (SELECT Id FROM Sales_Orders__r) FROM Opportunity WHERE Id IN :opportunities]) {
      System.assert(o.Sales_Orders__r.size() == 0);
      System.assertNotEquals('A sales order has been created', o.Notes__c);
    }
  }
}
19 / 31 · Permission-Based Tests

Permission-Based Tests

Permission-based tests ensure that code behaves as expected when it is run as a user with or without specific permissions.

Importance

Permission-based testing verifies that an application's access controls work as expected, ensuring that users have appropriate access to resources based on their permissions.

Pattern

The pattern for writing permission-based unit tests uses the following steps:

  1. Generate or load test data
  2. Create test users
  3. Execute test using System.runAs(user)
  4. Combine positive and negative test patterns

Interview angle

System.runAs() is the only way in Apex unit tests to switch the running user context — it does not enforce actual login permissions, but it does switch the user for record ownership, sharing rules, and field-level security enforcement in your code. For permission-based tests, you combine positive tests (user with permission can do X) with negative tests (user without permission gets an exception or sees no data) within the same test method using nested runAs blocks.

20 / 31 · Permission-Based Tests — Code Example

Permission-Based Tests

The following example uses System.runAs() to run code in the context of a specific user to test code behavior and record access to the user.

@isTest
public static void test1() {

  Profile p = [SELECT Id FROM Profile WHERE Name = 'Standard User'];
  User newUser = new User(Email='newuser@acme.com',UserName='newuser@acme.com.dev',LastName='Testing',Alias='newUser',
  ProfileId=p.Id,LanguageLocaleKey='en_US',LocaleSidKey='en_US',TimeZoneSidKey='America/Los_Angeles',EmailEncodingKey='UTF-8');

  // Code execution as newUser
  System.runAs(newUser) {
    System.assertEquals('newuser@acme.com.dev', UserInfo.getUserName());
    System.assertEquals(p.Id, UserInfo.getProfileId());
  }

  User currentUser = [SELECT Id, ProfileId FROM User WHERE UserName='currentuser@acme.com.dev'];
  // Code execution as currentUser
  System.runAs(currentUser) {
    System.assertNotEquals('newuser@acme.com.dev', UserInfo.getUserName());
    System.assertNotEquals(p.Id, UserInfo.getProfileId());
  }
}
21 / 31 · Mocks and Stubs

Mocks and Stubs

Mocks and stubs facilitate unit testing by simulating real objects and methods, allowing developers to test code in isolation from external dependencies.

Mocks & Stubs

A mock is used to mimic the behavior of complex real objects and is utilized at the object level. A stub provides predefined responses to method calls.

Using Mocks & Stubs

A mock is used to test interactions with external systems, such as HTTP callouts to third-party web services, by simulating responses. Stubs are used to test code that relies on the internal state or behavior of other objects, allowing the simulation of various conditions and responses without relying on the real implementation.

22 / 31 · Mocks and Stubs — Mock Callouts & Stubbing

Mocks and Stubs

Mocks and stubs facilitate unit testing by simulating real objects and methods, allowing developers to test code in isolation from external dependencies.

Mock Callouts

The HttpCalloutMock interface can be implemented to simulate HTTP callouts. The Test.setMock() method allows associating the mock with HTTP callouts.

Stubbing

The StubProvider interface is used to replace the behavior of methods within the test context. It is useful to test functionality that depends on the behavior of other classes or methods.

Interview angle

The distinction between HttpCalloutMock and StubProvider is commonly tested: HttpCalloutMock is for external HTTP callouts (REST/SOAP integrations); StubProvider (Stub API) is for mocking internal Apex method behavior. Both prevent test failures caused by external dependencies and ensure your unit tests truly test only the code under test.

23 / 31 · HTTP Callout Mock — Code Example

HTTP Callout Mock

The following example shows the use of HttpCalloutMock to simulate an HTTP response.

// Apex class that implements the HttpCalloutMock interface to simulate the response of a successful enrollment of a student:
public class EnrollHttpCalloutMock implements HttpCalloutMock {
  public HttpResponse respond(HTTPRequest req) {
    HttpResponse res = new HttpResponse();
    res.setHeader('Content-Type', 'application/json');
    res.setBody('{"success":true,"studentId":12345,"courseId":67,"yearLevel":3}'); // create fake response
    res.setStatusCode(200);
    return res;
  }
}

// Code contained and executed inside a test method:
Test.startTest();
Test.setMock(HttpCalloutMock.class, new EnrollHttpCalloutMock());
StudentApplicationWrapper application = generateStudentApplication(); // some helper method
Enrollment erm = StudentController.enroll(application); // invoke the method to test

// verify new record created from fake data
System.assertEquals(erm.ExternalStudentId__c, 12345);
System.assertEquals(erm.YearLevel__c, 3);
System.assertEquals(erm.CourseId__c, 67);
Test.stopTest();

Fed angle

At a regulated financial institution, integration tests against live external endpoints (payment processors, core banking APIs) cannot be run in CI/CD pipelines due to sandbox restrictions and data sensitivity. HttpCalloutMock is the required pattern — it lets the pipeline validate integration logic deterministically, and the mock class itself can be reviewed and approved as part of the deployment package, providing auditability of the expected integration contract.

Requirements & Solutions

27 / 31 · Requirement 1

Requirement 1

Scenario

The company recently removed a record type and added a new record type for ERP solutions on the Opportunity object. As a result, certain unit tests in a test class that references the Opportunity object have been failing. The architect needs to recommend a suitable approach to ensure that tests execute predictably. Furthermore, a developer is working on a test class for a new functionality that processes a large volume of opportunity data. A suitable test data strategy is required for this use case.

28 / 31 · Solution 1

Solution 1

Solution

To ensure that unit tests in the test class execute predictably, the test setup method in the test class should be updated. The test class should create its own test data and dynamically query for available record type Ids rather than hard-coding them. This would ensure that tests remain resilient to changes in record types. For large data volume testing, a CSV file containing the required number of opportunity records can be uploaded as a static resource. It can then be referenced in test classes.

Interview angle

Hard-coded record type Ids in test classes are a classic deployment failure mode — they break silently when a record type is renamed or replaced. The architect-level answer is always: query for record type Ids dynamically at test runtime using [SELECT Id FROM RecordType WHERE SObjectType='Opportunity' AND DeveloperName='ERP_Solution']. Combine this with the @TestSetup pattern and you eliminate the two most common test-class fragility sources simultaneously.

29 / 31 · Requirement 2

Requirement 2

Scenario

A team of senior developers in the IT department recently conducted a comprehensive code review of the support management application and found that Apex tests do not use enough negative unit tests. In addition, the existing test data strategy used for testing the inbound call volume functionality needs to be evaluated. The support department currently receives almost 300 calls per hour, but the existing test data being used in test classes is suitable for 150 calls per hour.

30 / 31 · Solution 2

Solution 2

Solution

To enhance negative unit testing, all the critical paths and potential failure points within the Apex classes should be identified. Thereafter, additional unit test methods should be created for negative test cases. Permission-based testing can be utilized to ensure that some negative tests cover scenarios where operations fail due to insufficient permissions or access rights, simulating different user roles interacting with the application. For the inbound call volume testing, the volume of test data should be increased by 100% to more accurately reflect the current operational volume of 300 calls per hour. Test data generation scripts or methods should be updated accordingly.

Fed angle

This solution maps directly to a Fed audit scenario: "show us evidence that your code handles failure gracefully and at production scale." The deliverable is a test suite that covers negative paths (documented as test cases in the deployment evidence), permission-based tests (proving least-privilege enforcement), and LDV tests at or above production record counts. All three are required for a credible change-control submission at a regulated institution.

High-Yield Exam Gotchas

  • @IsTest(SeeAllData=false) is the default and the best practice — never open org data access unless absolutely necessary for setup/metadata objects like User or Profile.
  • DML is always rolled back after a test, regardless of SeeAllData setting — only SOQL reads are affected by SeeAllData=true.
  • @TestSetup data is reset between test methods, not just created once — each test method gets a fresh copy, preventing cross-test contamination.
  • Hard-coded record type Ids will break on deployment — always query dynamically: [SELECT Id FROM RecordType WHERE SObjectType='X' AND DeveloperName='Y'].
  • Test.startTest()/stopTest() resets governor limits — code inside the bracket gets a fresh set of limits; use this to prove your production code fits within its own governor budget.
  • HttpCalloutMock ≠ StubProvider — HttpCalloutMock simulates external HTTP responses; StubProvider replaces internal Apex method behavior at the object level.
  • Negative test catch blocks must check both exception type and message — checking only type allows wrong exceptions to pass silently (false positive).
  • System.runAs() does not enforce login security — it switches the user context for sharing rules, record ownership, and UserInfo; it does not verify the user can actually log in.
  • 75% code coverage is required for production deployment — but coverage alone is not quality. Meaningful assertions covering positive, negative, and permission scenarios are the architect's standard.
  • CSV static resources are the LDV answer — when bulk-processing tests require hundreds or thousands of records, a pre-built CSV static resource is more maintainable and auditable than programmatic loop generation.
