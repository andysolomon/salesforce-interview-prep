Page 4 · Learning Objectives

After studying this topic, you should be able to:

  • Identify different development models and deployment tools used for migrating metadata.
  • Describe concepts related to source-driven development and tools to support the process.
  • Identify the appropriate deployment tool for different deployment scenarios.
Page 5 · Introduction

Introduction

Salesforce provides tools that allow developers to deploy changes from one environment to another. Depending on the scenario, or phase in the deployment process, a particular tool is needed to perform a certain task.

Page 6 · Deployment tool options

Deployment tool options

Salesforce Extensions for VS Code

Visual Studio Code extensions that empower the editor for Salesforce development and deployment of metadata to any org.

Change Sets

Deployment tool used for migrating metadata between related orgs such as a sandbox and production.

Developer Console

Native IDE for developing and deploying metadata to its associated org.

Code Builder

Web-based IDE optimized for development; no installation required.

Salesforce CLI

Command-line interface that uses the metadata API for development, deployment, and other lifecycle tasks.

Page 8 · The 4 phases

The 4 phases of a typical deployment

1. Develop & Test

Changes made in a separate development environment.

2. Integrate & Test

Changes deployed to a shared development environment for integration testing.

3. Test Release

Changes deployed to a full sandbox environment for user-acceptance testing.

4. Deploy Release

Changes deployed to a production environment.

3 development models

Salesforce DX + source control, sandboxes/scratch orgs.

Package Development

Source-of-truth in a repo, packages as release artifacts.

Page 10

Change Set Development Model

Page 11 · 5 steps

5 steps

1. Development Sandboxes

A separate Developer sandbox per developer keeps changes isolated until the team is ready to integrate.

2. Develop and Test

Developers use their Developer sandboxes to create and test customizations. Sandboxes do not contain production data.

3. Integration Testing

Change sets migrate customizations from Developer sandboxes to a shared Developer Pro sandbox.

4. User-Acceptance Testing

Change sets migrate to a full sandbox, which contains all the production data.

5. Production Release

Customizations are migrated to production using change sets. The full sandbox can be used for end-user training.

Page 12 · Considerations

Change Set Model — considerations

Tracking Changes

A change-tracking method must be established — especially for changes requiring manual migration.

Use Tracking Tools

A custom or third-party tool can be used to log changes made by each developer.

Manual Configuration

Configurations involving metadata not supported by the Metadata API require recreating manually in the destination org.

Metadata Coverage Report

Shows which metadata types are supported in the Metadata API and other channels.

Interview angle

Every change-set shop has a "manual deployment checklist" — the list of items the API can't migrate (profile FLS for some objects, dashboard owners, etc). Knowing the Metadata Coverage Report exists is the give-away that you've done this for real.

Page 13 · Using Change Sets — basics

Using Change Sets — basics

Declarative Tool

Change sets utilize an easy-to-use UI in Salesforce for small deployments.

No Local Files

Allow change management without using a local file system.

Related Orgs

Metadata deploys between related sandbox/production orgs.

Page 14 · Using Change Sets — gotchas

Using Change Sets — gotchas

Audit Changes

Previously deployed changes can be audited.

Multiple Targets

The same component can be deployed to multiple orgs.

Delete / Rename

Not possible to delete or rename components using change sets.

Version Control

Change sets do not support version control systems.

Page 20 · Sample flow

Sample flow

Develop & test in Scratch Orgs via Visual Studio Code → Build release (integration) in a Scratch Org → Test release (UAT) in a Partial Sandbox → Release (training & production) in a Full Copy Sandbox + Production Org.

Throughout: Salesforce CLI moves metadata between local repo and orgs; Version Control System is the source of truth.

Package Development Model

Package / content / VCS

Package

A package is a release artifact that contains a group of related code and customizations.

Package Content

Source and metadata are organized into a package.

Version Control

Versioning helps with change management. A VCS plays an integral role in the package development life cycle.

Page 23 · Repo / scratch / DX

Repo / scratch / DX

Code Repository

A source-control repository stores the source for the packages and maintains the source of truth.

Scratch Orgs

Scratch (development) orgs can be built from the source in the repository to work specifically on the package.

Salesforce DX

Used to test, build, and release packages. A Salesforce DX project organizes the source into a package directory.

Page 24 · Sync / CLI / unlocked

Sync / CLI / unlocked

Synchronization

Synchronization of the VCS is improved through change tracking of Setup features.

Salesforce CLI

Automated testing, CI, and CD are typically utilized in the package lifecycle. Salesforce CLI can be used throughout.

Unlocked Packages

Enterprise edition customers can utilize unlocked packages to develop internal business apps.

Page 25 · Version report & coverage

Version report & coverage

Version Report

The CLI command force:package:version:report retrieves details of a specific version of a managed 2GP or unlocked package.

Code Coverage

Adding the --verbose flag includes the code coverage percentage of each Apex class in the output.

Page 26 · Sample flow

Sample flow

Develop & build unit tests in Scratch Orgs → Compile & run tests in a Scratch Org → Build & run on staging/UAT in Dev Pro Sandbox + Partial Sandbox → Release for training & production in Full Sandbox + Production Org. Salesforce CLI drives the moves; VCS is source of truth.

Activities related to source development are performed in scratch orgs, whereas release and deployment testing activities are performed in sandbox orgs.

Salesforce DX Concepts

Page 28 · Source-driven / dev tools / source of truth

What is Salesforce DX

Salesforce DX (Developer Experience) introduces a new way of developing and managing applications on the Lightning Platform throughout the entire life cycle of an application.

Source-Driven

Promotes source-driven development, team collaboration, and custom app development agility.

Developer Tools

Tools developers are already familiar with — such as ANT or third-party IDEs — can be used.

Source of Truth

Source code and metadata is stored outside the org and managed using a VCS such as Git.

Page 29 · CLI / scratch / editor

What is Salesforce DX — CLI / scratch / editor

Salesforce CLI

Command-line interface used for development, continuous integration, and delivery.

Scratch Orgs

Used for development and help facilitate automated testing and continuous integration.

Code Editor

Enables any IDE or text editor to work with Salesforce CLI and VCS.

Editor Plugin

Salesforce Extensions for VS Code is used for development and working with scratch orgs, Apex, Lightning components, and Visualforce.

Page 30 · 1GP vs 2GP

1GP vs 2GP

1st-Generation (1GP)

Managed and unmanaged packages are created and deployed from an org.

2nd-Generation (2GP)

Managed 2G packages and unlocked packages are created and deployed from a local machine or repository.

Page 31 · Managed 2GP & unlocked

Managed 2GP & unlocked — note

Managed 2GPs are used for distributing apps on AppExchange. Unlocked packages provide more features compared to unmanaged packages such as version upgrades/downgrades, destructive changes, and more.
Page 32 · Environment setup

Environment setup for Salesforce DX

Enable Dev Hub

Enable the Developer Hub in the org (requires Production or Developer Edition) to track the number and status of scratch orgs.

Add Users in Dev Hub

Create additional users to allow team members to generate scratch orgs.

Enable 2GP Packaging

Enable Second-Generation Packaging in the org to develop 2GP managed packages.

Install Salesforce CLI

Required in the local development machine to create environments, synchronize code, and execute tests.

Page 33 · DX project structure

Salesforce DX Project

Salesforce DX implements a new project structure to contain org metadata, templates, sample data, and tests. A Salesforce DX project is a local directory structure of metadata in source format.

  • Configuration files for creating scratch orgs
  • Data to be loaded into orgs for development or testing
  • Tests created to validate a package
Project files should be stored in a VCS and retrieved during development.
Page 34 · DX project setup options

DX project setup options

  • Use the sample repository on GitHub — clone the sample GitHub repo provided by Salesforce as a starting point.
  • Create a Salesforce DX Project from existing source — start with an existing Salesforce app to create a DX project and retrieve existing source code.
  • Set up a fresh Salesforce DX Project — create an app on the Lightning Platform from scratch using a DX project.

Page 43 · Deploy or Retrieve — commands

Deploy or retrieve metadata — commands

Development

force:source:deploy is intended for working with a sandbox org for development or local testing.

Deployment

force:mdapi:deploy is intended for deploying code for integration testing, staging, or production.

Convert Source

force:mdapi:deploy requires the source code to be converted to metadata format using sfdx force:source:convert.

Interview angle

Critical distinction: force:source:deploy is for incremental sandbox iteration; force:mdapi:deploy is for production. The latter rolls back the entire deployment if any component errors, preserving the integrity of the target.

Local Dev

Page 53 · Enable real-time preview

Enable real-time preview

When developing Lightning web components, Salesforce allows real-time preview of changes without needing to deploy code to the org.

Requirements

  • Salesforce CLI installed in the local machine.
  • The Local Dev plugin (@salesforce/plugin-lightning-dev) installed locally.
  • Local Dev settings enabled in the target org: Setup → Local Dev → Enable Local Dev.
If real-time preview is not working, you may need to enable Lightning web security and clear the browser cache for desktop previews.
Page 54 · Launch preview mode

Launch preview mode

Run sf lightning dev app from the command line. It asks for the device (Desktop / Mobile - Android / Mobile - iOS) and which Lightning Experience app to load. Choosing the app launches the browser automatically and opens the app in preview mode.

Page 55 · Example

Real-time preview example

An LWC called "Study Guide Upload" is added as a navigation tab to a Lightning Experience App called "Tools". Changes saved locally are automatically reflected in the "preview mode" browser tab.

Page 56 · Limitations

Limitations

Real-time preview is not supported for all types of changes. Only the following are automatically reflected:

  • Basic HTML revisions (changing attributes, adjusting layout, etc.)
  • New reference to a component (e.g. adding <lightning-card>)
  • Basic CSS revisions (font-size, colors, etc.)
  • Importing a new CSS-only component (e.g. @import 'c/myAdditionalStyles';)
  • JavaScript changes in component methods that don't affect the component's public API

Scratch Orgs

Page 58 · Use cases

What are scratch orgs

Scratch orgs are temporary configurable Salesforce environments that can be quickly generated using Salesforce CLI to be used as a personal development environment.

Use cases

  • Starting a new project
  • Starting a new feature branch
  • Starting automated testing
  • Testing a new feature
  • Performing development tasks directly in an org
  • Starting from "scratch" with a fresh new org
Page 59 · Configuration

Scratch org configuration

Edition / Features

Scratch orgs can be customized with various Salesforce editions and tailored to include only the necessary features and preferences.

Definition File

Configuration can be shared to allow developers to replicate each other's scratch orgs, ensuring the team is working on the "same" environment.

Org Snapshots

A snapshot of a scratch org's configuration can be captured. A snapshot is a point-in-time copy usable to replicate the org.

Page 60 · vs sandboxes — basics

Scratch orgs vs sandbox orgs — basics

Limited

Scratch orgs have limited storage size and a short life span.

Purpose

Scratch orgs are not designed to replace sandbox orgs.

Page 61 · vs sandboxes — roles

Scratch orgs vs sandbox orgs — roles

Development

Scratch orgs are intended for developing customizations in modules or packages.

Testing

Scratch orgs are designed for testing an individual module or package.

Use Cases (Sandbox)

Sandbox orgs are used for user acceptance testing, as a staging environment, and for continuous delivery testing.

Page 67 · Common commands (1)

Common sf commands (1)

# Authorize a default Dev Hub org and assign an alias
sf org login web --set-default-dev-hub --alias my-dev-hub

# Create a scratch org using a definition file
sf org create scratch --definition-file config/project-scratch-def.json --alias MyScratchOrg

# Generate a Lightning web component
sf lightning generate component --type lwc --name myApp --output-dir force-app/main/default/lwc

# Run Apex tests
sf apex run test --result-format human

# Open the scratch org and view the pushed metadata
sf org open
Page 68 · Common commands (2)

Common sf commands (2)

# Generate a project with a default manifest (package.xml) file
sf project generate --name myProject --manifest

# Retrieve metadata in source format from an org
sf project retrieve start --source-dir path/to/source --target-org myOrg

# Deploy files in the force-app directory to a specified org
sf project deploy start --source-dir path/to/source --target-org myOrg

# Preview a deployment to determine any conflicts or issues
sf project deploy preview --source-dir force-app

# Preview a retrieve to determine any conflicts or issues
sf project retrieve preview

Page 79

Scenarios and Solutions

Page 80 · Scratch orgs

Scenario — temporary personal environments

Scenario

Developers want to automatically create and use temporary orgs as personal development environments based on specific configurations.

Solution

Scratch orgs — short-lived orgs generated automatically using Salesforce CLI for developing and testing applications. A configuration file can be shared to build scratch orgs with pre-configured metadata.

Page 81 · Version control

Scenario — spreadsheets are not change tracking

Scenario

Developers have been using spreadsheets to track changes made to Lightning components and Visualforce pages and need an efficient change tracking solution.

Solution

A version control system should track and manage org metadata. Typically Salesforce CLI is used to retrieve org metadata into a Salesforce DX project. A code repository containing the project stores files and tracks changes.

Page 82 · Sandbox dev

Scenario — sandbox development

Scenario

A developer is assigned a separate development sandbox for building a new feature. The developer needs to retrieve source from the sandbox as well as deploy to it.

Solution

Salesforce CLI can be used to interact with sandbox orgs for development and local testing. Using Salesforce Extensions for VS Code or Salesforce CLI directly, metadata can be conveniently deployed or retrieved between the org and local machine.

Page 83 · mdapi:deploy to production

Scenario — deploying to production

Scenario

A developer has worked on an update and tested it in a development org to fix a bug encountered in production. It is ready to go through integration testing and staging, then deployment to production.

Solution

For deploying changes to integration, staging, and production orgs, perform the deployment using force:mdapi:deploy. Unlike force:source:deploy, this command rolls back the entire deployment when any component has an error, and helps maintain the integrity of the target environments.

Bonus · Quick-Reference Cheatsheet

Quick-Reference Cheatsheet

The three development models

  • Change Set — UI-only, between related orgs, no VCS, no delete/rename. Best for small admin-style orgs.
  • Org Development — Salesforce DX + VCS + sandboxes. Source-driven, but the sandbox is still the workspace.
  • Package Development — VCS is source of truth; scratch orgs come and go; releases are packages (managed 2GP or unlocked). Best for modular, modern source-driven work.

The two deploy commands

  • force:source:deploy / sf project deploy start — incremental, source-format, partial-success allowed. Use for sandbox iteration.
  • force:mdapi:deploy — metadata-format, atomic / rolls back the whole deployment on any error. Use for integration / staging / production.
  • Convert source → metadata format with sfdx force:source:convert before force:mdapi:deploy.

Scratch vs sandbox — when to pick which

  • Scratch — temporary, configured from a definition file, ideal for module/package development & CI. Storage and lifespan limits.
  • Developer / Developer Pro sandbox — long-lived, supports source tracking, ideal for SFDX with Org Development Model.
  • Partial sandbox — staging / UAT with a sample of production data.
  • Full sandbox — exact prod copy. UAT, training, performance testing.

Required setup for Salesforce DX

  1. Enable Dev Hub in a Production or Developer Edition org.
  2. Add users to the Dev Hub if multiple developers need to spawn scratch orgs.
  3. Enable Second-Generation Packaging if shipping managed 2GP.
  4. Install Salesforce CLI locally.

Key CLI commands (sf v2 syntax)

  • sf org login web --set-default-dev-hub --alias my-dev-hub
  • sf org create scratch --definition-file config/project-scratch-def.json --alias MyScratchOrg
  • sf project deploy start --source-dir force-app --target-org myOrg
  • sf project retrieve start --source-dir force-app --target-org myOrg
  • sf project deploy preview --source-dir force-app (validate-only dry run)
  • sf apex run test --result-format human
  • sf lightning dev app (Local Dev real-time preview)
  • sf force:package:version:report -p <versionId> --verbose (per-class coverage in a package)

Editor / IDE landscape

  • VS Code + Salesforce Extension Pack — local install, full DX experience.
  • Code Builder — same experience but in-browser. Installed as a managed package; users need the CodeBuilderGroup permission set group. Extensions come from Open VSX, not Microsoft Marketplace.
  • Developer Console — native to the org, deploys only to that org. Mostly legacy for debugging.

Source tracking gotcha

Source tracking (force:source:status / sf project deploy preview) only works in Developer and Developer Pro sandboxes — and requires Enable Source Tracking in this Sandbox. Full / Partial sandboxes don't have it.

DevOps Center vs Change Sets

  • Both are declarative/UI deployment tools.
  • Change Sets: limited to related orgs, no VCS, no delete/rename, no version control history.
  • DevOps Center: GitHub-backed (the repo is the source of truth), pipelines with named environments, validate-only deployments. Requires GitHub auth + the DevOps Center managed package.

Local Dev limits to memorize

Real-time LWC preview supports: HTML edits, new component references, basic CSS edits, CSS-only imports, and JS changes that don't alter the component's public API. Everything else still needs a redeploy.

Two scenario tells

  • "Spreadsheet to track changes" → switch to VCS + SFDX.
  • "Deploying to production / partial deploys are dangerous" → use force:mdapi:deploy for atomic rollback.
