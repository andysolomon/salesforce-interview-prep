Introduction

When Apex classes, triggers, Visualforce controllers, controller extensions, or Apex tests are not working as expected, or performance issues are encountered, tools and techniques are available to identify the root causes.

This topic covers concepts and scenarios to determine the appropriate methods, procedures, and considerations for resolving issues generally caused by Apex.

Salesforce provides tools that enable developers to implement application performance profiling.

Performance profiling techniques help identify potential performance issues and apply best practices to improve performance.

Page 10 · Performance Profiling Methodology

Methodology (5 steps)

  1. Scope definition — split scenarios into different functionalities.
  2. Analysis — measure performance for each functionality.
  3. Identification — identify potential bottlenecks and their root causes.
  4. Remedy — fix the root causes of the bottlenecks.
  5. Rerun — compare results and repeat the previous steps until the bottlenecks are removed.

Profiling Performance Considerations

Page 26 · Considerations for Profiling Performance

Considerations for profiling performance

Role Users

Users with different roles may be used when profiling to identify the impact of data volume and sharing calculation overheads.

Governor Limit

Governor limit usage can be identified using LIMIT_USAGE in the Execution Log panel.

Business Process

Business processes should not be designed with the assumption that only optimal test results will be observed.

Query Performance

Query performance should be evaluated with a custom field without an index to establish the query's baseline performance.

Customer Support

Salesforce Customer Support should be consulted before running any load testing, including stress, bandwidth, or concurrent user testing.

Interview angle

The "no-index custom field" point is subtle — it's saying: test the worst case. If your query is fast only because of a system index you don't control, you don't actually know the floor.

Pages 27 · Performance Profiling Example — Apex controller

OppController class

public class OppController {
   public list<AggregateResult> lstAgg = new list<AggregateResult>();
   public OppController() {
       lstAgg = [
           SELECT StageName, SUM(Amount) Amount, COUNT(id) Total
           FROM Opportunity WHERE isClosed = false AND StageName != 'Canceled' GROUP BY StageName
       ];
   }
   public list<OppAgg> getResults() {
       list<OppAgg> lstResult = new list<OppAgg>();
       for (AggregateResult ar: lstAgg) {
           OppAgg objOppAgg = new OppAgg(ar);
           lstResult.add(objOppAgg);
       }
       return lstResult;
   }
   class OppAgg {
       public Integer Total {get;set;}
       public String StageName {get;set;}
       public Decimal Amount {get;set;}
       public OppAgg(AggregateResult ar) {
           Total = (Integer)ar.get('Total');
           StageName = (String)ar.get('StageName');
           Amount = (Decimal)ar.get('Amount');
       }
   }
}

Page 43 · Debug Logging Example — code

Debug logging — code

An Apex trigger executes static methods from two different classes and is not producing expected results.

trigger ContactTrigger on Contact (after update) {

  System.debug('ContactTrigger executed!');
  DemoClass.someMethod();
  UtilityClass.someMethod();
}
The developer needs to figure out where in the process the logic is failing and aims to trace the processes executed or invoked by the DemoClass class first.
Page 44 · Debug logging — trace flags

Debug logging — trace flags

By using trace flags, a debug level can be specified for the DemoClass to increase the log verbosity for transaction details associated with the class. A different debug level can be configured and assigned to UtilityClass and ContactTrigger to disable their logging (debug level = NONE).

Interview angle

Per-class trace flags are how you keep logs readable when a single transaction touches many classes — bump only the class you're investigating, silence the rest.

Page 45 · Tracking DML — code

Tracking DML — code

A developer is building custom functionality that involves an Apex class and triggers that perform DML statements at various execution points.

trigger ContactTrigger on Contact (after insert) {
   List<Coupon__c> coupons = new List<Coupon__c>();
   for (Contact c : Trigger.New) {
       if (c.Has_Coupon__c == TRUE) {
           Coupon__c coupon = new Coupon__c();
           coupon.Contact__c = c.Id;
           coupons.add(coupon);
           // other logic below...
       }
   }
   insert coupons;
}

trigger CouponTrigger on Coupon__c (after insert) {
   for (Coupon__c c : Trigger.New) {
       UtilityClass.logCoupon(c.Contact__c);
       // other logic below...
   }
}

public class UtilityClass {
   public static void logCoupon(Id contactId) {
       Coupon_Log__c cl = new Coupon_Log__c();
       cl.Contact__c = contactId;
       insert cl;
       // other logic below...
   }
}
Page 46 · Tracking DML — filter

Tracking DML — two techniques

  1. Filtering log messages — enter DML in the Filter input to match messages containing "DML". The filter is case-sensitive.
  2. Hiding executed units — in the Executed Units tab, click all the filter buttons except DML so only DML operations are shown.

Page 55

Apex Tests

Page 56 · Creating an Apex test class

Creating an Apex test class

Annotations

Test classes and methods should be annotated with @isTest. The (SeeAllData=true) annotation can be added for org data access.

Create Test Data

Test data should be created whenever possible. Test.loadData or a utility class can be used.

Start Test

Test code can be isolated from setup code with Test.startTest() — receives a fresh set of governor limits.

Code Execution

Execute all logic branches. Both single and bulk operations should be tested. Positive, negative, and user-context test cases should be covered.

Stop Test

Async code can be forced to complete with Test.stopTest(). Original governor limits are restored after this point.

Assertions

Use assert methods to verify results. Each test method should have at least one assertion. The more assertions, the better.

Apex Test Scenario / Solution I

Page 58 · Scenario I — Coverage

Scenario I — Poor code coverage

Scenario

An Apex class and its test class compile successfully in a development org. However, deployment fails due to poor code coverage results in the production org. The developer needs to increase coverage.

Page 59 · ItemDiscount class

The class under test

public class ItemDiscount {
  public static Decimal calculateAmount(Integer yearsMember, Decimal price) {
      Decimal amount = price;
      if (price < 1000) { // discount rates if price is below 1000
          if (yearsMember < 1) {
              amount = price - (price * 0.10);
          } else if (yearsMember >= 1 && yearsMember < 2) {
              amount = price - (price * 0.12);
          } else if (yearsMember >= 2 && yearsMember < 3) {
              amount = price - (price * 0.14);
          } else if (yearsMember >= 3 && yearsMember < 4) {
              amount = price - (price * 0.18);
          } else if (yearsMember >= 4 && yearsMember < 5) {
              amount = price - (price * 0.2);
          } else {
              amount = price - (price * 0.25);
          }
      } else amount = price - 100; // a fixed discount value
      return amount;
  }
}
Page 60 · Original test class

The original test class

@isTest
private class ItemDiscountTest {
  @isTest
  static void testYears() {
      Decimal price = 750;
      Integer years = 2;
      Decimal amount = ItemDiscount.calculateAmount(years, price);
      System.assertEquals((price - (price * 0.14)), amount);
  }

  @isTest
  static void testAmount() {
      Decimal price = 1000;
      Integer years = 5;
      Decimal amount = ItemDiscount.calculateAmount(years, price);
      System.assertEquals((price - 100), amount);
  }
}
Page 61 · Analysis

Analysis

Solution narrative

In ItemDiscount, if price is below 1,000, discount rates are applied depending on number of years a customer has been a member. Otherwise, a fixed discount value is applied. The test class executes only two scenarios — one where years is 2 and one where price is 1,000. Updating the test to cover other input values improves coverage accordingly.

Page 62 · Result of unoptimized test class

56% coverage — fails deployment

Running via the Developer Console reveals that areas highlighted in red are not covered. Overall coverage for ItemDiscount is 56% (9/16) — below the required 75% for production.

Page 63 · Improved testYears

Improved testYears()

Solution approach

Improve testYears() to execute all the logic branches: use a year-to-rate map to represent year and rate, iterate via a for loop, and apply a max rate if the member reaches five years.

Pages 64–65 · Solution code

Solution code

@isTest
public class ItemDiscountTest {

  @isTest
  static void testYears() {

      Decimal price = 750;

      // rate used when member has reached 5 years and beyond
      Decimal maxRate = 0.25;

      // create a year-to-rate mapping
      Map<Integer, Decimal> rateMap = new Map<Integer, Decimal>{
          0 => 0.10, 1 => 0.12, 2 => 0.14, 3 => 0.18, 4 => 0.2
      };

      // loop through the years to execute all branches
      for (Integer years = 0; years <= rateMap.size(); years++) {

          Decimal amount = ItemDiscount.calculateAmount(years, price);
          Decimal rate = years >= rateMap.size() ? maxRate : rateMap.get(years);
          System.assertEquals((price - (price * rate)), amount);
      }
  }

  @isTest
  static void testAmount() {

      Decimal price = 1000;
      Integer years = 5;
      Decimal amount = ItemDiscount.calculateAmount(years, price);
      System.assertEquals((price - 100), amount);
  }
}
Page 66 · 100% coverage result

100% coverage — passes deployment

After optimizing the test class, code coverage for ItemDiscount increases to 100% (16/16).

Interview angle

"Only 75% of Apex code must be covered to deploy" — but don't focus on the percentage. Good practice: ensure every block in the Apex class is covered. That's how you get the highest possible coverage a unit test can achieve.

Page 68 · Scenario II — Missing assertions

Scenario II — Production behavior diverged from dev

Scenario

An Apex trigger creates a Membership record when a Contact is created with Type = 'Member'. Depending on salary range, a certain Membership_Plan__c value is also auto-assigned. After production rollout, it was noticed that the value of Membership_Plan__c on generated membership records did not always match the contact's salary range.

Investigation revealed that a field update action associated with a record-triggered flow was also executing when a contact record was created. The issue did not occur in dev because dev did not have the flow. The developer was asked what could have been added to the test class to prevent this.

Page 69 · Original test class

Original test class

// Original test class
@isTest
public class MembershipTest {

  @isTest
  static void testRegistration() {

      // Create a new contact
      Contact con = new Contact();
      con.FirstName = 'John';
      con.LastName = 'Smith';
      con.Salary_Range__c = 'A';
      con.Type__c = 'Member';
      insert con;

      // Check if a membership belongs to the contact
      List<Membership__c> results = [SELECT Id, Membership_Plan__c FROM Membership__c WHERE Contact__c = :con.Id];
      System.assertEquals(1, results.size()); // check that there is only one membership record for the contact
  }
}
Page 70 · Solution

Solution — assert what matters

Diagnosis

The original test only checks that a membership record was created — not whether the membership plan matches the salary range. Adding this assertion catches the bug:

// Check if membership plan matches with the salary range
System.assertEquals(con.Salary_Range__c, results.get(0).Membership_Plan__c);
Test methods should contain at least one assertion. Good test methods include more than one. Add more test methods to cover all salary ranges and possible scenarios using both single and batch operations.

Interview angle

This is the canonical "passing test that doesn't catch the bug" story. Lesson: every assertion you add narrows the gap between "tests pass" and "feature works".

Page 72 · Scenario III — SeeAllData=true

Scenario III — Test fails only in production

Scenario

A developer created an Apex trigger that updates a custom field Vendor_Name__c on the Account when a related opportunity is won. A test class was written. In the sandbox, the test code compiles and coverage is satisfactory. However, when deployed to production, the Apex test class fails. The developer needs to fix it.

Page 73 · Test class

The failing test class

// Test Class
@isTest(SeeAllData=true)
public class OpportunityTriggerTest {

  @isTest
  static void testMyTrigger() {

      Opportunity opp = [SELECT Id, Name, Project__r.Vendor_Name__c FROM Opportunity
                         WHERE StageName = 'Negotiation/Review' LIMIT 1];
      opp.StageName = 'Closed Won';
      update opp;

      Account acc = [SELECT Id, Vendor_Name__c FROM Account WHERE Id = :opp.AccountId LIMIT 1];
      System.assertEquals(acc.Vendor_Name__c, opp.Project__r.Vendor_Name__c);
  }
}
Page 74 · Solution narrative

Diagnosis

Root cause

One likely cause is the dependency of the test class on existing org data, made evident by the @isTest(SeeAllData=true) annotation. The test scenario may throw a query exception if no opportunities are found in the Negotiation/Review stage. Whenever possible, it is recommended to create dedicated test data for the test class.

Page 75 · Test data approaches

Test data approaches

Test.loadData

Static resources contain data for test classes. A CSV file can be uploaded and loaded into a test method:
List<sObject> records = Test.loadData(Opportunity.sObjectType, 'myStaticResourceName');

Test Utility Class

Utility classes are public classes containing reusable code. A test utility class can generate data for test classes.

Page 76 · Test data factory

Test data factory example

@isTest
public class MyTestDataFactory {
  public static void createAccounts(Integer numAccts) {

      List<Account> accts = new List<Account>();

          Account a = new Account(Name='Test Account ' + i);
          accts.add(a);

  }

Approach

Page 81 · Solution narrative

Solution — bulk DML & startTest/stopTest

Fix

A DML statement should not be placed inside a for loop. The for loop should add opportunity records to a list variable, then a single insert can be applied to that list after the loop. This requires only one DML operation.

Use Test.startTest() and Test.stopTest() to ensure code between is executed under a fresh set of governor limits. Limits.getDmlStatements() and Limits.getLimitDmlStatements() can perform a runtime check to avoid hitting the limit for DML statements.

System.runAs() solution

Approach

The System.runAs() method executes code in the context of another user. Test methods can access org metadata such as Users and Profiles, even without using the SeeAllData=true annotation. Apex Test Scenario / Solution VI

Page 93 · Scenario VI — UNABLE_TO_LOCK_ROW

Scenario VI — UNABLE_TO_LOCK_ROW

Scenario

A developer has observed that when running certain test classes from the Salesforce user interface or Developer Console, the UNABLE_TO_LOCK_ROW error is sometimes encountered. The developer needs to determine the cause and take steps to prevent it.

Page 94 · Causes

Causes

Why it happens

Tests executed from the Salesforce UI or Developer Console run in parallel to speed up runtime. Data contention and UNABLE_TO_LOCK_ROW errors occur due to:

Same Records

Tests update the same records at the same time.

Duplicate Index

Records are created with duplicate index field values.

Page 95 · Disable parallel

Disable parallel execution

Prevented by deactivating parallel test execution. From Setup → Custom Code → Application Test Execution → Options, select Disable Parallel Apex Testing. The annotation @IsTest(isParallel=true) can be used on a test class to override disabled parallel testing.

Page 96 · Setup UI

Setup UI

From Setup → Custom Code → Application Test Execution, click Options → Disable Parallel Apex Testing checkbox. This executes test methods one at a time and prevents the occurrence of UNABLE_TO_LOCK_ROW errors.

Interview angle

Parallel testing is faster but flaky for tests that share records. Disable it org-wide as a safety default, then opt-in via isParallel=true on tests you've engineered for parallel safety (i.e. tests that create their own isolated data).

Bonus · Quick-Reference Cheatsheet

Quick-Reference Cheatsheet

Developer Console — the four Execution Overview tabs

  • Save Order — color-coded DML save sequence (triggers, validation rules, flows).
  • Limits — used/total for SOQL, SOQL_ROWS, DML, DML_ROWS, AGGS (needs debug level Finest).
  • Timeline — % time per category: APEX_CODE, DB, WORKFLOW, VALIDATION, CALLOUT, VISUALFORCE.
  • Executed Units — per-method/query call counts, heap size, row counts. Filter by Methods/Queries/Workflow/Callouts/DML/Validations/Triggers/Pages.

Tooling matrix

  • Client-side: Chrome DevTools, Firefox DevTools, Fiddler, Charles, WebPageTest.
  • Lightning JS: Setup → Lightning Components → Debug Mode (per-user; weekly banner).
  • Server-side: Developer Console (Stack Tree, Execution Stack, Execution Overview), Tooling API, Apex Timeline tool, Query Plan tab.

Trace flags

  • Set per-class and per-user. Bump only the class under investigation; set others to NONE.
  • Start at INFO, escalate to FINEST when needed (required for Limits tab data).

Test-failure root causes (the 6 scenarios memorized)

  1. Low coverage — exercise every branch (use a Map + for loop for combinatorics).
  2. Tests pass, prod breaks — missing assertions. Assert the actual business outcome, not just "a record exists".
  3. Works in sandbox, fails in prod — @isTest(SeeAllData=true) + reliance on org data. Use Test.loadData, factory class, or @testSetup.
  4. Limit exception — DML inside a for loop. Collect into a list, single DML after. Wrap in Test.startTest/stopTest for fresh limits; check Limits.getDmlStatements().
  5. Works for admin, fails for some users — permission/sharing-dependent. Wrap in System.runAs(nonAdminUser) { ... }.
  6. UNABLE_TO_LOCK_ROW — parallel tests contending on same records. Disable parallel testing org-wide; opt back in with @IsTest(isParallel=true) for tests engineered safely.

Profiling considerations

  • Profile with users of different roles — sharing calculations vary.
  • Use LIMIT_USAGE in Execution Log for governor visibility.
  • Establish baseline query perf with an un-indexed custom field.
  • Talk to Salesforce Customer Support before any load/stress/concurrent-user testing.
