Page 5 · Introduction

Introduction

This topic discusses how to create and execute unit test classes for testing Apex classes and triggers. Test classes and methods are always annotated with the @isTest annotation. Unit tests should be created to achieve the 75% minimum code coverage required for deployment, but developers should write test methods for all possible test cases.

Test data can be created for testing. A method annotated with @testSetup provides an easy way to create test data for all methods in a single test class. Test utility classes and test data stored as static resources allow for easy reuse of test data across test classes. Web service callouts cannot be tested directly, but Salesforce offers mock interfaces, which can be used to simulate test callouts.

Interview angle

Be ready to explain: why 75% (deployment gate, not a quality target), the difference between mocks/stubs/static resources, and when each is appropriate.

Apex Classes

Pages 13–14 · Creating Unit Tests for Apex Classes

Creating Unit Tests for Apex Classes

A separate Apex class, called a test class, is required to test a particular Apex class.

Class Annotation

Annotate with @isTest; be either private or public. Public test classes are generally used for test data factory classes.

Method Annotation

Each test method should be annotated with @isTest and take no arguments.

Setup Method

A test setup method (for creating test data) is defined using @testSetup.

Access Modifier

Access modifiers can be omitted from test methods since they are always accessible by the testing framework.

Page 15 · Writing Unit Tests

Writing Unit Tests

A unit test invokes the method or trigger being tested. If a method or trigger isn't called, it negatively impacts the code coverage computation.

Testing Methods

The method being tested can be called directly from the test method.

Testing Triggers

Include DML operations in test methods to invoke the triggers.

Running Tests

Unit tests should execute the Apex methods or triggers being tested.

Verifying Results

Test results should be verified with the use of assert methods.

Page 16 · Verifying Code Behavior

Verifying Code Behavior

Assert methods are used to verify code behavior. They throw an exception when the actual result does not match the expected result.

// System.assert(condition, msg);
System.assert(x == y, 'Oops, X does NOT equal Y');

// System.assertEquals(expected, actual, msg);
System.assertEquals(x, y, 'Oops, X does NOT equal Y');

// System.assertNotEquals(expected, actual, msg);
System.assertNotEquals(x, y, 'Oops, X does equal Y');

// Assert.isTrue(condition, msg);
Assert.isTrue(x == y, 'Oops, X does NOT equal Y');

// Assert.isFalse(condition, msg);
Assert.isFalse(x == y, 'Oops, X does NOT equal Y');

// Assert.areEqual(expected, actual, msg);
Assert.areEqual(x, y, 'Oops, X does NOT equal Y');

// Assert.areNotEqual(expected, actual, msg);
Assert.areNotEqual(x, y, 'Oops, X does equal Y');
The Assert class provides additional methods for checking instance types, null values, and explicitly throwing errors. Salesforce recommends using the Assert class for new code — it enhances flexibility and clarity over the older System.assert* methods.
Page 17 · Anatomy of an Apex Test Class

Anatomy of an Apex Test Class

@isTest
private class MyApexClass__Test {

    @testSetup
    private static void setupTestData() {
        // create records to use in the test methods
    }

    @isTest
    private static void myTestMethod() {
        // test business logic in an Apex method
        // use assert methods to verify results
    }
}
  • @isTest defines the Apex class as a test class.
  • A naming convention such as a "__Test" suffix is advised to easily identify test classes.
  • @testSetup defines a method used for creating test data.
  • Test methods must be static, must be void, must not accept any arguments.
  • Not every method in a test class has to be a test method.

Apex Class Testing Example

Page 19 · Example of Testing an Apex Class — Class being tested

The Apex class to test

This Apex class creates a sales order and updates a field for every opportunity that is closed won.

public class OpportunityUpdate {

    public static void processRecords(List<Opportunity> opps) {

        List<Sales_Order__c> salesOrders = new List<Sales_Order__c>();
        List<Opportunity> oppsToUpdate = new List<Opportunity>();

        for (Opportunity o : opps) {
            if (o.StageName == 'Closed Won') {
                Sales_Order__c s = new Sales_Order__c();
                s.Name = o.Name + ' Order';
                s.Opportunity__c = o.Id;
                s.Status__c = 'New';
                s.Account__c = o.AccountId;
                salesOrders.add(s);

                o.Notes__c = 'A sales order has been created for this opportunity.';
                oppsToUpdate.add(o);
            }
        }

        insert salesOrders;
        update oppsToUpdate;
    }
}

Page 21 · Example of Testing an Apex Class — Test method

Test method

    // This test method verifies whether a sales order is created when the stage of an opportunity
    // is changed to 'Closed Won'. It also verifies whether the Notes__c field on the opportunity is updated.
    @isTest
    static void testSalesOrderCreation() {
        List<Opportunity> opps = [SELECT Id, Name, StageName, AccountId, Notes__c
                                  FROM Opportunity WHERE StageName = 'Closed Won'];
        OpportunityUpdate.processRecords(opps);
        List<Sales_Order__c> salesOrders = [SELECT Id, Name, Opportunity__c, Status__c, Account__c
                                            FROM Sales_Order__c WHERE Opportunity__c IN :opps];
        Assert.isFalse(salesOrders.isEmpty()); // fail test if no sales order were created
        String note = 'A sales order has been created for this opportunity.';
        for (Sales_Order__c so : salesOrders) {
            for (Opportunity o : opps) {
                if (so.Opportunity__c == o.Id) {
                    Assert.areEqual(o.Name + ' Order', so.Name);       // fail if naming convention not followed
                    Assert.areEqual('New', so.Status__c);              // fail if order status is not 'New'
                    Assert.areEqual(o.AccountId, so.Account__c);          // fail if account IDs do not match
                    Assert.areEqual(note, o.Notes__c);                    // fail if the note was not saved
                }
            }
        }
    }
}

Apex Trigger Testing Example

Page 24 · Example of Testing an Apex Trigger — Trigger being tested

The trigger to test

This Apex trigger creates a new order when the status of an opportunity is changed to 'Closed Won'.

trigger OpportunityTrigger on Opportunity (before update) {
    List<Order> newOrders = new List<Order>();

    for (Opportunity opp : Trigger.new) {

        if (opp.StageName == 'Closed Won' &&
            (Trigger.oldMap.get(opp.Id).StageName != 'Closed Won')) {

            Order o = new Order();
            o.AccountId = opp.AccountId;
            o.EffectiveDate = System.today();
            o.Status = 'Draft';
            newOrders.add(o);
        }
    }

    insert newOrders;
}

Page 26 · Example of Testing an Apex Trigger — Test method

Test method (DML fires the trigger)

    // This test method verifies whether an order is created when the stage of an opportunity is changed to 'Closed Won'.
    @isTest
    static void testOrderCreation() {
        List<Opportunity> opps = [SELECT Id, Name, StageName, AccountId
                                  FROM Opportunity WHERE StageName = 'Prospecting'];
        List<Opportunity> newOpps = new List<Opportunity>();
        for(Opportunity opp : opps) {
            opp.StageName = 'Closed Won';
            newOpps.add(opp);
        }
        update newOpps;

        List<Order> orders = [SELECT Id, Status, EffectiveDate, AccountId
                              FROM Order WHERE AccountId = :opps[0].AccountId];
        Assert.isTrue(orders.size() > 0, 'No orders were found!');

        for (Order o : orders) {
            Assert.areEqual(o.Status, 'Draft');
            Assert.areEqual(o.AccountId, newOpps[0].AccountId);
            Assert.areEqual(o.EffectiveDate, System.today());
        }
    }
}

Interview angle

Triggers are invoked by DML, never called directly. Stress-test bulk behavior — the example uses 300 opportunities to ensure the trigger is bulk-safe.

Error Methods in Apex Testing

Page 29 · sObject Error Methods

Apex Testing with sObject Error Methods

The sObject class contains error methods used in Apex testing to track and obtain errors without performing any DML operation.

sObject.addError()

Dynamically add errors to specific fields.

// Example:
String field = 'Site';
String msg = 'website does not exist.';
account.addError(field, msg);

sObject.hasErrors()

Determine if an object instance contains any errors.

// Example:
Boolean has = account.hasErrors();
Assert.areEqual(true, has);

sObject.getErrors()

Retrieve a list of errors for a specific object instance.

// Example:
Integer size = account.getErrors().size();
Assert.areEqual(1, size);
Page 30 · sObject Error Methods Example

sObject Error Methods Example

Account a = new Account();
a.Name = 'ACME Inc.';
a.Site = 'https://www.nonworkingwebsite.com';

URLStatus status = (new URLStatus()).check(a.Site); // check if Site URL is accessible (mock)
Assert.areEqual(false, status.healthy);

a.addError('Site', status.message); // add error message to specific field
Assert.areEqual(true, a.hasErrors()); // assert that an message was added to the instance

List<Database.Error> errors = a.getErrors(); // get any errors added to the instance
Assert.areEqual(1, errors.size()); // assert that there should only be 1 error

Database.Error error = errors.get(0);
Assert.areEqual(StatusCode.FIELD_CUSTOM_VALIDATION_EXCEPTION, error.getStatusCode());
Assert.areEqual('Site is not working!', error.getMessage());
Assert.areEqual(1, error.getFields().size());

System.debug('message: ' + error.getMessage());
System.debug('status:  ' + error.getStatusCode());
System.debug('fields:  ' + error.getFields());
Errors added via addError are assigned to the FIELD_CUSTOM_VALIDATION_EXCEPTION exception type, although it is not related to custom validation rules.

Page 32

Test Setup Method

Pages 33–34 · Test Setup Methods

Test Setup Methods

A test class is allowed to only have one test setup method, used for creating test data.

Structure

Defined in a test class, takes no arguments, and returns no value.

Annotation

Annotated using @testSetup.

Run First

Runs first, before any test method in the class.

Test Data

Creates data once, accessible by all test methods.

Record Creation

Records created in a regular test method are rolled back at the end of method execution; records from @testSetup are rolled back at class execution — reducing test time.

Record Changes

If a test method changes records created by setup, those changes are rolled back at end of method, so every test method starts with the original, unchanged data.

Method Support

Test setup methods are not supported in a test class that uses @isTest(SeeAllData=True).

Pages 35–36 · Example of a Test Setup Method

Example of a Test Setup Method

@isTest
private class AccountTestClass {

    // The @testSetup annotation is used for a test setup method
    @testSetup static void setup() {

        List<Account> testAccounts = new List<Account>();

        for(Integer i=1; i<=300; i++) {
            testAccounts.add(new Account (Name = 'Test Account ' + i));
        }

        insert testAccounts;
    }

    // The test record created in test setup method can be used in a test method
    @isTest
    static void testMethod1() {
        Account acc = [SELECT Id, Name, Industry FROM Account WHERE Name = 'Test Account 1'];
        acc.Industry = 'Healthcare';
        update acc;
    }

    // Any changes to a test record created in a test setup method are rolled back at the end of a test method
    @isTest static void testMethod2() {
        Account acc = [SELECT Id, Name, Industry FROM Account WHERE Name = 'Test Account 1'];

        // Verify that the value of the Industry field currently has no value
        Assert.areEqual(null, acc.Industry);

        // The second test method can also make changes to the same test records
        acc.Industry = 'Communication';
        update acc;
    }
}

Interview angle

Be ready to articulate the rollback model: each test method starts from the setup snapshot, not from the previous method's state.

Test Utility Class

Page 38 · Test Utility Class

Test Utility Class

When test classes use similar test data, a test utility class or test data factory can be created and used across unit tests.

Annotation

Uses @isTest, which excludes the code from the org's code size limit and code coverage requirement.

Parameters

Methods can take parameters and return a value.

Method Call

Test creation methods are called directly from unit tests.

Method Access

Should be defined as global or public to ensure unit tests can access them.

Page 39 · Example of a Test Utility Class

Example of a Test Utility Class

// The @isTest annotation is used for the test utility class so that it is executed in test context.
@isTest
public class TestDataFactory {

    // A method in a test utility class can accept parameters and return a value
    public static List<Account> createTestAccounts(String t, String i) {

        List<Account> accounts = new List<Account>();
        for (Integer j = 1; j <= 300; j++) {
            Account a = new Account(Name = 'Test' + j, Type = t, Industry = i);
            accounts.add(a);
        }

        insert accounts;
        return accounts;
    }
}

Using Mock Callouts

Pages 47–49 · Generate REST Callout Mock Response

Generate REST Callout Mock Response

Salesforce does not allow performing callouts in test classes, and instead provides an interface for simulating callouts in test executions: HttpCalloutMock.

HttpCalloutMock interface

Access

The access modifier of the Apex class should be defined as either global or public.

Annotation

The class should be annotated with @isTest, since it is used only in test context.

Respond

The class only needs to implement a respond() method which accepts an HttpRequest and returns an HttpResponse.

Response

The HttpResponse should mimic what the actual REST-based web service would return.

Standalone Class

As a best practice, a separate class per callout to test.

Mock Response

In respond(), the mock response can be sent only for a specific endpoint and HTTP method.

Wiring it up in tests

Set Callout Mock

In the unit test, Test.setMock is used to set the mock callout and receive the fake response.

First Argument

HttpCalloutMock.class is the first argument to Test.setMock.

Second Argument

An instance of the interface implementation, e.g. Test.setMock(HttpCalloutMock.class, new MockContactServiceCallout());

Verify Response

The HttpResponse generated by the mock callout can be verified in the unit test method.

setMock Position

Test.setMock() should be added before the callout. If the test class creates test data, an 'uncommitted work' error will be thrown if the callout is invoked without enclosing it in Test.startTest() / Test.stopTest().

Interview angle

"Why do I need startTest/stopTest around a callout?" — Because mixing DML (test data creation) with callouts triggers the uncommitted work pending error; the start/stop boundary scopes the callout into its own transaction context.

Page 50 · REST Callout Mock Example

REST Callout Mock Example

// example callout mock class that simulates the response of a successful enrollment of a student:
public class EnrollHttpCalloutMock implements HttpCalloutMock {
    public HttpResponse respond(HttpRequest req) {
        HttpResponse res = new HttpResponse();
        res.setHeader('Content-Type', 'application/json');
        res.setBody('{"success":true,"studentId":12345,"courseId":67,"yearLevel":3}'); // create fake response
        res.setStatusCode(200);
        return res;
    }
}

// example code contained and executed inside a test method:
Test.startTest();
Test.setMock(HttpCalloutMock.class, new EnrollHttpCalloutMock());
StudentApplicationWrapper application = generateStudentApplication(); // some helper method
Enrollment erm = StudentController.enroll(application); // invoke the method to test

// verify new record created from fake data
Assert.areEqual(erm.ExternalStudentId__c, 12345);
Assert.areEqual(erm.YearLevel__c, 3);
Assert.areEqual(erm.CourseId__c, 67);
Test.stopTest();
Pages 51–53 · Generate SOAP Callout Mock Response

Generate SOAP Callout Mock Response

SOAP callouts can be tested by creating a class that implements the WebServiceMock interface based on classes generated by WSDL2Apex.

Standalone Class

A separate class for each callout to test.

Access Modifier

Defined as global or public.

Class Annotation

Annotated with @isTest.

Single Method

Implements a doInvoke() method.

Method Parameters

All information about the callout, including the response, is passed to doInvoke() through multiple input parameters.

Mock Response

The response is placed in the response parameter of type Map<String, Object>.

Specific Endpoint

In doInvoke(), a specific endpoint and method can be used.

Wiring in tests

First Argument

WebServiceMock.class is used as the first argument to Test.setMock.

Second Argument

An instance of the interface implementation of WebServiceMock.class, e.g. Test.setMock(WebServiceMock.class, new MockContactWebService());

Verify Response

The response parameter passed to the callout is populated and can be verified in the unit test method.

Page 54

Asynchronous Apex Testing

Page 55 · Asynchronous Apex Testing

Asynchronous Apex Testing

Asynchronous Apex is executed in a different transaction and time. However, unit tests can be defined in a way that causes it to run in a synchronous manner so that its result can be verified accordingly.

Future Method

Executed in a different transaction and only when resources are available.

Queueable Apex

Like future methods, but supports job chaining and other data types.

Batch Apex

Used to perform operations that require higher governor limits.

Scheduled Apex

Used to run Apex at scheduled intervals or once, by aborting after job completion.

Page 56 · Future Method Testing

Future Method Testing

To test an updateByCode future method, it is invoked between Test.startTest() and Test.stopTest().

@IsTest
private class ProductControllerTest {

  // ...

  @IsTest
  private static void testUpdateByCode() {
      Test.setMock(HttpCalloutMock.class, new ERPCalloutMock());

      Test.startTest();
      ProductController.updateByCode('123ABC'); // future method
      Test.stopTest();

      // verify results of updateByCode method
      List<Product_Log__c> logs = [SELECT Product_Code__c FROM Product_Log__c];
      Assert.areEqual(1, logs.size());
      Assert.areEqual('123ABC', logs[0].Product_Code__c);
  }

  // ...
}
After Test.startTest(), any asynchronous processes are collected. When Test.stopTest() is called, any collected processes are run synchronously. This allows any results to be verified later in the same transaction.
Page 57 · Testing Queueable Apex and Batch Apex

Testing Queueable Apex and Batch Apex

Queueable Apex and Batch Apex are tested in the same manner using Test.startTest() and Test.stopTest().

// ...  Queueable Apex test
@isTest
private static void testAssigner() {

    // get current records assigned to a specific owner
    List<Opportunity> opps = [SELECT Id FROM Opportunity
                              WHERE OwnerId = :users.get(0).Id];
    // create a job to assign opportunities to a new owner
    Assigner assignment = new Assigner(opps, users.get(1).Id);

    Test.startTest();
    System.enqueueJob(assignment); // reassign the records
    Test.stopTest();

    // validate results
    List<Opportunity> results = [SELECT Id FROM Opportunity
                                 WHERE OwnerId = :users.get(0)];
    Assert.areEqual(0, results.size());
}

// ... Batch Apex test
@isTest
private static void testCouponUpdates() {

    Test.startTest();
    // update coupon details on products
    CouponUpdate updates = new CouponUpdate();
    Id batchId = Database.executeBatch(updates);
    Test.stopTest();

    // validate results
    Assert.areEqual(100, [SELECT COUNT() FROM Product__c
        WHERE CouponDate__c = TODAY]);
}
Page 58 · Testing Scheduled Apex

Testing Scheduled Apex

Scheduled Apex is also asynchronous and is tested using the same approach. In this example, a schedulable class creates task reminders for sales users with unread leads.

// ...

// "unreadLeads" = leads that haven't been viewed yet
Map<Id, Lead> leadMap = new Map<Id, Lead>(unreadLeads);

List<Id> leadIds = new List<Id>(leadMap.keySet());

// job will be executed immediately regardless of the set date due to start and stop methods

// tasks should already have been created at this point
tasks = [SELECT Id FROM Task WHERE WhatId IN :leadIds];
Assert.areEqual(leadIds.size(), tasks.size(), 'Scheduled reminders failed!');
Page 59

Stubbing in Testing

Pages 60–61 · What is Stubbing

What is Stubbing

While a mock callout returns a fake response from a callout, a stub returns a fake response from an invoked method by using a mock version of the method's class.

Test Isolation

Stubbing prevents code dependencies from interfering in a test and lets the unit test isolate the method being tested.

Stub Class

Implements the StubProvider interface, then is instantiated via Test.createStub. System.StubProvider + System.Test.createStub make up the Apex stub API.

Method

The stub class has a method called handleMethodCall, which contains several parameters used to determine the method being invoked in the test (and cause it to, for example, return a custom value).

Stubbing

Actual code is designed to allow the stub class to be used in place of the actual class when testing. For example, to test classA.myMethod which depends on output from classB.myMethod, a mock version of classB is created and referenced in the test instead of the real class.

Page 62 · How to Use a Stub

How to Use a Stub

  1. Instantiate the stub class using the Test.createStub method.
  2. Execute Code — call Test.startTest() and execute the code that needs to be tested.
  3. Assert Results — call Test.stopTest() and verify the results using assertions.
Pages 63–65 · Stubbing Example

Stubbing Example

A VehicleDoctor class contains a method called checkVehicleStatus. This method depends on getTotalMilesTraveled from a Vehicle class.

public class VehicleDoctor {
  public Boolean checkVehicleStatus(Vehicle v) {
      Boolean status = true;
      Decimal miles = v.getTotalMilesTraveled();
      if (miles >= 100000.00) {
          status = false;
      }
      return status;
  }
}

public class Vehicle {
  public Decimal getTotalMilesTraveled() {
      Decimal distance = 0.00;
      // i.e.: some "complex" logic here to calculate distance
      // distance = ...
      return distance;
  }
}

Stub class implementing StubProvider

@isTest
public class VehicleMock implements System.StubProvider {
  Decimal distance;

  public VehicleMock(Decimal d) { // preset the distance via constructor
      this.distance = d;
  }

  public Object handleMethodCall(Object stubbedObject, String stubbedMethodName, Type returnType,
                                List<Type> listOfParamTypes, List<String> listOfParamNames, List<Object> listOfArgs){

      if (stubbedMethodName == 'getTotalMilesTraveled') {
          System.debug(this.distance);
          return this.distance; // stubbed method returns preset value
      }

      return null;
  }
}

Test class that uses the stub

@isTest
private class VehicleDoctorTest {

  @isTest
  static void testCheckVehicleStatus() {

      // instantiate the stub class
      Vehicle vm = (Vehicle) Test.createStub(Vehicle.class, new VehicleMock(100000.00));

      VehicleDoctor vd = new VehicleDoctor();
      Boolean status;

      Test.startTest();
      status = vd.checkVehicleStatus(vm);
      Test.stopTest();

      Assert.areEqual(false, status, 'expected result false');
  }
}
Test.createStub() returns an Object, so the value needs to be casted back to the proper data type (here, Vehicle).
Page 66 · Stub Limitations

Stub Limitations

Stubs are flexible, but the following Apex elements cannot be mocked:

Batch Apex classes and Inner classes

Classes that only have private constructors

Static methods (including future methods) and private methods

Class Properties (getters and setters)

Apex triggers

System types

Testing Flows with External Services

Page 68 · HttpCalloutMock for flows

HttpCalloutMock for invocable actions in flows

Apex unit tests can also be created for flows that use an invocable action with External Services. The HttpCalloutMock interface can simulate the callout to the external service endpoint.

global class StudentPortalHttpCalloutMock implements HttpCalloutMock {
  global HTTPResponse respond(HTTPRequest request) {
      // Assert expected request test data
      Assert.areEqual('GET', request.getMethod());
      Assert.areEqual('callout:StudentPortalService/G64509560', request.getEndpoint());
      Assert.areEqual('astro', request.getHeader('accessCode'));

      // Send response test data
      HttpResponse response = new HttpResponse();
      response.setHeader('Content-Type', 'application/json');
      response.setBody('{"level": 3, "name": "John Smith", ' +
          '"course": "BSME", "gender": "M", "birth": "20050101"}');
      response.setStatusCode(200);
      return response;
  }
}
In this example, the external service is registered with a Named Credential called StudentPortalService used to retrieve student information. The mock implementation tests the details of requests from the flow and responds with an appropriate HTTP response output.

Pages 75–76 · Unit Testing Best Practices

Unit Testing Best Practices

Annotate Test Classes

@isTest should be used for every test class.

Use Assert Methods

Assert methods should be used to prove that code behaves properly.

Inputs and Branches

Make method calls with both valid and invalid inputs, and each branch of conditional logic must be executed.

Catch / Handle Errors

Expected errors should be caught in a try-catch block, and caught exceptions should always be handled.

User Context

If required, the System.runAs method should be used to test code in different user contexts.

Trigger Tests

Tests should handle bulk trigger functionality, and all triggers must have at least one line of test coverage.

Individual Tests

Each class should be tested individually.

Page 77 · Test as Different Users

Test as Different Users

System.runAs enables code to run in the context of a specified user, enforcing the user's record sharing, object-level and field-level permissions to test code behavior and data security.

@isTest
public static void test2() {

    Profile p = [SELECT Id FROM Profile WHERE Name = 'Standard User'];
    User newUser = new User(Email='newuser@acme.com', UserName='newuser@acme.com.dev', LastName='Testing', Alias='newUser',
        ProfileId=p.Id, LanguageLocaleKey='en_US', LocaleSidKey='en_US', TimeZoneSidKey='America/Los_Angeles', EmailEncodingKey='UTF-8');

    System.runAs(newUser) {
        Assert.areEqual('newuser@acme.com.dev', UserInfo.getUserName()); // Execute code as newUser
        Assert.areEqual(p.Id, UserInfo.getProfileId());
    }

    User currentUser = [SELECT Id, ProfileId FROM User WHERE UserName='currentuser@acme.com.dev'];
    System.runAs(currentUser) {
        Assert.areEqual('currentuser@acme.com.dev', UserInfo.getUserName()); // Execute code as currentUser
        Assert.areEqual(currentUser.ProfileId, UserInfo.getProfileId());
    }
}

Best Practices for Setting Up Test Data

Data Dependency

Test data should reduce dependencies on data in sandbox and production orgs.

Data Generation

Test data should be created before calling Test.startTest.

Separate test classes should set up the necessary data.

Apex class to test

public class AccountClass {

  public static List<Account> processAccount(List<Account> accounts) {

      List<Account> updatedAccounts = new List<Account>();

      for (Account a : accounts) {
          if(a.Type == 'Reseller') {
              a.Industry = 'Manufacturing';
              updatedAccounts.add(a);
          }
      }

      update updatedAccounts;
      return updatedAccounts;
  }
}

Test class using a utility class

@isTest
private class AccountTest {

  @isTest
  static void testAccountProcessing () {

      String type = 'Reseller';
      String industry = 'IT';

@isTest
public class TestDataFactory {

  public static List<Account> createTestAccounts(String t, String i) {

      List<Account> accounts = new List<Account>();

      for (Integer j = 1; j <= 300; j++) {
          Account a = new Account(Name = 'Test' + j, Type = t, Industry = i);

      }

      insert accounts;
      return accounts;
  }
}

Test Coverage Best Practices

Optimize Coverage

Even though 75% of Apex code must be covered, cover as many lines as possible while ensuring every use case is covered.

Rerun Tests

Tests should be rerun to refresh code coverage numbers and get a correct estimate.

Managed Packages

Managed package tests are not included in the overall code coverage percentage.

Coverage Calculation

Be careful while adding new code lines — code coverage depends on the total number of code lines in the org.

Insufficient Coverage

If a deployment to production fails due to insufficient code coverage, more unit tests should be written.

Increase Coverage

Additional tests should be written for classes with less than 75% coverage in sandbox.

Best Practices for Parallel Test Execution

Parallel Execution

Tests executed from the Salesforce user interface and Developer Console are executed in parallel.

Issues and Errors

Data contention issues and UNABLE_TO_LOCK_ROW errors can arise due to parallel execution.

Same Records

Tests may update the same records if they do not create their own test data.

Turning Off

Avoid such errors by turning off parallel test execution: Setup → Application Test Execution → Options → Disable Parallel Apex Testing.

Bonus · Quick-Reference Cheatsheet

Quick-Reference Cheatsheet

Key annotations

  • @isTest — marks a class or method as a test; excluded from code-size and coverage limits.
  • @testSetup — one per class; runs once before all test methods; rolled back at class end.
  • @isTest(SeeAllData=true) — gives access to org data; incompatible with @testSetup.

Key APIs

  • Test.startTest() / Test.stopTest() — fresh governor limits; async work is collected then run synchronously at stopTest.
  • Test.setMock(HttpCalloutMock.class, …) / Test.setMock(WebServiceMock.class, …) — install mock callout before the callout fires.
  • Test.loadData(SObjectType, 'StaticResourceName') — load from CSV static resource.
  • Test.createStub(Class, instanceOfStubProvider) — returns an Object, cast to target type.
  • System.runAs(user) { … } — execute as a different user; enforces sharing & FLS.

Errors to recognize

  • Uncommitted work pending — DML before a callout; wrap callout in startTest/stopTest or do DML after.
  • UNABLE_TO_LOCK_ROW — parallel test execution + shared records; turn off parallel testing or isolate data.
  • FIELD_CUSTOM_VALIDATION_EXCEPTION — what sObject.addError produces; not necessarily from a validation rule.

Rules-of-thumb interview hits

  • 75% is the deployment floor, not a quality target.
  • Triggers fire via DML — never call directly; test in bulk (200+ records).
  • Prefer Assert.areEqual over System.assertEquals in new code.
  • Mocks ≠ stubs: mocks fake callouts, stubs fake method calls on a class.
  • Stubs can't mock: batch classes, inner classes, private-only-constructor classes, static/private methods, getters/setters, triggers, system types.
